    Day 4 — Responder, 인터넷 허용 목록, 취약점 관리¶

    과정: Information Security Core Skills · 강사: John Strand (BHIS) · 4일차 범위(지금까지): Responder 실습 해설 → NTLM 크래킹·릴레이·서명 → 인터넷 허용 목록 → 취약점 관리 → Nessus 보고서 실습

    4일차 한눈에 (1~2부)

    3일차에 준비한 Responder 실습으로 시작합니다. 같은 네트워크의 공격자는 트래픽을 돌려 NTLMv2 챌린지·응답을 가로채고, 오프라인으로 크래킹하거나 그대로 릴레이합니다 — 그래서 호스트 간 통신 차단, LLMNR 끄기, SMB 서명이 필요합니다. 이어서 공격자가 새로 산 도메인을 짧게 쓰고 버리는 습성을 역이용해, 웹 필터에서 "미분류(Uncategorized)"를 차단하는 것만으로 사실상의 인터넷 허용 목록을 만드는 법을 봅니다. 마지막으로 AI 시대의 취약점 관리 — CVSS를 한 단계 올려 보고, 무시되던 Low·Informational도 살피고, 시스템별이 아니라 취약점별로 묶어 처리하기 — 와 Nessus 보고서 실습입니다.

    이 페이지는 진행 중입니다

    현재 1~2부까지 정리되어 있습니다. 3~4부(웹 애플리케이션 보안·ZAP 실습, AD 하드닝·Ping Castle 실습, 마무리)는 이어서 추가합니다.

    1. Responder 실습 해설¶

    왜 Kali 대신 Ubuntu인가¶

    대부분의 강의에서 Kali는 Metasploit·Nmap·패스워드 크래킹 정도에 쓰입니다. 앞으로는 Docker 컨테이너나 허니팟 기술을 다룰 예정이라, 도구를 더 쉽게 설치할 수 있는 Ubuntu로 옮겼습니다. 새 환경은 화면 위쪽에 리눅스 IP를 바로 보여 줘서 매번 ifconfig를 칠 필요가 없습니다.

    클라우드에서는 포이즈닝이 안 된다 — 그래서 실습은 "흉내"¶

    Responder는 LLMNR, NBT-NS, mDNS 포이즈너를 켭니다(1일차 9장 — 이름을 못 찾을 때 네트워크 전체에 "이 이름 누구예요?"라고 외치는 방식들). 그런데 이 방식들은 AWS에서 동작하지 않습니다. VM 사이의 2계층(Layer 2) 통신을 격리하기 때문입니다. 그래서 실습에서는 Windows가 리눅스 쪽으로 직접 접속하게 해서 흉내 냅니다.

    공격자가 같은 네트워크에 있다면, 할 일은 트래픽을 자기 쪽으로 돌리는 것뿐이다. 그건 ARP 캐시 포이즈닝이나 LLMNR로 아주 쉽게 된다.

    Responder 화면을 보면 HTTP, HTTPS, SMB, Kerberos 등 여러 가짜 서버가 자격 증명을 훔칠 준비를 하고 있습니다(WPAD는 이 실습에서는 꺼 둠).

    분할(segmentation)이면 이 공격은 막힌다. 다만 실제로 그런 분할을 해 둔 조직은 아주 드물다.

    인증을 가로채는 순간¶

    Windows 탐색기 주소창에 \\<리눅스 IP>를 넣고 엔터를 치자마자 Responder에 administrator 계정의 인증 정보가 잡힙니다. 사용자가 패스워드를 다시 입력하면 그 값도 또 잡힙니다. 보이는 것은 NTLMv2 인증입니다.

    • 사용자 이름
    • 챌린지(challenge) — 서버가 보내는 무작위 값
    • 응답(response) — 패스워드 해시와 챌린지로 계산한 값

    챌린지도 평문으로 오가고, 응답도 평문으로 오간다. 그러면 그 목적이 거의 무너진다. 같은 네트워크에서 이 트래픽을 가로채면 이걸 가지고 크래킹할 수 있다.

    💡 보충 (강의 외) — 조금 더 정확하게

    강의에서는 "16바이트 챌린지", "인증을 되돌린다(reverse)"고 표현했는데, NTLMv2의 서버 챌린지는 8바이트이고 응답은 NT 해시를 열쇠로 한 HMAC-MD5 계산 결과입니다. 이 계산은 거꾸로 풀 수 없습니다. 공격자는 가로챈 챌린지와 응답을 가지고 후보 패스워드를 하나씩 넣어 같은 응답이 나오는지 오프라인으로 대입합니다. 그래서 패스워드가 약하면 깨지고, 길고 강하면 버틴다는 1일차의 결론이 그대로 적용됩니다.

    크래킹 — Hashcat 5600 모드¶

    패스워드 크래킹 폴더에서 Hashcat으로 크래킹합니다. 실습 파일 안의 IP 주소가 환경마다 달라서, 파일 속 IP를 방금 가로챈 값에 맞게 고쳐야 합니다. 이번에는 5600번 모드 — Hashcat에서 NetNTLMv2(NTLMv2 챌린지·응답)를 크래킹하는 모드입니다. 중첩 가상화 환경이라 시작이 느리지만, 결과에는 admin 계정, 챌린지, 그 안의 해시, 맨 끝에 크래킹된 패스워드가 나옵니다. 나머지 패스워드는 사전에 없어 깨지지 않으니 거기서 멈춥니다.

    Hashcat 모드 값의 종류 어디서 얻나
    -m 0 MD5 웹 DB 등
    -m 1000 NT 해시 SAM, NTDS.dit, LSASS 메모리 — Pass-the-Hash에 쓰임
    -m 5600 NetNTLMv2 네트워크에서 가로챈 챌린지·응답 — Responder로 잡은 값

    같은 "Windows 패스워드"라도 어디서 얻은 값이냐에 따라 모드가 다릅니다.

    크래킹 말고 릴레이도 있다 — ntlmrelayx¶

    ntlmrelayx는 가로챈 인증을 크래킹하지 않고 그대로 다른 여러 시스템에 넘겨서(relay) 인증해 버립니다. 그래서 이 실습의 결론은 3일차와 같습니다.

    그래서 방화벽이 중요하다. 누군가 바로 옆으로 뛰어넘어 올 수 있는 네트워크에서 호스트끼리 통신하게 두면 안 된다.

    Sysmon은 이걸 잡을까?

    크래킹은 공격자 컴퓨터에서 일어나니 Sysmon이 볼 수 없다. Sysmon이 볼 수 있는 건 피해자 시스템에서 공격자 시스템으로 나간 네트워크 연결 정도다.

    💡 보충 (강의 외) — 네트워크 쪽에서 보기

    • LLMNR(UDP 5355)·NBT-NS(UDP 137) 응답이 정상 DNS 서버가 아닌 일반 워크스테이션 IP에서 나오면 의심 신호
    • 워크스테이션이 서버가 아닌 다른 워크스테이션·낯선 IP로 SMB(445) 인증을 시도 (Zeek smb_mapping.log, ntlm.log)
    • 피해자 쪽 Sysmon 3(네트워크 연결)에서 System 프로세스가 낯선 내부 IP의 445로 연결

    방어는 LLMNR·NBT-NS 끄기, SMB 서명 강제(릴레이 차단), 워크스테이션 간 통신 차단, 인터넷으로 나가는 SMB 445 차단. 자세히: LLMNR과 NTLM 릴레이

    깊이 보기 ① 가로챈 값으로 할 수 있는 것 — 크래킹 vs 릴레이 vs Pass-the-Hash¶

    강의 외 보충 설명입니다.

    NTLM 인증은 "질문과 대답" 방식입니다. 서버가 무작위 **질문(챌린지)**을 던지면, 클라이언트는 자기 NT 해시를 열쇠로 써서 그 질문에 대한 **대답(응답)**을 계산해 돌려줍니다.

    • NT 해시는 패스워드에서 나온 고정된 열쇠입니다. 이 열쇠를 가진 사람은 어떤 질문이 와도 맞는 대답을 계산할 수 있으니, 언제든 어느 서버에든 몇 번이든 로그인할 수 있습니다 → Pass-the-Hash.
    • NetNTLMv2는 그 열쇠로 특정 질문 하나에 대해 계산한 한 번짜리 대답입니다. 다음 로그인 때는 서버가 다른 질문을 던지므로 녹음해 둔 옛 대답은 쓸모가 없습니다 → 재사용 불가, 오프라인 크래킹만 가능.
    • 릴레이는 값을 저장했다가 나중에 쓰는 게 아니라, 피해자와 진짜 서버 사이에 끼어 질문과 대답을 실시간으로 양쪽에 전달하는 것입니다.
    피해자 PC              공격자(ntlmrelayx)              진짜 서버(예: 파일 서버)
    │                         │                                │
    │── ① 인증하고 싶어요 ──▶│                                │
    │                         │── ② 인증하고 싶어요(피해자인 척) ─▶│
    │                         │◀──────── ③ 질문(챌린지) ────────│
    │◀── ④ 그 질문 그대로 ───│                                │
    │  (피해자가 자기 NT 해시로 대답 계산)                      │
    │── ⑤ 대답(응답) ───────▶│                                │
    │                         │──────── ⑥ 그 대답 그대로 ─────▶│
    │                         │◀──── ⑦ 인증 성공! ─────────────│
                        (이제 공격자가 피해자 계정으로 서버에 접속한 상태)

    진짜 서버의 질문을 피해자에게 넘기니, 피해자는 바로 그 질문에 대한 대답을 계산하고, 그 대답이 지금 서버가 기다리는 정답이라 그대로 통과합니다. 공격자는 패스워드도 NT 해시도 모르는 채로 피해자 계정 세션을 얻습니다. 그래서 릴레이는 패스워드가 아무리 강해도 통합니다.

    공격자가 가진 것 할 수 있는 것
    Pass-the-Hash NT 해시(고정된 열쇠) 언제든, 아무 서버에나, 반복해서 로그인
    가로챈 NetNTLMv2 한 번짜리 대답 재사용 불가 → 오프라인 크래킹만 가능
    NTLM 릴레이 아무것도 저장 안 함 (실시간 중계) 피해자가 인증을 시도하는 그 순간에만 다른 서버로 로그인

    릴레이의 조건: ① 실시간이어야 함, ② 피해자 계정이 대상 서버에서 권한이 있어야 의미가 있음, ③ 같은 PC로 되돌려 보내는 것(반사)은 오래전 패치로 기본적으로 막힘.

    로그에서는 (DFIR 관점): 릴레이가 성공하면 대상 서버에 4624(로그온 성공), 로그온 유형 3(네트워크), 인증 패키지 NTLM이 남습니다. 단서는 계정과 출발지가 맞지 않는다는 점 — 계정은 피해자(예: CORP\alice)인데 출발지 IP(IpAddress)는 공격자 PC이고, 워크스테이션 이름(WorkstationName)과 IP가 서로 맞지 않습니다.

    깊이 보기 ② SMB 서명은 어떻게 릴레이를 막나¶

    강의 외 보충 설명입니다.

    은행 창구에 비유하면 이렇습니다.

    • 릴레이 = 남의 신분 확인을 대신 통과한 것. 공격자는 창구 직원(서버)의 질문을 진짜 손님(피해자)에게 전달하고, 손님의 대답을 다시 직원에게 전달해 손님인 척 창구를 통과합니다.
    • SMB 서명 = 통과한 뒤에도 출금 전표마다 "인감 도장"을 요구하는 규칙. 로그인 후에 오가는 모든 요청(파일 열기, 명령 실행 등)마다 본인만 만들 수 있는 도장이 찍혀 있어야 서버가 받아 줍니다.
    • 공격자는 도장이 없다. 그래서 인증은 통과해도, 첫 번째 요청부터 서버가 거절합니다. 창구까지는 들어왔지만 아무 일도 처리하지 못합니다.

    주의: "가능"이 아니라 "필수"여야 한다.

    • 사용 가능(enabled): "도장 찍어도 되고 안 찍어도 됩니다." → 공격자가 "도장 없이 할게요"라고 하면 받아 줌 → 릴레이를 못 막음
    • 필수(required): "도장 없으면 무조건 거절" → 릴레이를 막음

    최근 Windows(Windows 11 24H2, Windows Server 2025)부터는 SMB 서명이 기본으로 필수로 바뀌고 있지만, 예전 버전이나 설정을 바꾼 환경은 여전히 필수가 아닐 수 있으니 실제 설정을 확인해야 합니다.

    깊이 보기 ③ 서명은 NT 해시가 있어야만 만들 수 있나¶

    강의 외 보충 설명입니다.

    NTLM으로 로그인한 경우에는 사실상 그렇습니다. (흔히 "NTLM 해시"라고 부르는 것은 정확히는 NT 해시입니다.)

    1. 피해자 PC가 서버의 질문에 대답을 계산하면서,
    2. 동시에 NT 해시 + 이번 질문과 대답에 들어간 값들을 섞어 **"이번 대화 전용 열쇠(세션 키)"**를 계산합니다.
    3. 서명은 이 세션 키로 만듭니다. 세션 키 자체는 네트워크로 전송되지 않습니다.

    그럼 파일 서버는 어떻게 아나? 파일 서버는 사용자의 NT 해시를 모르므로 도메인 컨트롤러(DC)에 물어봅니다. DC가 대답을 확인하고 세션 키도 계산해 **안전한 전용 통로(Netlogon 보안 채널)**로 파일 서버에 알려 줍니다. 그래서 세션 키를 아는 것은 피해자 PC, DC, 파일 서버 셋뿐이고, 전달만 한 공격자는 모릅니다. (Kerberos로 로그인하면 NT 해시 대신 Kerberos 티켓 안의 세션 키로 서명합니다 — 원리는 같습니다.)

    중요한 결론 — 해시를 이미 가졌다면 이야기가 다르다. 공격자가 NT 해시를 이미 가지고 있다면 세션 키를 직접 계산할 수 있으므로 서명도 직접 만들 수 있습니다. 즉 Pass-the-Hash는 SMB 서명으로 막히지 않습니다.

    공격 공격자가 NT 해시를 아나? SMB 서명(필수)으로 막히나?
    NTLM 릴레이 모름 (전달만 함) 막힘
    Pass-the-Hash 앎 (훔침) 안 막힘
    가로챈 NetNTLMv2 크래킹 크래킹에 성공하면 패스워드까지 앎 크래킹 후에는 안 막힘

    그래서 방어도 따로 필요합니다. SMB 서명 = 릴레이 대책, Pass-the-Hash 대책 = 3일차의 LAPS·워크스테이션 간 통신 차단·Credential Guard(Pass-the-Hash), 크래킹 대책 = 1일차의 길고 강한 패스워드.

    오늘 남은 실습 예고¶

    • 웹 테스트 실습 — 일부러 취약하게 만든 작은 웹 앱(Damn Small Vulnerable Web App)을 **ZAP(Zed Attack Proxy)**으로 공격 (3부)
    • Ping Castle 실습 — VM 없이 웹 사이트에서 Ping Castle 보고서를 분석 (4부)

    2. 인터넷 허용 목록 (Internet Allow Listing)¶

    1일차의 애플리케이션 허용 목록과 아주 비슷합니다. 효과가 매우 크지만, "회사가 쓰는 웹사이트를 전부 등록해야 한다"는 걱정 때문에 하지 않습니다.

    그럴 필요 없다. 사용자가 인터넷에 나갈 때 거치는 웹 프록시의 간단한 설정만으로 쉽게 할 수 있다.

    이렇게 하면 초기 침해와 C2 통신의 상당 부분이 막히고, 2일차의 RITA·AC-Hunter와 좋은 짝이 됩니다.

    왜 차단 목록으로는 안 되나¶

    인터넷은 크다. 정말 크다. 얼마나 어마어마하게 거대한지 믿기 힘들 정도다. 그리고 그 대부분은 쓸모없고 사악하다.

    공격자는 도메인을 어떻게 쓰나¶

    ① 사서 쓰고, 환불받는다. GoDaddy 같은 곳에서 도메인을 4.99달러 정도에 살 수 있고, 인터넷 규칙(ICANN)상 1~2주 정도 환불 기간이 있습니다. 공격자는 도메인을 사서 공격에 쓰고 환불받습니다 — "공격자는 무엇보다 알뜰하다".

    ② 다른 조직을 뚫어서 그 도메인을 쓴다. John은 Shodan(인터넷에 노출된 장비 검색 엔진)으로 보여 줍니다.

    • MongoDB 검색 → 노출된 데이터베이스 93,624개, 상당수가 지원 종료(EOL)·미패치
    • 엔터프라이즈 라이선스(비쌈)가 있으면 취약하거나 이미 침해된 시스템까지 검색
    • 이미지 검색에서 5900번 포트(VNC) → 화면이 그대로 보이는 세션들, ICS 태그 → 인증 없이 들어갈 수 있는 산업 제어 시스템들

    왜 짧게 쓸까? 돈 때문만이 아니라, 공격에 쓴 도메인은 보통 1~2주면 "타 버려서(burnt)" 차단 목록에 오르기 때문입니다.

    펜테스터는 다르게 한다 — 이미 분류된 도메인¶

    BHIS 같은 펜테스터는 만료된 도메인을 사서, URL과 위험 평가(SimilarWeb·ACR 점수)로 정렬해 주는 도구를 씁니다(자동 자막으로는 도구 이름이 분명하지 않습니다). 예전에 누군가 쓰다 만료되어 다시 매물로 나온 도메인이라, 보안 업체들이 이미 증권·거래, 정부·법률(예: Oregon City Parks .org), 엔터테인먼트, 기술·인터넷 같은 정상 분류를 붙여 둔 상태입니다. 목적은 도메인 필터링 우회입니다.

    실제 공격자는 이렇게 잘 안 한다. 새 도메인을 사서 쓴다. 이 차이가 아래 방어책의 핵심이다.

    사이트는 허용하고, 광고는 지운다¶

    사람들이 하루에 가는 웹사이트는 대부분 몇 개 안 됩니다. 예외는 링크를 다 누르는 사람들과 뉴스 사이트를 많이 보는 사람들인데, Yahoo처럼 뉴스 기사처럼 생긴 광고가 섞인 사이트에서 그걸 누르는 사람도 있습니다. 하지만 아주 드뭅니다.

    사람들이 가고 싶어 하는 사이트는 허용해 주고(Yahoo여도 좋다), 대신 광고를 지운다 — Ghostery나 AdBlock Plus 같은 것을 환경 전체에 돌린다. 이것만으로도 차단 목록 방식보다 노출이 훨씬 줄어든다.

    차단 목록 방식이 불리한 이유: Cisco나 Fortinet 같은 업체가 나쁜 사이트를 분류하는 데는 시간차가 있습니다 — 사이트가 공격을 시작한 시점과 업체가 막기 시작하는 시점 사이에 빈틈이 생깁니다.

    핵심 — "미분류(Uncategorized)"를 차단하라¶

    대부분의 웹 필터에는 분류 목록(애드웨어, 주류, 익명화 도구, 포르노, 도박 …)이 있습니다. 회사들은 성인물·도박 같은 것은 차단하지만, 오른쪽 아래의 "미분류(Uncategorized)"는 무시합니다.

    이걸 차단하면 큰 수고 없이 사실상의 허용 목록이 된다. 알려진 사이트만 갈 수 있게 되기 때문이다.

    공격자는 완전히 새로 산 도메인을 쓰므로, 방화벽·프록시 업체는 그 도메인을 한 번도 본 적이 없습니다.

    Cisco 같은 업체가 한 번도 본 적 없는 도메인에 사용자가 가게 두고 싶은가? 나쁜 생각 같지 않나?

    💡 보충 (강의 외)

    요즘 많은 프록시·DNS 필터에는 "새로 등록된 도메인(Newly Registered Domains, NRD)" 분류가 따로 있습니다(예: 등록 30일 이내). "미분류"와 함께 차단하면 공격자가 막 사서 쓰는 도메인을 효과적으로 걸러 냅니다.

    허용 목록 방식 세 가지¶

    • ① 모든 사이트를 하나하나 허용 — 대부분의 경우 멍청한 방법
    • ② 분류 기준으로 허용 — 위의 방식("미분류" 차단 포함)
    • ③ 사용자가 직접 허용 — Pi-hole로 가능. 처음 보는 도메인이면 "정말 가시겠습니까?" 팝업을 띄움

    이렇게 하면 C2 통신이 밖으로 나가기 아주 어려워진다. C2 악성코드에는 손이 없어서 그 버튼을 누를 수 없다.

    정상 사이트에서도 감염된다 — 범인은 광고¶

    허용 목록을 써도 감염은 뉴스 사이트, Facebook, 영화 사이트, 성인 사이트 같은 정상 사이트에서 일어날 수 있고, 그건 거의 언제나 광고를 통해서입니다.

    처음 감염시키는 서버는 보통 C2 서버가 아니다. 익스플로잇을 전달하는 서버와 명령·제어 서버가 따로 있다.

    그래서 감염 단계를 놓쳐도 C2로 나가는 통신을 막을 기회가 한 번 더 있습니다. 이런 분류 필터링은 OpenDNS 같은 DNS 기반 필터로도 할 수 있습니다.

    💡 보충 (강의 외) — Splunk로 \"처음 보는 도메인\" 찾기

    index=zeek sourcetype=zeek_dns earliest=-30d
| stats earliest(_time) AS first_seen count BY query
| where first_seen > relative_time(now(), "-1d")
| sort - count
    • index=zeek sourcetype=zeek_dns earliest=-30d — 최근 30일치 Zeek DNS 로그(인덱스·sourcetype 이름은 환경에 맞게).
    • stats earliest(_time) AS first_seen count BY query — 도메인(query)별로 처음 나타난 시각(first_seen)과 조회 횟수.
    • where first_seen > relative_time(now(), "-1d") — 처음 나타난 시각이 최근 24시간 안인 것만 = "30일 동안 없다가 오늘 처음 등장한 도메인".
    • sort - count — 조회가 많은 순.
    query                         first_seen   count
timeserversync.com            1729555200   168
cdn-update-check.net          1729560000    42

    새로 나타났는데 조회가 규칙적으로 많은 도메인(2일차 AC-Hunter의 WhatTime처럼 시간당 168회)은 C2를 의심해 볼 만합니다.

    DNS over HTTPS(DoH)에 대한 John의 생각¶

    DoH는 이름 조회를 암호화된 HTTPS로 보내는 기술로, 사생활 보호에는 좋습니다. 하지만 John은 불편해합니다.

    • 위험한 나라에 있는 사람이라도 John은 VPN을 권합니다.
    • DoH 업체 상당수가 "시민의 권리를 돕는다"는 겉모습 뒤에서 DNS 데이터를 모아 광고에 쓴다고 봅니다("좀 수상하다").
    • 회사에서는 DoH를 쓰지 말라:

    DNS는 암호화되어 있지 않아서, 사람들이 어디로 가는지 볼 수 있다. 그게 우리에게 어느 정도의 보호를 준다. DoH를 쓰면 그 가시성을 잃는다.

    💡 보충 (강의 외)

    회사에서는 그룹 정책으로 브라우저 자체 DoH를 끄고, 알려진 공개 DoH 서버(예: 1.1.1.1, 8.8.8.8, dns.google의 443 포트)로 나가는 통신을 막아 사내 DNS만 쓰게 하는 것이 일반적입니다. 그래야 2일차의 DNS 기반 탐지(dnscat2 같은 DNS 백도어 찾기)도 계속할 수 있습니다.

    3. 취약점 관리¶

    10년째 그대로다¶

    취약점 스캐너를 돌린다 → 외부에 노출된 취약점을 찾는다 → 보고서가 나온다. 아주아주 단순하다.

    일부 회사는 인증 스캔(credentialed scan) — 스캐너에 계정을 주고 설치된 프로그램을 다 조사 — 으로 옮겨 가지만, 많은 팀이 쏟아지는 데이터에 압도됩니다. 그리고 AI 시대에는 보고되는 취약점, 새 CVE와 익스플로잇이 폭증할 것이므로, 사람이 그 과정 안에 반드시 있어야 합니다.

    "높음·치명적만 고친다"는 망가졌다¶

    중간·낮음이나 공개 익스플로잇이 없는 것을 무시하면 AI 시대에는 문제가 생깁니다. 약간의 실력과 AI 도구, 시간, 토큰만 있으면 누구나 그런 취약점에서 익스플로잇까지 뽑아낼 수 있기 때문입니다.

    예전에 "중간"이던 것이 이제는 아마 "높음"이 되고 있다.

    John의 제안 — CVSS를 최소 1점씩 올려서 보라: 6.5 → 7.5, 8.5 → 9.5, 9.5 → 곧 익스플로잇이 나올 것으로.

    CVSS 점수 등급
    0.1 ~ 3.9 낮음 (Low)
    4.0 ~ 6.9 중간 (Medium)
    7.0 ~ 8.9 높음 (High)
    9.0 ~ 10.0 치명적 (Critical)

    "실제 익스플로잇이 없으면 패치하지 않는다"는 방식에 대해서는:

    익스플로잇이 나왔을 때는 이미 늦었다.

    예전에는 익스플로잇·웜이 무차별로 퍼졌고 방어자에게 시간이 있었지만, 이제는 특정 조직을 노린 공격에서도 AI의 도움으로 맞춤형 익스플로잇을 비교적 빨리 개발할 수 있습니다.

    💡 보충 (강의 외) — CVSS 말고 함께 볼 것

    • CISA KEV — 실제로 악용된 것이 확인된 취약점 목록
    • EPSS — 앞으로 30일 안에 악용될 확률

    둘 다 유용하지만 "이미 악용됐다/될 것 같다"는 신호가 쌓인 뒤 올라가므로, AI로 익스플로잇이 빨리 나오는 시대에는 늦을 수 있습니다. KEV·EPSS로 앞쪽을 정하되 그 아래도 무시하지 마세요.

    더 큰 문제 — 무시되는 Low·Informational¶

    더 큰 문제는, **낮음(Low)과 정보(Informational)**는 애초에 무시하면 안 되는 것이었다는 점이다.

    어떤 조직의 서버 팜에 Telnet 서버가 1,000대 있다고 해 봅시다(레거시 환경에서 실제로 있는 일). 스캔하면 접속 시 처음 나오는 배너가 이렇게 보입니다.

    login
login
login
mushroom
mushroom
login
router
login
...

    (재구성 — John이 말로 설명한 예)

    대부분은 login인데, router라고 뜬 한 대는 인증 없이 바로 들어갈 수 있는 Telnet 서버입니다. 엄청나게 큰 취약점이지만, 배너 문구는 아무 문자열이나 될 수 있어서 스캐너는 "그냥 로그인 배너"와 "큰 취약점일 수 있는 배너"를 구분하지 못하고 Informational로 분류합니다.

    AI 시대가 오기 전부터, 우리는 이미 놓치고 있는 Low·Informational을 엄청나게 안고 있었다. 그리고 대부분의 조직은 그걸 그냥 무시한다.

    깊이 보기 ④ 배너가 router로 나오면 왜 위험한가¶

    강의 외 보충 설명입니다.

    위험한 건 router라는 단어가 아니라, 로그인 요청 없이 바로 장비의 명령 입력 화면이 나왔다는 사실입니다. 정상적인 Telnet 서버는 먼저 누구냐고 묻습니다.

    $ telnet 10.1.0.1
Connected to 10.1.0.1.

User Access Verification

Username:

    router라고 나온 서버는 이렇게 생겼을 가능성이 높습니다.

    $ telnet 10.1.0.9
Connected to 10.1.0.9.

Router>

    Router>는 **로그인이 이미 끝난 뒤에 나오는 "명령을 입력하세요" 화면(프롬프트)**입니다. Cisco 장비는 이름을 정하지 않으면 기본 이름이 Router라서 프롬프트가 Router>로 나옵니다. 즉 접속하자마자 라우터 안에 들어와 있는 상태 — 문 앞에서 신분 확인을 해야 하는데, 문을 여니 바로 기계실 안인 것과 같습니다.

    라우터는 네트워크의 교차로라서, 들어오면 설정을 보고 네트워크 구조 파악, 경로를 바꿔 트래픽을 자기 쪽으로 돌리기(Responder와 같은 효과), ACL을 바꿔 막힌 길 열기, 다른 구간으로 넘어가는 발판으로 쓰기가 가능합니다. 게다가 Telnet은 암호화되지 않아 정상 로그인의 패스워드도 평문으로 흐릅니다.

    mushroom은 **"배너 문구는 아무거나 될 수 있다"**는 예입니다. 글자만 봐서는 그다음에 로그인 요청이 나올지 모릅니다. 스캐너는 배너의 첫 문구만 기록할 뿐 그게 "로그인 요청 화면"인지 "이미 들어온 명령 화면"인지 이해하지 못합니다. 사람이 읽어 봐야 압니다.

    시스템별이 아니라 취약점별로 묶어라¶

    시스템 하나하나 기준으로 보면 IP 1,000개 × IP당 취약점 약 25개 = 25,000개 — 불가능해 보여 막막해집니다. John은 이 접근이 거의 언제나 틀렸다고 합니다.

    사실 25,000개의 취약점이 있는 게 아니다. 보통은 수백 개의 취약점이 여러 시스템에서 계속 반복되는 것이다.

    질문을 뒤집습니다 — ❌ "이 시스템에는 어떤 취약점이 있나?" → ⭕ "이 취약점은 어떤 시스템들에 있나?" 그러면 수백 개만 쫓으면 되고, Microsoft 패치 관리, Ansible 스크립트 같은 자동화로 같은 수정을 여러 시스템에 한꺼번에 밀어 넣을 수 있습니다.

    💡 보충 (강의 외) — Splunk로 \"취약점별로 묶기\"

    Nessus 결과를 CSV로 내보내 Splunk에 조회 파일(lookup) nessus_scan.csv로 올렸다고 해 봅시다(열: Plugin ID, Name, Risk, Host, Port, Plugin Output 등).

    | inputlookup nessus_scan.csv
| stats dc(Host) AS host_count values(Host) AS hosts BY "Plugin ID" Name Risk
| sort - host_count
    • | inputlookup nessus_scan.csv — 인덱스 대신 올려 둔 CSV 파일을 불러옴(맨 앞에 |).
    • stats ... BY "Plugin ID" Name Risk — 취약점별로 묶음. 필드 이름에 공백이 있으면 큰따옴표로 감쌈.
      • dc(Host) AS host_count — dc는 고유 개수 — 이 취약점이 있는 서로 다른 호스트 수.
      • values(Host) AS hosts — 그 호스트들의 목록.
    • sort - host_count — 영향받는 호스트가 많은 순.
    Plugin ID  Name                              Risk    host_count  hosts
42263      Unencrypted Telnet Server         Medium  1000        10.1.0.1, 10.1.0.2, ...
57608      SMB Signing not required          Medium   812        10.2.0.5, 10.2.0.6, ...
...        Web Server Office File Inventory  None      14        10.3.1.20, ...

    (숫자는 설명용 예시) 25,000줄이 수백 줄로 줄고, "한 번 고치면 수백 대가 해결되는 것"이 맨 위에 보입니다. **"SMB 서명이 필수 아님"**은 깊이 보기 ②의 릴레이 방어와 바로 연결되는 항목 — Nessus는 Medium이지만 812대가 릴레이에 노출돼 있다는 뜻입니다. Nessus CSV에서 Informational은 Risk가 None으로 들어가니 걸러 내지 말고 같이 보세요.

    배너처럼 드문 값(2일차의 롱테일 분석)을 찾으려면:

    | inputlookup nessus_scan.csv
| search "Plugin ID"=42263
| stats count BY "Plugin Output"
| sort count
    • search "Plugin ID"=42263 — Telnet 서버 항목만.
    • stats count BY "Plugin Output" — 배너 내용이 같은 것끼리 개수.
    • sort count — 적은 순(-가 없으면 오름차순).
    Plugin Output        count
router                   1
mushroom                 2
login                  997

    맨 위에 1개뿐인 router가 바로 그 인증 없는 Telnet 서버입니다.

    취약점 스캔이 보는 범위는 좁다. MITRE ATT&CK 중 공개 애플리케이션 익스플로잇과 외부 원격 서비스 정도뿐이고, 매트릭스의 대부분과 침투 후 횡적 이동 기회는 보이지 않습니다. 그래서 3일차의 BloodHound나 4부의 Ping Castle 같은 도구가 따로 필요합니다.

    4. Nessus 보고서 실습 — 보물찾기¶

    Windows VM의 IntroLabs 폴더에 있는 Nessus 보고서(오래됐지만 개념은 같음)에서, 사람들이 흔히 무시하는 Low·Medium 중 반드시 고쳐야 할 것을 찾는 "보물찾기"입니다. 보고서 맨 아래에 John의 해설이 있습니다.

    ① Office File Inventory (Low)¶

    Ctrl+F로 "office" 검색 → 웹 서버에 올라와 있는 Office 문서 목록을 알려 주는 Low 항목.

    이건 우리가 아주 자주 보는 Low 항목이고, 실제로 이걸로 시스템에 들어간다.

    사람들이 웹 서버에 말도 안 되는 것들을 올리기 때문입니다 — passwords.doc, 시스템 설치를 단계별로 적은 설치 안내서 등.

    ② 백업 파일 (.bak)¶

    .bak 검색 → 웹사이트 페이지 목록에 이런 것들이 보입니다.

    /admin/
/admin/backup/backup.bak
/admin/telnet

    많은 웹사이트가 정기 백업을 .001, .002, .bak 같은 이름으로 같은 폴더에 저장해 두고, 그 안에는 **서버 측 포함 파일(server-side includes)**처럼 사용자 ID와 패스워드가 들어 있는 경우가 많습니다. 다른 사이트에서는 sourcecode.tar(소스 코드 묶음)도 보입니다.

    💡 보충 (강의 외) — 백업 파일이 위험한 이유

    웹 서버는 config.php를 받으면 실행해서 결과만 보여 주므로 그 안의 DB 패스워드는 보이지 않습니다. 그런데 config.php.bak이라는 이름이면 실행할 파일로 인식하지 않고 그냥 텍스트로 내려 줍니다 → 소스 코드와 DB 패스워드가 그대로 노출. 방어는 웹 루트에 백업 파일을 두지 않는 것, 그리고 .bak, .old, .tar, .zip 같은 확장자를 아예 내려 주지 않도록 막는 것입니다.

    (재구성 — 실제 보고서 화면 문구는 조금 다를 수 있음)

    깊이 보기 ⑤ "인증하세요"라고 하다가 왜 config term이 나오나¶

    강의 외 보충 설명입니다.

    화면의 "Please authenticate"는 실제로 인증을 확인하는 단계가 아니라, 그냥 적어 둔 안내 문구다.

    장비에는 설정이 따로 두 개 있습니다.

    • 배너(banner) — 접속하면 보여 주는 안내문. 아무 글이나 넣을 수 있음.
    • 인증(login) — 실제로 아이디·패스워드를 묻고 확인하는 설정.

    이 장비는 배너에는 "인증하세요"라고 써 놓고 정작 인증 설정은 하지 않은 것입니다. 문에 "출입 시 신분증을 제시하세요"라는 안내문은 붙어 있는데 문은 잠겨 있지 않은 것과 같습니다.

    config term은 Cisco의 configure terminal — 장비의 설정을 바꾸는 모드로 들어가는 명령입니다.

    프롬프트 단계 할 수 있는 것
    Router> 일반 사용자 모드 상태를 일부 볼 수 있음
    Router# 관리자(특권) 모드 모든 정보를 보고, 설정 모드로 들어갈 수 있음
    Router(config)# 설정 모드 장비 설정을 무엇이든 바꿀 수 있음

    그래서 깊이 보기 ④의 Router>보다 더 나쁜 상태입니다 — 인증이 없을 뿐 아니라 곧바로 최고 권한으로 설정을 바꿀 수 있는 곳에 들어와 있습니다.

    왜 이런 일이 생기나: 원격 접속 회선(VTY)에 인증을 안 걸어 둠(no login), 원격 접속 시 **곧바로 최고 권한(privilege level 15)**을 주도록 설정, 테스트하려고 풀어 뒀다가 되돌리지 않음, 오래된 장비라 아무도 설정을 확인하지 않음.

    방어: Telnet을 끄고 SSH만(transport input ssh), 원격 접속에 반드시 로그인(AAA나 로컬 계정), 관리 접속은 관리용 IP에서만 허용하는 ACL. 점검할 때는 23번 포트가 열린 장비의 배너를 모아 드문 것부터 보면 login이 아닌 이상한 화면을 빨리 찾을 수 있습니다.

    이 실습이 말하는 것¶

    높음·치명적만 보면 안 된다. Low·Informational도 봐야 한다. 그리고 이걸 조직에서 효과적으로 하려면, 플러그인 ID와 취약점 ID 기준으로 정렬해서 봐야 한다.

    지금까지 본 것은 일반적인 취약점 평가 스캔이고, 이것은 웹 애플리케이션, 모바일 애플리케이션, API 테스트와는 근본적으로 다릅니다 → 3부의 웹 애플리케이션 보안으로 이어집니다.

    여기까지가 4일차 1~2부입니다. 한 줄 요약:

    같은 네트워크의 공격자는 NTLMv2를 가로채 크래킹하거나 릴레이한다 — 호스트 간 통신 차단·LLMNR 끄기·SMB 서명(필수)이 답이고, 해시를 훔친 Pass-the-Hash는 따로 막아야 한다. 공격자는 새 도메인을 짧게 쓰고 버리므로 "미분류" 차단과 광고 제거만으로 사실상의 인터넷 허용 목록이 된다. 취약점은 CVSS를 한 단계 올려 보고, Low·Informational도 살피고, 취약점별로 묶어 자동화로 고쳐라.
