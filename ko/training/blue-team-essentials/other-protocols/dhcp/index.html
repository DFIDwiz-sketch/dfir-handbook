    DHCP — 눈여겨볼 프로토콜들, IP를 장비 이름으로 바꾸기, 몰래 꽂은 장비 찾기, DORA 한 단계씩¶

    이 페이지에서 다루는 것

    DNS·HTTP·이메일 다음으로 분석가가 꼭 알아야 할 프로토콜들(DHCP, SMB, SSH, RDP/VNC, PowerShell 원격, FTP, ICMP, 원격 관리 도구)이 왜 따로 묶이는지. 그 첫 번째로 DHCP를 다룹니다. 알림 속 IP 주소를 "어느 장비, 누구의 장비"로 바꾸는 첫 단계가 왜 DHCP인지, 그때 시간이 왜 중요한지, DHCP 로그로 몰래 꽂은 장비(rogue device)를 찾는 법(호스트 이름 규칙, MAC 주소의 OUI)과 그 한계, 그리고 주소를 받는 네 단계(DORA)를 패킷 단위로 따라갑니다. Windows DHCP 감사 로그와 Zeek dhcp.log를 칸별로 읽고, 가짜 DHCP 서버 같은 공격도 봅니다. 마지막에 확인 문제와 해설이 있습니다.

    표기

    [보충] = 꼭 알아야 할 실무 보충, [정정] = 흔히 잘못 알려진 내용 정정, [변경됨]/[주의] = 최근 바뀐 점과 옛 방식대로 하면 위험한 점. 호스트 이름, 도메인, IP, MAC은 모두 설명용 가상 값(.example, 문서용·사설 IP)입니다.

    한눈에 보는 핵심 8가지¶

    1. DNS·HTTP·SMTP 말고도 공격자가 옆으로 이동(lateral movement)하거나 데이터를 빼낼(exfiltration) 때 쓰는 프로토콜들이 있다. SMB, SSH, RDP/VNC, PowerShell 원격, FTP, ICMP, 그리고 모든 원격 접속·관리 도구가 그 대상이다.
    2. DHCP는 그 자체로 공격 통로라기보다, 분석가에게 "이 IP는 그 시각에 어느 장비였나"를 알려 주는 기록이다.
    3. 조사는 IP → 장비 이름(호스트 이름)·MAC → 사용자로 이어지는 사슬이고, DHCP 로그가 그 첫 고리다.
    4. IP는 빌려 쓰는(lease) 값이라 주인이 바뀐다. 반드시 알림이 난 시각에 그 IP를 쓰던 장비를 찾아야 한다.
    5. DHCP 서버는 보통 호스트 이름, 받은 IP, MAC 주소를 남긴다. 그래서 네트워크에 붙은 장비의 출석부 역할을 한다.
    6. 몰래 꽂은 장비는 호스트 이름 규칙(회사 이름 규칙에 맞나, 공유기·라즈베리파이 기본 이름인가)과 MAC의 OUI(앞 3바이트 = 제조사)로 찾을 수 있다.
    7. 하지만 호스트 이름과 MAC은 장비가 스스로 말하는 값이라 속일 수 있다. 실수로 꽂은 장비는 잘 잡히고, 준비한 공격자는 빠져나갈 수 있다. 요즘은 휴대폰·노트북의 MAC 무작위화도 OUI 판단을 흔든다.
    8. 주소는 Discover → Offer → Request → Acknowledge(DORA) 네 단계로 받는다. UDP 67번(서버)·68번(클라이언트), 처음에는 출발지 0.0.0.0, 목적지 브로드캐스트 255.255.255.255.

    이 묶음에서 다룰 프로토콜들¶

    지금까지 본 DNS, HTTP, 이메일은 공격의 입구와 통신선이었습니다. 피싱 메일로 들어오고, HTTP로 악성 파일을 받고, DNS나 HTTPS로 C2(명령·제어 서버)와 이야기합니다. 그런데 공격자가 한 대에 발을 들인 다음에는 할 일이 바뀝니다. 다른 서버로 옆으로 이동하고, 관리자 권한을 얻고, 마지막에 자료를 밖으로 빼냅니다. 이때 쓰는 프로토콜은 대부분 관리자들이 매일 쓰는 평범한 것들입니다.

    프로토콜 원래 쓰임 공격자가 노리는 이유 이어지는 페이지
    DHCP 장비에 IP 나눠 주기 직접 공격보다는 조사의 기준점. 가짜 DHCP 서버, 몰래 꽂은 장비 이 페이지
    SMB Windows 파일·프린터 공유 원격 실행(PsExec류), 파일 복사, 랜섬웨어 확산, 인증 정보 가로채기 SMB 페이지
    SSH 원격 셸, 파일 전송 밖으로 나가는 SSH 하나로 거꾸로 안으로 들어오는 터널을 만들 수 있음 SSH·RDP·VNC 페이지
    RDP/VNC 원격 데스크톱 탈취한 계정으로 화면을 그대로 조작, 인터넷에 열린 RDP SSH·RDP·VNC 페이지
    PowerShell 원격 원격 관리(WinRM) 파일을 남기지 않고 다른 PC에서 명령 실행 PowerShell 원격·FTP·ICMP 페이지
    FTP / ICMP 파일 전송 / 핑 평문 유출, ICMP 안에 데이터 숨기기(터널링) PowerShell 원격·FTP·ICMP 페이지
    원격 관리 도구 전부 원격 지원, 원격 관리 정상 소프트웨어라 백신이 잘 막지 않음 원격 관리 도구 페이지

    핵심 생각은 하나입니다. "이 프로토콜은 정상이냐 악성이냐"가 아니라 "이 장비에서, 이 상대에게, 이 시각에, 이 프로토콜이 쓰이는 게 정상이냐"를 묻습니다. 관리자 PC에서 서버로 가는 RDP는 일상이지만, 회계팀 PC에서 다른 회계팀 PC로 가는 RDP는 수상합니다. 그 판단을 하려면 먼저 "이 IP가 누구인가"를 알아야 하고, 그래서 이 묶음의 첫 주제가 DHCP입니다.

    DHCP가 분석가에게 왜 중요한가¶

    알림 속 IP를 "누구"로 바꾸기¶

    IDS(침입 탐지 시스템) 알림, 방화벽 로그, 프록시 로그는 대부분 장비를 IP 주소로만 적습니다. 하지만 대응은 사람과 장비에 대해 합니다. "10.20.30.41을 격리하라"보다 "재무팀 김 대리의 노트북 LT-FIN-0412를 격리하라"가 실제 행동입니다. 그 연결은 이렇게 이어집니다.

     Alert: src=10.20.30.41          (IDS / firewall / proxy)
        │  DHCP lease log at the alert time
        ▼
 Host: LT-FIN-0412  MAC 3c:52:82:aa:41:07
        │  asset inventory / EDR / AD computer object
        ▼
 Device owner: finance team, assigned to j.kim
        │  logon events (4624 on the host, 4768 on the DC)
        ▼
 User at that time: VICTIM\j.kim

    비유하면 호텔 방 번호입니다. 객실 1203호에서 소음 신고가 들어왔다고 해서 "1203호 사람"이 누군지 바로 알 수는 없습니다. 프런트의 체크인 기록을 봐야 그날 그 시각에 누가 묵었는지 압니다. 어제 1203호에 묵었던 손님은 오늘 다른 사람일 수 있습니다. IP가 방 번호, DHCP 임대(lease) 기록이 체크인 기록입니다.

    기술적으로 다시 말하면, DHCP는 IP를 정해진 시간(임대 기간, lease time) 동안만 빌려줍니다. 노트북이 회의실 무선망에 붙었다 떨어지고, 다음 날 다른 층에서 다시 붙으면 다른 IP를 받습니다. 임대가 끝난 IP는 다른 장비가 받아 갑니다. 그래서 "지금 이 IP를 쓰는 장비"를 찾으면 틀린 사람을 잡을 수 있습니다. 반드시 알림 시각을 포함하는 임대 기록을 찾아야 합니다.

    사슬의 나머지 고리 — 4624와 4768¶

    [보충] DHCP는 IP → 장비까지만 알려 줍니다. 장비 → 사람은 로그온 기록으로 잇습니다. 자주 쓰는 두 이벤트입니다.

    • Windows 이벤트 4624 (계정 로그온 성공, An account was successfully logged on). 그 PC에 누군가 로그온할 때마다 그 PC의 Security 로그에 남습니다. Logon Type 칸이 방식입니다. 2 = 앞에 앉아서 로그온(대화형), 3 = 네트워크로 접근(공유 폴더 등), 10 = RDP, 11 = 저장된 자격 증명으로 로그온(캐시). Source Network Address에 상대 IP가 찍힙니다. 공격자 관점에서는 훔친 계정으로 다른 PC에 들어갈 때 이 이벤트가 남기 때문에, 옆으로 이동한 흔적을 찾는 1순위 이벤트입니다.
    • Windows 이벤트 4768 (Kerberos TGT 요청, A Kerberos authentication ticket (TGT) was requested). 도메인 컨트롤러(DC)에 남습니다. 사용자가 도메인 PC에 로그온하면 먼저 DC에서 "입장권(TGT)"을 받는데, 이 이벤트에 계정 이름과 Client Address(요청한 IP)가 함께 찍힙니다. 그래서 DC 로그만 있어도 "그 시각 그 IP에서 로그인한 사용자"를 알 수 있습니다. 공격자에게는 AS-REP 로스팅이나 비밀번호 대입이 이 이벤트(실패 시 4771 등)로 드러나는 지점입니다.

    정리하면 DHCP(IP→장비) + 4768/4624(IP·장비→사용자)가 짝입니다. EDR을 쓰는 조직이면 EDR 콘솔이 이 연결을 대신 보여 주지만, EDR이 없는 장비(프린터, 개인 기기, 공격자의 장비)는 DHCP 기록이 유일한 단서인 경우가 많습니다.

    Windows DHCP 서버 감사 로그¶

    첫 줄(머리글)부터 칸별로 읽어 보겠습니다.

    • ID — 무슨 일인지를 나타내는 번호. 자주 보는 것: 10 = 새 임대(Assign), 11 = 갱신(Renew), 12 = 반납(Release), 13 = 그 IP가 이미 네트워크에서 쓰이고 있음(충돌), 14 = 주소 풀이 바닥남, 15 = 임대 거부, 16 = 임대 삭제, 17 = 임대 만료, 30·31·32 = DNS 등록 요청·실패·성공. 그 밖에 시작·종료, 권한 관련 번호들이 있습니다.
    • Date, Time — 서버의 현지 시각입니다. UTC가 아니므로 다른 로그와 맞출 때 시간대를 꼭 확인합니다.
    • Description — ID의 글자 설명.
    • IP Address — 빌려준 IP.
    • Host Name — 클라이언트가 스스로 알려 준 이름(DHCP 옵션 12 또는 81). 도메인에 가입한 Windows PC는 보통 FQDN(LT-FIN-0412.corp.victim.example)이 찍힙니다.
    • MAC Address — 구분 기호 없이 12자리로 찍힙니다. 3C5282AA4107 = 3c:52:82:aa:41:07.
    • User Name — 대부분 비어 있습니다. 사용자 이름이 나오는 기록이 아닙니다.
    • TransactionID — 한 번의 주고받기를 묶는 번호(DHCP 패킷의 xid). 같은 교환을 패킷 캡처에서 찾을 때 씁니다.
    • QResult — NAP(옛 네트워크 검역 기능) 결과. NAP는 오래전에 없어졌으므로 대개 의미 없는 값입니다.
    • VendorClass(Hex), VendorClass(ASCII) — DHCP 옵션 60. 장비가 알려 준 "나는 어떤 종류의 DHCP 클라이언트다". MSFT 5.0 = Windows, dhcpcd 9.4.1 = 많은 Linux(라즈베리파이 OS 포함), android-dhcp-… = 옛 Android.
    • RelayAgentInformation — DHCP 옵션 82. 중간 스위치·라우터(릴레이)가 붙여 주는 정보로, 설정에 따라 어느 스위치 어느 포트에서 왔는지가 들어갈 수 있습니다. 몰래 꽂은 장비의 물리적 위치를 찾을 때 금 같은 칸입니다.
    • DnsRegError — DNS 등록 오류 코드(0 = 문제 없음).

    1. 08:52:13, ID 10 — LT-FIN-0412가 10.20.30.41을 새로 받았습니다. 벤더 클래스가 MSFT 5.0이니 Windows입니다. 회사 이름 규칙(LT-부서-번호)에도 맞습니다.
    2. ID 30, 32 — DHCP 서버가 이 PC 대신 DNS에 LT-FIN-0412 → 10.20.30.41을 등록했습니다. 그래서 DNS 기록으로도 IP→이름을 찾을 수 있지만, DNS는 현재 값만 보여 주므로 과거 시각 조사에는 DHCP 기록이 더 정확합니다.
    3. 12:52:20, ID 11 — 4시간 뒤 갱신. 이 망의 임대 기간이 8시간이면, 절반이 지났을 때 갱신하는 정상 동작입니다(아래 DORA 절의 T1 참고).
    4. 13:07:45, ID 10 — 호스트 이름 raspberrypi, MAC B8:27:EB:…, 벤더 클래스 dhcpcd. raspberrypi는 라즈베리파이 OS의 기본 이름이고, B8:27:EB는 라즈베리파이 재단에 등록된 OUI입니다. 회사 규칙에 안 맞는 이름 + 회사가 사지 않는 제조사 + Linux 클라이언트. 조사 대상 1순위입니다. 릴레이 정보(0x0104000A0114)로 어느 스위치 포트인지 네트워크 팀과 확인합니다.
    5. 17:31:02, ID 12 — LT-FIN-0412가 IP를 반납(퇴근하며 종료). 이 시각 이후 10.20.30.41이 찍힌 알림은 다른 장비일 수 있습니다.

    Zeek dhcp.log¶

    네트워크 센서에 Zeek가 있으면, 서버 종류와 상관없이 DHCP 대화를 기록합니다. Zeek는 DORA 네 패킷을 한 줄로 묶어 보여 줍니다.

    $ zeek-cut -d ts client_addr server_addr mac host_name client_fqdn assigned_addr lease_time msg_types < dhcp.log
2026-11-18T13:07:45+0000  10.20.30.77  10.20.0.5  b8:27:eb:5c:19:a0  raspberrypi  -  10.20.30.77  28800.000000  DISCOVER,OFFER,REQUEST,ACK
2026-11-18T13:42:10+0000  -            192.168.8.1  b8:27:eb:5c:19:a0  raspberrypi  -  192.168.8.103  43200.000000  DISCOVER,OFFER,REQUEST,ACK

    명령 부분:

    • zeek-cut — Zeek 로그에서 원하는 칸만 뽑는 도구. -d는 유닉스 시간(초)을 사람이 읽는 날짜로 바꿉니다.
    • 뒤에 적은 이름들 — 뽑을 칸 목록. < dhcp.log는 그 파일을 입력으로 넣는다는 뜻입니다.

    칸별 해석:

    • ts — 첫 패킷 시각.
    • client_addr — 클라이언트가 이미 가지고 있던 IP. 처음 받는 중이면 비어 있습니다(-).
    • server_addr — 응답한 DHCP 서버 IP. 우리 회사 DHCP 서버 목록에 없는 값이면 경보 대상입니다.
    • mac, host_name, client_fqdn — 클라이언트가 스스로 알려 준 MAC과 이름(옵션 12, 81).
    • assigned_addr — 최종으로 받은 IP.
    • lease_time — 임대 기간(초). 28800초 = 8시간.
    • msg_types — 이 대화에 들어 있던 메시지 종류. DISCOVER,OFFER,REQUEST,ACK가 정상 DORA입니다. 갱신이면 REQUEST,ACK만 있습니다.

    둘째 줄이 중요합니다. 같은 라즈베리파이가 35분 뒤 192.168.8.1이라는 처음 보는 서버에게서 192.168.8.103을 받았습니다. 우리 망의 주소 체계(10.20.x.x)와도 다릅니다. 이것은 누군가 집에서 쓰는 무선 공유기를 꽂아 그 공유기가 DHCP 서버 노릇을 하고 있다는 신호일 가능성이 큽니다(소형 공유기는 192.168.x.1을 많이 씁니다). 이런 가짜 DHCP 서버(rogue DHCP server)는 다른 직원 PC에도 엉뚱한 게이트웨이·DNS를 나눠 줄 수 있어 위험합니다(아래 공격 절).

    [보충] 패킷 캡처를 직접 볼 때는 Wireshark·tshark 필터 dhcp를 씁니다(아주 옛 버전은 bootp). 호스트 식별 실습은 호스트 식별에 있습니다.

    DHCP로 몰래 꽂은 장비 찾기¶

    공격자가 건물에 들어와(또는 청소 업체·방문객으로 위장해) 회의실 벽의 랜 포트에 작은 장비를 꽂고 나가는 시나리오가 있습니다. 라즈베리파이 같은 작은 컴퓨터가 망에 붙어 밖으로 연결을 열어 두면, 공격자는 원격으로 회사 안에 들어온 셈입니다. 이것을 처음부터 막는 장치가 네트워크 접근 제어(NAC, Network Access Control), 대표적으로 802.1X 포트 인증입니다. NAC가 없거나 빈틈이 있으면 들어온 뒤에라도 알아채야 하고, 대부분의 장비가 가장 먼저 하는 일이 DHCP로 주소를 받는 것이므로 DHCP 로그가 가장 먼저 그 흔적을 봅니다. 직원이 집 공유기나 개인 기기를 실수로 꽂는 경우도 똑같이 잡힙니다.

    단서 1 — 호스트 이름¶

    회사 장비에는 대개 이름 규칙이 있습니다. 예를 들어 LT-<부서>-<번호>(노트북), WS-<층>-<번호>(데스크톱), SRV-…(서버). 그러면 두 가지 검사를 할 수 있습니다.

    • 허용 목록(allow list) 방식: 규칙에 맞지 않는 이름은 전부 확인. 예: 정규식 ^(LT|WS|SRV)-[A-Z]{2,4}-\d{4}(\.corp\.victim\.example)?$. 맞으면 통과, 안 맞으면 검토 대상.
    • ^와 $ — 이름 전체가 규칙과 맞아야 한다는 뜻(앞뒤에 다른 글자 금지).
    • (LT|WS|SRV) — 셋 중 하나로 시작.
    • [A-Z]{2,4} — 대문자 2~4자(부서 코드).
    • \d{4} — 숫자 4자리.
    • (\.corp\.victim\.example)? — 도메인 접미사는 있어도 되고 없어도 됨.
    • 차단 목록(deny list) 방식: 회사에 있으면 안 되는 기본 이름을 찾기. raspberrypi, kali, ubuntu, DESKTOP- 뒤에 무작위 글자(조직에서 이름을 안 바꾼 새 Windows), 공유기 제조사 이름이 들어간 기본 이름, android-…, iPhone, Galaxy-… 같은 개인 기기 이름.

    허용 목록이 더 엄격하지만 예외(프린터, 회의실 장비, 출입 통제 장비 같은 IoT)가 많아 오탐이 생기기 쉽습니다. 실무에서는 둘을 함께 쓰고, 예외 장비는 목록으로 관리합니다.

    단서 2 — MAC 주소의 OUI¶

    MAC 주소는 6바이트(48비트)이고, 보통 b8:27:eb:5c:19:a0처럼 씁니다. 앞 3바이트(b8:27:eb)가 OUI(조직 고유 식별자, Organizationally Unique Identifier)로, IEEE가 제조사에 나눠 준 번호입니다. 뒤 3바이트는 제조사가 기기마다 붙이는 일련번호입니다. 비유하면 자동차 차대번호 앞자리의 제조사 코드와 같습니다.

     b8 : 27 : eb : 5c : 19 : a0
 └─── OUI ───┘  └─ device ─┘
 maker (IEEE)   serial chosen by maker

    이걸로 할 수 있는 검사:

    • 허용 목록: "우리 회사 노트북은 전부 A사 제품"이라면, A사 OUI가 아닌 MAC이 회사 유선망에 붙으면 확인합니다. 단, 노트북의 MAC은 실제로는 랜 칩 제조사(예: Intel, Realtek)나 도킹 스테이션·USB 랜 어댑터 제조사의 OUI일 수 있으므로, 목록은 실제 자산의 MAC을 모아서 만듭니다.
    • 차단 목록: 회사가 쓰지 않는 소형 컴퓨터, 소비자용 공유기, IoT 제조사의 OUI.

    OUI는 IEEE가 공개한 등록 목록이나 Wireshark가 배포하는 제조사 데이터베이스(Wireshark의 OUI 조회 도구와 manuf 파일)로 찾을 수 있습니다. Wireshark는 화면에서 MAC 앞부분을 제조사 이름으로 바꿔 보여 주기도 합니다(Raspberr_5c:19:a0처럼).

    [보충] OUI를 볼 때 꼭 알아야 할 두 가지가 있습니다.

    1. "로컬 관리(locally administered)" 비트. 첫 바이트의 아래에서 두 번째 비트가 1이면, 그 MAC은 제조사가 준 것이 아니라 소프트웨어가 만든 주소입니다. 쉽게 보는 법: 두 번째 16진수 글자가 2, 6, A, E이면 로컬 관리 주소입니다(예: da:a1:19:…, 4a:…, f6:…). 이런 MAC에는 OUI가 없으니 제조사 조회가 의미 없습니다. 휴대폰의 개인 정보 보호용 무작위 MAC, 가상 머신, 일부 VPN·컨테이너 인터페이스가 이렇습니다.
    2. OUI가 항상 3바이트 단위는 아닙니다. IEEE는 큰 블록(MA-L, 24비트 = 3바이트) 말고도 작은 블록(MA-M 28비트, MA-S 36비트)도 팝니다. 그래서 앞 3바이트만으로는 여러 소규모 제조사가 섞인 블록일 수 있습니다. 조회 도구가 이 구분을 해 주는지 확인합니다.

    한계 — 장비가 스스로 말하는 값이다¶

    호스트 이름과 MAC은 클라이언트가 DHCP 패킷에 적어 보내는 값입니다. 서버는 그대로 믿고 기록할 뿐 확인하지 않습니다. 이메일의 From:처럼요. 그래서:

    • 준비한 공격자는 회사 이름 규칙을 알아내(예: 다른 PC의 DHCP 요청을 엿듣거나 프린터 라벨을 보고) LT-FIN-0419 같은 그럴듯한 이름을 붙이고, 회사 노트북 제조사의 OUI로 MAC을 바꿀 수 있습니다. 심지어 실제로 있는 장비의 이름과 MAC을 그대로 복제할 수도 있습니다.
    • 반대로 직원이 실수로 꽂은 개인 공유기나 기본 설정 그대로인 라즈베리파이는 이름도 MAC도 그대로라 잘 잡힙니다.

    그래서 DHCP 기반 탐지는 "완벽한 문지기"가 아니라 "싸고 넓게 펼친 첫 그물"입니다. 그물을 빠져나간 경우를 위해 다음을 함께 봅니다.

    • 같은 이름·MAC이 동시에 두 곳에서 나타남. 복제한 장비와 진짜 장비가 같은 시간에 서로 다른 스위치 포트·IP에서 보이면 강한 신호입니다.
    • 이름과 다른 특징이 맞지 않음. Windows 이름 규칙을 따르는데 벤더 클래스가 dhcpcd(Linux)라면, 또는 DHCP 요청의 옵션 목록(옵션 55, Parameter Request List) 순서가 Windows와 다르다면 이상합니다. 운영체제마다 요청하는 옵션 목록이 달라, 이것으로 운영체제를 추정하는 방법을 DHCP 지문(DHCP fingerprinting)이라고 합니다.
    • 자산 목록·EDR에 없는 장비. DHCP에는 나오는데 EDR 에이전트가 없고 자산 목록에도 없으면 확인합니다.
    • 스위치 쪽 기록. 포트 링크 업/다운, 802.1X 실패 로그, 옵션 82 릴레이 정보로 물리적 위치를 찾습니다.

    DHCP 동작 — DORA 네 단계¶

    이제 프로토콜 자체를 봅니다. DHCP(Dynamic Host Configuration Protocol)는 고정 IP를 받지 않은 장비가 주소를 자동으로 받는 프로토콜입니다. IP 주소만이 아니라 서브넷 마스크, 기본 게이트웨이(라우터), DNS 서버, 도메인 이름, 임대 기간도 함께 받습니다. UDP를 쓰고, 서버는 67번, 클라이언트는 68번 포트입니다.

    처음 문제는 이것입니다. 막 켜진 장비는 자기 IP도 없고 DHCP 서버가 어디 있는지도 모릅니다. 그래서 "누구든 들리면 대답해 주세요"라고 브로드캐스트로 외치는 데서 시작합니다. 비유하면 처음 온 회사 사무실에서 "자리 배정 담당자 계세요?"라고 크게 묻는 것과 같습니다.

     Client (no IP yet)                               DHCP server 10.20.0.5
   MAC 3c:52:82:aa:41:07

 1. DISCOVER  0.0.0.0:68  ───────────────────▶  255.255.255.255:67   "Any DHCP server out there?"
 2. OFFER     10.20.30.41:68 ◀───────────────  10.20.0.5:67          "You can have 10.20.30.41"
 3. REQUEST   0.0.0.0:68  ───────────────────▶  255.255.255.255:67   "I'll take 10.20.30.41 from 10.20.0.5"
 4. ACK       10.20.30.41:68 ◀───────────────  10.20.0.5:67          "Confirmed, 8 hours"

    한 단계씩 봅니다.

    1. Discover(찾기). 클라이언트에게 아직 IP가 없으니 출발지 IP는 0.0.0.0, 포트 68. 목적지는 같은 망 전체에 보내는 브로드캐스트 255.255.255.255, 포트 67. 이더넷 목적지 MAC도 ff:ff:ff:ff:ff:ff(전원에게)입니다. 패킷 안에 자기 MAC(chaddr 칸), 호스트 이름(옵션 12), 벤더 클래스(옵션 60), 원하는 설정 목록(옵션 55)을 담습니다. 예전에 쓰던 IP가 있으면 "그거 다시 주세요"(옵션 50)도 넣습니다.
    2. Offer(제안). 그 망의 DHCP 서버(여러 대일 수도 있음)가 "이 주소 어때요?"라고 답합니다. 출발지는 서버 IP:67. 제안하는 IP(yiaddr 칸)와 임대 기간(옵션 51), 서브넷 마스크(옵션 1), 라우터(옵션 3), DNS 서버(옵션 6), 서버 식별자(옵션 54)를 담습니다. 목적지는 클라이언트 설정에 따라 제안한 IP로 유니캐스트(이더넷으로는 그 클라이언트 MAC으로)이거나 브로드캐스트입니다. 클라이언트가 아직 IP를 갖고 있지 않으므로, 서버는 IP 계층이 아니라 MAC 주소를 보고 배달합니다.
    3. Request(요청). 클라이언트는 여러 제안 중 하나(보통 가장 먼저 온 것)를 고르고 "이 서버의 이 주소를 쓰겠습니다"라고 답합니다. 여기가 헷갈리는 부분인데, 이 요청도 다시 브로드캐스트(0.0.0.0 → 255.255.255.255)로 보냅니다. 이유는 둘입니다. 클라이언트는 아직 IP 사용 확정을 못 받아 0.0.0.0을 써야 하고, 제안을 보낸 모든 서버가 이 요청을 들어야 선택받지 못한 서버가 "내 제안은 취소"하고 그 주소를 풀에 돌려놓기 때문입니다. 패킷의 서버 식별자(옵션 54)가 선택한 서버를 가리킵니다.
    4. Acknowledge(확인, ACK). 선택된 서버가 "확정"이라고 보냅니다. 이제 클라이언트는 그 IP를 임대 기간 동안 씁니다. 많은 클라이언트는 쓰기 전에 ARP로 "이 IP 쓰는 장비 있나요?"를 한 번 더 확인하고, 이미 누가 쓰고 있으면 DHCPDECLINE을 보냅니다(Windows 감사 로그의 ID 13이 이런 충돌과 관련됩니다).

    [보충] DORA 말고도 알아 두면 로그 해석이 쉬워지는 것들입니다.

    • 갱신(renewal). 임대 기간의 절반(T1)이 지나면 클라이언트는 받은 서버에 직접 유니캐스트로 REQUEST를 보내고, 서버가 ACK하면 연장됩니다(감사 로그 ID 11, Zeek msg_types=REQUEST,ACK). 그 서버가 대답하지 않으면 87.5%(T2) 시점부터는 브로드캐스트로 아무 서버에게나 연장을 요청합니다. 그래서 정상적인 장비는 하루 종일 일정 간격으로 갱신 기록을 남깁니다.
    • NAK. 서버가 "그 주소는 못 줘요"라고 거절(다른 망으로 옮긴 노트북이 옛 주소를 달라고 할 때 흔함). 클라이언트는 Discover부터 다시 합니다.
    • RELEASE. 클라이언트가 "다 썼어요" 하고 반납(ipconfig /release, 정상 종료 시 일부). 감사 로그 ID 12.
    • INFORM. IP는 이미 있는데 설정(DNS 등)만 물어볼 때.
    • 릴레이(relay). 브로드캐스트는 라우터를 넘지 못하는데, 회사에는 층마다 다른 망이 있고 DHCP 서버는 데이터센터에 한두 대뿐입니다. 그래서 각 망의 라우터·L3 스위치가 DHCP 릴레이(Cisco 장비의 ip helper-address 설정)로 브로드캐스트를 받아 서버에 유니캐스트로 전달합니다. 이때 패킷의 giaddr 칸에 릴레이 주소가 들어가 서버가 "어느 망의 주소를 줄지" 알고, 옵션 82로 스위치·포트 정보를 붙일 수 있습니다.
    • DHCP의 패킷 형식은 옛 BOOTP를 그대로 물려받았습니다. 그래서 칸 이름이 ciaddr(클라이언트의 현재 IP), yiaddr("your" IP, 받을 IP), siaddr, giaddr, chaddr(클라이언트 MAC) 같은 모양이고, 옛 Wireshark 필터 이름이 bootp였습니다.

    DHCP를 노리는 공격¶

    [보충] DHCP는 인증이 전혀 없습니다. 처음 들리는 대답을 믿습니다. 그래서 같은 망(같은 브로드캐스트 영역)에 있는 사람이라면 다음을 할 수 있습니다.

    • 가짜 DHCP 서버(rogue DHCP server). 진짜 서버보다 먼저 Offer를 보내 게이트웨이나 DNS 서버를 공격자 장비로 알려 줍니다. 그러면 피해 PC의 트래픽이나 DNS 질의가 공격자를 거쳐 갑니다(중간자 공격). 위의 집 공유기 사례처럼 실수로도 생깁니다. 탐지: Zeek dhcp.log의 server_addr나 패킷의 옵션 54가 승인된 서버 목록에 없음, 클라이언트가 예상과 다른 대역·게이트웨이·DNS를 받음. 예방: 스위치의 DHCP 스누핑(DHCP snooping) — 서버가 연결된 포트에서 온 Offer/ACK만 통과시킵니다. Active Directory 환경의 Windows DHCP 서버는 AD에서 "승인"받아야 동작하지만, 이 장치는 다른 운영체제의 가짜 서버에는 아무 효과가 없습니다.
    • 주소 풀 고갈(DHCP starvation). 가짜 MAC을 바꿔 가며 Discover를 대량으로 보내 서버의 주소를 다 빌려 가 버립니다. 정상 장비는 주소를 못 받고(감사 로그 ID 14 "풀 고갈"), 그 틈에 가짜 서버가 대신 대답합니다. 탐지: 짧은 시간에 처음 보는 MAC이 수백 개, 로컬 관리 비트가 켜진 MAC 폭증. 예방: 포트당 MAC 수 제한(port security), DHCP 요청 속도 제한.
    • IPv6로 끼어들기. Windows는 IPv6를 기본으로 켜 두고 DHCPv6 응답을 기다립니다. IPv6를 안 쓰는 회사망에서도 공격자가 DHCPv6 서버인 척하면 PC들이 공격자를 IPv6 DNS 서버로 받아들이게 만들 수 있습니다. 이 방식은 공격 도구 이름을 따 흔히 mitm6라고 부르며, 그 뒤에 인증 정보를 가로채는 NTLM 릴레이로 이어집니다(LLMNR·NTLM 릴레이). IPv4 DHCP 로그만 보면 이 공격은 보이지 않습니다.
    • VPN을 우회시키는 경로 주입(TunnelVision, CVE-2024-3661, 2024 공개). DHCP 옵션 121(classless static route)로 "이 대역은 이쪽 게이트웨이로 보내라"는 경로를 내려보내면, VPN보다 더 구체적인 경로가 우선해서 VPN에 연결된 상태인데도 트래픽이 VPN 밖으로 나가게 만들 수 있습니다. 공격자가 같은 망(카페·호텔 와이파이 등)에서 DHCP 서버를 장악하거나 가짜 서버를 띄워야 합니다. 옵션 121을 구현하지 않는 Android는 영향이 없었고, 대응은 VPN 제품의 킬 스위치·방화벽 규칙이나 네트워크 격리 기능입니다.

    SOC에서 DHCP 로그를 쓰는 순간¶

    • 모든 IP 기반 알림의 보강(enrichment). SIEM에서 알림이 생길 때 그 시각의 DHCP 임대를 자동으로 붙여 "IP + 호스트 이름 + MAC"으로 보여 주게 합니다. 분석가가 손으로 찾는 시간을 줄이고, 시간이 지나 IP가 재사용돼도 틀리지 않습니다.
    • 새 장비 경보. 처음 보는 MAC, 규칙에 안 맞는 호스트 이름, 차단 목록 OUI, 처음 보는 DHCP 서버.
    • 사고 범위 정하기. 감염 PC가 그날 어느 망·어느 IP들을 옮겨 다녔는지(노트북은 하루에도 여러 IP를 씁니다) 알아야 그 IP들로 찍힌 다른 로그를 빠짐없이 찾습니다.
    • 보존 기간 확인. 기본 감사 로그는 요일별 덮어쓰기라 약 일주일. 사고는 몇 주 뒤에 발견되는 경우가 많으므로 SIEM 수집이 필수입니다. 클라우드 관리형 무선 장비, 방화벽 내장 DHCP, 홈 라우터처럼 DHCP 서버가 여러 곳에 흩어져 있다면 그 전부를 모아야 합니다.

    2026년 관점¶

    [2026 현재] 그대로 유효한 것

    DORA 네 단계, UDP 67·68, 브로드캐스트로 시작하는 구조, 임대 개념, DHCP 로그로 IP→장비를 잇는 조사 방식, 호스트 이름·MAC·OUI로 수상한 장비를 찾는 방법과 그 한계(장비가 스스로 말하는 값)는 그대로입니다. DHCP에 인증이 없어 같은 망의 공격자가 끼어들 수 있다는 점도 바뀌지 않았습니다.

    [변경됨] 바뀐 것

    • MAC 무작위화가 기본이 됐습니다. iOS·iPadOS(14부터)와 Android(10부터)는 와이파이 망마다 다른 무작위 MAC을 기본으로 쓰고, Apple은 이후 주기적으로 주소를 바꾸는 "순환(rotating)" 방식도 추가했습니다. Windows도 무작위 하드웨어 주소 옵션을 제공합니다. 그래서 무선망에서는 OUI로 제조사를 판단할 수 없는 장비가 많고, 같은 휴대폰이 다른 장비처럼 보이기도 합니다. 회사 기기는 MDM(모바일 기기 관리)으로 회사 망에서 고정 MAC을 쓰게 하고, 인증(802.1X) 결과로 장비를 식별하는 쪽이 정확합니다.
    • IP→장비 연결의 중심이 EDR·NAC로 옮겨 갔습니다. EDR은 장비가 스스로 자기 IP 변화를 보고하고, NAC·무선 컨트롤러는 인증 계정과 MAC·IP를 함께 기록합니다. DHCP 로그는 여전히 필요하지만 EDR이 없는 장비(IoT, 개인 기기, 공격자 장비)를 찾는 용도가 더 중요해졌습니다.
    • 원격·클라우드 근무로 "회사 망 안의 IP"의 의미가 약해졌습니다. 재택 노트북은 집 공유기의 DHCP를 쓰므로 회사 DHCP 로그에 나타나지 않습니다. 이런 장비는 VPN/ZTNA 접속 기록과 EDR로 추적합니다.
    • 새 DHCP 공격이 계속 나옵니다. 2024년 공개된 TunnelVision(옵션 121로 VPN 우회)이 대표적이고, IPv6(DHCPv6·라우터 광고)를 이용한 중간자 공격은 여전히 침투 테스트에서 자주 쓰입니다.
    • IPv6 SLAAC 장비는 DHCP 로그에 안 남을 수 있습니다. IPv6를 쓰는 망에서는 장비가 라우터 광고만으로 스스로 주소를 만들 수 있어(SLAAC), 주소→장비 연결은 라우터·스위치의 이웃 테이블(NDP) 기록으로 보완해야 합니다.

    [주의] 지금 그대로 하면 틀리거나 위험한 것

    • "지금 그 IP를 쓰는 장비"로 조사하지 않습니다. 반드시 알림 시각의 임대를 찾습니다. 시간대(서버 현지 시각 vs UTC)도 맞춥니다.
    • OUI만으로 "회사 장비다/아니다"를 단정하지 않습니다. 무작위 MAC, 복제된 MAC, 랜 칩·도킹 스테이션 제조사 OUI가 섞여 있습니다. 로컬 관리 비트부터 확인합니다.
    • DNS의 현재 이름 조회(역방향 조회 포함)를 과거 기록 대신 쓰지 않습니다. DNS는 지금 값만 보여 줍니다.
    • AD 승인만 믿고 가짜 DHCP 서버 대비를 끝냈다고 보지 않습니다. 스위치의 DHCP 스누핑이 실제 방어입니다.
    • IPv4 DHCP 로그만 보고 "새 장비 없음"이라 하지 않습니다. IPv6, 고정 IP로 설정한 장비(공격자는 DHCP 없이 직접 IP를 정할 수 있음)는 DHCP에 아예 나타나지 않습니다. ARP·스위치 MAC 테이블·NAC 기록을 함께 봅니다.

    확인 문제¶

    문제 1¶

    11월 18일 14:20(서버 현지 시각)에 IDS가 10.20.30.41에서 외부로 나가는 C2 통신 알림을 냈습니다. 다음 날 아침 분석가가 Get-DhcpServerv4Lease로 조회하니 10.20.30.41은 지금 WS-HR-0107이 쓰고 있었습니다. 분석가는 WS-HR-0107을 격리하려고 합니다. 위의 감사 로그 예시를 참고해, 이 판단이 왜 위험한지와 올바른 순서를 말해 보세요.

    정답과 해설

    위험한 이유: Get-DhcpServerv4Lease는 지금 살아 있는 임대만 보여 줍니다. IP는 빌려 쓰는 값이라 주인이 바뀝니다. 감사 로그 예시를 보면 10.20.30.41은 08:52에 LT-FIN-0412가 받았고 12:52에 갱신, 17:31에 반납했습니다. 알림 시각 14:20에는 LT-FIN-0412가 쓰고 있었고, 다음 날 그 IP가 WS-HR-0107에게 넘어간 것입니다. 지금 주인을 격리하면 엉뚱한 PC를 격리하고 진짜 감염 PC는 놓칩니다.

    올바른 순서:

    1. 알림 시각(시간대 확인: IDS가 UTC라면 서버 현지 시각으로 바꿈)을 포함하는 임대 기록을 감사 로그나 SIEM에서 찾음 → LT-FIN-0412, MAC 3C5282AA4107
    2. 그 장비를 자산 목록·EDR에서 확인하고, 그 시각의 사용자를 DC의 4768(TGT 요청, Client Address) 또는 그 PC의 4624로 확인
    3. LT-FIN-0412가 지금 쓰는 IP(다른 IP일 수 있음)를 찾아 격리하고, 그날 그 장비가 쓴 다른 IP들로 찍힌 로그도 찾음

    문제 2¶

    다음 Zeek dhcp.log 두 줄에서 각각 무엇이 수상한지, 무엇을 확인해야 하는지 말해 보세요. 회사의 DHCP 서버는 10.20.0.5, 10.20.0.6 두 대이고, 노트북 이름 규칙은 LT-<부서>-<4자리>입니다.

    ts=2026-11-18T09:14:02Z client_addr=- server_addr=10.20.0.5 mac=da:3f:91:07:c2:5e host_name=LT-FIN-0412 assigned_addr=10.20.40.18 msg_types=DISCOVER,OFFER,REQUEST,ACK
ts=2026-11-18T09:20:11Z client_addr=- server_addr=10.20.44.200 mac=3c:52:82:19:aa:02 host_name=LT-ENG-0233 assigned_addr=10.20.44.150 msg_types=DISCOVER,OFFER,REQUEST,ACK
    정답과 해설

    첫째 줄: 이름 LT-FIN-0412는 규칙에 맞지만, MAC da:3f:…의 두 번째 글자가 a → 로컬 관리 주소(소프트웨어가 만든 MAC)입니다. 회사 노트북이 회사 유선망에서 무작위 MAC을 쓸 이유는 보통 없고, 무엇보다 같은 이름 LT-FIN-0412의 원래 MAC은 3c:52:82:aa:41:07이었습니다. 확인할 것: 같은 시각 진짜 LT-FIN-0412가 다른 곳(다른 IP·포트)에 있었는지(있다면 이름 복제를 의심), EDR에서 그 노트북의 네트워크 어댑터 설정이 바뀌었는지, 옵션 82나 스위치 기록으로 물리 포트.

    둘째 줄: 이름과 MAC은 평범하지만 server_addr=10.20.44.200이 승인된 DHCP 서버가 아닙니다. 누군가 그 망에서 DHCP 서버 노릇을 하고 있습니다(실수로 꽂은 공유기, 서버 역할을 켠 장비, 또는 공격자의 가짜 서버). 확인할 것: 이 대화의 ACK에 담긴 게이트웨이(옵션 3)·DNS(옵션 6)가 무엇이었는지(공격자 장비를 가리키면 중간자 공격), 10.20.44.200의 MAC과 스위치 포트, 같은 망의 다른 클라이언트도 이 서버에서 주소를 받았는지. 예방책으로 그 스위치의 DHCP 스누핑 설정을 점검합니다.

    문제 3¶

    동료가 "우리는 DHCP 로그로 새 장비를 다 잡으니까, 망에 몰래 꽂힌 장비는 없다"고 합니다. 이 말이 틀린 이유를 최소 세 가지 들고, 보완책을 말해 보세요.

    정답과 해설

    틀린 이유:

    1. 호스트 이름과 MAC은 장비가 스스로 적는 값이라, 회사 규칙에 맞는 이름과 회사 노트북 제조사 OUI(또는 실제 장비의 MAC 복제)로 위장할 수 있습니다.
    2. DHCP를 안 쓰면 아예 기록이 없습니다. 공격자는 망의 대역을 엿보고 고정 IP를 직접 설정할 수 있습니다. IPv6 SLAAC 주소도 DHCP 로그에 안 남을 수 있습니다.
    3. MAC 무작위화 때문에 정상 기기도 매번 새 장비처럼 보여 "새 MAC"이 너무 많아지고, 진짜 수상한 것이 묻힙니다.
    4. (추가) 기본 감사 로그는 약 일주일만 남고, DHCP 서버가 여러 곳(무선 컨트롤러, 방화벽, 지점 라우터)에 흩어져 있으면 일부만 보고 있을 수 있습니다.

    보완책: 802.1X 같은 NAC로 접속 자체를 인증, 스위치의 MAC 테이블·ARP 기록과 DHCP 기록을 비교해 "DHCP 없이 나타난 장비" 찾기, 자산 목록·EDR 목록과 대조, 같은 이름·MAC의 동시 출현 탐지, 옵션 55·60을 이용한 DHCP 지문으로 이름과 운영체제가 맞는지 확인, 모든 DHCP 소스를 SIEM으로 장기 보관.
