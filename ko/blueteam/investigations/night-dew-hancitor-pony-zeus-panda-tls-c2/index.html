    사례 요약

    AD 도메인(NIGHTDEW)에 속한 Windows 7 PC 한 대(CHICAGO-7FA3-PC, 사용자 faith.hoffman)​의 43분짜리 캡처를, 홈 랩의 pcapbox VM에서 처음 보는 PCAP이라고 생각하고 처음부터 분석한 기록이에요. Arkime를 중심으로 쓰고, 개수를 세거나 정렬하거나 프로토콜을 자세히 볼 때는 Splunk(Zeek 로그)​를 같이 써요.

    사용자가 로그인하고 35초 뒤 PC가 api.ipify[.]org로 공인 IP를 확인하고, lysedsohap[.]com/4/forum.php에 자기 정보(컴퓨터 이름, 도메인\사용자, 공인 IP, OS)를 담은 체크인을 보내요. 응답을 CyberChef(Base64 → XOR 0x7A)​로 풀면 "이 주소에서 파일을 받아라"라는 명령 3개가 나와요. PC는 1초 뒤 해킹된 WordPress 사이트에서 암호화된 파일 3개를 받아요. 그다음 다른 프로그램이 작은 암호화 POST 2개(훔친 비밀번호로 추정)를 보내고, DC에 32초 동안 1,522번 netlogon 로그인 확인 요청(비밀번호 대입)​을 보내요. 다운로드 2분 뒤부터는 기본값 자체 서명 인증서(Default Company Ltd)를 쓰는 TLS로 두 번째 C2를 시작해요. 전형적인 Hancitor → Pony → Zeus Panda Banker 감염 사슬과 같은 모양이에요. 마지막에 Snort 룰 하나를 한 단계씩 설명하고 테스트한 뒤, 룰 8개를 함께 테스트해요.

    단계마다 같은 순서예요. 목적 → Arkime → Splunk(그쪽이 편할 때) → 결과 → 결과 읽기. 질문 상자는 분석하면서 실제로 나온 질문과 답이에요. SPL 쿼리는 모두 한 줄씩 설명해요.

    전체 원칙은 모르는 PCAP을 분석한다는 거예요. 화면에 나온 것만으로 판단해요. 그래서 악성코드 계열 이름은 추정으로 적어요(공개 자료와 맞지만 해시 조회나 샌드박스로 확인하지는 못했어요).

    이 페이지의 지표는 실제 값이에요

    도메인, IP, 해시는 2018년 실제 악성 트래픽에서 나온 값이에요. 본문과 표에서는 무력화(hxxp, [.])했고, 코드 블록 안은 입력한 그대로 두었어요. 절대 접속하지 마세요. 추출한 파일은 격리된 분석 VM 밖에서 절대 열지 마세요.

    0-1. 넣기¶

    1. PCAP 이름을 원하는 케이스 이름으로 바꿉니다. 예: 20180511_NIGHT_DEW.pcap
    2. 호스트 PC에서 \\10.50.10.60\incoming에 넣습니다.
    3. pcapbox에서 처리 기록을 지켜봅니다.
    tail -f /data/logs/ingest.log
    • tail -f: 파일 끝을 보여 주고, 새 줄이 생기면 계속 출력해요. Ctrl+C로 멈춥니다.

    질문: cname과 sname의 차이는 무엇인가요?

    Kerberos 요청에는 항상 "누가"​와 "무엇을 쓰려고"​가 들어 있어요.

    • cname(client name) — 요청한 쪽, "나는 누구다". 사람 계정(faith.hoffman)이나 컴퓨터 계정(CHICAGO-7FA3-PC$).
    • sname(service name) — 쓰려는 서비스, 서비스종류/서버이름 모양이에요.
      • krbtgt/NIGHTDEW.ORG — 로그인할 때 맨 처음 받는 입장권(TGT)
      • cifs/nightdew-dc.nightdew.org — DC의 파일 공유(SMB). 로그인 스크립트, 그룹 정책을 가져갈 때 써요.
      • ldap/Nightdew-DC... — DC의 디렉터리(LDAP) 조회
      • host/chicago-7fa3-pc..., chicago-7fa3-pc$ — PC 자기 자신을 위한 티켓

    그래서 "faith.hoffman(cname)이 krbtgt(sname)를 요청했다" = "faith.hoffman이 도메인에 로그인했다"​는 뜻이에요.

    • 2줄: 시각, 요청한 IP, DC IP, 요청 종류, 계정, 서비스, 성공 여부, 오류 메시지를 표로 보여 줘요.
    • 3줄: 시간 순서로 정렬합니다.

    \"수상한 외부 IP\" 빠르게 고르는 법

    1. 세션 수가 많은데 목적지가 하나뿐인 곳 (비콘 후보)
    2. 도메인 이름이 무작위 글자 조합인 곳
    3. 세션 하나에 받은 양이 큰 곳 (다운로드)
    4. 서로 다른 외부 IP가 몇 초 안에 연달아 나오는 곳 (한 프로그램의 연속 동작)

| stats count as sessions min(ts) as first max(ts) as last sum(orig_bytes) as sent sum(resp_bytes) as received values(id_resp_p) as ports by id_resp_h
| eval first=strftime(first,"%H:%M:%S"), last=strftime(last,"%H:%M:%S")
| sort - sessions
    • 1줄: PC가 시작한 연결에서 내부(10.0.0.0/8), 멀티캐스트(224.0.0.0/4), 브로드캐스트 목적지를 빼요. Splunk는 IP 필드에 CIDR 대역을 알아들어요.
    • 2줄: 외부 IP마다 한 줄 — 연결 수, 처음과 마지막 시각, 보낸 바이트와 받은 바이트, 쓴 포트.

    4-4. C2 응답을 CyberChef로 풀기¶

    목적: ③의 1,436바이트 응답을 읽을 수 있는 글로 바꿉니다.

    알아보고 푸는 순서:

    1. base64인가? 글자가 A–Z a–z 0–9 + /(그리고 =)로만 되어 있어요. 그런데 base64로 풀면 읽을 수 없는 바이트가 나와요. 한 겹 더 감싸져 있다는 뜻이에요.
    2. 1바이트 XOR이 흔해요. 1바이트 키는 256가지뿐이라 전부 해 보면 돼요(brute force). 맞는 키를 고르려면 정답에 나올 글자인 crib(크립)​을 줘요. 이 응답 직후 PC가 파일을 받았으니 응답에 주소가 있을 것 → crib은 http.
    3. 키 0x7a(문자 z)에서만 {l:http://wansaiful.com/wp-content/plugins/easy-media-dow...가 나왔어요.

    CyberChef 레시피:

    1. Arkime에서 응답 본문(Destination 쪽)을 처음부터 끝까지 복사합니다.
    2. Recipe에 From Base64를 넣어요.
    3. 그 아래 XOR Brute Force를 넣고 Key length 1, Crib http. 키 7a 줄에 {l:http://...가 보여요.
    4. XOR Brute Force를 XOR(Key 7a, HEX)로 바꾸면 전체가 풀려요.

    질문: 위에서 CyberChef에 넣는 이유는 무엇인가요? 설명해 주세요.

    CyberChef는 영국 GCHQ가 공개한 브라우저용 데이터 변환 도구예요. 요리처럼 Input(재료) → Recipe(작업을 순서대로 쌓기: base64, XOR, 압축 풀기 등) → Output(결과, 바로바로 보임). 코드 없이 여러 단계를 이을 수 있고, 레시피를 저장하거나 보고서에 적어 두면 다른 분석가가 똑같이 재현할 수 있어요. 실무에서는 오프라인 버전(HTML 파일 하나)을 쓰세요. 증거를 웹사이트에 붙여 넣으면 정보가 밖으로 나갈 수 있어요.

    왜 base64를 먼저, XOR을 나중에? 서버가 명령을 두 겹으로 포장했어요. (1) {l:http://...}를 XOR로 섞어 깨진 바이트로 만들고, (2) 그 바이트를 HTTP로 보내기 쉽게 base64 글자로 바꿨어요. 푸는 쪽은 거꾸로 — 마지막에 싼 것부터 벗깁니다.

    왜 숨겼을까? http://wansaiful.com/...1이 그대로 보이면 IDS나 프록시가 쉽게 잡아요. 한 번 섞어 두면 단순한 탐지를 피할 수 있어요. 대신 키가 1바이트라 분석가는 금방 풀어요.

    XOR Brute Force와 crib. XOR은 같은 키로 한 번 더 하면 원래대로 돌아와요. 키만 알면 돼요. 1바이트면 256번만 해 보면 되고, crib(http)은 256개 결과 중 정답을 골라 줘요. crib은 트래픽에서 본 행동(응답 직후 다운로드)을 근거로 정한 거예요. 그냥 찍은 게 아니에요.

    풀기 전에도 힌트가 있었어요. base64 글자에 Eg4OCkBV가 여러 번 반복돼요. 계산해 보면:

    원문         h    t    t    p    :    /
XOR 0x7a     12   0e   0e   0a   40   55
base64       E g 4 O         C k B V

    Eg4OCkBV = http:/를 XOR한 뒤 base64로 바꾼 모양이에요. 주소가 15개라 계속 반복된 거죠. 인코딩된 덩어리에 같은 조각이 반복되면, 원문에도 반복이 있고 키가 짧고 고정돼 있을 가능성이 높아요. 진짜 암호화(AES 등)는 이런 반복이 안 보여요.

    http로 안 나오면? Key length를 2, 4로 늘려 보고, crib을 바꿔 봐요(MZ는 exe, <html, {). 그래도 안 되면 진짜 암호화일 가능성이 커서, 악성코드 파일을 리버싱해 키를 찾아야 해요.

    Arkime에도 Unbase64, UnXOR Brute 버튼이 있지만, CyberChef는 단계를 자유롭게 잇고 재현 가능한 레시피를 남길 수 있어요.

    질문: Issuer CN이나 Subject CN, Issuer Org나 Subject Org는 다 같은 말인가요?

    아니에요. Subject(대상) = 인증서가 누구의 것인지(서버). Issuer(발급자) = 누가 서명했는지(보통 인증 기관). 둘 다 이름이 여러 칸으로 나뉘어요.

    칸 뜻
    CN (Common Name) 대표 이름. Subject CN은 보통 도메인(www.example.com), Issuer CN은 인증 기관 이름
    O (Organization) — Arkime에서는 Org 회사·기관 이름
    OU 부서
    L 도시
    ST 주·도
    C 나라 코드 두 글자

    정상 서버 인증서(예시):

    Subject : CN=www.example.com,  O=Example Corp,       C=US
Issuer  : CN=Example CA 2018,  O=Example Trust Inc,  C=US

    이번 인증서:

    Subject : C=XX, L=Default City, O=Default Company Ltd   (CN 없음)
Issuer  : C=XX, L=Default City, O=Default Company Ltd   (CN 없음)

    의심할 점 세 가지: Subject와 Issuer가 같음(자체 서명), 값이 전부 기본값, Subject CN이 비어 있음 — PC는 robwassotdint.ru(SNI)로 접속했는데 인증서에 그 도메인이 없어요. 정상 브라우저라면 경고를 띄울 상황인데 통신이 계속됐으니, 인증서를 검사하지 않는 프로그램(악성코드)​이에요.

    Arkime 필드: cert.subject.cn, cert.issuer.cn(CN 칸) · cert.subject.on, cert.issuer.on(Org 칸). 대충 만든 C2 인증서를 찾는 헌팅 쿼리:

    cert.issuer.on == "Default Company Ltd" && cert.subject.on == "Default Company Ltd"

    cert.hash는 IP나 도메인이 바뀌어도 같은 인증서를 찾아요.

    cert.hash == 86:af:39:2e:9b:42:ec:50:e2:87:f6:42:9e:f7:48:4c:48:bb:bd:95

    Arkime는 DCE/RPC에서 어떤 기능을 불렀는지까지는 풀어 주지 않아요. Zeek은 DCE/RPC 전용 분석기가 있어서 인터페이스와 기능 이름을 하나하나 기록해요. 이런 경우가 바로 Splunk(Zeek 로그)가 더 편한 경우예요.

    그래도 Arkime로 세션 자체는 확인할 수 있어요. tags == 20180511_NIGHT_DEW && port.dst == 49158로 보면 패킷 1,529 / 1,526개, 데이터 779,560 / 231,472바이트라 크기가 맞아요.

    질문: 여기서 PSH가 많이 보이는 이유가 무엇인가요?

    PSH(Push)​는 보내는 쪽이 "이번 메시지는 여기까지야. 기다리지 말고 바로 프로그램에 넘겨"​라고 표시하는 플래그예요. 보통 한 메시지의 마지막 패킷에 붙어요.

    이 세션은 1,529 + 1,526 = 3,055패킷 중 3,046개에 PSH가 있어요. 빠진 건 SYN, SYN-ACK, FIN, 빈 ACK 몇 개뿐이에요.

    이유는 메시지가 패킷 하나에 다 들어가기 때문이에요. 779,560 B ÷ 1,522 ≈ 요청당 512 B, 231,472 B ÷ 1,522 ≈ 응답당 152 B. 패킷 하나에 1,400 B 넘게 담을 수 있으니 요청 하나가 패킷 하나이고, 그 패킷이 곧 메시지의 끝이라 PSH가 붙어요 → 요청 1,522 + 응답 1,522 ≈ PSH 3,044개. 크기가 매번 거의 같다는 건 같은 기능을 반복 호출했다는 뜻이에요.

    ACK가 5개뿐인 이유: DC가 "받았어"(ACK)를 응답 패킷에 같이 실어 보내서, ACK만 따로 보내는 빈 패킷이 거의 필요 없었어요.

    wansaiful[.]com 다운로드와 비교해 보면, 서버 쪽 203패킷 중 PSH는 151개였어요. 큰 파일은 꽉 찬 패킷 여러 개로 오고 PSH는 덩어리의 끝에만 붙어요.

    모양 뜻
    PSH ≈ 전체 패킷 수 작은 메시지를 계속 주고받는 대화형 통신: 반복 요청(이번 대입 공격), 비콘, 원격 셸 명령
    PSH가 적고 패킷이 많음 한 방향으로 큰 데이터 전송: 다운로드, 업로드

    Payload8은 각 방향의 첫 데이터 8바이트예요. PC 05 00 0b 07 ..., DC 05 00 0c 07 .... 05 00은 DCE/RPC 버전 5.0, 세 번째 바이트는 메시지 종류 — 0b(11)는 Bind(이 인터페이스를 쓰겠다), 0c(12)는 Bind Ack(허락). 포트 번호(49158)만으로 프로토콜을 알기 어려울 때 첫 8바이트가 큰 도움이 돼요.

    8단계 — Snort 룰 하나, 그리고 테스트하는 법¶

    8-1. 어떤 룰을, 왜¶

    핵심 하나만 고른다면 체크인 POST가 가장 좋아요.

    • 도메인이나 IP가 바뀌어도 잡혀요. C2 도메인은 자주 바뀌지만 본문 형식(GUID=...&BUILD=...&INFO=...)은 그대로예요.
    • 감염의 시작을 잡아요. "이 PC가 방금 C2에 등록했다"는 뜻이에요.
    • 오탐이 거의 없어요. 정상 사이트가 이 세 이름을 이 순서로 보내는 경우는 매우 드물어요.
    alert tcp $HOME_NET any -> $EXTERNAL_NET 80 (msg:"Malware check-in POST GUID/BUILD/INFO - Sung"; flow:to_server,established; content:"POST"; depth:4; content:"GUID="; content:"&BUILD="; distance:0; content:"&INFO="; distance:0; sid:1000001; rev:1;)

    8-2. 룰을 한 부분씩¶

    헤더

    • alert — 맞으면 알림을 내요.
    • tcp — TCP만 봐요.
    • $HOME_NET any -> $EXTERNAL_NET 80 — 내부 어느 포트에서든 외부 80번(HTTP)​으로 가는 것만. pcapbox에서 HOME_NET은 사설 대역 전체예요.

    옵션 (괄호 안)

    • msg:"..." — 알림 설명. 끝에 작성자 이름을 붙이는 건 팀 방식이에요.
    • flow:to_server,established — TCP 연결이 맺어진 상태에서 클라이언트가 서버로 보내는 데이터만 봐요. 응답이나 연결 시작 패킷은 건너뛰어서 빠르고 정확해져요.
    • content:"POST"; depth:4; — 데이터의 처음 4바이트가 POST인지(depth:4 = 앞에서 4바이트 안에서만). HTTP 요청의 첫 단어를 확인하는 거예요.
    • content:"GUID="; — 어딘가에 GUID=가 있는지.
    • content:"&BUILD="; distance:0; — distance:0은 "바로 앞에서 찾은 위치 뒤에서부터" 찾으라는 뜻이라, &BUILD=가 GUID= 뒤에 있어야 맞아요.
    • content:"&INFO="; distance:0; — &INFO=도 &BUILD= 뒤에. 세 단어가 이 순서대로 나올 때만 울려요.
    • sid:1000001; — 룰 번호(직접 만든 룰은 1000000 이상).
    • rev:1; — 룰 버전. 고칠 때마다 1씩 올려요.

    알림이 몇 개 나와야 할까? 첫 체크인에만 이 본문이 있으면 1개, 비콘도 같은 본문을 보내면 21개예요. 테스트 전에 Arkime에서 비콘 하나를 확인해요.

    1. 시간 범위 All, 검색: tags == 20180511_NIGHT_DEW && host.http == lysedsohap.com && http.method == POST
    2. Start Time 정렬: 맨 위가 02:08:04 체크인, 다음이 /mlu/forum.php, /d2/about.php, 그다음 02:10:15부터 비콘.
    3. 02:10:15 세션의 +를 눌러 펼치고 아래 패킷 내용으로 스크롤. Src만 켜면 요청 쪽만 보여서 편해요.
    4. 헤더 아래 빈 줄 다음이 본문이에요. Content-Length를 체크인(123)과 비교해요.
    5. 마지막 비콘(02:48:25)도 똑같이. 처음과 끝이 같으면 중간도 같다고 봐도 돼요.

    두 비콘 모두 본문이 같았고 Content-Length: 123 → 21개를 예상합니다.

    1. /data/rules/local.rules에 룰 넣기

    방법 A — 호스트 PC 메모장

    1. 탐색기 주소창에 \\10.50.10.60\rules(사용자 analyst, Samba 암호).

    4. 맨 아래 빈 줄에 붙여 넣고 저장(Ctrl+S).

    방법 B — SSH에서 nano

    nano /data/rules/local.rules
    • 맨 아래로 내려가 붙여 넣고(PuTTY/PowerShell은 마우스 오른쪽 클릭), Ctrl+O → Enter로 저장, Ctrl+X로 나와요.

    잘 들어갔는지 확인:

    tail -3 /data/rules/local.rules
    • tail -3: 마지막 3줄. 맨 마지막 줄에 룰이 한 줄로 통째로 보이면 돼요.

    둥근 따옴표는 룰을 망가뜨려요

    웹이나 워드에서 복사하면 "가 “ ”로 바뀔 수 있어요. Snort는 못 읽으니 이상하면 따옴표를 직접 다시 치세요.

    2. 문법 검사

    오타가 있으면 Snort가 아예 실행되지 않아요. 그래서 PCAP을 돌리기 전에 항상 문법부터 검사해요.

    sudo snort -T -c /etc/snort/snort.conf 2>&1 | tail -5
    • -T — 테스트 모드: 패킷은 안 보고 설정과 룰만 읽어서 검사해요.
    • -c /etc/snort/snort.conf — 이 설정 파일을 써요(안에서 local.rules를 include해요).
    • 2>&1 — Snort는 결과를 오류 출력으로 내보내서, 그것까지 화면으로 모아요.
    • | tail -5 — 마지막 5줄.

    성공:

            Snort successfully validated the configuration!
Snort exiting

    실패하면 ERROR 줄이 나와요. 예:

    ERROR: /data/rules/local.rules(9) Unmatched quote in rule option 'msg'.
Fatal Error, Quitting..

    (9)가 몇 번째 줄인지 알려 줘요. 그 줄의 따옴표, 세미콜론, 괄호를 확인하세요.

    • mkdir -p /tmp/snortlog — 임시 폴더(-p는 이미 있어도 오류 없음).
    • -r 파일 — 네트워크 대신 이 PCAP을 읽어요.
    • -A console — 알림을 화면에 한 줄씩.
    • -q — 시작 안내문 숨기기.
    • -k none — 체크섬 검사 끄기. 캡처한 PCAP은 체크섬이 틀린 경우가 많아서, 이게 없으면 Snort가 그 패킷을 버려 알림이 안 뜰 수 있어요.
    • -U — 시각을 UTC로, -y — 날짜에 연도.
    • -l /tmp/snortlog — Snort가 기록 파일을 쓸 폴더(아래 오류 참고).

    4. 고칠 때마다 rev:1 → rev:2로 올려서, 어떤 버전으로 시험했는지 보고서에 남겨요.

    부분 뜻
    alert tcp TCP 패킷을 검사하고, 맞으면 알림
    $HOME_NET any -> $EXTERNAL_NET $HTTP_PORTS 내부 아무 포트 → 외부 웹 포트(80 등). 방향이 중요해요
    flow:to_server,established TCP 연결이 맺어진 뒤, 서버 쪽으로 가는 데이터만
    content:"POST"; http_method HTTP 메서드가 POST
    content:"/4/forum.php"; http_uri URI에 /4/forum.php가 있음
    content:"GUID="; http_client_body; depth:5 요청 본문의 맨 앞 5바이트가 GUID=
    content:"&BUILD="; ... distance:0 그 뒤 어딘가에 &BUILD= (distance:0 = 앞 조건이 끝난 곳부터 찾기)
    content:"&INFO=" 그 뒤에 &INFO=
    classtype:trojan-activity 분류: 트로이목마 활동
    sid:1000011; rev:1 룰 번호(사용자 룰은 1000000 이상)와 수정 판
    • 왜 URI만 보지 않나요? /4/forum.php는 정상 게시판에도 있을 수 있는 주소예요. 본문의 GUID=...&BUILD=...&INFO= 구조까지 보면 오탐이 크게 줄고, 공격자가 도메인을 바꿔도 잡혀요.
    • sid 1000013은 도메인이나 URI 없이 어색한 헤더 조합(octet-stream + Content-Encoding: binary)만 봅니다. 이런 행동 룰은 다른 서버를 쓰는 같은 악성코드도 잡을 수 있어요.
    • sid 1000014는 TLS Client Hello(|16 03| = TLS 핸드셰이크, 6번째 바이트 |01| = Client Hello) 안의 SNI 이름을 봅니다. 암호화 전이라 보여요.
    • sid 1000015는 반대 방향(서버 → PC)의 인증서에서 Default Company Ltd를 찾습니다. 악성만 잡는 룰은 아니어서(테스트 서버도 이럴 수 있음) 분류를 bad-unknown으로 낮췄어요.
    • DNS 룰(1000016–1000018)의 |01 00 00 01 00 00 00 00 00 00|는 "일반 질문 1개, 답 0개"라는 DNS 헤더예요. 그래서 질문만 잡고 답은 안 잡습니다. |0a|lysedsohap|03|com|00|은 DNS가 이름을 저장하는 방식(글자 수 + 글자)입니다. 0a = 10글자 lysedsohap, 03 = 3글자 com, 00 = 끝.

    분석하면서 만난 랩 문제¶

    이 사례를 위해 pcapbox를 준비하면서 만난 문제예요. 다시 만날 테니 남겨 둡니다.

    • pcapbox 매뉴얼 7단계 뒤 호스트에서 Arkime/Splunk가 안 열림. VM 방화벽은 8-6단계에서야 8000/8005를 열어요. 먼저 열기: sudo firewall-cmd --permanent --add-port=8000/tcp --add-port=8005/tcp.
    • firewall-cmd: error: argument --add-service: not allowed with argument --add-port. 이 firewalld는 포트와 서비스를 한 명령에 섞지 못해요. 두 명령으로: --add-port=... 다음 --add-service=samba, 그리고 sudo firewall-cmd --reload.
    • Arkime 웹 암호를 매뉴얼 기본값 그대로 둠. arkime_add_user.sh는 계정을 만드는 명령이라 다시 실행해도 암호가 안 바뀌어요. 로그인 → Settings → Password에서 바꾸고, 관리자는 Users에서 다른 계정도 바꿀 수 있어요.
    • 호스트 전용 VMnet을 만들 때마다 VMware NAT가 죽음(Application 로그 이벤트 1000/1001: vmnat.exe 0xc0000005 크래시, VM은 DHCP로 IP를 받는데 NAT 게이트웨이 .2로 핑이 안 됨). 원인은 랩 대역이 호스트의 실제 네트워크와 겹친 것이었어요. 호스트 Wi-Fi가 /23 대역이고 게이트웨이가 10.10.10.1(VMnet2의 호스트 주소와 같음), 유선망이 172.16.0.0/16(VMnet3 대역과 같음)이었어요. 해결: 랩을 겹치지 않는 대역으로 옮기기(여기서는 10.50.10.0/24, 10.60.0.0/16). VMnet을 만들기 전에 PowerShell에서 확인: Get-NetIPAddress -AddressFamily IPv4, Get-NetRoute -DestinationPrefix 0.0.0.0/0.

    배운 점¶

    1. 시계부터 맞추세요. 브라우저 시간의 Arkime와 UTC의 Splunk가 정확히 9시간 30분 달랐어요. 타임라인을 한 줄 쓰기 전에 모든 도구를 UTC로.
    2. 모르는 PCAP은 HTTP부터. 평문이고 양이 적고, 이야기가 시작되는 곳을 보여 줘요.
    3. 크기와 시각으로 사건을 잇기. ipify 응답 14바이트 = IP= 14글자, netlogon 1,522 × 512 B = 780 KB 업로드. 숫자가 맞으면 연결이 증명돼요.
    4. crib은 행동에서. 응답 직후 다운로드 → 응답에 http가 있을 것. base64 안의 반복 조각은 짧은 XOR 키의 힌트.
    5. 헤더가 아니라 내용으로 판단. text/plain은 암호화된 바이너리였고, 서버 시계는 5분 틀렸어요.
    6. 비콘 두 개, 프로그램 두 개. 120초 HTTP와 약 300초 TLS, 서로 다른 User-Agent와 프로토콜.
    7. 열린 의문은 끝까지. "왜 이렇게 많이 보냈지?"가 정상 DC 통신처럼 보이던 곳에 숨은 비밀번호 대입으로 이어졌어요.
    8. 보이는 도구를 쓰세요. Zeek의 DCE/RPC 분석기는 기능 이름을 보여 줬고, Arkime는 못 보여 줬어요.
    9. 공격자가 쉽게 못 바꾸는 것으로 룰을. 본문 형식은 도메인이 바뀌어도 그대로라, 룰 하나로 21개를 오탐 없이 잡았어요.
    10. 트래픽으로 알 수 없는 것과 볼 곳을 적으세요. 대입한 계정 → DC 이벤트 4776, 대입한 프로세스 → PC 4625/4624.
    11. 작아도 POST는 다 열어 보세요. 440바이트는 "보낸 양이 큰 연결" 검색에 안 나오지만 훔친 비밀번호를 담을 수 있어요.
    12. 도메인 환경에서는 Kerberos가 사용자를 알려 줍니다. $로 끝나면 컴퓨터 계정, 없으면 사람 계정이에요. 이번에는 악성코드가 C2에 보낸 INFO=가 같은 사용자를 한 번 더 확인해 줬습니다.
    13. 정상 서비스도 악성 활동의 일부일 수 있어요. api.ipify[.]org 자체는 정상이지만, 0.5초 뒤 그 답이 C2로 갔습니다. "무엇에 접속했나"보다 "앞뒤로 무엇이 있었나"가 중요해요.
    14. 암호화돼 있어도 패턴과 메타데이터는 보입니다. TLS 내용은 못 봤지만 SNI, 자체 서명 기본값 인증서, 간격, 바이트 수만으로 C2라고 판단했어요.
    15. 감염 사슬을 따라가세요. 다운로더(Hancitor) → 명령 → 다운로드 → 다음 악성코드(정보 탈취, 은행 트로이목마). 다운로드 직후 처음 나타나는 목적지는 거의 항상 다음 단계예요.
