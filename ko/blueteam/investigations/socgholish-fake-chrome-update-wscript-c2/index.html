    Sorting through the alerts — 가짜 Chrome 업데이트에서 WScript C2와 후속 C2 시도까지¶

    사례 요약

    malware-traffic-analysis.net **2018-06-30 "Sorting through the alerts"**를 홈 랩 pcapbox VM에서 분석한 기록입니다. **주 도구는 Splunk(Zeek 로그)**이고, Splunk로 볼 수 없는 것(페이지 내용, POST 본문)만 Arkime로 봅니다. 윈도우 7 PC 한 대(CONSERVATOR-PC, 사용자 lloyd.maxwell)가 해킹된 교회 웹사이트를 엽니다. 사이트의 .js 파일 7개에 숨겨진 스크립트가 브라우저를 **리다이렉터(TDS)**를 거쳐 가짜 "Update Chrome" 페이지로 보내고, 그 페이지가 Dropbox에서 Chrome_72.3.22.js를 내려받게 합니다. 46초 뒤 사용자가 그 파일을 실행합니다. wscript.exe가 C2에 XOR로 감춘 POST 3개(호스트, 사용자, 도메인, 프로세스 목록)를 보내고 349 KB 암호화 페이로드를 받아 %TEMP%에서 Chrome_72.3.22.exe로 실행합니다. 그 뒤 페이로드가 IP 주소만으로 C2 서버 두 곳에 약 7.5분마다 접속을 시도하지만, 한 곳은 거절하고 한 곳은 대답이 없습니다. 간단한 Snort 룰 하나와 짧은 티켓으로 마무리합니다.

    단계마다 같은 순서예요. 목적 → Splunk → Arkime(Splunk로 안 보일 때만) → 결과 → 결과 읽기 → 티켓 기록. SPL 쿼리는 모두 한 줄씩 설명합니다. 질문 상자는 분석하면서 나오는 질문과 답이에요.

    Splunk에는 Zeek의 요약(누가, 언제, 얼마나 크게, 어떤 이름)이 들어 있어요. Zeek는 페이지 본문과 POST 본문을 저장하지 않아요. 그래서 답이 트래픽 안에 있을 때는 그 한 번만 Arkime로 가서 보고 다시 Splunk로 돌아옵니다.

    결과 블록은 같은 PCAP에서 만든 값이에요. Zeek가 재시도 연결을 나누는 방식 때문에 여러분 Splunk의 연결 개수가 한두 개 다를 수 있어요. 결론은 바뀌지 않습니다.

    도메인, IP, 해시는 2018년 실제 악성 트래픽에서 나온 값이에요. 본문과 표에서는 무력화(hxxp, [.])했고, 코드 블록 안은 입력한 그대로 두었어요. 절대 접속하지 마세요. 추출한 파일은 실행하지 마세요.

    0단계 — PCAP 넣고 시계 확인하기¶

    목적: PCAP에 케이스 이름을 붙여서 이전 실습 로그와 섞이지 않게 하고, 모든 도구가 UTC로 보이게 해요.

    1. 파일 이름을 20180630_SORTING_ALERTS.pcap으로 바꾸고 \\10.50.10.60\incoming에 넣어요.
    2. pcapbox에서 tail -f /data/logs/ingest.log를 보다가 DONE case=20180630_SORTING_ALERTS가 나오면 끝이에요. START 줄의 sha256=이 증거 해시예요.
    3. Splunk Preferences → Time zone = UTC, Arkime Settings → General → Timezone = UTC, 시간 범위 All. (이유: Night Dew 두 번째 분석 0-2)

    Splunk에 케이스가 들어왔는지 확인:

    index=zeek sourcetype=zeek:conn
| stats count by pcap_case
    • index=zeek sourcetype=zeek:conn — Zeek의 연결 로그예요(연결 하나 = 한 줄).
    • stats count by pcap_case — 케이스 이름마다 줄 수를 세요(pcap_case = .pcap을 뺀 파일 이름).
    pcap_case                  count
20180511_NIGHT_DEW         216
20180630_SORTING_ALERTS    623

    ts와 _time 중 무엇을 쓰나요?

    Zeek 자체의 시간은 ts 필드예요(1970년부터 센 초). pcapbox는 이 값을 Splunk의 _time에도 넣지만, 이 페이지의 쿼리는 모두 ts로 정렬하고 출력해요. 그러면 _time이 색인 시각으로 찍히는 Splunk에서도 맞게 나와요.

    eval t=strftime(ts,"%H:%M:%S.%3N")는 1530390473.623을 20:27:53.623으로 바꿔요(%3N = 밀리초).

    1단계 — 큰 그림¶

    목적: 캡처 시간, 내부 PC 개수, PC마다 얼마나 바쁜지 봐요.

    Splunk¶

    쿼리 ① — 캡처 시간

    index=zeek sourcetype=zeek:conn pcap_case=20180630_SORTING_ALERTS
| stats min(ts) as first max(ts) as last count as sessions
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S"), last=strftime(last,"%Y-%m-%d %H:%M:%S")
    • 1줄: 이 케이스만 봐요.
    • 2줄: 요약 한 줄 — 가장 이른 ts, 가장 늦은 ts, 연결 개수.
    • 3줄: epoch 초를 읽을 수 있는 날짜로 바꿔요.
    first                 last                  sessions
2018-06-30 20:27:15   2018-06-30 20:59:05   623

    쿼리 ② — 누가 연결을 시작하나

    index=zeek sourcetype=zeek:conn pcap_case=20180630_SORTING_ALERTS
| stats count as sessions dc(id_resp_h) as destinations sum(orig_bytes) as sent sum(resp_bytes) as received by id_orig_h
| sort - sessions
    • id_orig_h = 연결을 시작한 IP예요.
    • dc(id_resp_h) = 서로 다른 목적지 개수(distinct count)예요.
    • orig_bytes / resp_bytes = 시작한 쪽이 보낸 바이트 / 상대가 보낸 바이트예요.
    • sort - sessions = 많은 순서로 정렬해요.
    id_orig_h      sessions  destinations  sent      received
172.16.2.169   622       185           846554    34117200
172.16.2.9     1         1             62        0

    Arkime (빠른 교차 확인)¶

    SPIView → General도 같은 모습이에요. Src IP는 거의 다 172.16.2.169, Dst IP는 DC 172.16.2.9가 가장 많고 그다음은 CDN·광고 주소가 많아요.

    결과 읽기¶

    • PC는 한 대예요. 172.16.2.169가 모든 연결을 시작해요. 172.16.2.9(주어진 DC)는 NetBIOS 응답 하나만 보내요. 경보는 이 PC 때문이에요.
    • 31분 동안 목적지 185곳 — 비콘에 필요한 것보다 훨씬 많아요. 사람이 웹을 보고 있다는 뜻이에요(뉴스 사이트 하나가 광고·CDN 호스트를 수십 개 불러요). 악성 트래픽은 그 사이에 숨은 몇 줄이라서 "가장 많이 통신한 곳"으로는 못 찾아요. 그래서 HTTP를 읽어요(3단계).
    • 34 MB 받음 — 대부분 웹 페이지와 (3단계에서 보듯) Chrome 구성 요소 업데이트예요.

    티켓 기록: 없음. 베이스라인은 발견 사항이 아니에요.

    2단계 — 172.16.2.169는 누구인가¶

    목적: 티켓에 들어갈 호스트 이름, MAC, 사용자를 찾아요.

    2-1. DHCP — 이번에는 비어 있어요¶

    index=zeek sourcetype=zeek:dhcp pcap_case=20180630_SORTING_ALERTS
| table ts client_addr mac host_name

    결과: 한 줄도 없어요.

    질문: DHCP에 아무것도 없으면 어떻게 하나요?

    캡처가 시작될 때 PC가 이미 유효한 IP 임대를 갖고 있어서 다시 요청하지 않은 거예요. 윈도우가 자기 이름을 말하는 다른 곳을 봐요.

    • Kerberos — 로그온할 때 컴퓨터 계정(이름$)과 사용자.
    • DNS — 윈도우는 DC에 자기 이름을 등록해요(<이름>.<도메인>에 대한 SOA 질의 = 동적 DNS 업데이트).
    • NetBIOS 브라우저 알림(브로드캐스트로 가는 UDP 138) — Zeek는 기록하지 않고 Arkime는 보여 줘요.
    • MAC — Zeek conn.log는 그 옵션을 켰을 때만 orig_l2_addr가 있어요. Arkime는 세션마다 MAC을 항상 보여 줘요.

    2-2. Kerberos¶

    index=zeek sourcetype=zeek:kerberos pcap_case=20180630_SORTING_ALERTS
| eval t=strftime(ts,"%H:%M:%S")
| sort ts
| table t id_orig_h request_type client service success error_msg
    • request_type: AS = 로그온(TGT 요청), TGS = 서비스용 티켓 요청.
    • client = 계정/영역(REALM). 이름이 $로 끝나면 컴퓨터, $가 없으면 사람이에요.
    • service = 티켓의 용도(krbtgt/... = 로그온 티켓 자체, cifs/ = 파일 공유, ldap/ = 디렉터리).
    • error_msg = 요청이 실패한 이유.

    배운 점¶

    1. 바쁜 웹 브라우징은 짧은 공격을 숨겨요. 목적지 185곳 중 감염은 1분 동안의 호스트 4개예요. HTTP를 호스트별로 묶고, 아는 정상(BITS, CryptoAPI, CDN)부터 지워요.
    2. Referer가 곧 사슬이에요. 악성 요청이 모두 교회 사이트의 /new/를 가리켰어요. 다른 탭이 아니라 그 사이트가 시작했다는 증거예요.
    3. 새 User-Agent = 새 프로그램. 다운로드 46초 뒤 Chrome → MSIE 7.0 + UA-CPU로 바뀌면 사용자가 파일을 실행한 거예요.
    4. "누가/언제/얼마나"는 Splunk, "정확히 무엇"은 Arkime. Zeek는 크기와 해시를 줬고, 리다이렉트 URL, 다운로드 링크, 프로필 정보는 본문 안에만 있었어요.
    5. 간단한 속임수에는 간단한 레시피. "두 글자마다 하나, 뒤집기"와 "hex + 1바이트 XOR"은 2단계, 4단계 CyberChef 레시피로 풀려요. 형식에서 고른 crib(폼 전송의 &1=)이 모든 키를 찾았어요.
    6. 인코딩된 페이로드는 EXE 검색을 피해 가요. text/plain으로 표시된 349 KB hex 글자가 페이로드였어요. MIME 형식이 아니라 크기와 앞뒤 상황으로 판단해요.
    7. 실패한 연결도 증거예요. 페이로드 직후, 하드코딩된 IP로, 일정한 박자로, 바이트 없이 REJ와 S0 — 깨끗한 PC가 아니라 C2가 죽어 있는 감염이에요.
    8. 트래픽으로 볼 수 없는 것과 그걸 찾을 곳을 적어요. .js와 .exe 내용·해시, 지속성, 진짜 악성코드 계열은 모두 호스트에서 나와요.
