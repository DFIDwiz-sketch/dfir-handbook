    Sorting through the alerts — 가짜 Chrome 업데이트에서 WScript C2와 후속 C2 시도까지¶

    사례 요약

    malware-traffic-analysis.net의 2018-06-30 "Sorting through the alerts" 실습을 홈 랩 pcapbox VM에서 한 단계씩 분석한 기록이에요. 주 도구는 Splunk(Zeek 로그)이고, Splunk로 볼 수 없는 것(페이지 내용, POST 본문)만 Arkime로 봐요. 윈도우 7 PC 한 대(CONSERVATOR-PC, 사용자 lloyd.maxwell)가 해킹된 교회 웹사이트를 열어요. 사이트에 숨겨진 스크립트가 브라우저를 지문 검사 리다이렉터(TDS)를 거쳐 가짜 "Update Chrome" 페이지로 보내고, 그 페이지가 Dropbox에서 Chrome_72.3.22.js를 내려받게 해요. 46초 뒤 사용자가 그 파일을 실행해요. wscript.exe가 C2에 XOR로 감춘 POST 3개(호스트, 사용자, 도메인, 프로세스 목록)를 보내고 349 KB 인코딩된 페이로드를 받아 %TEMP%의 Chrome_72.3.22.exe로 보고해요. 10초 뒤부터 PC는 하드코딩된 C2 IP 두 곳에 약 7.5분마다 접속을 시도해요. 한 곳은 거절하고 한 곳은 대답이 없어요. 간단한 Snort 룰 하나와 짧은 보고서로 마무리해요.

    0단계 — PCAP 넣고 케이스 확인¶

    목적: PCAP에 케이스 이름을 붙여서 다른 실습 로그와 섞이지 않게 하고, 모든 도구가 UTC로 보이게 해요.

    1. 파일 이름을 20180630_SORTING_THROUGH_THE_ALERTS.pcap으로 바꾸고 \\10.50.10.60\incoming에 넣어요.
    2. pcapbox에서 tail -f /data/logs/ingest.log를 보다가 DONE case=20180630_SORTING_THROUGH_THE_ALERTS가 나오면 끝이에요.
    3. Splunk Preferences → Time zone = UTC, Arkime Settings → Timezone = UTC, 시간 범위 All.
    index=zeek sourcetype=zeek:conn
| stats count by pcap_case
    • index=zeek — Zeek 로그가 든 인덱스(Splunk의 "서랍")만 봐요.
    • sourcetype=zeek:conn — 연결 로그예요. 연결 하나가 한 줄이에요.
    • | — 왼쪽 결과를 다음 명령으로 넘겨요.
    • stats count by pcap_case — 케이스 이름마다 줄 수를 세요.

    _time이 아니라 ts

    Zeek의 이벤트 시간은 ts(epoch 초)예요. 이 페이지의 쿼리는 모두 ts로 정렬하고 출력해요. 그러면 _time이 색인 시각으로 찍히는 Splunk에서도 맞게 나와요. eval t=strftime(ts,"%H:%M:%S")로 읽기 쉽게 바꿔요.

    케이스 이름이 길 때

    Splunk에서는 pcap_case=20180630_SORTING*처럼 *(아무 글자)를 써도 돼요. 다른 케이스와 겹치지 않을 때만요. Arkime의 tags ==에는 전체 이름을 써요.

    1단계 — 베이스라이닝¶

    베이스라이닝 = 나쁜 것을 찾기 전에 이 캡처의 평소 모습을 먼저 아는 거예요. 시간 범위, 로그 종류, 내부 PC, 얼마나 바쁜지, 누구인지를 봐요.

    1-1. 어떤 로그가 있나¶

    index=zeek pcap_case=20180630_SORTING_THROUGH_THE_ALERTS
| stats count by sourcetype
| sort - count
    • sourcetype을 안 적어서 이 케이스의 모든 로그 종류를 가져와요. sort - count = 많은 순서(-는 내림차순).

    [데이터] 결과 읽기:

    • zeek:dhcp가 없어요. 캡처가 시작될 때 PC가 이미 IP를 갖고 있었다는 뜻이에요. 호스트 이름은 다른 곳에서 찾아야 해요(1-5).
    • 웹 로그가 가장 많아요(ssl 265, http 134). 누군가 웹을 보고 있었어요. HTTPS가 HTTP의 두 배지만, HTTP 134개는 내용을 다 볼 수 있어서 핵심 재료가 돼요.
    • 도메인 로그(kerberos, ldap, dce_rpc, smb_*, ntlm) = AD PC가 DC와 하는 평소 대화예요(로그온, 그룹 정책). 사용자와 컴퓨터 이름이 여기 있어요.
    • ocsp(인증서 확인), ntp(시간), weird(이상한 패킷)는 보통 별일 아니에요. software는 Zeek가 알아본 프로그램 목록이에요(1-5에서 써요).

    1-2. 캡처 시간 범위¶

    index=zeek sourcetype=zeek:conn pcap_case=20180630_SORTING_THROUGH_THE_ALERTS
| stats min(ts) as first max(ts) as last count as sessions
| eval duration_min=round((last-first)/60,1)
| eval first=strftime(first,"%Y-%m-%d %H:%M:%S"), last=strftime(last,"%Y-%m-%d %H:%M:%S")
    • 2줄: 전체를 한 줄로 요약해요 — 가장 이른 시간, 가장 늦은 시간, 연결 수. as는 결과에 이름을 붙여요.
    • 3줄: eval로 새 필드를 계산해요. 분 단위, 소수 한 자리.

    CyberChef 레시피

    1. Input: 따옴표 안쪽 글자만(129글자 — Input 아래 ABC로 확인).

    2. 가장 흔한 단순한 겹은 1바이트 XOR이에요(키 256개뿐). 맞는 키는 crib(원래 글에 꼭 있을 글자)으로 골라요. 폼 데이터(이름=값&…)이고 바깥 이름이 한 글자(a=, b=)라서 &1=을 써 봐요.

    1. From Hex
    2. XOR Brute Force — Key length 1, Crib &1=. 읽을 수 있는 줄의 키를 적어요.
    3. XOR로 바꿔요 — 그 키, HEX.
    4. URL Decode(%5C → \, %3A → :, %7C → |).

    질문: 어떤 글자에 어떤 해독을 쓰는지 규칙이 있나요?

    네, 대부분 쓰인 글자의 종류가 알려 줘요. 0-9a-f, 짝수 길이 → From Hex. A-Z a-z 0-9 + /에 끝이 = → From Base64. %xx → URL Decode(보통 마지막 겹). \x41 → Unescape string, \u0041 → Unescape Unicode Characters, 쉼표로 나뉜 10진수 → From Charcode. TVqQ(Base64) / 4d5a(hex)로 시작 → EXE, H4sI / 1f8b → gzip. 풀었는데 알아볼 수 없고 Entropy가 낮거나 중간 → 1바이트 XOR. Crib은 그 겹에서 꼭 있을 글자예요: 폼 데이터는 &1=, 주소는 http, 체크인은 베이스라이닝에서 찾은 호스트·사용자 이름, EXE는 This program. XOR 다음에 URL 인코딩이 있으면 경로 crib은 C:\가 아니라 C%3A%5C예요.

    배운 점¶

    1. 베이스라이닝 메모는 나중에 빛나요. 설명 안 되던 세 줄(조용한 IP 두 곳, 이상한 User-Agent 하나)이 감염 전체였어요. 각각은 나중에 새 사실이 나와서야 설명됐어요.
    2. 바쁜 브라우징은 짧은 공격을 숨겨요. 목적지 184곳 중 감염은 1분 동안의 몇 곳이에요. 아는 정상(CDN, 광고, BITS, CryptoAPI, 광고 플랫폼 CNAME)을 지우고 남은 것을 읽어요.
    3. DNS 없음 + 일정한 박자 = 프로그램. DNS 없는 목적지 서브서치가 184곳을 C2 IP 두 곳으로 줄였어요.
    4. Referer가 곧 사슬이에요. 악성 요청은 모두 교회 페이지를 가리켰어요.
    5. 새 User-Agent = 새 프로그램. 다운로드 46초 뒤 MSIE 7.0 + UA-CPU는 파일이 실행됐다는 신호였고, b=가 증명했어요.
    6. 누가/언제/얼마나는 Splunk, 정확히 무엇은 Arkime. 다운로드 URL과 프로필 정보는 본문에만 있었어요.
    7. 해독기는 숨긴 글자와 같이 다녀요. 함수를 읽고 옮기거나, 오프라인 콘솔에서 함수만 실행해요. 해독기가 없으면 모양을 읽어요: 글자 종류 → 겹 → 형식에서 고른 crib.
    8. 레시피를 탓하기 전에 입력을 확인해요. 따옴표, 빠진 앞부분, 잘린 줄 접기가 결과를 다 바꿨어요. ABC와 Zeek의 본문 길이로 잡아요.
    9. 도구의 한계를 알아요. 값이 두 개인 host가 숫자를 두 배로, Arkime의 200패킷 제한이 c=를 숨겼고, 재색인은 모든 걸 두 배로 만들 뻔했어요.
    10. 데이터와 추측을 구별해요. "시간이 맞는다"는 추측, "풀어 낸 코드에 그렇게 있다"는 증거예요. 보고서에는 증거를 써요.
