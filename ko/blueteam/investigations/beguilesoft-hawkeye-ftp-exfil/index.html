    BEGUILESOFT — HawkEye Keylogger: FTP로 빠져나간 비밀번호, 키로그, 스크린샷¶

    사례 요약

    malware-traffic-analysis.net 2019-05-02 "BEGUILESOFT" PCAP을 홈 랩의 pcapbox VM에서 Splunk 중심으로 분석하고, 패킷 내용이 필요할 때만 Arkime를 쓴 기록입니다. AD 도메인의 윈도우 7 PC 한 대(Breaux-Win7-PC, 사용자 adriana.breaux)가 자기 공인 IP를 확인한 다음, 무료 호스팅 서비스 files.000webhost[.]com에 FTP 계정 snifferzett으로 로그인합니다. 그리고 10~15분 간격으로 세 번 접속해 파일 5개를 올려요.     실제로 분석한 순서 그대로예요. 베이스라이닝 → 수상한 목적지 → FTP 상세 → Arkime로 내용 확인 → Snort. SPL 쿼리는 모두 한 줄씩 설명하고, 결과가 어떻게 나왔는지와 어떻게 읽는지를 붙였어요. 질문 상자는 분석하면서 실제로 나온 질문과 답이에요.

    이 페이지의 지표는 실제 값입니다

    도메인, IP, 계정 이름은 2019년 실제 악성 트래픽에서 나온 값입니다. 본문과 표에서는 무력화([.])했고, 코드 블록 안은 입력한 그대로 두었어요. 절대 접속하지 마세요. 피해자의 실제 비밀번호는 이 페이지에 싣지 않았어요.

    0단계 — 첫 쿼리 전에¶

    PCAP을 20190502_BEGUILESOFT.pcap이라는 이름으로 \\10.50.10.60\incoming에 넣었어요. 그래서 케이스 이름은 20190502_BEGUILESOFT예요(Splunk 필드 pcap_case, Arkime 태그). 쿼리 전에 두 가지를 확인해요.

    1. Splunk 시간 범위 = All time. pcapbox에서는 _time이 패킷 시간(2019년)이라서, 기본값 "Last 24 hours"로 두면 결과가 하나도 안 나와요.
    2. Splunk 계정 시간대 = UTC (계정 메뉴 → Preferences). strftime은 Splunk 계정 시간대로 출력하기 때문이에요.

    설치와 넣는 방법은 Night Dew — 0단계에 있어요.

    1단계 — 베이스라이닝¶

    목적: 나쁜 것을 찾기 전에 기본부터 알아 둬요. 캡처가 언제 시작하고 끝나는지, 어떤 로그가 있는지, 어떤 내부 PC가 통신하는지, 그리고 호스트명, MAC, DC, 사용자예요. 호스트 정보 말고는 보고서에 넣지 않아요.

    1-1. 캡처 시간과 로그 종류¶

    index=zeek pcap_case="20190502_BEGUILESOFT"
| stats count AS events min(ts) AS first max(ts) AS last BY sourcetype
| eval first=strftime(first, "%Y-%m-%d %H:%M:%S"), last=strftime(last, "%Y-%m-%d %H:%M:%S")
| sort - events
    • 1줄은 이 케이스의 Zeek 이벤트를 모두 가져와요. pcap_case는 pcapbox가 PCAP 파일 이름을 넣어 둔 필드예요.
    • 2줄 stats는 엑셀의 피벗처럼 "묶어서 계산"하는 명령이에요. BY sourcetype은 로그 종류(conn, dns, http…)별로 묶으라는 뜻이고, 묶음마다 count(개수), min(ts)(가장 이른 시간), max(ts)(가장 늦은 시간)를 구해요. AS는 결과 칼럼 이름을 정해요.
    • 3줄 eval은 새 값을 계산하거나 덮어써요. ts는 1556832918 같은 epoch 숫자라서, strftime으로 사람이 읽을 수 있는 날짜로 바꿔요.
    • 4줄 sort - events는 개수가 많은 순서로 정렬해요. -가 내림차순이에요.

    1-2. DHCP — 호스트명, MAC, 도메인¶

    index=zeek sourcetype=zeek:dhcp pcap_case="20190502_BEGUILESOFT"
| eval time=strftime(ts, "%Y-%m-%d %H:%M:%S")
| table time assigned_addr mac host_name domain msg_types
    • sourcetype=zeek:dhcp는 DHCP 로그만 가져와요.
    • table은 원하는 칼럼만 원하는 순서로 보여 줘요.
    • assigned_addr는 DHCP 서버가 준 IP, mac은 PC의 MAC, host_name은 PC가 스스로 알린 이름(보고서의 HOSTNAME), domain은 DHCP가 알려 준 도메인 이름, msg_types는 DHCP 메시지 종류예요.
    time                 assigned_addr  mac                host_name       domain           msg_types
2019-05-02 21:35:21                 84:8f:69:09:86:c0  Breaux-Win7-PC  beguilesoft.com  INFORM ACK

    assigned_addr가 왜 비어 있나요?

    msg_types가 REQUEST가 아니라 INFORM이에요. INFORM은 IP를 이미 가진 PC(고정 IP나 예전에 받은 주소)가 도메인 이름 같은 설정만 물어보는 메시지예요. 새로 "배정된" IP가 없으니 칸이 비어요. IP는 다음 쿼리에서 나와요(10.0.0.227). table에 client_addr를 추가하면 PC가 요청할 때 쓴 IP도 볼 수 있어요.

    1-3. 어떤 내부 IP가 통신을 시작하나¶

    index=zeek sourcetype=zeek:conn pcap_case="20190502_BEGUILESOFT"
| where cidrmatch("10.0.0.0/8", id_orig_h) OR cidrmatch("172.16.0.0/12", id_orig_h) OR cidrmatch("192.168.0.0/16", id_orig_h)
| stats count AS conns dc(id_resp_h) AS dests BY id_orig_h
| sort - conns
    • id_orig_h는 연결을 시작한 쪽 IP예요.
    • where는 조건이 참인 이벤트만 남기는 필터예요. cidrmatch("10.0.0.0/8", id_orig_h)는 "이 IP가 10.0.0.0/8 대역 안에 있는가?"를 묻는 함수예요. 사설 대역 3개를 OR로 이어서 내부 IP만 남겨요.
    • count는 연결 수, dc(id_resp_h)는 "distinct count", 즉 서로 다른 목적지 IP 수예요. BY id_orig_h라서 내부 IP 하나당 한 줄이 나와요.
    id_orig_h    conns  dests
10.0.0.227   99     10

    통신을 시작하는 내부 PC는 하나뿐이고, 목적지도 10개뿐이에요. 분석 대상은 10.0.0.227이에요.

    1-4. Kerberos — DC와 사용자 계정¶

| stats count BY id_orig_h id_resp_h client

    • QUIT는 접속 종료예요. 이번에는 클라이언트가 QUIT하기 전에 서버가 421로 먼저 끊었어요.

    명령 뜻 분석 포인트
    RETR 다운로드 (서버 → 클라이언트) 외부에서 악성 파일을 받아 올 때
    APPE 기존 파일 뒤에 이어 붙이기 STOR처럼 유출에 쓰일 수 있음
    PORT / EPRT Active 모드 (서버가 클라이언트로 접속해 옴) NAT·방화벽 때문에 요즘은 드묾
    EPSV PASV의 확장판 (IPv6 지원, 포트만 알려 줌) 229 (\|\|\|포트\|) 형태
    LIST / NLST 폴더 목록 보기 정찰
    CWD / MKD / DELE 폴더 이동, 폴더 생성, 파일 삭제 흔적 지우기에 DELE
    SYST / FEAT 서버 종류, 지원 기능 묻기 정상 클라이언트도 씀

    악성코드가 거의 항상 PASV를 쓰는 이유: 감염 PC는 보통 NAT 뒤에 있어서 밖에서 안으로 접속할 수 없어요. Passive 모드는 클라이언트가 밖으로 나가서 연결하니까 늘 성공해요.

    응답 코드는 첫 자리만 알아도 돼요: 1xx 진행 중(150 데이터 연결 연다), 2xx 성공(220 인사, 227 Passive 모드, 230 로그인 OK, 226 전송 완료), 3xx 추가 정보 필요(331 비밀번호 달라), 4xx 일시적 실패(421 서비스 종료), 5xx 영구 실패(530 로그인 실패, 550 파일 없음/권한 없음).

    질문: PASV와 STOR이 뭔가요?

    FTP 서버를 택배 회사 창고라고 생각해 보세요. 감염된 PC가 창고에 물건(훔친 파일)을 맡기러 가는 상황이에요.

    FTP에서는 말(명령)을 주고받는 창구와 물건(파일)을 넣는 문이 따로 있어요. 창구는 항상 같은 곳(포트 21)이지만, 물건 넣는 문은 그때그때 새로 열어요. 그래서 PC가 먼저 이렇게 말해요.

    PC:     PASV
서버:   227 Entering Passive Mode (145,14,144,10,158,203)

    PC가 "물건 넣을 문 하나 열어 주세요"라고 하면, 서버가 "145.14.144.10의 40651번 문을 열었어요, 거기로 오세요"라고 답하는 거예요. 앞의 숫자 네 개가 IP이고, 문 번호는 158 × 256 + 203 = 40651이에요. Passive(수동)는 서버는 문만 열고 가만히 기다리고, PC가 그 문으로 찾아간다는 뜻이에요.

    문이 열리면 PC가 어떤 파일을 맡길지 말해요.

    PC:     STOR HawkEye_Keylogger_Keylog_Records_2_BREAUX-WIN7-PC ... .txt
서버:   150 ...                           ← "네, 그 문으로 넣으세요"
        [PC가 40651번 문으로 파일 내용 891바이트를 보냄]
서버:   226 File successfully transferred  ← "잘 받았어요"

    STOR는 Store(저장하다)의 줄임말이에요. 내 PC에서 서버로 파일을 올리는(업로드) 명령이에요. 반대로 내려받는(다운로드) 명령은 RETR(Retrieve, 가져오다)예요.

    파일 하나를 올릴 때마다 항상 PASV → STOR가 짝으로 나와요. 문을 열고 파일을 넣고, 다음 파일이 있으면 또 문을 열고 넣어요. 그래서 zeek:ftp 결과에 PASV와 STOR가 번갈아 나왔던 거예요. 기억할 것은 하나예요. 내부 PC가 외부 서버로 STOR를 했다 = 우리 쪽 파일이 밖으로 나갔다. 이번에는 STOR가 5번이니까 파일 5개가 나간 거예요.

    4단계 — Arkime로 내용 보기¶

    Splunk는 모양을 보여 주고, 패킷 내용(비밀번호, 파일 내용)은 Arkime에서 봐요. FTP는 암호화가 없어서 다 읽혀요.

    tags == 20190502_BEGUILESOFT && ip.src == 10.0.0.227 && port.dst == 21
tags == 20190502_BEGUILESOFT && ip.src == 10.0.0.227 && (ip.dst == 145.14.145.4 || ip.dst == 145.14.144.10 || ip.dst == 145.14.145.99)
tags == 20190502_BEGUILESOFT && ip.src == 10.0.0.227 && port.dst == 37280
tags == 20190502_BEGUILESOFT && ip.src == 10.0.0.227 && http.host == whatismyipaddress.com
    1. FTP 제어 세션 → 세션 3개(로그인과 STOR 명령).
    2. 000webhost로 간 모든 트래픽 → 세션 8개(제어 3 + 데이터 5).
    3. Stealer Records가 지나간 데이터 연결.
    4. 공인 IP 확인 요청.

    tags == <케이스>는 pcapbox에서 이 케이스 세션만 보게 해요. 실제 망에서는 빼요.

    질문: HawkEye_Keylogger를 Arkime에서 검색하려면?

    Sessions 검색창에서는 바로 찾을 수 없어요. Arkime은 FTP 명령 안의 파일 이름을 필드로 저장하지 않거든요. 패킷 내용 속 글자를 찾을 때는 Hunt를 써요.

    1. 먼저 Sessions 검색창에 범위를 넣어요: tags == 20190502_BEGUILESOFT && port.dst == 21. Hunt는 지금 검색 결과의 세션만 뒤져서, 범위를 좁힐수록 빨라요.
    2. 위 메뉴 Hunt → Create a packet search job.
    3. 칸 채우기: Name hawkeye_ftp · Search HawkEye_Keylogger · Search type ascii (case insensitive) (Snort의 nocase와 같아요) · Src/Dst Src만 체크(STOR는 PC가 보내니까) · Max packets per session 기본값.
    4. Create를 누르면 작업이 돌고, 끝나면 매칭된 세션 수가 나와요. 여기서는 3개예요(제어 세션 3개 모두에 HawkEye_Keylogger STOR가 있으니까요).
    5. 결과는 Sessions에서 huntName == hawkeye_ftp로 다시 볼 수 있어요. 매칭된 세션에 hunt 이름이 붙어서 필드처럼 검색돼요.

    빠른 대안: Arkime은 FTP 로그인 계정은 Users 필드로 저장해요. 그래서 이건 검색창에서 바로 돼요.

    tags == 20190502_BEGUILESOFT && user == snifferzett

    정리하면, 패킷 안의 아무 글자 → Hunt, Arkime이 필드로 뽑아 둔 값(IP, 포트, 도메인, user 등) → 검색창이에요. Hunt는 여러 세션에 문자열 찾기를 한꺼번에 돌린다고 생각하면 돼요.

    5단계 — Snort 룰 하나¶

    depth나 distance 없이 가장 쉬운 버전이에요.

    alert tcp $HOME_NET any -> $EXTERNAL_NET 21 (msg:"HawkEye Keylogger FTP upload - Sung"; content:"HawkEye_Keylogger"; nocase; sid:1000021; rev:1;)

    괄호 앞(헤더) — 어떤 패킷을 볼지:

    • alert는 조건에 맞으면 알림을 낸다는 뜻이에요.
    • tcp는 TCP 패킷만 봐요.
    • $HOME_NET any는 출발지가 내부망이고, 출발지 포트는 아무거나예요.
    • ->는 방향이에요. 내부에서 밖으로 나가는 패킷이에요.
    • $EXTERNAL_NET 21은 목적지가 외부이고 포트 21(FTP 명령 포트)이라는 뜻이에요.

    괄호 안(옵션) — 패킷 안에서 무엇을 찾을지:

    • msg는 알림이 뜰 때 보이는 이름이에요.
    • content:"HawkEye_Keylogger"는 패킷 내용에 이 글자가 있는지 찾아요.
    • nocase는 대소문자를 구분하지 않아요. hawkeye_keylogger도 잡혀요.
    • sid는 룰 번호예요. 직접 만든 룰은 1000000 이상을 써요.
    • rev는 룰 버전이에요.

    질문: depth나 distance 없이 룰을 쓸 수 있나요?

    네, 위 룰이에요. depth와 distance는 "글자가 패킷의 어디쯤에 있는지"를 지정해서 오탐을 줄이고 속도를 높여요. 하지만 HawkEye_Keylogger라는 글자 자체가 아주 특이해서, 정상 FTP 트래픽에서 나올 일이 거의 없어요. 그래서 위치를 지정하지 않아도 충분해요. STOR 조건을 뺀 것도 같은 이유예요. 포트 21로 이 파일 이름이 나가는 경우는 사실상 업로드뿐이에요. flow와 classtype도 뺐어요. 방향은 헤더의 ->와 포트 21이 이미 정해 주니까요.

    예상 결과: \\10.50.10.60\rules\local.rules에 넣고 snort-test 20190502_BEGUILESOFT를 돌리면 알림 3건이에요. HawkEye_Keylogger가 들어간 STOR가 3번이었거든요(Stealer_Records, Keylog_Records_2, Keylog_Records_3). 스크린샷 STOR 2번은 파일 이름에 그 글자가 없어서 안 잡혀요. 자세한 테스트 방법은 Night Dew — 8-3에 있어요.

    배운 점¶

    1. 로그 종류 목록이 이미 단서예요. TLS가 하나도 없는 사무실 PC에 FTP가 있다는 것만으로 유출 경로가 보였어요.
    2. DHCP INFORM에는 배정 주소가 없어요. IP는 conn에서, 이름과 MAC은 DHCP에서 가져와요.
    3. 보낸 양과 받은 양이 방향을 알려 줘요. 보낸 게 MB 단위이고 받은 게 0인 ftp-data = 업로드.
    4. PASV 계산으로 파일과 크기를 이어요. p1 × 256 + p2 = ftp-data 포트.
    5. Zeek은 명령에 마지막 응답을 붙여요. 업로드 실패라고 하기 전에 원본 세션을 봐요.
    6. 평문 프로토콜은 증거를 그대로 줘요. FTP에서 공격자 계정과 훔친 파일 전부가 보였어요.
    7. 악성코드 이름은 조심해서 붙여요. "HawkEye"는 악성코드가 스스로 쓴 파일 이름에서 나온 거라 강한 근거지만, 샘플 분석은 아니에요.
    8. 피해자 비밀번호는 보고서에 적지 않아요. "증거 참고"라고 써요.
