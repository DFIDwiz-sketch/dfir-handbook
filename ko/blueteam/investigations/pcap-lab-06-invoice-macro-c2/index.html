    PCAP 실습 06 — 청구서 Word 매크로에서 Hancitor 유형 C2까지¶

    사례 요약

    maricheika.net 도메인의 윈도우 7 PC가 Internet Explorer로 invoice_284615.doc를 받았습니다. 이 문서에는 자동 실행 VBA 매크로가 들어 있었습니다. 약 2분 뒤 PC는 api.ipify.org로 공인 IP를 확인했습니다. 이어서 perranrowsin.com으로 2분마다 POST를 보냈고, 해킹된 워드프레스 사이트에서 파일 3개를 더 받았습니다. 이 통신 패턴은 Hancitor와 일치합니다(추정, 오프라인이라 해시 조회는 못 함).
    증거 Phase1_PCAP_6.pcap, 2018-10-01 18:37:28 – 18:58:35 UTC (21분)
    환경 인터넷이 막힌 리눅스 분석 VM, Zeek 4.x, tshark
    주 도구 Zeek 로그 + zeek-cut, awk, grep. 더 쉬운 곳은 tshark
    실습 안내 트레이닝 → PCAP 침해사고 분석 실습 → 실습 6

    0단계 — 준비와 Zeek 로그 만들기¶

    cd ~/Investigation_6

    부분 이유
    sha256sum ... \| tee pcap.sha256 분석하는 동안 증거가 바뀌지 않았다는 것을 나중에 증명합니다. tee는 화면에 보여 주면서 파일로도 저장합니다.
    mkdir zeek_full && cd zeek_full Zeek은 지금 있는 폴더에 로그를 씁니다. 전용 폴더를 쓰면 로그가 한곳에 모이고, 나중에 Zeek을 다시 돌려도 덮어써지지 않습니다.
    -C 체크섬 오류를 무시합니다. 보내는 PC에서 캡처하면 체크섬을 네트워크 카드가 계산하기 때문에 "틀린" 값으로 보일 때가 많습니다. -C가 없으면 Zeek이 그 패킷을 버릴 수 있습니다.
    -r ../Phase1_PCAP_6.pcap 실시간 인터페이스 대신 파일을 읽습니다.
    local 기본 정책 스크립트를 불러옵니다. 센서가 실제로 돌리는 것과 같습니다.
    frameworks/files/extract-all-files 전송된 모든 파일을 extract_files/에 저장합니다. 나중에 해시를 구하고 살펴볼 수 있습니다.
    policy/protocols/conn/mac-logging conn.log에 MAC 주소 칸(orig_l2_addr, resp_l2_addr)을 추가합니다.
    2>/dev/null 경고 메시지를 숨깁니다.

    ls를 하면 conn.log, dns.log, http.log, files.log, dhcp.log, kerberos.log, ssl.log와 extract_files/ 폴더가 보여야 합니다.

    3단계 — 문서보다 먼저 악성 활동이 있었나?¶

    18:38:00을 감염 시작으로 정하기 전에, 그 전에 수상한 것이 없었는지 확인합니다. 캡처는 18:37:28에 시작하므로 문서 요청까지 32초밖에 없습니다. 먼저 일어난 일이 거의 없겠지만, 그래도 확인합니다.

    zeek-cut -u ts query answers < dns.log | awk -F'\t' '$1 <= "2018-10-01T18:38:01+0000"'
zeek-cut -u ts host uri < http.log     | awk -F'\t' '$1 <  "2018-10-01T18:38:00+0000"'
    • awk -F'\t'는 탭(Zeek의 구분자)으로 칸을 나눕니다. $1은 첫 번째 칸, 즉 시각입니다.
    • ISO 형식 시각은 글자 그대로 비교해도 됩니다. 큰 단위(연→월→일→시…)부터 적기 때문에 글자 순서가 곧 시간 순서입니다.
    • 예상되는 결과: 윈도우 부팅·로그인 때의 질의(DC를 찾는 _ldap._tcp… SRV, wpad, isatap, msftncsi)와, 다운로드 직전의 pitchbocaraton.com 질의입니다. 다른 모르는 도메인이 있으면 사고 시작 시점이 더 앞으로 갑니다. 다른 수상한 것이 없으면 문서 다운로드가 첫 악성 이벤트입니다.

    어떤 이벤트 직전을 보는 두 가지 방법

    • grep -B 15 "msword": 찾은 줄과 그 앞 15줄을 보여 줍니다(-A는 뒤, -C는 앞뒤). "바로 전에 무슨 일이?"를 빨리 볼 때 씁니다.
    • awk -F'\t' '$1 <= "…"': 시간 범위를 정확히 자릅니다. 보고서용으로 씁니다.

    User-Agent로 요청을 보낸 프로그램 구분하기¶

    요청 User-Agent 판단

    ipify, /4/forum.php, 워드프레스 /1 /2 /3 Windows NT 6.1; Win64; x64; Trident/7.0; rv:11.0 IE처럼 보이지만 진짜 브라우저와 다름 → 다른 프로그램(1단계 악성코드)
    /mlu/forum.php, /d2/about.php Mozilla/4.0 (compatible; MSIE 7.0; …) 2018년 윈도우 7에서 IE 7은 말이 안 됨 → 또 다른 프로그램에 박혀 있는 문자열

    PC 한 대에 진짜 브라우저 하나와 악성코드 User-Agent 두 개가 있습니다. 목적지별로 User-Agent를 비교하는 것은 사용자 웹 서핑과 악성코드를 구분하는 가장 빠른 방법 중 하나입니다.

    비콘 간격 재기¶

    zeek-cut ts uri < http.log | grep "/4/forum.php" | awk '{ if (prev) print $1 - prev; prev = $1 }'
    • -u를 빼면 ts가 초 단위 숫자(epoch)로 나오므로 awk로 뺄셈을 할 수 있습니다.
    • prev는 바로 앞 줄의 시각입니다. 지금 시각에서 앞 시각을 빼면 간격이 나옵니다.
    • 연속된 POST 사이 간격은 매번 약 120초입니다(위 시각 18:42:30 → 18:44:31 → 18:46:31 …에서 계산). 이렇게 일정한 간격은 비콘입니다. 사람은 이렇게 규칙적으로 움직이지 않습니다.

    왜 "Hancitor"인가 (그리고 왜 추정인가)¶

    아래 순서는 2018년 Hancitor의 잘 알려진 패턴입니다.

    1. 매크로가 든 Word 문서
    2. api.ipify.org로 IP 확인
    3. /4/forum.php로 POST
    4. 해킹된 워드프레스 경로에서 번호 붙은 파일들을 GET
    5. /mlu/forum.php, /d2/about.php로 추가 체크인(추가 정보 탈취 악성코드)

    확인된 것: 매크로 문서 → IP 확인 → C2 POST → 추가 다운로드 → 2분 간격 비콘. 추정인 것: 계열 이름. 인터넷이 막혀서 해시를 조회하지 못했습니다. 보고서에는 *"Hancitor"*가 아니라 *"consistent with Hancitor"*로 씁니다.

    7단계 — 감염 PC의 공인 IP (8번)¶

    PC는 사설 주소를 쓰고, 밖으로 나갈 때 게이트웨이의 NAT가 공인 주소로 바꿔 줍니다. LAN 안에서 캡처한 pcap에는 그 공인 주소가 패킷 헤더에 보이지 않습니다. 대신 IP 확인 서비스의 응답에 들어 있습니다. api.ipify.org는 물어본 쪽의 공인 IP를 글자 하나로 돌려줍니다.

    zeek-cut host uri resp_fuids < http.log | grep ipify   # 응답의 파일 ID 찾기
cat extract_files/*FGnsSi1OKpfguaYN9d; echo              # 응답 본문 보기

    31.44.188.95
    • resp_fuids는 응답 본문의 ID입니다. Zeek은 이 본문도 다른 다운로드처럼 파일로 저장합니다.
    • echo는 빠진 줄바꿈만 넣어 줍니다. 없으면 IP 뒤에 프롬프트가 붙습니다.
    tshark -r ../Phase1_PCAP_6.pcap -Y 'http.response and http.response_for.uri contains "ipify"' \
       -T fields -e http.file_data

    명령 하나로 끝나고 파일 ID도 필요 없습니다. ipify 요청에 대한 응답 본문을 바로 출력합니다. tshark 버전에 따라 16진수로 나오면 뒤에 | xxd -r -p를 붙입니다. Wireshark에서는 요청을 우클릭 → Follow → HTTP Stream을 열면 파란 글자(서버 응답)에 IP가 있습니다.

    _ldap._tcp.dc._msdcs.<도메인>은 윈도우가 "이 도메인의 DC가 누구야?"라고 묻는 DNS SRV 질의입니다. 응답이 DC 이름을 다시 확인해 줍니다.

    tshark -r ../Phase1_PCAP_6.pcap -Y "dns.flags.response == 1 && dns.qry.type == 33" \
       -T fields -e dns.qry.name -e dns.srv.target | sort -u

    dns.qry.type == 33은 SRV 레코드이고, dns.srv.target은 SRV가 가리키는 호스트입니다.

    dhcp.log에는 localdomain인데 왜 도메인이 maricheika.net인가?

    zeek-cut domain < dhcp.log의 결과는 localdomain이었습니다. 이것은 DHCP 서버의 기본 접미사입니다(VMware NAT나 가정용 공유기에서 흔함). Active Directory 도메인이 아닙니다. AD 도메인은 Kerberos와 DNS에서 확인한 maricheika.net입니다. 이 결과는 DHCP 서버가 DC와 다른 장비라는 것도 보여 줍니다.

    서브넷 마스크와 게이트웨이¶

    dhcp.log에는 마스크와 게이트웨이 칸이 없습니다. Zeek 스크립트로도 출력할 수 있지만 tshark는 한 줄이면 됩니다. 여기서는 tshark가 더 알맞은 도구입니다.

    tshark -r ../Phase1_PCAP_6.pcap -Y dhcp -T fields \
       -e ip.src -e dhcp.option.subnet_mask -e dhcp.option.router | sort -u

    0.0.0.0
172.16.1.125
172.16.1.254    255.255.255.0    172.16.1.1
    줄 보낸 쪽 이유
    0.0.0.0 아직 IP가 없는 PC(Discover / Request) PC는 알려 줄 마스크·게이트웨이가 없음 → 빈 칸
    172.16.1.125 IP를 받은 뒤 갱신·정보 요청을 보내는 PC 여전히 클라이언트 메시지 → 빈 칸
    172.16.1.254 255.255.255.0 172.16.1.1 DHCP 서버(Offer / ACK) 옵션 1(마스크)과 옵션 3(게이트웨이)은 서버만 알려 줌

    sort -u는 완전히 같은 줄을 하나로 합칩니다. 그래서 많은 DHCP 패킷이 세 줄이 됐습니다. 마스크 255.255.255.0 = /24이고 PC IP가 172.16.1.125이므로, LAN은 172.16.1.0/24, 게이트웨이는 172.16.1.1, DHCP 서버는 172.16.1.254입니다.

    Zeek만으로 게이트웨이 찾기

    MAC 주소로 (0단계의 mac-logging 스크립트가 필요): 인터넷으로 가는 패킷의 목적지 MAC은 게이트웨이입니다.

    zeek-cut id.resp_h resp_l2_addr < conn.log | grep -v "^172\.16\." | awk '{print $2}' | sort | uniq -c
zeek-cut id.resp_h resp_l2_addr < conn.log | grep "^172\.16\." | grep <게이트웨이MAC> | sort -u

    이벤트 스크립트로 (서버 응답의 마스크와 게이트웨이를 출력. 기존 로그를 덮어쓰지 않도록 빈 폴더에서 실행):

    zeek -C -r ../Phase1_PCAP_6.pcap -e 'event dhcp_message(c: connection, is_orig: bool, msg: DHCP::Msg, options: DHCP::Options) { if (!is_orig) print c$id$resp_h, options?$subnet_mask ? fmt("%s", options$subnet_mask) : "-", options?$routers ? fmt("%s", options$routers) : "-"; }'

    교훈¶

    • 내부 호스트가 하나면 트리아지가 빠릅니다. 그래도 IP, MAC, 호스트 이름은 두 곳(DHCP + Kerberos/conn)에서 확인합니다.
    • **"문서 뒤에 EXE가 없다"**가 "감염이 없다"는 뜻은 아닙니다. 악성코드가 문서 안에 있을 수 있으니, 이어지는 통신을 봅니다.
    • User-Agent를 비교합니다. 사용자의 진짜 브라우저와 다른 문자열, 또는 말이 안 되는 문자열(2018년의 IE 7)은 악성코드를 가리킵니다.
    • 질문마다 맞는 도구를 씁니다. 전체 그림, 파일, HTTP는 Zeek이 좋고, DHCP 옵션이나 응답 본문 하나를 읽을 때는 tshark가 더 쉽습니다.
    • 오타 확인. zeek-cut 칸이 비어 있으면 대부분 필드 이름을 잘못 쓴 것입니다.
    • 확인된 것과 추정을 구분합니다. 해시를 조회할 수 없을 때의 악성코드 계열 이름은 특히 그렇습니다.
