    0단계 — Arkime가 데이터를 보여주는 방식¶

    세션이란¶

    Arkime는 패킷을 한 개씩 보여주지 않고 세션(session) 단위로 묶어서 보여줍니다. 세션은 "A가 B와 나눈 대화 하나"​라고 생각하면 됩니다. 예를 들어 10.3.11.194:51234 → 8.8.8.8:53이 세션 하나입니다.

    세션마다 이런 정보가 붙어 있습니다.

    • 시작 시간(Start Time)과 끝 시간(Stop Time)
    • 패킷 수, 바이트 수
    • 프로토콜(tcp, udp, http, tls, dns …)
    • 분석된 경우 HTTP라면 호스트·URI·User-Agent, TLS라면 인증서, DNS라면 질의한 이름

    쓰게 될 화면¶

    탭 용도
    Sessions 검색 결과 세션 목록. 줄 왼쪽의 +를 누르면 세션 상세와 패킷 내용이 열림
    SPI View "각 필드에 어떤 값이 몇 번 나왔는지" 세어서 보여줌. Splunk의 stats count by 필드와 같은 역할

    Files Arkime가 읽어 들인 PCAP 파일 목록

    Sessions 화면 맨 위에는 검색창, 그 아래에 시간 범위(Start / End), Bounding, 그리고 시간대별 막대그래프가 있습니다.

    함정 1 — 시간 범위¶

    기본값이 Last hour(최근 1시간)

    시간 범위 드롭다운의 기본값은 보통 Last hour입니다. PCAP이 며칠 전 것이면 화면에 아무것도 안 나옵니다. "데이터가 없네?" 하고 당황하는 경우가 대부분 이것 때문입니다.

    • 조사할 기간을 알면 Start / End에 날짜를 직접 넣습니다.
    • 모르면 일단 All로 바꿔서 데이터가 언제부터 언제까지 있는지 확인합니다.
    • 검색창은 비워 두고 Search를 누릅니다.

    그러면 위쪽에 시간대별 막대그래프가 나옵니다. 여기서 볼 것은 두 가지입니다.

    • 데이터가 처음 시작하는 시점과 끝나는 시점
    • 갑자기 막대가 솟는 구간 — 트래픽이 몰린 때, 나중에 다시 볼 후보

    그래프 위의 Session / Packets / Bytes 버튼으로 기준을 바꿀 수 있습니다. Bytes로 바꿨을 때 솟는 구간은 큰 파일 전송이 있었다는 뜻일 수 있어서, 나중에 유출(exfil)을 찾을 때 단서가 됩니다.

    함정 2 — 시간대¶

    브라우저 시간대로 표시됨

    Arkime는 기본으로 브라우저(내 PC)의 현지 시간으로 표시합니다. 그런데 보고서는 보통 UTC로 씁니다. 예를 들어 내 PC가 UTC+10:30이면, 이걸 놓치면 모든 시간이 10시간 30분씩 어긋납니다.

    오른쪽 위 사용자 메뉴 → Settings → General → Timezone Format → UTC. 바꾸고 나면 그래프 축의 시간 뒤에 UTC가 붙습니다(예: 2020/03/11 21:25:00 UTC). 이걸로 설정이 맞는지 확인할 수 있습니다.

    1단계 — 데이터 시작·끝 시간과 세션 수¶

    목적: 분석할 데이터가 언제부터 언제까지인지, 얼마나 많은지 파악합니다. 보고서의 모든 시간은 이 범위 안에 있어야 합니다.

    질문: 세션 단위라고 했는데, 데이터의 시작 시간과 끝 시간은 어떻게 보나요?

    세션마다 Start Time(첫 패킷 시간)과 Stop Time(마지막 패킷 시간)이 있습니다. 그래서 데이터 전체의 시작과 끝은 이렇게 정합니다.

    • 데이터 시작 = 모든 세션 중 가장 빠른 Start Time
    • 데이터 끝 = 모든 세션 중 가장 늦은 Stop Time

    방법 1: 세션 목록 정렬 (가장 정확)

    1. Sessions 탭, 시간 범위 All, 검색창 비우고 Search
    2. 목록 위의 Start Time 열 제목을 클릭합니다. 한 번 누르면 오름차순(오래된 것부터), 다시 누르면 내림차순이에요. 제목 옆 작은 화살표로 방향을 확인합니다.
    3. 오름차순일 때 첫 줄의 Start Time = 데이터 시작
    4. 이번에는 Stop Time을 클릭해 내림차순(최신부터)으로 → 첫 줄의 Stop Time = 데이터 끝

    끝 시간을 Start Time 내림차순으로 보지 않는 이유: 일찍 시작해서 오래 이어진 세션(긴 다운로드나 C2 연결)은 Start Time이 이르더라도 Stop Time이 가장 늦을 수 있습니다. 그래서 끝은 Stop Time으로 봅니다.

    방법 2: 타임라인 그래프 (대략)

    시간 범위를 All로 두면 막대그래프의 가장 왼쪽 막대와 가장 오른쪽 막대가 데이터가 있는 구간입니다. 마우스를 막대 위에 올리면 그 시간대가 나옵니다. 빠르게 감 잡기에는 좋지만 초 단위까지 정확하지는 않으니, 보고서에는 방법 1의 값을 씁니다.

    방법 3: Files 탭 (참고용)

    상단 메뉴 Files 탭의 First Date 열이 각 PCAP 파일의 첫 패킷 시간입니다. 파일이 여러 개면 어떤 파일이 어느 시점부터인지 볼 수 있습니다. 끝 시간은 나오지 않습니다.

    전체 세션 수는 세션 목록 위에 이렇게 나옵니다.

    Showing 1 - 50 of 1,131 entries

    실제 결과:

    Start  2020/03/11 21:22:35 UTC
End    2020/03/11 22:06:41 UTC
Duration 00:44:06   (shown at the right of the time bar)
Sessions 1,131

    시간 막대 오른쪽의 00:44:06이 데이터 길이입니다. 시간 막대의 Bounding: First Packet은 "세션의 첫 패킷 시간이 범위 안에 있는 세션을 보여준다"는 뜻입니다.

    2단계 — 전체 그림: 프로토콜과 내부 PC¶

    목적: 이 네트워크에서 주로 무슨 통신이 오가는지, 누가 내부이고 누가 외부인지 정합니다. 이걸 기준선(baseline)​이라고 합니다. 나중에 "평소와 다른 것"을 찾을 때 비교 대상이 됩니다.

    쿼리: 검색창을 비우고 Search → SPI View 탭 → General 섹션.

    실제 결과:

           http (44)  dcerpc (41)  smb (30)  llmnr (29)  ssdp (16)  ntp (9)  mdns (8)  quic (6)  igmp (1)

    프로토콜 읽기¶

    프로토콜 뜻 판단
    ldap (79), krb5 (78), dcerpc (41), smb (30), dns (325) 윈도우 PC가 도메인에 로그인하고 정책을 받을 때 나오는 통신 Active Directory 환경. 정상. 단, 나중에 워크스테이션끼리 SMB/DCERPC가 오가면 측면 이동(lateral movement)을 의심

    여기서 예상 밖의 것이 있는지 메모합니다. 예를 들어 워크스테이션 망인데 ssh, irc, rdp가 보이면 기록해 둡니다. 이번 데이터에는 없었습니다.

    내부와 외부 정하기¶

    보고서에는 INTERNAL IP와 EXTERNAL IP를 나눠 적어야 하므로, 이건 분석 처음에 꼭 정합니다. 사설 대역이 내부, 나머지가 외부입니다.

    사설 대역 범위 CIDR 표기
    10.x.x.x 10.0.0.0 – 10.255.255.255 10.0.0.0/8
    172.16–31.x.x 172.16.0.0 – 172.31.255.255 172.16.0.0/12
    192.168.x.x 192.168.0.0 – 192.168.255.255 192.168.0.0/16

    내부 PC가 시작한 세션만 보려면:

    ip.src == 10.0.0.0/8
    조각 뜻
    ip.src 출발지 IP 필드. (ip만 쓰면 출발지·목적지 둘 다, ip.dst는 목적지만)
    == "같다"는 비교 연산자
    10.0.0.0/8 CIDR 표기. 10.0.0.0 ~ 10.255.255.255 전체. Arkime는 IP 필드에 CIDR을 그대로 받아 줍니다

    결과는 세션 목록이고, 각 줄은 Start Time | Stop Time | Src IP / Port | Dst IP / Port | Packets | Databytes / Bytes | Info 형식입니다.

    결과 읽기:

    • 내부망은 10.3.11.0/24. 세션을 시작한 쪽은 거의 다 10.3.11.x입니다.
    • 10.3.11.119, .194, .218이 대부분의 트래픽을 만듭니다 → 사용자가 쓰는 워크스테이션일 가능성이 높습니다.
    • 10.3.11.3은 출발지로 3번뿐. 서버는 보통 요청을 받는 쪽이라 Src IP로는 적게 나옵니다 → 서버, 아마 도메인 컨트롤러(DC) 로 추측. 3단계에서 확인합니다.

    • 52.242.211.89 (1): 외부 IP가 출발지로 한 번 나옵니다. 보통은 내부가 외부로 접속하니 눈에 띕니다. 원인은 대부분 둘 중 하나입니다.

      • 캡처가 시작되기 전부터 이미 연결되어 있던 세션이라 Arkime가 처음 본 패킷이 서버 쪽 응답이었음 (흔함, 대개 무해)
      • 실제로 외부에서 안으로 들어온 연결 (주의 필요)

      5단계에서 확인합니다.

    3단계 — DC 확인¶

    목적: 10.3.11.3이 정말 도메인 컨트롤러인지 확인합니다.

    쿼리:

    ip.dst == 10.3.11.3
    조각 뜻
    ip.dst 목적지 IP 필드
    == 10.3.11.3 "10.3.11.3으로 들어간 세션만 보여줘"

    실제 결과 (SPI View → General):

    Dst IP     10.3.11.3 (571)
Protocols  udp (371)  dns (325)  tcp (200)  ldap (79)  krb5 (78)  dcerpc (41)  smb (24)  ntp (9)
Src IP     10.3.11.119 (251)  10.3.11.194 (170)  10.3.11.218 (150)

    • 들어오는 571개가 dns, ldap, krb5, dcerpc, smb, ntp뿐입니다. DNS(이름 조회) + Kerberos(로그인) + LDAP(디렉터리) + RPC + SMB(정책 파일) + NTP(시간 동기화)가 한 서버로 모이면 전형적인 DC 겸 DNS 서버입니다.
    • 전체 krb5 78개가 전부 이 서버로 갑니다.

    4단계 — Kerberos로 호스트이름과 사용자 찾기¶

    목적: 보고서에는 IP + 호스트이름을 같이 적어야 합니다. Kerberos 통신에는 컴퓨터 계정 이름과 사용자 계정 이름이 모두 들어 있습니다.

    쿼리:

    ip.src == 10.3.11.0/24 && protocols == krb5
    조각 뜻
    ip.src == 10.3.11.0/24 출발지가 내부망 PC 아무거나
    && AND(그리고). 앞 조건과 뒤 조건을 둘 다 만족해야 함
    protocols == krb5 프로토콜이 Kerberos인 세션

    검색한 다음 SPI View에서 아래쪽의 krb5 섹션을 찾아 펼칩니다.

    질문: krb5 섹션에 정보가 cname, cname Cnt, Realm 같은 이름밖에 안 나와요. 어떻게 해야 하나요?

    SPI View는 속도 때문에 필드 이름만 먼저 보여주고, 값은 사용자가 요청할 때 불러옵니다. 지금 보이는 cname, Realm, sname 같은 것들은 값이 아니라 필드 버튼이에요. 1단계에서 Dst IP, Protocols, Src IP 값이 바로 보였던 건 이 세 개가 기본으로 켜져 있기 때문입니다.

    값을 보려면 둘 중 하나를 합니다.

    • cname 버튼(이름 부분)을 클릭 → cname 값만 불러옵니다.
    • 오른쪽의 Load All 클릭 → krb5 섹션의 필드를 전부 불러옵니다. 처음엔 이게 편합니다.

    필드 뜻

    Realm 도메인 이름
    sname 접속하려는 서비스. krbtgt/도메인 = 로그인 티켓, cifs/서버 = 파일 공유, ldap/서버 = 디렉터리 조회, host/PC = 그 PC 자체
    cname Cnt 등 Cnt "세션 하나에 값이 몇 개 있었나"라는 숫자. 지금은 무시

    5단계 — 외부 "출발지" 52.242.211.89 확인¶

    목적: 외부 IP가 세션을 시작한 것처럼 보이는 이유를 확인합니다. 진짜 인바운드 공격인지, 단순한 착시인지.

    쿼리:

    ip.src == 52.242.211.89

    실제 결과: 세션 1개. 줄 왼쪽 +를 눌러 상세를 엽니다.

    Time        2020/03/11 21:32:00 UTC - 21:32:00 UTC
Src IP/Port 52.242.211.89 : 443 { ARIN }
Dst IP/Port 10.3.11.194 : 50355
Src         Packets 1  Bytes 229  Databytes 0
Dst         Packets 1  Bytes 54   Databytes 0
Src Ethernet  20:e5:2a:b6:93:f1  OUI Netgear
Dst Ethernet  b8:ca:3a:ec:3b:8f  OUI Dell Inc.
TCP Flags   SYN 0  SYN-ACK 0  ACK 0  PSH 1  RST 1  FIN 0  URG 0

    결과 읽기 (세션 상세 읽는 연습):

    ① TCP Flags: SYN 0 SYN-ACK 0 PSH 1 RST 1 정상적인 TCP 연결은 항상 SYN → SYN-ACK → ACK(3-way handshake)로 시작합니다.

    client → server  SYN        "연결해도 될까?"
server → client  SYN-ACK    "좋아"
client → server  ACK        "그럼 시작할게"

    여기는 SYN이 0입니다. 즉 연결이 시작되는 장면을 Arkime가 보지 못했다는 뜻입니다. 이 연결은 원래 노트북이 먼저 만든 건데, 그 시작 부분이 캡처에 없습니다.

    ② 포트: 52.242.211.89:443 → 10.3.11.194:50355 443은 HTTPS 서버 포트이고, 50355는 클라이언트가 잠깐 쓰는 임시 포트(ephemeral port, 보통 49152 이상)입니다. 실제로는 노트북(클라이언트)이 서버에 접속한 연결이고, Arkime가 처음 본 패킷이 서버가 보낸 것이라서 서버를 Src로 표시했을 뿐입니다.

    ③ 패킷 흐름: 서버 PSH 1개 → 노트북 RST 1개 PSH는 "데이터를 바로 넘겨라", RST는 "이 연결 끊어(모르는 연결이야)"입니다. 서버가 데이터를 보냈는데 노트북은 이미 그 연결을 닫은 상태라서 RST로 답한 겁니다. 흔히 보이는 정리 동작입니다.

    ④ 페이로드: 깨진 글자 TLS로 암호화된 데이터라서 읽을 수 없는 게 정상입니다.

    ⑤ MAC 주소 팁 Src MAC이 Netgear(공유기/게이트웨이), Dst MAC이 Dell(노트북)입니다. 외부 IP에서 오는 패킷은 항상 게이트웨이를 거쳐서 들어오기 때문에 외부 IP의 MAC은 게이트웨이 MAC으로 보입니다. 외부 IP 옆에 내부 장비 MAC이 보인다면 오히려 이상한 것입니다.

    결론: { ARIN }은 미국 등록 대역(Microsoft Azure 쪽)입니다. 외부에서 들어온 공격이 아니라 끝나 가던 HTTPS 연결의 마지막 조각입니다. 무해합니다. 이렇게 의심했다가 배제한 것도 보고서에 남기는 게 중요합니다. 다른 분석가가 같은 걸 다시 확인하지 않아도 되니까요.

    6단계 — 평문 HTTP 44개 훑기¶

    목적: 본격적으로 수상한 것을 찾습니다. HTTP는 암호화가 안 되어 있어서 어디에 접속해서 무엇을 받았는지가 다 보입니다.

    쿼리:

    ip.src == 10.3.11.0/24 && protocols == http
    조각 뜻
    ip.src == 10.3.11.0/24 내부 PC가 시작한 연결만
    && 그리고
    protocols == http 평문 HTTP만

    검색 → SPI View → http 섹션 → Load All.

    중요한 필드¶

    필드 뜻 왜 보나
    Hostname (host.http) 접속한 도메인 어디에 갔나
    URI 요청한 경로와 파일 무엇을 받았나 (예: /files/update.exe)
    Request Method GET(받기), POST(보내기) 외부로 가는 POST가 많으면 유출이나 C2 의심
    Status Code 200(성공), 404(없음) … 실제로 받았는지
    Useragent 요청을 보낸 프로그램 브라우저가 아닌 이상한 값이면 의심
    Body Magic 받은 파일의 실제 종류 application/x-dosexec = 윈도우 실행 파일(.exe/.dll). 파일 이름을 .jpg로 위장해도 이 값은 속일 수 없음
    Body MD5 받은 본문의 MD5 해시 나중에 IOC로 사용

    먼저 정상 잡음 걸러내기¶

    윈도우는 평소에도 HTTP로 이런 곳에 자주 접속합니다. 이런 건 넘어가도 됩니다.

    www.msftconnecttest.com   /connecttest.txt    (internet connectivity check)

    • wsimg.com, nebula.wsimg.com, img.secureserver.net — GoDaddy 웹사이트 이미지와 스크립트

    의심 후보 4가지¶

    ① bolton-tech.com/YAS20.exe — 실행 파일 다운로드

    URI 끝이 .exe입니다. 그리고 Body Magic에 application/x-dosexec(2)​가 있고, 서버 응답 content-type에도 application/x-msdownload(1)가 있습니다. 실제로 윈도우 실행 파일이 HTTP로 내려왔다는 증거입니다. 평문 HTTP로 이름 모를 사이트에서 exe를 받는 건 매우 수상합니다.

    ② 64.44.133.131/images/cursor.png(2), /images/imgpaper.png(1) — 도메인 없이 IP로 접속

    도메인 이름 없이 IP 주소로 직접 HTTP 접속을 했습니다("naked IP"). 정상 웹사이트는 거의 항상 도메인을 씁니다. 그리고 이름은 .png인데, x-dosexec가 2개였죠. 하나가 YAS20.exe라면 나머지 하나는 이 "png" 중 하나일 수 있습니다. 즉 그림인 척하는 실행 파일일 가능성이 있습니다. 9단계에서 확인합니다.

    ③ 203.176.135.102:8082/yas20/LAPTOP-7XMV2SN_W10018363.CF3A…/81/ — 가장 결정적

    이 URI를 조각내서 보면:

    203.176.135.102:8082   → raw IP + non-standard port 8082
/yas20/                → campaign / group tag (same name as YAS20.exe!)
LAPTOP-7XMV2SN         → hostname of 10.3.11.194 (found in step 4)
W10018363              → Windows 10 build 18363
CF3A0EAB425F...CAED6   → unique ID per infected PC (bot ID)
/81/ , /90/            → command / data-type number

    감염된 PC가 자기 이름을 URL에 넣어서 공격자 서버에 보고하는 모양입니다. 그리고 숫자를 맞춰 보면 /81/ 4개 + /90/ 1개 = 5개인데, POST가 정확히 5개이고 multipart/form-data(파일·데이터 업로드 형식)도 5개입니다. 경계값(boundary)도 ---------ATBOXLGQOOBDZTLA처럼 무작위 대문자입니다. 그러니까 이 5번의 POST는 PC에서 공격자 서버로 데이터를 올려 보낸 것, 즉 C2 통신 또는 정보 유출 후보입니다. (이 짝짓기는 아직 추론입니다. 10단계에서 확인합니다.)

    yas20 태그와 /호스트명_W10빌드.봇ID/명령번호/ 형식은 Trickbot 악성코드의 C2 패턴과 매우 비슷합니다. 다만 아직은 가설입니다.

    ④ checkip.amazonaws.com — 내 공인 IP 확인

    사람은 이 주소를 거의 직접 열지 않습니다. 악성코드가 감염 직후 "내가 어느 나라, 어느 회사 네트워크에 있지?"​를 확인할 때 자주 씁니다.

    YAS20.exe 세션 상세 읽기¶

    세션을 펼치면 아래쪽에 Source(PC가 보낸 것)와 Destination(서버가 보낸 것)이 나옵니다.

    1. 브라우저가 아니라 "스크립트"가 받았습니다.

    GET /YAS20.exe HTTP/1.1
Connection: Keep-Alive
Accept: */*
User-Agent: Mozilla/4.0 (compatible; Win32; WinHttp.WinHttpRequest.5)
Host: bolton-tech.com

    요청 헤더가 딱 4줄뿐입니다. 사람이 Edge에서 링크를 눌렀다면 Referer(어느 페이지에서 왔는지), Accept-Language 같은 헤더가 더 붙고, User-Agent도 ...Edg/80...처럼 나왔을 겁니다. WinHttp.WinHttpRequest.5는 VBScript, JScript, PowerShell, 오피스 매크로가 파일을 받을 때 쓰는 윈도우 기능입니다. 그래서 사용자가 악성 문서나 스크립트를 열었고, 그게 exe를 몰래 받아 온 것으로 추정할 수 있습니다. 이게 초기 침투(Initial Access) 단서입니다.

    2. 서버 응답이 실행 파일입니다.

    HTTP/1.1 200 OK
Date: Wed, 11 Mar 2020 21:24:36 GMT
Server: Apache
Last-Modified: Tue, 10 Mar 2020 11:32:37 GMT
Content-Length: 466944
host-header: c2hhcmVkLmJsdWVob3N0LmNvbQ==
Content-Type: application/x-msdownload

    Content-Type: application/x-msdownload이고 Content-Length: 466944(약 456KB)입니다. Last-Modified: 10 Mar 2020이니까 감염 하루 전에 서버에 올려 둔 파일입니다.

    3. CyberChef 연습: 이상한 헤더 해독

    host-header: c2hhcmVkLmJsdWVob3N0LmNvbQ==

    끝이 ==로 끝나는 건 Base64의 전형적인 모양입니다. CyberChef의 From Base64에 넣으면:

    shared.bluehost.com

    공유 웹호스팅 서비스라는 뜻입니다. bolton-tech.com은 공격자가 만든 사이트라기보다 해킹당해서 악성 파일 보관소로 쓰인 일반 사이트일 가능성이 높습니다.

    8단계 — 폐쇄망에서 판단하는 법과 CyberChef¶

    인터넷이 없을 때¶

    실제 작전 환경은 대부분 폐쇄망입니다.

    못 하는 것 대신 하는 것
    VirusTotal 해시 조회, 도메인·IP 평판 조회, 검색 트래픽에 보이는 행동만으로 악성 여부를 판단

    행동 근거의 예(이번 사례에서 쓴 것들):

    • Body Magic이 x-dosexec이다 → 실행 파일을 받았다
    • 도메인 없이 IP로, 비표준 포트(8082)로 접속했다
    • URI에 PC 이름과 고유 ID가 들어 있다
    • 외부로 POST(업로드)를 했다
    • 브라우저가 아닌 이상한 User-Agent를 썼다
    • 일정한 패턴으로 반복 접속하거나 연결을 오래 붙잡는다(비콘)

    하나만으로는 약하지만, 여러 개가 같은 PC, 같은 시간대에 모이면 강한 근거가 됩니다.

    • Body MD5는 그래도 기록합니다. 지금 조회할 수는 없지만, 보고서의 IOC로 남기면 나중에 내부 위협 정보 DB나 악성코드 분석팀이 씁니다. *"Further malware analysis is required"*가 바로 이런 경우에 쓰는 문장입니다.
    • 해당 세션은 Download PCAP으로 저장해서 증거(EVIDENCE LOCATIONS)로 남깁니다.
    • 악성코드 이름은 분석가 지식으로 판단한 것이라 "Trickbot-like pattern (unconfirmed)", "consistent with Trickbot"​처럼 확정이 아닌 표현으로 씁니다.

    파일 정체 확인 Detect File Type, MD5 / SHA256 실행 파일이면 앞부분이 MZ

    보고서용 IOC 무력화 Defang URL, Defang IP Addresses zoomer.com → zoomer[.]com

    10단계 — POST 확인과 업로드 방향¶

    질문: 21:36:59 세션이 POST라는 건 어떻게 알았나요?

    솔직히, 그때는 세션을 직접 열어 보고 안 게 아니라 숫자를 맞춰서 추론한 것이었습니다. SPI View의 http 섹션에서 숫자 세 개가 맞아떨어졌습니다.

    Request Method:            GET (39)   POST (5)
http.request.content-type: multipart/form-data ... 5 values (1 each)
URI:  .../81/ (4)   .../90 (1)    → total 5

    전체 HTTP 44개 중 POST가 딱 5개, 203.176.135.102로 간 URI도 4 + 1 = 5개, 업로드 형식도 5개. 다른 사이트들은 전부 그림·폰트·스크립트를 받는(GET) 요청이라 "이 5개가 POST다"라고 추정했습니다.

    하지만 이건 추론이지 증거가 아닙니다. SPI View는 숫자만 셀 뿐 어느 세션이 POST인지 짝을 지어 주지 않습니다. 세션 목록의 Info 칸에도 URI만 나오고 Method는 안 나옵니다. 보고서에 쓰기 전에는 반드시 직접 확인합니다.

    http.method == POST
    조각 뜻
    http.method HTTP 요청 방식 필드
    == POST POST인 것만

    11단계 — 업로드된 본문을 보는 법¶

    /90 세션의 Source 아래에는 본문 대신 파란 글씨로 90만 보입니다.

    질문: natural을 ascii로 바꿔도 파란 글씨 90만 보입니다.

    natural / ascii / utf8 / hex는 글자를 어떻게 표시할지만 바꾸는 옵션이라서 그렇습니다. 본문을 파일 링크로 바꿔서 보여주는 건 별도 설정이 하고 있습니다.

    방법 1: Packet Options에서 "Images & Files" 끄기

    natural 오른쪽의 Packet Options ▾ → Hide Images & Files(이미지·파일 숨기기). 버전에 따라 Show Images & Files에 체크가 되어 있는 형태일 수 있는데, 그러면 체크를 해제합니다. 이 옵션이 켜져 있으면 Arkime는 HTTP 본문을 파일로 뽑아서 링크로만 보여줍니다. 끄면 본문이 원래 바이트대로 펼쳐지고, 이 상태에서 ascii나 hex로 바꾸면 multipart 내용이 보입니다.

    방법 2: Source Raw로 받아서 CyberChef로 보기

    세션을 펼쳤을 때 맨 위 버튼 중 Source Raw를 누르면 PC가 서버로 보낸 바이트 전체(헤더 + 업로드 본문)가 파일 하나로 내려받아집니다. (Destination Raw는 서버가 PC로 보낸 쪽입니다.) CyberChef 오른쪽 위 Input 창의 폴더 아이콘(Open file as input)​으로 열고, 깨져 보이면 Recipe에 Strings를 추가해 읽을 수 있는 글자만 뽑습니다.

    방법 3: 파란 90 링크를 직접 클릭해도 본문만 파일로 받을 수 있습니다. 같은 방법으로 CyberChef에서 엽니다.

    질문: Issuer CN, ON과 Subject CN, ON은 무엇인가요?

    HTTPS 인증서는 "이 서버는 진짜 ○○가 맞다"는 신분증입니다. 신분증에 "누구 것인지"와 "누가 발급했는지"가 적혀 있듯이, 인증서에도 두 부분이 있습니다.

    • Subject(주인): 이 인증서가 누구 것인지. 예: www.bing.com
    • Issuer(발급자): 이 인증서를 누가 확인하고 서명해 줬는지. 예: Microsoft IT TLS CA 5

    각각 안에 이름 항목이 여러 개 있습니다.

    항목 뜻 예
    CN (Common Name) 대표 이름. 웹사이트라면 보통 도메인 www.bing.com
    ON (Organization Name) 회사·기관 이름. 표준 이름은 O이고 Arkime가 ON으로 표시 Microsoft Corporation
    OU (Organizational Unit) 회사 안의 부서 이름. Arkime 화면의 Org Unit Microsoft IT 
    Subject CN  = name of the certificate owner (domain)   e.g. www.bing.com
Subject ON  = owner's organisation                     e.g. Microsoft Corporation
Issuer CN   = name of the issuer                       e.g. Microsoft IT TLS CA 5
Issuer ON   = issuer's organisation                    e.g. Microsoft Corporation

    인증서는 사슬(chain)로 이어져 있습니다. 발급자도 또 다른 발급자에게 인증서를 받습니다.

    [cert 3] Subject: Baltimore CyberTrust Root   Issuer: Baltimore CyberTrust Root  ← root, signs itself
     ↓ signs
[cert 2] Subject: Microsoft IT TLS CA 5       Issuer: Baltimore CyberTrust Root  ← intermediate issuer
     ↓ signs
[cert 1] Subject: www.bing.com                Issuer: Microsoft IT TLS CA 5      ← the actual website

    서버는 접속할 때 보통 인증서 1과 2를 같이 보냅니다. 루트(3)는 윈도우에 이미 들어 있어서 안 보냅니다. 그래서 위 결과에서 microsoft it tls ca 5가 Issuer CN(49)에도, Subject CN(49)에도 나옵니다. 인증서 1에서는 발급자로, 인증서 2에서는 주인으로 등장한 것입니다. 반면 baltimore cybertrust root는 Issuer에만 있고 Subject에는 없습니다. 루트 인증서 자체는 전송되지 않았기 때문입니다.

    결과 읽기 — 대부분은 정상, 어울리지 않는 것이 섞여 있음:

    Microsoft, Baltimore CyberTrust, DigiCert, Let's Encrypt가 많은 건 윈도우가 Microsoft 서버와 늘 통신하기 때문입니다. 그 사이에:

    질문: 발급자와 주인이 똑같은지 어떻게 판별했나요?

    솔직히 처음에는 SPI View의 숫자를 보고 추론했습니다.

    Issuer CN:  example.com (4)              Subject CN:  example.com (4)
Issuer ON:  Global Security (4)          Subject ON:  Global Security (4)
Issuer OU:  IT Department (4)            Subject OU:  IT Department (4)
Issuer ON:  Internet Widgits Pty Ltd (2) Subject ON:  Internet Widgits Pty Ltd (2)

    같은 이름이 Issuer와 Subject 양쪽에 같은 개수로 나와서 "스스로 서명한 인증서"로 본 것입니다.

    그런데 이건 증거가 아닙니다. 위의 사슬을 떠올려 보세요. let's encrypt authority x3도 Issuer(2)와 Subject(2)에 똑같이 나오는데, 이건 자체 서명이 아니라 사슬 때문입니다. 인증서 A의 발급자이면서 인증서 B의 주인인 것이죠. 그리고 SPI View는 전체 개수만 셀 뿐, 어떤 값들이 같은 인증서 안에 있었는지는 알려 주지 않습니다.

    진짜 자체 서명 인증서라면 같은 인증서 하나 안에서 Issuer와 Subject가 같아야 합니다.

    self-signed:   [one cert]  Subject: example.com  /  Issuer: example.com   ← equal inside one cert
normal chain:  [cert A]    Subject: site         /  Issuer: CA X
               [cert B]    Subject: CA X         /  Issuer: root          ← equal across two certs

    직접 확인하는 방법: 세션을 펼치면 TLS 부분에 Certificate가 있고, 서버가 보낸 인증서가 한 장씩 따로 나옵니다. 확인할 것은 두 가지입니다.

    1. 인증서가 몇 장인지: 정상 사이트는 보통 2장 이상(사이트 + 중간 발급자). 자체 서명은 대개 딱 1장
    2. 그 한 장 안에서 Issuer와 Subject가 같은지

    16단계에서 이렇게 확인해서 확정했습니다. 그리고 Arkime가 인증서를 분석해서 태그를 자동으로 붙여 줍니다. 자체 서명이면 cert:self-signed, 정식 발급 기관이 서명했으면 cert:certificate-authority. 앞으로는 이 태그로 바로 검색할 수 있습니다.

    tags == "cert:self-signed"

    대상별 역할 판단¶

    1. 190.214.13.2:449 = 주 C2 채널

    • 449는 표준 서비스가 거의 쓰지 않는 포트입니다.

    비콘의 두 종류

    샘플 보고서에는 "2:45 간격 비콘"처럼 일정한 간격을 적는 예가 있지만, 여기는 간격이 일정하지 않고 대신 연결을 길게 유지합니다. 비콘에는 두 종류가 있습니다.

    • 길게 붙잡기: 연결을 열어 두고 명령을 기다림, 시작 시간은 불규칙, 바이트는 작음

    그런데 21:36:19~21:37:21에만 20개 넘게 몰려 있습니다(137번 22개, 138번 21개). 12단계에서 /90 POST 안에 이런 내용이 있었습니다.

    /c net view /all
System error 6118 has occurred.

    net view는 NetBIOS 브로드캐스트로 "주변에 어떤 PC가 있어?"라고 묻는 명령입니다. 악성코드가 net view를 실행한 흔적이 네트워크에도 그대로 찍힌 것입니다. 응답을 못 받아서 6118 오류가 났고요. 호스트에서 본 증거(업로드 내용)와 네트워크 증거가 같은 시간에 맞아떨어지는 좋은 예입니다.

    TCP 445 (SMB): 측면 이동 시도¶

    21:36:47, 같은 1초 안에 445 포트로 여러 PC를 두드렸습니다.

    21:36:47  → 10.3.11.119:445   smb x2 + no data x1
21:36:47  → 10.3.11.218:445   smb x2 + no data x1
21:36:47  → 10.3.11.1:445     (gateway) 2 sessions, 0 bytes
21:36:47  → 10.3.11.254:445   1 packet, 0 bytes
21:36:47  → 10.3.11.131:445   1 packet, 0 bytes
21:37:17  → 10.3.11.119:445, 10.3.11.218:445   one more smb each

    왜 수상한가:

    • 445는 SMB(파일 공유) 포트입니다. 워크스테이션끼리는 보통 파일 공유를 하지 않습니다. 파일 서버나 DC로 가는 게 정상입니다.
    • 1초 안에 5개 주소를 연달아 찔렀습니다. 사람이 하는 행동이 아니라 스캔입니다. Src Port도 49818 → 49919 → 49921 → … 처럼 줄줄이 이어져 있습니다.
    • .254와 .131은 1패킷(SYN)만 보내고 답이 없습니다. 앞에서 본 적 없는 주소라서 아마 존재하지 않는 PC일 겁니다. 악성코드가 "있는지 없는지 모르니 일단 찔러 보는" 것입니다.
    • 실제로 대답한 건 다른 두 노트북(.119, .218)​입니다. 감염 PC가 같은 망의 다른 PC로 퍼질 수 있는지 시험한 것입니다.

    그런데 성공했을까? SMB 세션들이 5패킷, 데이터 51바이트밖에 안 됩니다. 대략 이런 흐름입니다.

    SYN → SYN-ACK → ACK → (SMB negotiate request, 51 bytes) → connection closed

    파일을 복사하거나 로그인한 흔적이라면 수 KB에서 수백 KB가 오갔을 겁니다. 그래서 "시도는 했지만 성공 흔적은 없음"​으로 보입니다. 이것도 추론이라 세션을 열어서 확인합니다.

    SMB 세션 하나 열어 보기¶

    21:37:17의 10.3.11.194:50097 → 10.3.11.119:445 세션. 볼 것은 두 가지입니다.

    • General의 Src / Dst Databytes: 51바이트가 어느 쪽에서 나갔는지, .119가 데이터를 돌려줬는지
    • SMB 섹션(있다면): Share(접근한 공유 폴더), User(로그인 계정), Filename 같은 값이 있는지

    실제 결과:

    Dst           Packets 2  Bytes 120  Databytes 0
Src Ethernet  b8:ca:3a:ec:3b:8f  Dell Inc.
Dst Ethernet  10:98:36:59:9d:cc  Dell Inc.
Src IP/Port   10.3.11.194 : 50097
Dst IP/Port   10.3.11.119 : 445
Payload8      Src 0000002fff534d42 ( /.SMB )
TCP Flags     SYN 1  SYN-ACK 1  ACK 1  PSH 1  RST 1  FIN 0  URG 0

Source (10.3.11.194:50097)
/.SMBr...

    결과 읽기:

    • 감염 PC가 보낸 51바이트는 SMB 접속 요청(Negotiate Protocol Request)​입니다. \xffSMB 뒤의 r(0x72)이 협상 명령이고, 제안한 버전이 NT LM 0.12 하나뿐입니다. 이건 아주 오래된 SMB 버전 1(SMBv1)​의 이름입니다.
    • .119는 데이터를 하나도 돌려주지 않고(Dst Databytes 0) Dst 패킷 2개(SYN-ACK + RST)로 연결을 끊었습니다. 대상 PC에서 SMBv1이 꺼져 있어서 거절한 것입니다(윈도우 10은 기본으로 SMBv1 비활성).
    • SMBv1만 골라서 찔러 보는 건 EternalBlue(MS17-010) 같은 웜 방식 확산 시도에서 흔히 보이는 모습입니다(EternalBlue / SMBv1).
    • 공유 폴더, 계정, 파일 접근 흔적이 전혀 없어서 "시도했지만 실패"로 확정합니다.

    18단계 — 범위 확인 2: 다른 PC도 같은 서버와 통신했나?¶

    목적: 다른 PC도 감염됐는지 확인합니다. 특히 SMB 시도를 받은 .119와 .218이 나중에 악성 IP로 통신했다면 측면 이동이 성공해서 감염된 것입니다.

    쿼리:

    ip.dst == [50.87.248.17, 64.44.133.131, 203.176.135.102, 190.214.13.2, 185.14.31.98, 185.180.198.50, 51.254.164.244, 45.148.120.153, 199.247.13.144, 209.97.130.197] && ip.src != 10.3.11.194
    조각 뜻
    ip.dst == [...] 지금까지 찾은 악성 IP 10개 중 아무거나로 간 연결
    ip.src != 10.3.11.194 그런데 출발지가 감염 PC가 아닌 것

    실제 결과: 0개.

    결과 읽기: 다른 PC는 아무도 악성 IP와 통신하지 않았습니다. 감염 PC는 10.3.11.194 한 대로 확정입니다. .119와 .218은 네트워크 데이터상 감염 흔적이 없습니다. 결과가 1개라도 나왔다면 그 PC도 조사 대상이었을 것입니다.

    • 시간 범위와 시간대부터 맞추기. "Arkime에 아무것도 안 나와요"는 대부분 Last hour 기본값 때문이고, 시간이 10시간씩 어긋나는 건 시간대 때문입니다.

    • TCP 플래그와 바이트 방향을 읽어 "연결해서 주고받음"과 "찔러 봤다가 거절됨"을 구분하세요.
