    Arkime만으로 분석하기 — 스크립트 다운로더에서 비밀번호 탈취, TLS C2, 침해사고 티켓까지¶

    사례 요약

    mondogreek.com 도메인의 윈도우 10 PC 한 대가 브라우저가 아닌 스크립트로 YAS20.exe를 받았습니다. 12분 안에 공인 IP를 확인하고, 449·447 포트로 암호화된 C2를 열고, 모듈을 더 받고, 훔친 브라우저 비밀번호와 정찰 정보를 평문 HTTP POST로 보냈고, 같은 망을 SMB 445로 훑었습니다(거절됨). 패턴은 Trickbot과 일치합니다(추정, 오프라인이라 해시 조회 불가). 전 과정을 Arkime 웹 화면만으로 풀었고, 디코딩에만 CyberChef를 썼으며, 마지막에 침해사고 티켓을 완성합니다.
    증거 PCAP 1개, 2020-03-11 21:22:35 – 22:06:41 UTC (44분 06초), 세션 1,131개
    환경 폐쇄망, 인터넷 없음(VirusTotal, OSINT 불가). Arkime v5.6.4 웹 화면 + CyberChef(오프라인)
    결과물 침해사고 티켓: 인덱스, 설명, 영향받은/외부 장비, 검색 쿼리, 증거 위치, 작업 로그와 짝이 맞는 도구 출력

    0단계 — Arkime가 데이터를 보여주는 방식¶

    Arkime는 패킷을 한 개씩 보여주지 않고 세션 단위로 묶습니다. 세션은 두 끝점 사이의 대화 하나입니다. 예: 10.3.11.194:51234 → 8.8.8.8:53. 세션마다 시작·끝 시간, 패킷 수, 바이트, 프로토콜, 그리고 분석된 경우 HTTP/DNS/TLS 필드가 붙습니다.

    쓰게 될 탭:

    탭 용도
    Sessions 검색 결과 세션 목록. +를 누르면 상세와 패킷이 열림
    SPI View 필드마다 값과 개수 — Splunk의 stats count by field와 비슷
    Connections 누가 누구와 통신하는지 그래프
    Settings 시간대(UTC로 설정)

    함정 1 — 시간 범위

    시간 선택의 기본값은 **Last hour(최근 1시간)**입니다. 오래된 PCAP은 아무것도 안 나옵니다. 첫 검색 전에 All로 바꾸거나 Start/End를 직접 넣으세요.

    함정 2 — 시간대

    Arkime는 기본으로 브라우저(내 PC)의 시간대로 표시합니다. 티켓은 UTC로 씁니다. Settings → General → Timezone Format → UTC로 바꾸면 그래프 축의 시간 뒤에 UTC가 붙습니다.

    데이터 시작·끝 시간과 세션 수¶

    질문: 세션 단위라면 데이터의 시작 시간과 끝 시간은 어떻게 보나요?

    세션마다 Start Time(첫 패킷)과 Stop Time(마지막 패킷)이 있습니다.

    • 데이터 시작 = 모든 세션 중 가장 빠른 Start Time

    • 데이터 끝 = 모든 세션 중 가장 늦은 Stop Time

    • Sessions 탭, 시간 범위 All, 검색창 비우고 Search

    • Start Time 열 제목을 눌러 오름차순 → 첫 줄의 Start Time이 데이터 시작
    • Stop Time 열 제목을 눌러 내림차순 → 첫 줄의 Stop Time이 데이터 끝

    끝 시간은 Start Time 내림차순이 아니라 Stop Time으로 봅니다. 일찍 시작해 오래 이어진 세션(다운로드, C2 연결)이 가장 늦게 끝날 수 있기 때문입니다.

    다른 방법: 타임라인 막대그래프(첫 막대와 마지막 막대, 대략 볼 때), Files 탭(읽어 들인 PCAP의 First Date, 시작만). 전체 개수는 목록 위 Showing 1 - 50 of 1,131 entries에 나옵니다.

    2단계 — Kerberos로 호스트이름과 사용자 찾기¶

    티켓에는 IP + 호스트이름이 필요합니다. Kerberos에는 컴퓨터 계정과 사용자 계정 이름이 모두 들어 있습니다.

    ip.src == 10.3.11.0/24 && protocols == krb5
    부분 뜻
    ip.src == 10.3.11.0/24 출발지가 내부 PC 아무거나(CIDR 사용 가능)
    && 그리고 — 두 조건을 모두 만족
    protocols == krb5 Kerberos 세션만

    질문: krb5 섹션에 cname, Realm, sname 같은 필드 이름만 나오고 값이 안 나와요. 어떻게 하나요?

    SPI View는 속도 때문에 필드 이름을 먼저 보여주고 값은 요청할 때 불러옵니다. cname, Realm, sname은 값이 아니라 필드 버튼입니다.

    • 필드 이름(예: cname)을 누르면 그 필드 값만 불러오고,
    • 섹션 오른쪽 Load All을 누르면 섹션의 모든 필드를 불러옵니다.

    cname Cnt, Realm Cnt처럼 Cnt가 붙은 것은 세션당 값 개수라서 지금은 무시해도 됩니다.

    결과:

    7단계 — 무엇을 올려 보냈는지 읽기¶

    질문: 21:36:59 세션이 POST라는 건 어떻게 알았나요?

    처음에는 본 게 아니라 추론이었습니다. SPI View에 POST (5), multipart/form-data × 5, C2 URI /81/ × 4 + /90 × 1 = 5가 있었고, 나머지 HTTP는 모두 그림·폰트·스크립트를 받는 GET이었습니다.

    SPI View는 값을 셀 뿐 어느 세션에 어떤 값이 있는지는 알려 주지 않고, 세션 목록의 Info 칸에는 URI만 나오고 Method는 안 나옵니다. 그래서 티켓에 쓰기 전에 직접 확인해야 합니다.

    질문: Issuer CN / ON과 Subject CN / ON은 무엇인가요?

    인증서는 서버의 신분증입니다.

    • Subject(주인) = 이 인증서가 누구 것인지(예: www.bing.com)
    • Issuer(발급자) = 누가 확인하고 서명했는지(예: Microsoft IT TLS CA 5)

    각각 안에 CN(Common Name, 대표 이름 — 웹사이트는 보통 도메인), ON(Organization Name, 회사 이름 — 표준 이름은 O이고 Arkime는 ON으로 표시), OU / Org Unit(부서)이 있습니다.

    인증서는 사슬로 이어집니다:

    [cert 3] Subject: Baltimore CyberTrust Root   Issuer: Baltimore CyberTrust Root   ← root, signs itself
     ↓ signs
[cert 2] Subject: Microsoft IT TLS CA 5       Issuer: Baltimore CyberTrust Root   ← intermediate
     ↓ signs
[cert 1] Subject: www.bing.com                Issuer: Microsoft IT TLS CA 5       ← the website

    서버는 보통 1번과 2번을 보내고, 루트는 윈도우에 이미 들어 있습니다. 그래서 microsoft it tls ca 5는 Issuer CN(49)과 Subject CN(49) 양쪽에 나오고, baltimore cybertrust root는 Issuer에만 나옵니다.

    질문: 발급자와 주인이 같다는 건 어떻게 판별했나요?

    처음에는 SPI View 숫자로 봤습니다. example.com이 Issuer CN(4)과 Subject CN(4)에 있었고, "Global Security", "IT Department", "Internet Widgits"도 마찬가지였습니다. 이건 힌트일 뿐 증거가 아닙니다. let's encrypt authority x3도 사슬 때문에 2 + 2로 나옵니다(인증서 A의 발급자이면서 인증서 B의 주인).

    자체 서명은 인증서 한 장 안에서 발급자 = 주인입니다:

    self-signed:  [one cert]  Subject example.com  /  Issuer example.com    ← equal in the same cert
normal chain: [cert A]    Subject site         /  Issuer CA X
              [cert B]    Subject CA X         /  Issuer root           ← equal across two certs

    세션 상세의 Certificate 부분에서 확인합니다. 인증서가 한 장씩 따로 나옵니다. (1) 몇 장인지(자체 서명은 보통 한 장), (2) 그 한 장 안에서 발급자 = 주인인지 봅니다. Arkime는 세션에 태그도 자동으로 붙입니다: cert:self-signed 또는 cert:certificate-authority.

    tags == "cert:self-signed"

    이상한 값이 중요한 이유: example.com은 문서 예시용으로 예약된 도메인이라 실제 서비스가 인증서를 받을 수 없습니다. "Global Security / IT Department"는 그럴듯하지만 의미 없는 이름입니다(이 조합은 Trickbot C2 인증서에서 널리 보고됨). Internet Widgits Pty Ltd는 OpenSSL에서 아무것도 안 바꾸고 엔터만 치면 들어가는 기본값입니다.

    교훈¶

    • 시간 범위와 시간대부터 맞추기 — "Arkime에 아무것도 안 나와요"는 대부분 Last hour 기본값 때문입니다.
    • SPI View는 세기만 하고 짝을 지어 주지 않습니다. 숫자가 맞아떨어지는 것(POST 5 = C2 URI 5)은 추론입니다. 티켓에 쓰기 전에 직접 검색이나 세션 상세로 확인하세요.
    • Issuer와 Subject에 같은 이름이 있다고 자체 서명은 아닙니다 — 사슬도 그렇게 보입니다. 인증서 한 장 안에서 확인하거나 cert:self-signed 태그를 쓰세요.
    • 헌팅 전에 잡음 걸러내기: 윈도우 업데이트/OCSP, 폰트, CDN, 멀티캐스트, NetBIOS 브로드캐스트.
    • 평문 C2는 선물입니다. Hide Images & Files로 POST 본문을 읽으면 피해자, 훔친 계정, 공격자의 다음 행동까지 나옵니다.
    • TCP 플래그와 바이트 방향을 읽어 "연결해서 주고받음"과 "찔러 봤다가 거절됨"을 구분하세요.
    • 배제한 것도 증거입니다. 무해한 외부 출발지, 거절된 SMB, 결과 0개인 범위 확인을 Not Found로 남기세요.
    • 다른 사람이 읽는 문서에서는 비밀 정보를 가리고 IOC를 무력화하세요.
