# 침해를 발견했을 때 — 체류 시간, 침해 유형, 단기·장기 백도어, 공격자 동기, 비즈니스 위험, 공격자에 대해 아는 것 { #dwell-type-motivation }

!!! abstract "이 페이지에서 다루는 것"
    경보 분류도 끝났고 조사도 끝났는데, 답이 "맞다, 누가 들어와 있다"로 나왔습니다. 이 페이지는 바로 그다음 순간, **"이제 어떡하지?"** 를 다룹니다. 손이 먼저 가는 답 — 랜선 뽑고, 밀어 버리고, 다 막기 — 은 맞을 때도 있지만 최악의 선택일 때도 있습니다. 결정하려면 대응자는 다섯 가지를 묻습니다. 공격자 쫓아내기(attacker eviction)에 관한 Frode Hommedal의 잘 알려진 작업에서 나온 질문들입니다. **(1) 얼마나 오래 있었나?**(체류 시간, 그리고 실제 증거로 추정하는 법), **(2) 어떤 종류의 침해인가?**(한 가지를 노린 치고 빠지기인가, 몇 년 머물려는 작전인가), **(3) 들어올 문이 몇 개인가?**(단기·장기 백도어 패턴을 가상 Zeek 로그로 보고, 서두른 정리가 왜 조용한 쪽을 놓치는지), **(4) 왜 우리를 노리나?**(전략적 표적, 전술적 디딤돌, 아니면 그냥 공짜 인프라), **(5) 지금 비즈니스 위험이 얼마나 큰가?** — 다른 모든 요소를 뒤집을 수 있는 요소 — 그리고 마지막으로 **우리는 공격자에 대해 실제로 무엇을 아나?** 를 킬 체인 단계 × 고통의 피라미드 수준 지식 매트릭스로 펼쳐서 빈칸을 드러냅니다. Wattle Ridge Energy의 가상 침해 하나가 페이지 전체를 관통하고, Windows 이벤트 **7045**, **4697**, **4698**, **4624** 를 설명합니다. 다음 페이지에서 이 답들을 대응 방식 선택으로 바꿉니다.

!!! note "표기"
    **[보충]** = 꼭 알아야 할 실무 보충, **[정정]** = 흔히 잘못 알려진 내용 정정, **[변경됨]**/**[주의]** = 최근 바뀐 점과 옛 방식대로 하면 위험한 점. 회사(Wattle Ridge Energy, `wattleridge.example`), 사람, 호스트 이름, 도메인, IP, 로그 줄은 모두 설명용 가상 값(`.example`, 문서용·사설 IP)입니다. 프레임워크, 연구자, 공개된 사건은 실제이며 제 말로 설명했습니다.

## 한눈에 보는 핵심 8가지 { #key-points }

1. **"침해 확인"은 결정의 끝이 아니라 시작이다.** 얼마나 빨리, 얼마나 세게 대응할지는 여러 요소가 한꺼번에 정한다. 질문 하나로 정해지지 않는다.
2. **체류 시간이 계산을 바꾼다.** 들어온 지 몇 분 만에 찾은 백도어는 지금 죽인다. 2년 동안 있던 백도어라면 거의 틀림없이 다른 것들이 더 붙어 있다. 배우는 데 며칠 더 쓰는 위험은, 하나를 놓친 채 쫓아내는 위험보다 작다.
3. **체류 시간은 첫 경보가 아니라 가장 이른 증거로 추정한다.** 그리고 우리 로그가 진짜 시작점까지 거슬러 올라가지 못할 수 있다는 걸 기억한다.
4. **침해 유형:** 치고 빠지기(smash and grab)는 한 가지를 빨리 원하고 은밀함에 별 관심이 없다. 지속 접근(persistent access) 작전은 머물고 싶어서 깊이 파고든다. 두 번째가 훨씬 걷어 내기 어렵다.
5. **끈질긴 공격자는 문을 여러 개 둔다.** 매일 쓰는 시끄럽고 대화형인 **단기(short-haul)** 백도어와, 드물게만 연락하는 조용한 **장기(long-haul)** 백도어를 보험으로. 처음 찾은 것만 지우면 그들은 다시 문을 열고 들어온다.
6. **동기:** 우리가 **전략적** 목표인가(머물려고 끝까지 싸운다), **전술적** 디딤돌인가(뭔가 빨리 얻고 떠난다), 아니면 그냥 **인프라**인가(아무 컴퓨터나 상관없다. 다시 설치하면 보통 다른 데로 간다)?
7. **비즈니스 위험은 모든 걸 뒤집을 수 있다.** 안전 시스템, 핵심 서버, 진행 중인 데이터 유출이 걸려 있으면 지금 행동하고, 지저분한 쫓아내기를 감수한다. 개인 PC 몇 대라면 지켜보며 배울 여유가 더 있다.
8. **모르는 걸 안다.** 공격자에 대한 지식을 킬 체인과 고통의 피라미드에 대 본다. 빈칸이 많거나 IP·해시만 안다면, 능숙한 공격자를 쫓아낼 준비는 아직 안 된 것이다.

## SOC에서 왜 중요한가 { #why }

부엌에서 흰개미 한 마리를 발견했다고 해 봅시다. 집이 새 집이고, 그 흰개미가 한 시간 전에 들여온 장작 상자에서 나온 게 분명하다면, 상자를 버리면 끝입니다. 하지만 집이 20년 됐고 걸레받이를 두드리면 속이 빈 소리가 난다면, 눈에 보이는 한 마리에 약을 뿌려 봤자 달라지는 게 없습니다. 개미집은 벽 속에 있고, 눈에 띈 개미는 그냥 밖으로 나온 녀석들일 뿐입니다. 좋은 방역 전문가는 먼저 얼마나 오래 있었는지, 개미집이 어디까지 퍼졌는지, 무너지기 직전인 기둥이 있는지부터 알아본 뒤에 "여기만 뿌리기", "집 전체 처리", "오늘 밤 모두 대피" 중 하나를 고릅니다.

기술 이야기로 돌아오면, SOC 도구는 반응하기를 아주 쉽게 만들어 줍니다. 클릭 한 번이면 호스트가 격리되고, 규칙 하나면 도메인이 막히고, 스크립트 하나면 비밀번호가 바뀝니다. 큐의 대부분을 차지하는 흔한 감염에는 이게 맞습니다. 하지만 몇 달째 안에 있는 공격자에게 같은 반사 행동을 하면, 보통은 우연히 본 부분만 지우고, 우리가 무엇을 찾았는지 공격자에게 정확히 알려 주고, 우리가 못 찾은 접근 경로로 공격자를 밀어 넣게 됩니다. 이 페이지의 질문들은 "확인"과 "행동" 사이의 멈춤입니다. 우리가 진짜 어떤 문제를 안고 있는지 정하는 몇 분, 혹은 며칠이죠. 이 답들은 [보안 사고 모델 섹션](../mental-models/kill-chain-did-nist-ir.md#ir-cycle)의 침해 대응 주기로 바로 이어집니다. *이번* 사건에서 "봉쇄(Contain)"와 "제거(Eradicate)"가 무엇을 뜻해야 하는지를 정해 줍니다.

## 페이지 전체에 쓰는 예제 { #example }

Wattle Ridge Energy의 EDR이 엔지니어링 도면을 담은 파일 서버 `WR-FS02`에서 중간 심각도 경보를 띄웁니다.

```text
Alert:      Suspicious service binary in non-standard path
Host:       WR-FS02 (10.20.8.12)
Process:    C:\ProgramData\Microsoft\Crypto\RSA\svcnetcfg.exe
Parent:     services.exe
Signer:     (unsigned)
Network:    TLS to 198.51.100.61:443 every ~60 s (cdn-sync-check.example)
First seen by EDR: 2026-11-20 03:12 UTC  (EDR agent installed on this host 2026-11-19)
```

한 줄씩 읽어 봅시다.

- `Process` — 프로그램이 아니라 암호 키 자료가 들어 있어야 할 폴더에 숨은 실행 파일. 섞여 들어가기 좋은 전형적인 자리입니다.
- `Parent: services.exe` — Windows 서비스로 돌고 있으니, 부팅할 때마다 시작됩니다(Windows 서비스를 이용한 지속성, ATT&CK T1543.003 Create or Modify System Process: Windows Service).
- `Signer: (unsigned)` — 코드 서명이 없습니다. Microsoft가 `ProgramData\Microsoft`에 넣는 거의 모든 파일과 다릅니다.
- `Network` — 아무도 모르는 도메인으로 약 60초마다 TLS 세션. 웹 프로토콜을 쓰는 명령·제어(C2) 비컨입니다(T1071.001).
- `First seen by EDR` — 여기가 함정입니다. EDR은 어제야 이 서버에 설치됐습니다. "처음 보임"은 공격자가 들어온 때가 아니라 *센서*가 보기 시작한 때를 알려 줄 뿐입니다.

분석가는 악성임을 확인합니다(모르는 해시, 업무 담당자 없음, 비컨 패턴, 이상한 경로). 이제 다섯 가지 질문입니다.

## 질문 1: 얼마나 오래 있었나? (체류 시간) { #dwell-time }

**체류 시간(Dwell Time)** 은 공격자가 처음 발판을 마련한 때부터 방어자가 발견한 순간까지의 시간입니다. 어떻게 대응할지를 정하는 가장 강한 요소 중 하나입니다.

양 끝을 생각해 봅시다.

- **바로 탐지.** 사용자가 첨부 파일을 연 지 몇 초 만에 EDR이 드로퍼를 막았습니다. 공격자는 자격 증명을 훔치거나, 옆으로 이동하거나, 두 번째 백도어를 심을 시간이 없었습니다. 지금 죽이세요. 호스트를 격리하고 파일을 지우면 아마 그걸로 끝이고, 기다리면 그들에게 시간만 줍니다.
- **2년 뒤에 발견.** 능숙하고 끈질긴 공격자라면 2년은 자격 증명을 모으고, 계정을 만들고, 다른 호스트를 장악하고, 서로 관계없는 예비 접근 경로를 심기에 충분한 시간입니다. 찾은 감염 하나를 지운다고 *그들*이 사라지지는 않습니다. 그리고 배우는 동안 며칠 더 두는 **추가 위험(incremental risk)** 은, 그들이 이미 가진 700일 남짓에 비하면 작습니다 — 단, 가까이서 지켜보고, 그들이 핵심 자산 쪽으로 움직이면 바로 끼어들 수 있어야 합니다.

이렇게 생각하면 편합니다.

| 체류 시간 | 보통 뜻하는 것 | 기울기 |
| --- | --- | --- |
| 몇 분~몇 시간 | 퍼질 시간이 거의 없음. 첫 발판이 아마 유일함 | 빨리 행동: 봉쇄하고 정리 |
| 며칠~몇 주 | 자격 증명 탈취와 수평 이동 가능성. 한 대라고 단정하기 전에 범위 확인 | 빠르지만 신중하게 범위 잡고 행동 |
| 몇 달~몇 년 | 발판·계정·백도어가 여럿일 것으로 예상. 공격자는 우리 네트워크를 안다 | 먼저 철저히 범위 잡기, 한꺼번에 행동 |

이 기울기는 규칙이 아닙니다. 공격자의 실력과 유형(질문 2와 4), 비즈니스 위험(질문 5)이 어느 쪽으로든 바꿀 수 있습니다.

### 증거로 체류 시간 추정하기 { #estimating-dwell }

도구의 "처음 보임"이 진짜 시작인 경우는 드뭅니다. 분석가는 `WR-FS02`와 그 주변에서 **믿을 만한 가장 이른 증거**를 찾습니다.

**1. 서비스는 언제 설치됐나?** Windows **System** 로그는 새 서비스를 **이벤트 ID 7045**("A service was installed in the system")로 남깁니다. 관리자든, 설치 프로그램이든, 공격자든 서비스를 만들면 서비스 제어 관리자(Service Control Manager)가 이걸 씁니다. 공격자가 신경 쓰는 이유는, 서비스 생성이 부팅할 때마다 `SYSTEM` 권한으로 코드를 돌리는 가장 간단한 방법 중 하나이고, 원격 실행 도구가 다른 PC에서 페이로드를 띄우는 흔한 방법이기도 해서입니다.

```text
Log Name:   System
Source:     Service Control Manager
Event ID:   7045
TimeCreated: 2024-10-02T14:41:07Z
Service Name:  NetCfgSync
Service File Name:  C:\ProgramData\Microsoft\Crypto\RSA\svcnetcfg.exe
Service Type:  user mode service
Service Start Type:  auto start
Service Account:  LocalSystem
```

- `TimeCreated: 2024-10-02` — 2년도 더 전입니다. 조용한 파일 서버의 System 로그는 크기를 넉넉히 잡아 두면 몇 년 치가 남아 있을 수 있습니다. 바쁜 서버라면 한참 전에 덮어써졌을 수도 있고요.
- `Service Name: NetCfgSync` — 섞여 들어가려고 고른, 따분하고 그럴듯한 이름.
- `auto start`와 `LocalSystem` — 부팅 때 로컬 최고 권한으로 시작.

"Audit Security System Extension"(보안 시스템 확장 감사)이 켜져 있으면, **Security** 로그에도 **이벤트 ID 4697**("A service was installed in the system")이 **서비스를 만든 계정**과 함께 남습니다. *누가* 했는지 알려 주니 훨씬 쓸모가 큽니다. 분석가가 찾았습니다.

```text
Event ID:   4697
TimeCreated: 2024-10-02T14:41:07Z
Subject:  Account Name: svc-backup   Account Domain: WATTLERIDGE   Logon ID: 0x3E7A21
Service Name: NetCfgSync
```

- `svc-backup` — 백업 서비스 계정이 백도어를 설치했습니다. 공격자는 2024년 10월에 이미 이 계정의 자격 증명을 갖고 있었다는 뜻이고 — 이 계정은 자기가 백업하는 *모든* 서버에서 쓸 수 있을지도 모릅니다.
- `Logon ID: 0x3E7A21` — 이 값이 짝이 되는 **4624**(계정 로그온 성공) 이벤트와 이어 줍니다. 같은 Logon ID로 4624를 찾으면 로그온 유형(3 = 네트워크, 10 = 원격 대화형/RDP)과 출발 IP — 공격자가 *어디서* 왔는지 — 가 나옵니다.

**2. 더 이른 게 있나?** 4624를 보니 오래된 점프 서버 `10.20.3.41`에서 온 네트워크 로그온입니다. 그 호스트에서 분석가는 **2024-08-19** 날짜의 **이벤트 ID 4698**("A scheduled task was created")을 찾습니다. 이름을 바꾼 실행 파일을 매일 밤 돌리는 작업입니다. 예약 작업(T1053.005 Scheduled Task)은 재부팅해도 살아남고 일상 유지 보수처럼 보여서 공격자가 아주 좋아하는 지속성 방법입니다. 점프 서버의 발판이 파일 서버보다 7주 더 오래됐습니다.

**3. 네트워크는 뭐라고 하나?** 프록시는 13개월 치 로그를 보관합니다. `cdn-sync-check.example`로 간 가장 이른 요청은 2025년 11월인데 — 그건 로그가 거기서 시작하기 때문일 뿐입니다. **공격보다 데이터가 먼저 끝납니다.**

분석가는 사건 메모에 이렇게 씁니다. *"확인된 가장 이른 활동 2024-08-19(WR-JMP01의 예약 작업). 실제 시작은 더 이를 수 있음. 프록시와 EDR 보관 기간이 거기까지 닿지 않음. 체류 시간 27개월 이상."*

**[보충]** 파일 타임스탬프는 조심해서 다루세요. 공격자는 파일에 보이는 시각을 바꿀 수 있어서("타임스톰핑(timestomping)"), 2019년 거라고 주장하는 실행 파일은 아무것도 증명하지 못합니다. 시스템이 직접 쓰고 위조하기 어려운 시각 — 이벤트 로그 레코드, 서비스 레지스트리 키의 마지막 쓰기 시각, MFT의 NTFS `$FILE_NAME` 속성, Prefetch와 Amcache 항목 — 을 우선하고, 여러 출처가 서로 맞는지 확인하세요.

## 질문 2: 어떤 종류의 침해인가? { #intrusion-type }

공격자가 무엇을 이루려는지 알 수 있으면, 걷어 내기가 얼마나 어려울지도 예상할 수 있습니다. 크게 두 가지입니다.

**치고 빠지기(Smash and grab).** 공격자는 특정한 것 — 설계도, 데이터베이스, 송금 — 이나 빠른 피해를 원합니다. 얻으면 떠납니다. 그들에게는 은밀함보다 속도가 중요해서 깊은 지속성에 공을 많이 들이지 않습니다. 시도를 계속 막으면 지쳐서 다른 데로 갈 수 있으니, **빠른 대응**이 맞는 경우가 많습니다.

**지속 접근(Persistent access).** 목표가 *머무는 것*입니다. 계속 메일을 읽고, 프로젝트를 지켜보고, 이 접근이 값어치를 가질 순간을 기다립니다. 이런 공격자는 은밀함과 여러 개의 복귀 경로에 투자하고, 우리가 알아챌 때쯤이면 대개 깊이 뿌리를 내린 상태입니다. 걷어 내는 건 훨씬 큰 일입니다.

증거에서는 이렇게 보입니다.

| 증거 | 치고 빠지기 쪽 | 지속 접근 쪽 |
| --- | --- | --- |
| 타임라인 | 침입부터 유출까지 몇 시간~며칠 | 몇 달 동안 낮고 꾸준한 활동 |
| 수집 | 큰 압축 파일을 만들어 한 번에 내보냄(T1560 Archive Collected Data) | 작고 규칙적으로 빼 감 — 매주 CEO 메일함(T1114.002 Remote Email Collection), 오랜 기간 키로깅(T1056.001 Keylogging) |
| 지속성 | 간단한 방법 하나, 또는 없음 | 서로 다른 호스트·계정에 관계없는 여러 방법 |
| 소음 | 시끄러운 도구, 뒷정리 거의 없음 | 조용하고 조심스러움, 관리자 활동에 섞여 듦 |
| 노리는 곳 | 목표물이 있는 곳 | 메일 서버, ID 시스템, 관리 도구 — 오래 지켜보기 좋은 자리 |

Wattle Ridge에서는 파일 서버 백도어가 2년 동안 있었지만 큰 데이터 유출 흔적은 없습니다. 대신 서버의 파일 감사 로그를 보면, 새 변전소 설계 프로젝트 폴더에서 매달 도면 몇 장씩 열렸습니다. 작고, 규칙적이고, 목표가 뚜렷합니다. **지속 접근**으로 보입니다.

## 단기 백도어와 장기 백도어 { #short-long-haul }

끈질긴 공격자는 왜 걷어 내기가 이렇게 어려울까요? 공격자 입장이 되어 봅시다. 이 네트워크에 계속 머무는 게 내 일이라면, 백도어 하나에만 기대겠습니까? 당연히 아니죠. **서로 관계없는** 백도어를 여러 개 — 다른 악성코드, 다른 C2 서버, 다른 호스트 — 심어서, 방어자가 하나를 찾아도 나머지는 살아남게 할 겁니다. 발판이 다양할수록 정리 작업이 하나를 놓칠 가능성이 커지고, 그러면 그냥 다시 걸어 들어오면 됩니다.

이걸 정리하는 흔한 방식이 두 종류로 나누는 겁니다.

- **단기 백도어(Short-haul backdoor)** — 매일 쓰는 도구. C2와 자주 통신하고, 대화형 작업(명령, 파일 전송, 터널링)을 지원하고, 은밀함을 우선하지 않습니다. 공격자의 악성코드를 찾았다면 대개 이쪽입니다. 가장 시끄러우니까요.
- **장기 백도어(Long-haul backdoor)** — 보험. 대부분 잠들어 있고, 드물게(하루에 한 번, 일주일에 한 번, 또는 신호가 올 때만) 연락하고, 다른 프로토콜이나 정상 클라우드 서비스를 쓰는 경우가 많고, 단기 도구를 다시 설치하라는 지시를 기다리는 것 말고는 아무것도 안 할 수도 있습니다. 단기 백도어가 발견되는 날에도 살아남도록 만든 겁니다.

### 둘이 Zeek 로그에서 어떻게 보이나 { #zeek-example }

분석가가 `WR-FS02`의 Zeek `conn.log`를 뽑습니다(열 일부 생략).

```text
ts                    id.orig_h    id.resp_h      id.resp_p  proto  service  duration  orig_bytes  resp_bytes
2026-11-25T03:12:04   10.20.8.12   198.51.100.61  443        tcp    ssl      0.41      612         1180
2026-11-25T03:13:05   10.20.8.12   198.51.100.61  443        tcp    ssl      0.39      598         1180
2026-11-25T03:14:04   10.20.8.12   198.51.100.61  443        tcp    ssl      0.44      604         1180
2026-11-25T03:15:06   10.20.8.12   198.51.100.61  443        tcp    ssl      18.72     4210        391044
```

- `ts` — 약 60초마다 연결 하나. 규칙적인 **비컨**입니다.
- `id.resp_h 198.51.100.61`, 포트 `443`, `service ssl` — 단기 C2(`cdn-sync-check.example`)로 가는 TLS.
- `orig_bytes` / `resp_bytes`가 600 / 1180 안팎 — "나한테 시킬 일 있어?" 하고 묻는 작은 체크인이고, 응답 크기가 매번 거의 같습니다.
- 마지막 줄: `duration 18.72`, `resp_bytes 391044` — C2가 약 380KB를 보냈습니다. 명령이나 도구가 전달됐고, 누군가 대화형으로 작업하고 있었습니다.

이게 단기 백도어입니다. 시끄럽고 잦습니다. 이제 분석가는 검색을 모든 호스트, **30일 범위**로 넓혀서, 아주 적은 내부 호스트가, 드물지만 수상할 만큼 규칙적으로 접속하는 목적지를 찾습니다. 다른 서버 `WR-HIS01`(운영 네트워크에 있는 히스토리안 데이터베이스)에서 결과 하나가 눈에 띕니다.

```text
ts                    id.orig_h    id.resp_h      id.resp_p  proto  service  duration  orig_bytes  resp_bytes
2026-10-29T02:00:13   10.40.2.7    203.0.113.140  443        tcp    ssl      0.62      801         2304
2026-11-05T02:00:09   10.40.2.7    203.0.113.140  443        tcp    ssl      0.58      795         2304
2026-11-12T02:00:11   10.40.2.7    203.0.113.140  443        tcp    ssl      0.60      799         2304
2026-11-19T02:00:12   10.40.2.7    203.0.113.140  443        tcp    ssl      0.59      803         2304
2026-11-26T02:00:10   10.40.2.7    203.0.113.140  443        tcp    ssl      0.61      797         2304
```

- **7일마다** 연결 하나, 늘 02:00, 늘 같은 크기. 1분짜리 비컨은 잘 보이지만, 주 1회짜리는 긴 기간을 보지 않으면 안 보입니다.
- `10.40.2.7` — *다른* 네트워크 구역의 *다른* 호스트, *다른* C2 주소. 파일 서버 악성코드와 이어 주는 건 똑같이 규칙적이고 똑같이 설명이 안 된다는 점뿐입니다.
- 매번 `resp_bytes 2304` — 서버가 매주 "할 일 없음"이라고 답합니다. 기다리는 중입니다.

이게 **장기 백도어** 후보입니다(넓은 뜻에서 T1008 Fallback Channels의 예이기도 합니다. 첫 경로가 죽을 때를 대비한 두 번째 경로). SOC가 첫날 그냥 `WR-FS02`를 격리하고 `cdn-sync-check.example`을 막았다면, 공격자는 매일 쓰던 도구를 잃고, 알아채고, 일주일 뒤 `WR-HIS01`로 돌아왔을 겁니다. 이번에는 방어자가 무엇을 찾았는지 정확히 알고서요.

**모범 사례: 대응하기 전에 범위부터 잡는다.** 너무 빨리 움직이면 적이 적응합니다. 경험 많은 팀은 한 걸음 더 나가기도 합니다. 단기 백도어 사본을 다 찾았다고 판단하면, 평범한 장애처럼 보이게 그 능력을 **일부러** 끊고 모든 센서를 바짝 지켜봅니다. 그러면 공격자는 장기 백도어를 깨울 수밖에 없고, 그것까지 드러납니다. 그다음 한꺼번에 모두 걷어 냅니다. 좋은 가시성, 계획, 경영진 지원이 필요한 고난도 작전이지, 야간 근무 중에 즉흥으로 할 일이 아닙니다. 이걸 제대로 해내는 게 블루팀 기술의 일부입니다.

**[보충]** 장기 접근이 꼭 악성코드일 필요는 없습니다. 요즘 환경에서 가장 조용한 예비 문은 흔히 **ID(계정)** 입니다. 비밀번호가 알려진 잊힌 서비스 계정(T1078 Valid Accounts), VPN 계정, 클라우드 애플리케이션에 추가된 자격 증명(T1098.001 Additional Cloud Credentials), 메일을 밖으로 전달하는 메일함 규칙. 이런 건 비컨을 전혀 보내지 않습니다. 범위 잡기에는 호스트뿐 아니라 계정과 클라우드 ID가 꼭 들어가야 합니다.

## 질문 3: 왜 우리를 노리나? (공격자 동기) { #motivation }

질문 2와 비슷해 보이지만 다릅니다. 질문 2는 *어떤 방식의 공격*을 보고 있는지 물었습니다. 이 질문은 **공격자의 큰 그림에서 우리 조직이 어떤 역할을 하는지** 묻습니다. 그게 머물려고 얼마나 버틸지를 알려 주니까요.

| 역할 | 뜻 | 공격자의 행동 | 기울기 |
| --- | --- | --- | --- |
| **전략적(Strategic)** | 우리에 대한 접근이 중요한 장기 목표에 쓰임(우리 업계를 노린 국가 첩보, 우리 설계를 노린 경쟁자) | 아주 끈질김. 쫓겨나면 새 도구로 다시 시도 | 신중한 범위 잡기, 완전한 쫓아내기, 재침입 예상 |
| **전술적(Tactical)** | 잠깐만 필요 — 데이터 한 묶음, 또는 협력사·고객으로 가는 우리 신뢰 관계(T1199 Trusted Relationship) | 집요할 수는 있지만 지속성보다 속도에 집중. 막히면 다른 출처로 바꿀 수도 | 그들이 노리는 목표를 지킨다. 빠른 행동도 대개 괜찮음 |
| **인프라(Infrastructure)** | 우리가 누군지 관심 없음. 우리 PC는 인터넷 되는 CPU일 뿐 — 스팸, DDoS, 암호화폐 채굴, 트래픽 중계, 남을 공격하는 발판 | 들키면 떠남. PC 한 대를 위해 싸울 이유가 별로 없음 | 방해: 빨리 다시 설치하고 넘어감 |

인프라 경우는 조금 더 볼 만합니다. 봇넷 운영자는 세계 곳곳의 컴퓨터로 스팸을 보내고, fast-flux DNS를 돌리고, 공격을 합니다. 주인이 누구라서가 아니라 쓸 수 있어서입니다. 때로는 우리 호스트가 훨씬 큰, 심지어 국가가 운영하는 작전의 작은 부분일 수도 있지만, 우리는 표적이 아니라 **수단**입니다. 이럴 때는 빨리 다시 설치해서 끊어 버리면, 그들은 대개 다른 선택지를 쓰러 갑니다.

Wattle Ridge의 공격자는 변전소 설계를 읽고, 운영 히스토리안에 앉아 있고, 2년 동안 조용히 접근해 왔습니다. **전략적** 관심의 모습입니다. 끈질김과 싸움을 각오해야 합니다.

## 질문 4: 지금 비즈니스 위험이 얼마나 큰가? { #business-risk }

다른 모든 요소를 뒤집을 수 있는 요소가 하나 있습니다. **공격자가 심각한 피해에 얼마나 가까이 있느냐**입니다. 체류 시간이나 동기가 어떻든, 걸린 게 충분히 크면 그들이 차지한 위치 하나만으로 대응이 정해질 수 있습니다.

- **공격자가 산업 제어 시스템(ICS, Industrial Control System) 장비나 안전 기능을 쥐고 있다** — 긴급도가 극히 높습니다. 지금 행동하세요. 터빈이나 화학 공정이 폭주하지 않게 막는 안전 시스템을 침입자가 끌 수 있다면 사람이 죽을 수 있습니다. 공격자에게 알려지고 나중의 쫓아내기가 어려워지더라도, 그 시스템은 바로 안전한 상태로 만들어야 합니다. (이게 왜 중요한지 보여 주는 실제 공개 사례: 산업 시설의 안전 계장 시스템(SIS)을 노린 2017년 Triton/TRISIS 악성코드.)
- **공격자가 핵심 서버에 있다** — 그 서버가 무슨 일을 하는지, 공격자가 그걸로 무엇을 할 수 있는지에 따라 중간~높은 긴급도.
- **공격자가 개별 사용자 PC에만 있다** — 긴급도가 낮습니다. 지켜보며 배울 여유가 더 있습니다.

**진행 중인 피해는 모든 걸 바꿉니다.** 데이터가 지금 나가고 있거나, 암호화가 시작됐거나, 백업이 지워지고 있다면(T1490 Inhibit System Recovery, T1486 Data Encrypted for Impact), 먼저 봉쇄하고 배우는 건 나중입니다. "지켜보며 배우기"는 결코 피해를 구경해도 된다는 허락이 아닙니다.

Wattle Ridge: 파일 서버에는 설계도가 있고(심각하지만, 설계도 유출은 천천히 타는 불입니다), 히스토리안 `WR-HIS01`은 운영 네트워크에 있습니다. 분석가가 네트워크 구성도와 방화벽 규칙을 확인합니다. 히스토리안은 제어 네트워크에서 **읽기**만 할 수 있고 명령은 보낼 수 없으며, 지금까지 장악된 엔지니어링 워크스테이션은 없습니다. 비즈니스 위험: **높지만 당장은 아님**. 제어 네트워크 쪽으로 움직인 증거가 나오면 결정은 "지금 행동"으로 뒤집힙니다.

## 질문 5: 우리는 공격자에 대해 실제로 무엇을 아나? { #knowledge }

마지막 질문은 우리 자신의 지식, 그리고 공격자를 볼 수 있는 능력에 관한 것입니다.

- **실력.** 부주의한 기회주의자인가, 자원이 많고 규율 잡힌 팀인가? 꼼꼼한 로그 정리, 맞춤 악성코드, 참을성 있는 주 1회 비컨은 뒤쪽을 가리킵니다.
- **그들의 방법을 얼마나 잘 아나?** [고통의 피라미드](../mental-models/pyramid-attack-summary.md#pyramid)를 떠올리세요. IP 주소, 도메인, 해시 몇 개만 아는가(그들은 싸게 바꿀 수 있음), 아니면 도구와 TTP를 아는가(바꾸기 비싸고, 아직 못 본 발판을 찾게 해 주는 것)?
- **공격의 모든 단계를 볼 수 있나?** [사이버 킬 체인](../mental-models/kill-chain-did-nist-ir.md#kill-chain)을 떠올리세요. 어떻게 들어왔나? 어떻게 이동하나? 어떻게 버티나? 어떻게 데이터를 빼 가나? 답하지 못한 단계마다 발판이 숨을 수 있는 자리입니다.

Frode Hommedal은 이 두 축을 합쳐 **사이버 위협 인텔리전스 매트릭스(CTIM, Cyber Threat Intelligence Matrix)** 라고 불렀습니다. 한 축에는 공격 생애 주기 단계, 다른 축에는 아는 것의 깊이(단순 지표부터 TTP까지), 그리고 실제로 탐지할 수 있는지를 둡니다. Ryan Stillions의 **탐지 성숙도 수준(DML, Detection Maturity Level)** 모델과도 가깝습니다. 맨 아래 단순 지표부터 맨 위 공격자의 목표와 전략 이해까지 탐지 능력의 수준을 매기는 모델입니다. 이런 매트릭스를 채우면 **지식의 빈칸**이 보이고, 빈칸이 너무 많으면 고급 공격자를 쫓아낼 준비가 아직 안 됐다는 뜻입니다.

이틀째의 Wattle Ridge 매트릭스입니다.

| 단계 | 지표(IP, 도메인, 해시) | 도구 | TTP(행동) | 탐지할 수 있나? |
| --- | --- | --- | --- | --- |
| 초기 접근 | — | — | — | **모름**(우리 로그보다 이전) |
| 실행과 지속성 | 해시 둘, 서비스 이름 `NetCfgSync` | 맞춤 백도어(두 계열?) | Windows 서비스(T1543.003), 예약 작업(T1053.005) | 예 — 7045/4697/4698 경보 이제 켜짐 |
| 자격 증명 접근 | — | — | `svc-backup` 자격 증명 사용, 방법 모름 | **아니요** |
| 수평 이동 | 출발지 `10.20.3.41` | — | 서비스 계정으로 네트워크 로그온(T1078) | 일부 — 4624 유형 3, 하지만 잡음이 많음 |

읽는 법: 실행, 지속성, C2는 꽤 잘 압니다. 하지만 초기 접근, 자격 증명 탈취, 데이터가 나가는 방법, 클라우드 쪽 전체가 비어 있거나 "모름"입니다. 오늘 쫓아내면, SOC는 아는 것만 지우고 빈 줄에 있는 모든 경로를 공격자에게 남겨 주게 됩니다. 이 매트릭스가 곧 **조사 계획**이 됩니다. 빈칸을 채우고, 그다음에 결정합니다.

| 질문 | Wattle Ridge의 답 | 기우는 쪽 |

| 침해 유형 | 지속 접근(작고 규칙적인 읽기) | 먼저 범위 잡기, 발판 여럿 예상 |
| 백도어 | `WR-FS02`의 단기, `WR-HIS01`의 장기 후보, 더 있을 수도 | 채널 하나를 일찍 끊지 않기 |
| 동기 | 전략적(업계 설계, 운영 네트워크) | 끈질김과 재침입 예상 |
| 비즈니스 위험 | 높지만 당장은 아님. 제어 시스템 쪽으로 움직이면 "지금 행동"으로 뒤집힘 | 바짝 지켜보되 행동 신호를 정해 둠 |
| 지식 | 빈칸이 큼(초기 접근, 자격 증명, 유출, 클라우드) | 아직 쫓아낼 준비 안 됨 |

답이 같은 쪽을 가리킵니다. **지켜보고, 배우고, 준비하되, 즉시 행동할 신호를 분명히 정해 둔다** — 그리고 모든 걸 한꺼번에 쫓아낸다. 그 대응을 어떻게 고르고 실행하는지가 다음 페이지의 주제입니다.

## 2026년 관점 { #trends }

!!! success "[2026 현재] 지금도 그대로 유효"
    다섯 질문은 여전히 쓸모 있고, "끈질긴 공격자를 쫓아내기 전에 범위부터 잡는다"는 진지한 침해 대응의 표준 관행입니다. 첩보 사건에서는 지금도 서로 관계없는 여러 발판과 드물게 비컨을 보내는 예비 접근이 흔히 발견됩니다. 안전이나 진행 중인 파괴가 걸리면 여전히 비즈니스 위험이 모든 걸 뒤집습니다. Windows 이벤트 7045, 4697, 4698, 4624는 지속성이 언제, 어떻게 설치됐는지 추정하는 핵심 호스트 증거이고, Zeek `conn.log`는 긴 기간에 걸친 느린 비컨을 찾기에 여전히 좋은 곳입니다.

!!! info "[변경됨] 바뀐 점"
    - **체류 시간 수치.** Mandiant의 M-Trends 2026(2025년 조사 대상)은 **전 세계 체류 시간 중앙값이 14일로, 전년의 11일보다 늘었다**고 보고했고, **첩보 사건은 중앙값 122일**이었습니다. 이 페이지가 걱정하는 바로 그 전략적 공격자에게 긴 체류는 여전히 보통입니다. 조직이 스스로 침해를 찾아낸 비율은 52%였습니다. 중앙값은 넓은 분포를 가리니, 우리 사건의 예측이 아니라 배경으로만 쓰세요.
    - **넘겨주기가 거의 즉시 일어납니다.** 같은 보고서에서 초기 접근부터 두 번째 위협 그룹에게 넘기기까지의 중앙값은 8시간 이상(2022년)에서 **22초**(2025년)로 줄었습니다. "기회주의형" 발판이 사람이 경보를 보기도 전에 랜섬웨어 운영자의 발판이 될 수 있으니, 짧은 체류 시간이 더는 작은 사건을 보장하지 않습니다.
    - **장기 접근은 ID와 클라우드에 삽니다.** 클라우드 애플리케이션의 추가 자격 증명, OAuth 권한 부여, 전달 규칙, VPN 계정, 장악된 경계 장비(방화벽, VPN 게이트웨이, 라우터)가 이제 흔한 예비 접근이고, 많은 경우 EDR이 깔린 호스트를 전혀 건드리지 않습니다. 일부 국가 행위자는 장악한 경계 장비와 소규모 사무실 장비를 엮어 중계망을 만들고 트래픽을 숨깁니다. "인프라" 동기의 현대판입니다.
    - **ATT&CK가 재구성됐습니다.** v19(2026년 4월)에서 예전 Defense Evasion(방어 회피) 전술이 **Stealth**와 **Defense Impairment** 둘로 나뉘었고, 일부 기법(예: 로그 지우기, 보안 도구 끄기)은 새 ID로 옮겨졌습니다. 현재 버전은 v20(2026년 10월)입니다. 이 페이지의 ID(T1543.003, T1053.005, T1071.001, T1008, T1078, T1098.001, T1114.002, T1056.001, T1560, T1199, T1486, T1490)는 보고서에 넣기 전에 현재 매트릭스와 대조하세요.
    - **AI 보조 분류가 범위 잡기를 돕습니다.** SOC 코파일럿과 EDR 조사 보조 기능이 호스트 이력을 요약하고 관련 개체를 빨리 제안해 줘서 지식 매트릭스를 더 빨리 채울 수 있습니다. 하지만 센서가 본 것을 요약할 뿐, 우리 로그가 시작되기 전 기간은 알려 주지 못합니다.

!!! warning "[주의] 옛 방식대로 하면 틀리거나 위험한 점"
    - **도구의 "처음 보임"을 침해의 시작으로 여기지 마세요.** 센서가 보기 시작한 때입니다. 믿을 만한 가장 이른 증거를 찾고, 데이터가 어디서 끝나는지 적어 두세요.
    - **피해가 진행 중일 때 "체류 시간이 길다"를 기다릴 이유로 삼지 마세요.** 랜섬웨어 전조, 대량 데이터 유출, 백업 삭제, 안전 시스템 쪽으로 손을 뻗는 것 — 모두 지금 봉쇄하라는 뜻입니다.
    - **체류 시간이 짧다고 호스트 한 대라고 단정하지 마세요.** 넘겨주기가 거의 즉시 일어나니, 감염이 새것으로 보여도 새 계정, 새 원격 접속 도구, 자격 증명 사용을 확인하세요.
    - **호스트만 범위에 넣지 마세요.** 서버는 다 청소했는데 클라우드 추가 자격 증명이나 메일 전달 규칙이 남았다면, 그 쫓아내기는 실패한 겁니다.
    - **"단기를 끊어 장기를 끌어내기"를 계획 없이 즉흥으로 하지 마세요.** 강한 가시성, 경영진 동의, 준비된 대응이 필요합니다. 잘못하면 그냥 섣부른 차단일 뿐입니다.

## 확인 문제 { #quiz }

### 문제 1

동료가 말합니다. "EDR이 이 백도어를 어제 처음 봤으니까 체류 시간은 하루야. 호스트만 격리하면 돼." 이 추론의 문제는 무엇이고, 진짜 체류 시간을 추정하려면 어떤 증거를 보겠습니까?

??? success "정답과 해설"
    "EDR이 처음 봄"은 **센서**가 파일을 처음 관찰한 때지, 공격자가 들어온 때가 아닙니다. 게다가 이 경우 EDR은 바로 전날 설치됐습니다. 실제 시작은 훨씬 이를 수 있습니다.

    **믿을 만한** 가장 이른 증거를 찾습니다. System 로그 **7045**(서비스 설치), Security **4697**(서비스 설치, 누가 했는지 포함), 예약 작업 생성 **4698**, 공격자가 어디서 왔는지 보려고 Logon ID로 이어지는 **4624** 로그온, 레지스트리 마지막 쓰기 시각, NTFS `$FILE_NAME` 타임스탬프, Prefetch/Amcache, 그리고 C2 도메인에 대한 가장 오래된 프록시·DNS·방화벽 기록. 그다음 출발 호스트로 따라가서 반복합니다. 확인된 가장 이른 날짜와 **로그 보관 기간이 끝나는 지점**을 함께 적습니다. 공격이 우리 데이터보다 오래됐을 수 있으니까요. 체류 시간이 길다면 호스트 한 대 격리로는 아마 부족합니다.

### 문제 2

단기 백도어와 장기 백도어의 차이를 설명하고, 단기 백도어를 찾자마자 지우면 왜 사건이 더 나빠질 수 있는지 쓰세요.

??? success "정답과 해설"
    **단기** 백도어는 공격자가 매일 쓰는 도구입니다. 잦은 비컨, 대화형, 별로 은밀하지 않음 — 그래서 보통 가장 먼저 발견됩니다. **장기** 백도어는 보험입니다. 드물게(매일 또는 매주) 연락하고, 다른 호스트·C2·프로토콜을 쓰는 경우가 많고, 단기 도구를 잃었을 때 접근을 되살리려고 대부분 기다리기만 합니다.

    단기 백도어를 바로 지우면 공격자가 알아채고, 우리가 못 찾은 장기 백도어로 바꿔서 돌아옵니다. 이번에는 우리가 무엇을 찾았는지 알고, 그걸 피하도록 도구를 바꿀 수도 있습니다. 더 나은 방법: 먼저 범위를 잡고(긴 기간 비컨 헌팅, 계정, 클라우드 ID, 다른 호스트), 그다음 모든 발판을 같은 시간에 걷어 냅니다. 고급 팀은 장기 백도어를 끌어내려고 바짝 지켜보며 단기 채널을 일부러 끊기도 하지만, 계획이 있을 때만입니다.

### 문제 3

각 상황에서 공격자 동기가 전략적, 전술적, 인프라 중 무엇일 가능성이 가장 높은지, 그게 대응에 어떤 영향을 주는지 쓰세요. (a) 테스트 웹 서버의 암호화폐 채굴기, (b) 우리 관리 서비스 계정으로 한 고객사 네트워크에 들어간 뒤 우리 쪽에서는 조용해진 침입자, (c) 2년 동안 매달 국방 사업 설계 문서를 읽은 행위자.

??? success "정답과 해설"
    (a) **인프라.** 아무 CPU나 상관없고, 우리는 표적이 아닙니다. 빨리 다시 설치하고, 들어온 경로를 패치하고, 같은 지표를 다른 곳에서 훑습니다. 공격자는 아마 다른 데로 갈 겁니다.

    (b) **전술적.** 다른 누군가에게 가려고 우리 신뢰 관계(T1199 Trusted Relationship)가 필요했습니다. 그 경로를 빨리 지키고(자격 증명 교체, 연결 제한), 고객에게 알리고, 우리 쪽에 뭔가 남겨 뒀는지 확인합니다. 다만 우리에게 머물려고 싸울 가능성은 낮습니다.

    (c) **전략적.** 우리 데이터가 목표이고, 2년을 투자했습니다. 발판이 여럿이고 돌아오려 할 거라고 예상합니다. 신중하게 범위를 잡고, 지식 빈칸을 채우고, 한꺼번에 실행할 완전한 쫓아내기를 계획하고, 이후에도 강하게 감시합니다. 그 내내 비즈니스 위험이 우선할 수 있습니다. 안전에 중요한 곳에 닿거나 대량 유출을 시작하면 즉시 행동합니다.
