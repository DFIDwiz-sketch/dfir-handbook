# 로그 형식과 구조 — 비정형 로그, CSV, 키-값, JSON, CEF/LEEF, 그리고 SIEM은 구글이 아니다 { #formats-structure }

!!! abstract "이 페이지에서 다루는 것"
    로그의 **형식**이 왜 그 로그를 탐지에 쓸 수 있느냐 없느냐를 결정하는지 봅니다. 가장 나쁜 경우인 **비정형(unstructured)** 로그, 즉 syslog 헤더 뒤에 자유로운 문장이 붙은 로그부터 시작합니다. 이걸 파싱하려면 메시지 종류마다 정규식이 하나씩 필요하고, 여러 프로그램이 한 파일에 쓰거나 개발자가 문구를 바꾸면 소리 없이 깨지는 이유를 봅니다. 다음으로 **정형(structured)** 형식인 **CSV**, **키-값 쌍**, **JSON**(그리고 XML)을 같은 기록 하나로 비교합니다. 크기, 튼튼함, 중첩 지원이 어떻게 다른지요. 그다음 SIEM용 형식인 **CEF**와 **LEEF**의 헤더 칸과 이스케이프 규칙을 하나씩 뜯어 봅니다. 마지막으로 SIEM 안에서 구조가 왜 중요한지 봅니다. 파싱이 **인덱싱**을 만들고, 인덱싱이 검색을 빠르게 하고, 파싱이 실패하면 규칙이 조용히 놓친다(미탐, false negative)는 것. 그리고 **검색 범위를 좁히는 법** — 로그 종류 먼저, 그다음 필드 — 과, 검색창이 웹 검색 엔진처럼 생겼어도 그렇게 동작하지 않는 이유로 마무리합니다. 마지막에 확인 문제와 해설이 있습니다.

!!! note "표기"
    **[보충]** = 꼭 알아야 할 실무 보충, **[정정]** = 흔히 잘못 알려진 내용 정정, **[변경됨]**/**[주의]** = 최근 바뀐 점과 옛 방식대로 하면 위험한 점. 호스트 이름, 도메인, 계정, IP, 파일 이름은 모두 설명용 가상 값(`.example`, 문서용·사설 IP)입니다.

## 한눈에 보는 핵심 8가지 { #key-points }

1. 로그는 SIEM이 거기서 **핵심 칸을 믿을 만하게 뽑아낼 수 있을 때만** 탐지에 쓸모가 있다. 그게 얼마나 어려운지는 형식이 정한다.
2. <strong>비정형 로그</strong>는 모양이 정해진 syslog 헤더 뒤에 자유 문장이 붙는다. 파싱하려면 프로그램마다 **메시지 종류마다** 정규식이 필요하고, 문구가 바뀌면 그 정규식은 소리 없이 깨진다.
3. 여러 프로그램을 한 파일(예: `/var/log/syslog`)에 섞으면 문제가 몇 배가 된다. 줄마다 다른 프로그램이 다른 모양의 문장을 쓰기 때문이다.
4. **CSV**는 가장 작지만, 읽는 쪽이 **칸 이름과 순서**를 미리 알아야 한다. 칸 하나를 넣거나 빼거나 순서를 바꾸면 그 뒤의 모든 칸이 밀린다.
5. **키-값** 쌍은 값마다 이름을 달고 다녀서, 칸을 넣고 빼고 섞어도 파싱이 깨지지 않는다. 좋은 중간 지점이다. 다만 값 안의 공백과 구분 문자를 조심해야 한다.
6. **JSON**이 가장 튼튼하다. 이름 붙은 칸, 데이터 타입, **중첩과 배열**. 대신 가장 길다. XML도 같은 능력이 있고, 계층 구조를 잃지 않고 JSON으로 바꿀 수 있다. 탐지용 데이터는 고를 수 있다면 JSON.
7. **CEF**와 **LEEF**는 SIEM을 위한 형식이다. syslog 헤더, 그다음 **어느 제품이 만든 이벤트인지** 알려 주는 파이프(`|`) 구분 헤더, 그다음 키-값 확장 칸.
8. 파싱이 **인덱싱**을 만들고, 인덱싱이 검색을 빠르게 한다. 모든 검색은 **로그 종류**와 값이 들어 있을 **필드**로 좁힌다. `sara` 한 단어만 치는 건 가장 느리고 가장 부정확한 검색이다.

## 분석가에게 형식이 중요한 이유 { #why }

[수집 페이지](collection-methods.md)에서 이벤트가 호스트에서 SIEM까지 가는 길을 따라갔습니다. 그 길의 상자 중 하나가 **파싱**이었죠. 로그 한 줄을 `user`, `src_ip`, `url` 같은 이름 붙은 칸으로 자르는 일입니다. 그 뒤에 하는 모든 일이 이 자르기가 맞았느냐에 달려 있습니다. "서비스 계정이 워크스테이션에서 로그인하면 경보"라는 규칙은 `user` 칸이 뽑히지 않았으면 울릴 수가 없습니다. `src_ip=10.20.30.41`을 검색해도, 파서가 그 IP를 `message`라는 칸에 통째로 넣어 버렸다면 아무것도 안 나옵니다. 두 경우 모두 오류 메시지가 없습니다. 그냥 **결과가 없을** 뿐이고, 그건 "아무 일도 없었다"와 똑같아 보입니다.

서류 정리실을 떠올려 보세요. 모든 편지가 *보낸 사람*, *날짜*, *제목* 칸이 인쇄된 정해진 양식으로 오면, 직원은 한 시간에 수천 통을 정리하고 몇 초 만에 아무거나 찾아 줍니다. 그런데 편지가 저마다 다른 손글씨 쪽지로 오면, 직원은 하나하나 읽으면서 보낸 사람 이름이 어디 있는지 짐작해야 합니다. 몇 통은 잘못 꽂히고, "X가 보낸 것 전부" 찾기는 그걸 조용히 놓칩니다. 로그 형식의 차이는 바로 이 양식과 손글씨 쪽지의 차이입니다.

## 비정형 로그 { #unstructured }

대부분의 Linux 로그와 네트워크 장비 로그는 모양이 알려진 **syslog 헤더**로 시작합니다(시각, 호스트, 프로그램, 그리고 있을 수도 없을 수도 있는 PID — [syslog 형식](../linux-logging/syslog.md) 참고). 콜론 뒤에 **메시지**가 오는데, 메시지는 개발자가 쓰기로 한 아무 문장입니다. 같은 `/var/log/syslog`(또는 `auth.log`) 파일 안에 나란히 있을 수 있는 세 줄을 보죠.

```
Nov 20 07:23:51 web-07 dhclient[75879]: bound to 10.20.40.17 -- renewal in 703 seconds.
Nov 20 08:17:59 web-07 CRON[55171]: pam_unix(cron:session): session opened for user root(uid=0) by (uid=0)
Nov 20 09:08:01 web-07 sudo:    sara : TTY=pts/2 ; PWD=/var/log ; USER=root ; COMMAND=/usr/sbin/service ssh start
```

한 줄씩 읽으면:

- **1번 줄.** 헤더: `Nov 20 07:23:51`(연도도 시간대도 없음), 호스트 `web-07`, 프로그램 `dhclient`, PID `75879`. 메시지: DHCP 클라이언트가 주소 `10.20.40.17`을 받았고 703초 뒤에 갱신하겠다는 뜻입니다. IP와 숫자가 문장 속에 묻혀 있고, 무엇이 무엇인지 알려 주는 이름표가 없습니다.
- **2번 줄.** 프로그램 `CRON`, PID `55171`. 그런데 메시지가 **또 다른** 프로그램의 태그 `pam_unix(cron:session)`로 시작하고, 그다음에 문장이 옵니다. 사용자 `root`의 세션이 열렸다는 내용입니다. 사용자 이름은 "for user"라는 단어 뒤에 있고 `(uid=0)`과 붙어 있습니다.
- **3번 줄.** 프로그램 `sudo`, PID 없음. 이 메시지는 반쯤 정형입니다. `sara`가 `root` 권한으로 명령을 실행했고, `TTY`, `PWD`, `USER`, `COMMAND`가 ` ; `로 나뉘어 있습니다. 그런데 정작 명령을 실행한 사람 `sara`에는 이름표가 없습니다. 앞에 공백을 채운 첫 단어일 뿐이죠.

프로그램 셋, 완전히 다른 메시지 모양 셋이 한 파일에 있습니다. 이걸 칸으로 만들려면 메시지 종류마다 <strong>정규식(regular expression, regex)</strong>이 따로 필요합니다. `sudo` 줄용이라면 이런 모양입니다.

```
^(?<ts>\w{3}\s+\d+\s[\d:]{8})\s(?<host>\S+)\ssudo:\s+(?<user>\S+)\s:\sTTY=(?<tty>\S+)\s;\sPWD=(?<pwd>\S+)\s;\sUSER=(?<run_as>\S+)\s;\sCOMMAND=(?<command>.+)$
```

조각조각 보면:

- `^(?<ts>\w{3}\s+\d+\s[\d:]{8})` — 줄 맨 앞에서 시각을 잡습니다. 글자 세 개(`Nov`), 공백 하나 이상, 날짜, 공백, 숫자와 콜론으로 된 여덟 글자(`09:08:01`). `(?<ts>…)`는 잡은 부분에 `ts`라는 이름을 붙입니다.
- `\s(?<host>\S+)` — 공백 하나, 그다음 호스트 이름(공백이 아닌 글자들이 이어진 것).
- `\ssudo:\s+` — 글자 그대로 `sudo:`, 그 뒤에 공백 하나 이상(sudo가 사용자 이름 앞을 공백으로 채우기 때문).
- `(?<user>\S+)\s:\s` — 명령을 실행한 사용자, 그다음 ` : `.
- `TTY=(?<tty>\S+)\s;\sPWD=(?<pwd>\S+)\s;\sUSER=(?<run_as>\S+)\s;\s` — 이름표 붙은 부분들과 ` ; ` 구분자.
- `COMMAND=(?<command>.+)$` — 줄 끝까지 전부가 명령입니다.

3번 줄에 적용하면 결과는 이렇습니다.

| 칸 | 값 |
| --- | --- |
| `ts` | `Nov 20 09:08:01` |
| `host` | `web-07` |
| `user` | `sara` |
| `tty` | `pts/2` |
| `pwd` | `/var/log` |
| `run_as` | `root` |
| `command` | `/usr/sbin/service ssh start` |

이제 이게 얼마나 쉽게 깨지는지 보세요.

1. **있다 없다 하는 부분.** cron 작업 안에서 `sudo`를 돌리면 터미널이 없어서 `TTY=unknown`이 되거나 일부가 빠집니다. 비밀번호를 틀리면 `sara : 3 incorrect password attempts ; TTY=pts/2 ; ...`처럼 정규식이 예상 못 한 덩어리가 끼어들어서 줄 전체가 안 맞습니다.
2. **없을 거라 가정한 곳의 공백.** `PWD=(?<pwd>\S+)`는 `/home/sara/My Files` 같은 디렉터리에서 실패합니다.
3. **나머지 모든 메시지.** 이 정규식은 `dhclient`나 `CRON` 줄에는 아무 소용이 없습니다. 프로그램마다, 그리고 같은 프로그램의 메시지 **종류**마다 패턴이 따로 필요합니다. `sshd` 하나만 해도 서로 다른 문장을 수십 가지 씁니다.
4. **버전 변경.** 개발자가 문구를 바꾸면(PAM 최신 버전은 "session opened for user root(uid=0) by (uid=0)"라고 쓰고, 옛 버전은 "session opened for user root by (uid=0)"라고 썼습니다) 옛 정규식은 조용히 안 맞게 됩니다.

위험한 건, 정규식이 실패해도 로그는 **여전히 들어온다**는 점입니다. 이벤트는 원문 텍스트만 가진 채 저장되고, `user`나 `command`에 기대던 규칙은 그냥 값을 한 번도 못 봅니다. 이게 <strong>미탐(false negative)</strong>이고, 아무도 알아채지 못하기 때문에 가장 나쁜 종류의 오류입니다.

<strong>[보충]</strong> 대부분의 SIEM은 파싱에 실패한 이벤트에 표시를 남깁니다(기본 소스 타입, Elastic/Logstash 파이프라인의 `tags: _grokparsefailure` 같은 표시, 또는 "unparsed" 분류). 일주일에 한 번 "소스별로 몇 %가 파싱에 실패했나"를 보면, 조사 도중이 아니라 그 전에 고장 난 파서를 찾을 수 있습니다. Linux에서는 [systemd 저널](../linux-logging/log-files-journal.md#journal)이 조금 도와줍니다. `_PID`, `_UID`, `_COMM`, `SYSLOG_IDENTIFIER` 같은 칸을 구조화해서 저장하므로, 저널에서 JSON으로 수집하면 헤더 칸은 공짜로 얻습니다. 다만 `MESSAGE` 내용은 여전히 자유 문장입니다.

## 정형 로그 형식 { #structured }

해결책은 **모양이 예측 가능한** 형식으로 기록하는 겁니다. 그러면 프로그램에 대해 아무것도 몰라도 범용 파서가 모든 줄을 정확히 자를 수 있습니다. 같은 DNS 연결 기록을 흔한 세 가지 모양으로 써 보면:

```
CSV:        10.20.30.41,198.51.100.53,55001,53,udp
Key-value:  src_ip=10.20.30.41 dest_ip=198.51.100.53 src_port=55001 dest_port=53 proto=udp
JSON:       {"src_ip":"10.20.30.41","dest_ip":"198.51.100.53","src_port":55001,"dest_port":53,"proto":"udp"}
```

각 줄의 길이는 38, 78, 96바이트입니다. 하루 10억 건이면 저장 공간과 라이선스에서 실제 돈 차이가 납니다. 하지만 곧 보겠지만, 파서가 깨졌을 때의 비용이 더 큽니다.

| 형식 | 칸 이름이 데이터와 같이 다니나? | 칸 추가·삭제·순서 변경에 버티나? | 중첩·목록 | 크기 |
| --- | --- | --- | --- | --- |
| CSV / TSV | 아니요 — 읽는 쪽이 이름과 순서를 알아야 함 | 아니요 — 바뀐 곳 뒤가 전부 밀림 | 없음 | 가장 작음 |
| 키-값 | 예 | 예 | 없음(평평한 구조만) | 중간 |
| JSON | 예 | 예 | 있음 | 가장 큼 |
| XML | 예 | 예 | 있음 | 가장 큼(흔히 JSON보다 더 큼) |

### CSV(쉼표로 구분한 값) { #csv }

CSV 로그는 값을 정해진 순서로 늘어놓은 것뿐입니다. 파싱하려면 SIEM에 미리 알려 줘야 합니다. 1번 칸은 `src_ip`, 2번 칸은 `dest_ip`, 3번 칸은 `src_port`, 이런 식으로요. 아주 효율적이지만 아주 약합니다. 방화벽 업그레이드로 `dest_ip` 뒤에 `action` 칸이 새로 끼었다고 해 보죠.

```
Before:  10.20.30.41,198.51.100.53,55001,53,udp
After:   10.20.30.41,198.51.100.53,allow,55001,53,udp
```

옛 칸 목록을 그대로 쓰는 SIEM은 이제 `src_port=allow`, `dest_port=55001`, `proto=53`으로 읽고, 마지막 값은 이름이 아예 없습니다. 오류는 하나도 안 납니다. `dest_port=53` 규칙은 더 이상 울리지 않고, "상위 목적지 포트" 대시보드는 `55001`로 가득 찹니다. CSV의 함정이 두 개 더 있습니다. 값 안에 쉼표가 들어 있으면(URL 쿼리 문자열, 사용자 에이전트, `C:\Users\sara\Q1,Q2.xlsx` 같은 파일 경로) 따옴표로 감싸야 하는데 모든 프로그램이 제대로 감싸 주지는 않습니다. 그리고 빈 값(`10.20.30.41,,55001,...`)은 잘못 읽기 쉽습니다.

<strong>[보충]</strong> 좋은 절충안은 **스스로를 설명하는** 헤더가 달린 CSV/TSV 파일입니다. Zeek 로그가 딱 그렇습니다.

```
#separator \x09
#fields	ts	uid	id.orig_h	id.orig_p	id.resp_h	id.resp_p	proto	service
#types	time	string	addr	port	addr	port	enum	string
1795164723.436	CkV1aB3xYz9	10.20.30.41	55001	198.51.100.53	53	udp	dns
```

- `#separator \x09` — 칸은 탭으로 나뉩니다.
- `#fields` — 칸 이름을 순서대로 파일 안에 직접 적어 둡니다.
- `#types` — 칸마다 데이터 타입. 그래서 `id.orig_p`를 글자가 아니라 포트로 읽습니다.
- 그러면 데이터 줄은 헷갈릴 게 없습니다. Zeek 업그레이드로 칸이 늘어도 `#fields` 줄이 같이 바뀌고, 그 줄을 읽는 파서는 알아서 맞춥니다. (Zeek은 JSON으로 바로 쓸 수도 있고, 요즘 SOC는 대부분 그쪽을 선호합니다.)

### 키-값 쌍 { #key-value }

여기서는 값마다 이름을 달고 다닙니다. `key=value`. 파서가 위치가 아니라 이름을 찾기 때문에, 칸을 넣고 빼고 섞어도 아무것도 안 깨집니다. 방화벽이 줄 어딘가에 `action=allow`를 추가해도 옛 칸들은 여전히 자기 이름으로 찾아지고, 새 칸은 그냥 하나 더 생깁니다. 많은 방화벽과 프록시가 이렇게 기록하는 이유이고, 대부분의 SIEM이 `key=value` 텍스트를 설정 없이 자동으로 뽑아내는 이유이기도 합니다.

약점은 **구분 문자**입니다.

```
src_ip=10.20.30.41 user=sara msg=login failed for sara reason=bad password
```

`msg`는 어디서 끝날까요? 단순한 파서는 공백으로 잘라서 `msg=login`, 그다음 의미 없는 단어들, 그다음 `reason=bad`를 얻습니다. 잘 만든 프로그램은 값을 따옴표로 감싸거나(`msg="login failed for sara"`) 공백을 이스케이프하지만, 그렇지 않은 프로그램도 있습니다. 게다가 공격자가 값의 일부를 마음대로 정할 수 있다면 — 예를 들어 로그인 화면에 입력하는 사용자 이름 — 가짜 칸을 **끼워 넣을** 수도 있습니다.

```
user=x src_ip=203.0.113.99 action=success
```

이 문자열 전체가 사용자 이름으로 이스케이프 없이 기록되면, 허술한 파서는 `user=x`, 그리고 애플리케이션이 쓴 적 없는 두 번째 `src_ip`와 `action=success`를 봅니다. 이걸 <strong>로그 인젝션(log injection)</strong>이라고 합니다(CWE-117, 로그 출력값 무력화 미흡). 보안에 중요한 데이터에는 JSON처럼 따옴표 규칙이 엄격한 형식을 고르는 이유 중 하나입니다.

### JSON과 XML { #json-xml }

<strong>JSON(JavaScript Object Notation)</strong>은 키-값 쌍의 장점에 세 가지를 더합니다. 엄격한 따옴표·이스케이프 규칙(그래서 파서가 값이 어디서 끝나는지 늘 압니다), <strong>데이터 타입</strong>(`55001`은 숫자, `"udp"`는 문자열, `true`는 참/거짓), 그리고 <strong>중첩</strong> — 객체 안의 객체와 배열(목록). 짧은 엔드포인트 프로세스 이벤트를 JSON으로 보죠. 읽기 쉽게 여러 줄로 썼지만 로그 파일에서는 한 줄입니다.

```json
{
  "@timestamp": "2026-11-20T09:08:01.512Z",
  "host": { "name": "web-07", "ip": ["10.20.40.17", "fe80::a1b2:3c4d"] },
  "user": { "name": "sara", "effective": { "name": "root" } },
  "process": {
    "executable": "/usr/sbin/service",
    "args": ["service", "ssh", "start"],
    "parent": { "name": "sudo", "pid": 81244 }
  },
  "event": { "category": ["process"], "type": ["start"] }
}
```

- `@timestamp` — 날짜, 시각, 밀리초, 그리고 `Z`(UTC) 시간대까지 다 있습니다. syslog 헤더의 `Nov 20 09:08:01`과 비교해 보세요.
- `host` — `name`과, IP 주소 두 개짜리 **배열**을 가진 **객체**입니다. CSV나 키-값으로는 `ip1`, `ip2` 같은 칸을 지어내지 않고는 "이 호스트는 IP가 둘"을 표현할 수 없습니다.
- `user.name`과 `user.effective.name` — 중첩 덕분에 `sara`가 명령을 실행했고, 그 명령은 `root`**로서** 실행됐다는 게 분명히 보입니다. 이렇게 점으로 이은 칸 이름(`user.effective.name`)이 대부분의 SIEM에서 중첩 데이터를 검색하는 방법입니다.
- `process.args` — 명령줄이 목록이라서, `ssh`가 쪼개야 하는 문자열의 일부가 아니라 독립된 원소입니다.
- `event.category` / `event.type` — 분류용 칸입니다(공통 스키마에서 온 것. 다음 페이지에서 다룹니다).

JSON의 대가는 크기입니다. 모든 이벤트마다 칸 이름이 반복되고 따옴표와 중괄호도 붙으니까요. 하지만 파싱이 믿을 만하고 따로 정규식을 짤 필요가 없습니다. **XML**도 같은 능력을 가졌고(Windows 이벤트 로그가 XML입니다 — [이벤트 구조](../windows-logging/event-structure-channels.md) 참고), 둘 다 계층 구조라서 XML은 구조를 잃지 않고 JSON으로 바뀝니다. 수집 페이지에서 Windows 이벤트를 syslog 문장으로 납작하게 만들지 말고 XML이나 JSON으로 보내라고 한 이유가 이겁니다.

**간단한 원칙:** 탐지에 쓸 데이터라면 파싱이 쉽고 믿을 만한 게 작은 것보다 중요합니다. 프로그램이 JSON(또는 그 소스 고유의 정형 형식)을 지원하면 그걸 고르세요.

## SIEM 중심 형식: CEF와 LEEF { #cef-leef }

어떤 SIEM은 자기만의 형식을 정했습니다. 들어오는 모든 이벤트가 같은 기본 구조를 갖고, **어느 제품이 만들었는지 분명히 밝히게** 하려고요. 가장 잘 알려진 둘이 **CEF**(Common Event Format, ArcSight용으로 만들어졌고 Microsoft Sentinel을 포함해 널리 지원됨)와 **LEEF**(Log Event Extended Format, IBM QRadar가 씀)입니다. 얼핏 보면 둘은 똑같이 생겼습니다. syslog 헤더, 그다음 소스를 설명하는 파이프 구분 헤더, 그다음 키-값 확장 칸.

### CEF { #cef }

CEF 헤더는 이렇습니다.

```
CEF:Version|Device Vendor|Device Product|Device Version|Signature ID|Name|Severity|Extension
```

이메일 보안 게이트웨이에서 온 가상의 예:

```
<134>Nov 20 08:50:00 mailgw01.corp.example CEF:0|ExampleSec|MailShield|4.2.1|av-1007|Malicious attachment blocked|8|externalId=995 rt=Nov 20 2026 08:49:58 UTC src=203.0.113.45 dst=10.20.50.10 suser=billing@supplier.example duser=a.chen@corp.example fname=invoice_2026-11.zip fileHash=0123456789abcdef0123456789abcdef01234567 act=blocked cs1Label=policy cs1=inbound-attachments
```

칸별로 보면:

| 부분 | 값 | 뜻 |
| --- | --- | --- |
| `<134>` | PRI 134 | facility 16(`local0`), severity 6(`info`): 16 × 8 + 6 = 134. syslog **전송**의 severity이지 이벤트 자체의 심각도가 아님 |
| `Nov 20 08:50:00 mailgw01.corp.example` | syslog 헤더 | 언제, 어느 장비가 메시지를 보냈나 |
| `CEF:0` | 버전 | CEF 형식 버전 0(흔한 쪽. 버전 1도 있음) |
| `ExampleSec` | Device Vendor | 제품을 만든 회사 |
| `MailShield` | Device Product | 어느 제품 |
| `4.2.1` | Device Version | 제품 버전. 파서가 이상해진 시점이 업그레이드와 겹치는지 볼 때 유용 |
| `av-1007` | Signature ID | 이 **종류**의 이벤트에 업체가 붙인 ID. 묶어 보기와 규칙에 가장 유용한 칸 |
| `Malicious attachment blocked` | Name | 이벤트 종류를 사람이 읽을 수 있게 설명한 문장 |
| `8` | Severity | 업체가 매긴 심각도, 0(가장 낮음)~10(가장 높음). 7~8은 "높음" |
| 마지막 `|` 뒤 전부 | Extension | 공백으로 나눈 `key=value` 쌍 |

확장 칸의 키 이름은 CEF가 정한 사전에서 옵니다. 그래서 CEF는 어느 업체 것이든 똑같이 파싱됩니다. `rt`(이벤트 수신 시각), `src`/`dst`(출발지·목적지 IP), `spt`/`dpt`(포트), `suser`/`duser`(보낸·받는 사용자), `fname`(파일 이름), `fileHash`, `act`(취한 조치), `externalId`(업체 자체의 이벤트 번호). 사전에 없는 내용은 `cs1` 같은 **사용자 정의 칸**에 넣고, 그 칸의 뜻은 `cs1Label`에 적습니다. 여기서는 "걸린 정책은 `inbound-attachments`"라는 뜻이죠. 이 칸들을 잘 보세요. 많은 제품에서 가장 흥미로운 데이터가 `cs1`~`cs6`에 들어 있고, 각 칸이 이 제품에서 무슨 뜻인지는 라벨이 알려 줍니다.

이스케이프 규칙: 헤더 안에서 글자 그대로의 `|`는 `\|`로, 역슬래시는 `\\`로 씁니다. 확장 칸 안에서는 글자 그대로의 `=`를 `\=`로, 역슬래시를 `\\`로 씁니다. 확장 값 안에는 공백이 있어도 됩니다. 파서는 다음 `key=`가 시작되는 곳에서 값이 끝난다고 보거든요. 바로 그래서 값 안에 이스케이프 안 된 `=`가 있으면(예: URL 쿼리 문자열) CEF 파싱이 깨집니다.

### LEEF { #leef }

LEEF도 생각은 같고 헤더만 조금 다릅니다.

```
LEEF:2.0|Vendor|Product|Version|EventID|Delimiter|Extension
```

웹 프록시에서 온 가상의 예:

```
<13>Nov 20 08:52:04 proxy02.corp.example LEEF:2.0|ExampleNet|EdgeProxy|7.1|deny|^|devTime=Nov 20 2026 08:52:03^src=10.20.30.88^dst=198.51.100.80^usrName=sara^url=http://files.download.example/setup.exe^cat=Uncategorized^action=blocked
```

- `<13>` — PRI 13: facility 1(`user`), severity 5(`notice`).
- `LEEF:2.0` — 형식 버전 2.0. 버전 1.0에는 구분 문자 칸이 없고 속성 사이를 늘 **탭**으로 나눕니다.
- `ExampleNet|EdgeProxy|7.1` — CEF처럼 업체, 제품, 버전.
- `deny` — <strong>EventID</strong>: 이 이벤트 종류에 업체가 붙인 식별자. QRadar는 업체 + EventID를 자기 이벤트 분류에 연결합니다.
- `^` — 속성 사이에 쓸 **구분 문자**(2.0의 기능). URL에 나오지 않는 캐럿을 골랐기 때문에 값을 이스케이프할 일이 없습니다.
- 속성들 — `devTime`(장비에서의 이벤트 시각), `src`, `dst`, `usrName`, `url`, `cat`(분류), `action` — 은 LEEF가 미리 정한 키 이름이고, 업체가 자기 키를 더할 수도 있습니다.

분석가에게 왜 중요하냐면: SIEM이 CEF나 LEEF를 받는다면 **헤더 칸**(업체, 제품, 시그니처·이벤트 ID, 심각도)은 업체가 확장 칸을 대충 채워도 늘 믿을 만합니다. `Device Product` + `Signature ID`에 건 규칙은 메시지 문구가 바뀌어도 살아남습니다. 그리고 이벤트가 이상해 보이면, 헤더의 장비 버전을 마지막 정상 이벤트와 비교하는 게 첫 번째 할 일입니다.

## SIEM 안에서 구조가 그렇게 중요한 이유 { #why-structure }

SIEM은 검색할 때 저장된 모든 바이트를 `grep`하지 않습니다. 할 수는 있습니다. 그걸 <strong>전문 검색(full-text search)</strong>이라고 하는데, 몇 달 치 데이터에서는 끔찍하게 느립니다. 대신 SIEM은 받을 때 이벤트를 **파싱**해서, 가장 자주 검색되는 칸 — 사용자 이름, IP 주소, 호스트 이름, 도메인, 이벤트 ID — 을 꺼내 **인덱스**에 씁니다. 인덱스는 책 뒤의 찾아보기처럼 "이 값 → 이 값이 든 이벤트들"을 연결하는 조회용 구조입니다. 인덱스된 칸으로 검색하면 맞는 이벤트로 곧장 갑니다.

Squid 프록시 기본 형식 한 줄을 보죠.

```
1795164723.436     17 10.20.30.88 TCP_MISS/503 861 GET http://updates.vendor.example/check.aspx sara HIER_NONE/- text/html
```

| 위치 | 값 | 뜻 |
| --- | --- | --- |
| 1 | `1795164723.436` | 유닉스 에포크 초 + 밀리초로 쓴 시각: 2026-11-20 08:52:03.436 UTC |
| 2 | `17` | 프록시가 이 요청에 쓴 시간(밀리초) |
| 3 | `10.20.30.88` | 클라이언트 IP |
| 4 | `TCP_MISS/503` | 캐시 결과(`TCP_MISS` = 캐시에서 주지 않음) / 클라이언트가 받은 HTTP 상태(503) |
| 5 | `861` | 클라이언트에 보낸 바이트 수 |
| 6 | `GET` | HTTP 메서드 |
| 7 | `http://updates.vendor.example/check.aspx` | 요청한 URL |
| 8 | `sara` | 인증된 사용자 이름(프록시가 인증을 안 했으면 `-`) |
| 9 | `HIER_NONE/-` | 프록시가 가져온 방식(여기서는 상위 프록시 없음) |
| 10 | `text/html` | 응답의 콘텐츠 타입 |

이건 CSV를 공백으로 나눈 것 같은 **위치 기반** 형식입니다. 파서가 맞으면 SIEM은 `10.20.30.88`을 출발지 IP 인덱스에, `updates.vendor.example`을 도메인/URL 인덱스에, `sara`를 사용자 인덱스에 쓰고, 줄 전체는 저장소에 넣습니다. 나중에 "이번 달 이 도메인에 간 사용자는?" 같은 질문은 인덱스에서 몇 초 만에 답이 나옵니다. 그런데 파서가 한 칸만 어긋나도 — 예를 들어 프록시가 다른 형식으로 기록하도록 설정돼 있다면 — "사용자" 인덱스가 `HIER_NONE/-`로 채워지고, 사용자 질문은 엉터리 답이나 빈 답을 돌려줍니다.

파싱은 검색보다 **규칙**에 더 중요합니다. `url`을 위협 인텔리전스 목록과 대조하는 규칙은 존재하지 않는 칸과는 대조할 수 없습니다. 경보가 안 울리고, 미탐이 됩니다. 그러니 대역폭이나 라이선스 비용 때문에 정말 어쩔 수 없는 게 아니라면, 소스가 출력 형식을 고르게 해 줄 때 작은 쪽보다 더 정형적이고 튼튼한 쪽을 고르세요.

<strong>[보충]</strong> SIEM마다 칸을 *언제* 뽑는지가 다르고, 내가 쓰는 SIEM이 어느 쪽인지 알아 둘 가치가 있습니다.

- <strong>쓸 때 스키마(schema-on-write)</strong>(인덱스 시점 추출): 이벤트가 들어올 때 칸을 파싱합니다. 검색은 빠르지만, 파서 버그가 저장된 데이터에 굳어 버리고, 고쳐도 새 이벤트에만 적용됩니다. Elastic과 대부분의 클라우드 SIEM(Microsoft Sentinel 테이블, Chronicle UDM)이 주로 이렇게 동작합니다.
- <strong>읽을 때 스키마(schema-on-read)</strong>(검색 시점 추출): 원문을 저장하고 단어 단위로 인덱싱한 뒤, 이름 붙은 칸은 검색할 때 뽑습니다. Splunk가 주로 이렇게 동작합니다. 파서를 고치면 옛 데이터에도 바로 적용되지만, 칸으로 걸러도 후보 이벤트를 읽어서 칸을 뽑는 일은 여전히 해야 합니다.

어느 쪽이든 분석가의 규칙은 같습니다. 소스마다 어떤 칸이 실제로 뽑히고 인덱싱되는지 알고, 파싱 실패율을 확인하세요.

## SIEM은 구글이 아니다 { #not-google }

SIEM 검색창은 웹 검색 엔진처럼 생겼고, 그래서 사람들은 거기에 웹 검색하듯 칩니다. `sara`가 감염됐을지도 몰라서 그녀의 프록시 로그를 보고 싶다고 해 보죠. 묻는 방법이 셋 있습니다.

1. `sara`
2. 어디든 `sara`가 들어 있는 프록시 로그
3. **사용자** 칸이 `sara`인 프록시 로그

Splunk 검색 언어(SPL)로는 아래처럼 쓸 수 있습니다. SPL을 처음 보는 분을 위한 짧은 설명: 검색은 이벤트가 모두 만족해야 하는 조건을 공백으로 나눠 늘어놓은 것입니다(공백 = AND). `index=`는 어느 데이터 저장 구역을 검색할지 고릅니다(SOC는 보통 로그 종류마다 인덱스를 따로 둡니다. `proxy`, `wineventlog`, `firewall`처럼요). `field=value`는 그 이름의 칸이 그 값일 때만 맞습니다. 그리고 그냥 단어 하나는 이벤트 원문 어디에든 나오면 맞습니다. 시간 범위는 따로 정합니다(시간 선택기, 또는 `earliest=`).

```
sara
```

- 인덱스 없이 단어 하나. Splunk는 **기본 인덱스들**에서 원문에 `sara`라는 단어가 든 모든 이벤트를 찾습니다. Windows 로그, 방화벽 로그, DNS, 전부요. SIEM에게 일이 가장 많고, 결과도 가장 부정확합니다. 파일 공유 `\\fs01\sara-backup`, `sara@partner.example`로 간 메일, `sara_report.exe` 프로세스까지 다 나옵니다.

```
index=proxy sara
```

- `index=proxy`가 프록시 데이터로 범위를 줄입니다. 하지만 `sara`는 여전히 이벤트의 **아무** 부분에나 맞습니다. 사용자 칸뿐 아니라 `http://intranet.corp.example/team/sara/` 같은 URL이나 리퍼러에도요. 1번보다는 빠르지만, 사용자 이름이 있을 리 없는 칸까지 뒤지고, 다른 사람의 트래픽도 섞여 나옵니다.

```
index=proxy user=sara
```

- `index=proxy`로 데이터를 줄이고, `user=sara`로 뽑아낸 `user` 칸이 정확히 `sara`인 이벤트만 고릅니다. 범위가 가장 작고, 답은 정확히 원했던 것입니다. 결과는 이런 모양일 겁니다.

```
_time                   src_ip        user  method  url                                             status
2026-11-20 08:52:03.436 10.20.30.88   sara  GET     http://updates.vendor.example/check.aspx        503
2026-11-20 08:52:09.102 10.20.30.88   sara  GET     http://files.download.example/setup.exe         200
```

다른 SIEM에서도 원리는 같습니다. Microsoft Sentinel의 KQL에서는 **테이블**이 인덱스 역할을 하므로, `CommonSecurityLog | where SourceUserName == "sara"`(로그 종류 하나, 칸 하나)가 `search "sara"`(모든 테이블, 모든 열)보다 낫습니다. Elastic에서는 알맞은 데이터 뷰에서 `user.name: "sara"`가 그냥 `sara`보다 낫습니다.

<strong>[정정]</strong> 3번이 얼마나 더 빠른지는 SIEM 구조에 따라 다릅니다. 쓸 때 스키마 SIEM에서는 칸으로 좁힌 검색이 그 칸의 인덱스를 직접 쓰므로 속도 차이가 큽니다. Splunk에서는 원문 단어 인덱스로 `sara`가 든 이벤트를 먼저 찾고 그다음 `user` 칸을 확인하기 때문에, 큰 속도 이득은 `index=`(그리고 좁은 시간 범위)에서 오고 `user=sara`는 주로 **정확도**를 사 줍니다. 어느 SIEM이든 중요한 순서는 같습니다. **시간 범위, 그다음 로그 종류, 그다음 칸.**

인덱스가 동작하는 방식에서 나오는 습관 두 가지 더:

- **앞에 붙는 와일드카드를 피하세요.** `user=*sara`는 인덱스를 쓸 수 없어서(인덱스는 값의 앞부분 기준으로 정렬돼 있음) 전부 훑게 만듭니다. `user=sara*`는 보통 괜찮습니다.
- **어떤 칸이 인덱싱되는지 아세요.** 어떤 SIEM 구조는 모든 로그의 모든 칸을 인덱싱할 수 없습니다. 인덱스가 데이터보다 커질 테니까요. 그런 시스템에서는 자주 검색하는 칸(IP, 사용자 이름, 호스트 이름, 도메인, 해시, 이벤트 ID)이 인덱싱되는지 확인하고, 인덱싱된 칸으로 먼저 검색을 짜세요. 인덱싱 안 된 칸 하나만으로 거르면 SIEM은 이벤트를 하나씩 읽는 방식으로 돌아갑니다.

## SOC에서 써먹기 { #soc-use }

새 로그 소스를 맡았을 때, 또는 "당연히 나와야 할" 검색 결과가 안 나왔을 때:

1. **형식.** 이 소스는 비정형 문장, CSV, 키-값, JSON, CEF/LEEF, XML 중 무엇인가? 더 정형적인 출력으로 바꿀 수 있나?
2. **파서.** 어느 파서가 처리하고, 몇 %가 파싱에 실패하나? 원본 이벤트 몇 개를 뽑아낸 칸과 나란히 놓고 보세요.
3. **업그레이드.** 결과가 바뀐 즈음에 장비 버전(CEF/LEEF 헤더, 에이전트 버전)이 바뀌었나? CSV 칸이 밀렸나?
4. **칸.** 어떤 칸이 뽑히고 어떤 칸이 인덱싱되나? 규칙이 기대는 칸이 모든 이벤트에 있나?
5. **검색 범위.** 시간 범위, 그다음 로그 종류(`index=`, 테이블, 데이터 뷰), 그다음 칸. 그냥 단어 검색은 탐색할 때만.
6. **인젝션.** 외부 사람이 영향을 줄 수 있는 칸(사용자 이름, URL, 사용자 에이전트)에서 형식이 구분 문자를 이스케이프하나?

## 2026년 관점 { #trends }

!!! success "[2026 현재] 지금도 그대로 유효"
    형식의 순위(튼튼함은 비정형 < CSV < 키-값 < JSON/XML, 크기는 그 반대), 자유 문장을 정규식으로 파싱하는 위험, 위치 기반 형식의 약함, 파싱이 인덱싱과 규칙을 만든다는 점, "시간, 로그 종류, 그다음 칸으로 좁혀라"는 모두 그대로입니다. CEF는 여전히 네트워크·보안 장비가 SIEM으로 이벤트를 보내는 흔한 방법이고, LEEF는 여전히 QRadar의 기본 형식입니다.

!!! info "[변경됨] 바뀐 점"
    - **이제 JSON이 기본 전송 형식입니다.** 에이전트, 클라우드 서비스, EDR 제품은 압도적으로 JSON을 내보내고, 보통 HTTPS로 보냅니다(업체 HTTP 수집기, OpenTelemetry). syslog 문장과 CEF는 이제 주로 장비와 옛 제품의 몫입니다.
    - **공통 스키마가 파이프라인 안으로 들어왔습니다.** Elastic은 2023년에 ECS를 OpenTelemetry에 기여했고, 둘은 OpenTelemetry 시맨틱 컨벤션으로 합쳐지는 중입니다. AWS, Splunk 등 많은 회사가 지원하는 <strong>OCSF(Open Cybersecurity Schema Framework)</strong>는 2023년에 1.0이 나왔고 2024년에 Linux Foundation에 합류했습니다. AWS Security Lake는 데이터를 OCSF로 저장합니다. Microsoft Sentinel은 ASIM으로, Google SecOps는 UDM으로 정규화합니다. 다음 페이지에서 다룹니다.
    - **수집기 변화.** Microsoft Sentinel에서는 은퇴한 Log Analytics 에이전트(MMA)에 기대던 옛 CEF/syslog 커넥터가 지원 중단됐고, 이제 CEF와 syslog는 Linux 전달 서버의 Azure Monitor Agent를 거쳐 들어옵니다("CEF via AMA"). CEF가 태어난 ArcSight는 지금 OpenText 소속이고, QRadar의 SaaS 사업은 2024년에 Palo Alto Networks로 넘어갔으며, QRadar 소프트웨어(와 LEEF)는 IBM에서 계속됩니다.
    - **싼 저장 계층이 검색 습관을 바꿉니다.** 데이터 레이크와 저가 계층(예: 2025년부터 정식 제공된 Microsoft Sentinel 데이터 레이크, 그리고 다른 업체의 비슷한 계층)은 엄청난 양을 싸게 저장하지만 검색이 더 느리고 인덱싱된 칸도 적습니다. 그런 곳에서는 시간과 로그 종류로 좁히는 게 더더욱 중요합니다.
    - **AI가 돕는 파싱.** 여러 SIEM과 파이프라인 도구가 이제 AI가 만든 파서와 자연어 검색을 제공합니다. 새 소스를 붙이는 속도는 빨라지지만, AI가 만든 파서도 결국 파서입니다. 그 위에 규칙을 쓰기 전에 뽑힌 칸을 원본 이벤트와 대조해 보세요.

!!! warning "[주의] 옛 방식대로 하면 틀리거나 위험한 점"
    - **보안에 중요한 데이터를 바이트 아끼자고 CSV나 비정형 출력으로 고르지 마세요.** 밀린 칸 하나가 소리 없는 미탐입니다.
    - **업그레이드 뒤에 원본 이벤트 몇 개를 확인하기 전까지는 파서를 믿지 마세요.** 업체는 작은 버전에서도 형식을 바꿉니다.
    - **"결과 없음"을 "일어나지 않았다"로 받아들이지 마세요.** 그 소스에 그 칸이 실제로 있고 채워져 있는지 먼저 확인하세요.
    - **실제 조사에서 SIEM에 그냥 단어를 치지 마세요.** 느리고 상관없는 이벤트까지 끌려옵니다. 시간, 로그 종류, 그다음 칸으로 좁히세요.
    - **외부 사람이 영향을 줄 수 있는 키-값이나 CEF 값을 안전하다고 가정하지 마세요.** 형식이 `=`, 공백, `|`를 어떻게 이스케이프하는지 확인하세요.

## 확인 문제 { #quiz }

### 문제 1

방화벽 로그가 CSV로 들어옵니다. `src_ip,dest_ip,src_port,dest_port,proto`. 주말 업그레이드 뒤로 "`dest_port=4444`로 나가는 연결 경보" 규칙이 한 번도 안 울렸고, "상위 목적지 포트" 대시보드에는 다섯 자리 숫자가 가득하며, `src_port`에 `allow`라는 새 값이 보입니다. 무슨 일이 일어났고, 어떻게 확인하고, 오래 가는 해결책은 무엇인가요?

??? success "정답과 해설"
    **무슨 일:** 업그레이드가 `dest_ip` 뒤에 새 칸(`allow` 같은 `action` 칸)을 끼워 넣었습니다. CSV는 데이터에 칸 이름이 없어서 SIEM은 여전히 옛 칸 목록을 적용합니다. 그래서 `allow`를 `src_port`로, 진짜 출발지 포트를 `dest_port`로 읽고(그래서 55001 같은 다섯 자리 "목적지 포트"), 진짜 목적지 포트는 `proto`에 들어갑니다. 오류는 없었습니다. `dest_port=4444` 규칙은 그 칸에서 4444를 볼 일이 없어졌을 뿐입니다. 미탐입니다.

    **확인:** 업그레이드 전과 후의 원본 이벤트 몇 개를 나란히 놓고 쉼표 개수를 세어 보세요. 장비 자체 로그나 릴리스 노트에서 버전을 확인하고, 이 소스의 파싱 실패나 "남는 칸" 수가 업그레이드 시점에 뛰었는지 보세요.

    **오래 가는 해결:** 방화벽이 지원한다면 스스로를 설명하는 형식 — 키-값, JSON, CEF — 으로 바꾸세요. 그러면 칸이 늘거나 순서가 바뀌어도 다른 칸이 밀리지 않습니다. CSV밖에 없다면 칸 목록을 고치고, 칸 개수나 숫자가 아닌 포트 비율이 바뀌면 경보하는 감시를 걸고, 업그레이드 때마다 파서를 다시 확인하세요. 그다음 영향받은 기간에 대해 고친 칸으로 `dest_port=4444` 헌팅을 다시 돌리세요.

### 문제 2

게이트웨이가 이 이벤트를 보냅니다.

```
<134>Nov 20 10:02:11 mailgw01.corp.example CEF:0|ExampleSec|MailShield|4.2.1|av-1007|Malicious attachment blocked|8|src=203.0.113.45 duser=r.kim@corp.example fname=po_7781.docm act=blocked cs1Label=policy cs1=inbound-attachments
```

업체, 제품, 이벤트 종류 ID, 업체 심각도, 그리고 PRI 134가 알려 주는 것을 말해 보세요. 규칙은 어떤 헤더 칸에 걸겠고, 왜 `Name` 문장이 아니라 그 칸들인가요?

??? success "정답과 해설"
    - 업체 `ExampleSec`, 제품 `MailShield`, 버전 `4.2.1`.
    - 이벤트 종류(Signature ID) `av-1007`, Name은 "Malicious attachment blocked".
    - 업체 심각도는 0~10 중 `8` — 높음.
    - PRI `134` = facility 16(`local0`) × 8 + severity 6(`info`). 이건 보내는 쪽 설정이 정한 **syslog 전송** 우선순위이고, 이벤트가 얼마나 심각한지는 말해 주지 않습니다. 그건 CEF의 Severity 칸이 말해 줍니다.
    - 확장 칸: 출발지 IP `203.0.113.45`, 받는 사람 `r.kim@corp.example`, 파일 `po_7781.docm`, 조치 `blocked`, 그리고 라벨이 걸린 **정책**이라고 알려 주는 사용자 정의 칸 `inbound-attachments`.

    **규칙을 걸 칸:** `Device Vendor` + `Device Product` + `Signature ID`(필요하면 `act`도). 모든 CEF 파서가 똑같이 뽑는 고정된 식별자이기 때문입니다. `Name`은 사람이 읽으라고 쓴 문장이라 업체가 아무 릴리스에서나 문구를 바꾸거나 번역할 수 있고, 그러면 거기에 건 규칙은 소리 없이 깨집니다. 자유 문장을 정규식으로 파싱할 때와 같은 문제입니다.

### 문제 3

사고 대응 중에 동료가 90일 치 전체 데이터에서 `10.20.30.88` 한 단어로 검색합니다. 검색이 몇 분이나 돌고, 소스 타입 열두 개에 걸쳐 240만 건이 나옵니다. 여러분에게 필요한 건 지난 24시간 동안 그 워크스테이션**에서 나간** 프록시 요청입니다. 더 나은 검색을 쓰고, 각 부분을 설명하고, 왜 더 빠르고 정확한지 말해 보세요.

??? success "정답과 해설"
    더 나은 검색(SPL. 시간 선택기를 지난 24시간으로 두거나 검색 안에 직접 씀):

    ```
    index=proxy src_ip=10.20.30.88 earliest=-24h
    ```

    - `index=proxy` — 모든 인덱스 대신 프록시 데이터만. SIEM이 건드려야 할 데이터를 가장 크게 줄이는 부분입니다.
    - `src_ip=10.20.30.88` — 그 주소가 **출발지** 칸에 있는 이벤트만. 그냥 값만 쳤을 때는 그 워크스테이션이 목적지였던 이벤트, DHCP 메시지, Windows 이벤트, 방화벽 로그, 그 문자열이 든 아무 URL이나 텍스트까지 다 맞았습니다.
    - `earliest=-24h` — 90일 대신 지난 24시간만. 시간은 모든 SIEM이 검색을 좁힐 때 가장 먼저 쓰는 기준입니다.

    더 빠른 이유는 조건 하나하나가 SIEM이 읽어야 할 데이터를 줄이고, 칸 조건은 원문을 훑는 대신 뽑아서 인덱싱한 칸을 쓰거나 빨리 확인할 수 있기 때문입니다. 더 정확한 이유는 물어본 그대로를 돌려주기 때문입니다. 사고 시간대에, 프록시 로그에서, 그 호스트**에서 나간** 요청. 다만 먼저 이 소스의 프록시 파서가 정말 `src_ip`를 뽑는지 확인하세요. 칸 이름이 다르다면(`c_ip`, `client_ip`) 파서가 만드는 이름을 쓰세요.
