# 문자열 — 찍히는 글자의 줄, strings 명령, 인코딩과 바이트 순서, 분류에 어떻게 도움이 되나 { #strings }

!!! abstract "이 페이지에서 다루는 것"
    수상한 파일을 **실행하지 않고 입을 열게 하는** 가장 싼 방법을 다룹니다. 먼저 <strong>문자열(string)</strong>이 무엇인지(모두 "찍히는" 글자로 풀리는 바이트가 끊김 없이 이어진 줄) 정의하고, 왜 "텍스트 파일"과 "바이너리 파일"이 `strings` 명령 앞에서 그렇게 다르게 행동하는지 봅니다. 그다음 이 페이지를 위해 만든 무해한 시험용 실행 파일에 `strings`를 돌리고, 출력 줄을 하나하나 읽습니다. 어떤 게 잡음이고, 어떤 게 결정적 단서이며, 어떤 게 탐지 규칙으로 만들 가치가 있는지. 같은 파일을 헥스 덤프로 보면서 어떤 글은 **왜** 안 보이는지 확인하고, Windows가 글을 대부분 UTF-16 리틀 엔디언으로 저장하기 때문에 인코딩·바이트 순서 옵션(`-e l`, `-e b`, `-e S`, `-t x`)으로 해결합니다. 이어서 문자열이 실무에서 **어떻게 도움이 되는지** — IOC(도메인, URL, IP, 파일 경로, 레지스트리 키, 사용자 에이전트), 정적 분석과 동적 분석, 샌드박스가 내가 못 찾는 문자열을 보여 주는 이유, **패킹**과 **압축**이 문자열에 하는 일, PCAP·PDF·이미지에 쓰는 법 — 을 다룹니다. 마지막에 "파일 내용과 알아보기" 묶음 전체를 정리합니다. 끝에 확인 문제와 해설이 있습니다.

!!! note "표기"
    **[보충]** = 꼭 알아야 할 실무 보충, **[정정]** = 흔히 잘못 알려진 내용 정정, **[변경됨]**/**[주의]** = 최근 바뀐 점과 옛 방식대로 하면 위험한 점. 호스트 이름, 도메인, 계정, IP, 파일 이름은 모두 설명용 가상 값(`.example`, 문서용·사설 IP)입니다. 이 페이지의 "실행 파일" 샘플은 이 페이지를 위해 만든 무해한 시험용 파일입니다. PE 비슷한 헤더와 심어 둔 글 몇 줄만 있고, 아무 일도 하지 않습니다.

## 한눈에 보는 핵심 8가지 { #key-points }

1. 바이트 하나는 0~255의 숫자다. <strong>인코딩(encoding)</strong>(ASCII, UTF-8, UTF-16…)이 그 숫자 일부를 글자에 대응시킨다. **문자열**은 모두 **찍히는(printable)** 글자로 풀리는 바이트가 끊김 없이 이어진 줄이고, 찍히지 않는 바이트를 처음 만나는 곳에서 끝난다.
2. **텍스트(plaintext) 파일**(`.txt`, `.ps1`, `.vbs`, `.js`, `.bat`, `.svg`)은 처음부터 끝까지 찍히는 글자라서 `strings`를 돌리면 파일이 그대로 나온다. **바이너리(binary) 파일**(`.exe`, `.dll`, `.zip`, `.docx`, `.jpg`)은 찍히는 덩어리와 안 찍히는 바이트가 섞여 있고, `strings`가 빛나는 곳이 바로 여기다.
3. `strings -n N`은 최소 길이를 정한다. 짧은 덩어리는 대부분 **우연**(어쩌다 찍히는 값이 된 무작위 바이트)이다. 잡음을 줄이려면 `-n`을 올리고, 짧은 지표를 찾을 땐 내린다.
4. `strings` 출력의 대부분은 쓰레기다. 찾는 건 몇 개의 **결정적 단서**다. DOS 스텁 문장(Windows 실행 파일이다), 불러오는 DLL 이름(무엇으로 만들었고 무엇을 할 수 있나), URL, 도메인, IP, 파일 경로, 레지스트리 키, 사용자 에이전트, 그리고 나중에 헌팅할 수 있는 **특이하고 유일한 단어**.
5. **ASCII 모드로는 UTF-16 글을 절대 못 찾는다.** Windows 프로그램은 많은 글을 UTF-16LE(`h\0t\0t\0p\0`)로 저장하는데, 이건 글자 하나마다 널(null)이 끼인 모양이다. 언제나 `-e l`(16비트 리틀 엔디언)로 두 번째 검사를 하고, `-e b`, `-e L`, `-e B`, `-e S`도 알아 둔다.
6. 파일을 실행하지 않고 문자열을 읽는 건 <strong>정적 분석(static analysis)</strong>이다. 안전하고 빠르다. 샌드박스에서 실행해 보는 건 <strong>동적 분석(dynamic analysis)</strong>이다. 샌드박스는 디스크 위의 파일에 `strings`를 돌려서는 볼 수 없는, **메모리**에서 긁어 온 문자열을 보여 주는 경우가 많다.
7. **패킹**, **암호화**, **압축**은 문자열을 숨긴다. 읽을 만한 문자열이 거의 없고 패커 표시(예: `UPX0`/`UPX1`)가 있다면 그 자체가 발견 사항이다(T1027.002). 압축 파일은 먼저 풀고, 패킹된 코드는 메모리나 난독화 해제 도구(FLOSS)를 쓴다.
8. `strings`는 거의 무엇에나 통한다. PCAP(호스트, URL, 사용자 에이전트, 쿠키), PDF, 이미지(메타데이터), 메모리 덤프. 분류(triage) 도구이므로, 흥미로운 문자열 하나하나는 결론이 아니라 **확인할 단서**다.

## SOC에서 왜 중요한가 { #why }

앞 페이지의 경보를 떠올려 봅시다. 사용자가 `files-share.example`에서 `invoice_tool`을 받았고, 바이트는 `MZ`로 시작하고, `file`은 32비트 Windows 실행 파일이라고 합니다. 이제 **무엇인지**는 압니다. 다음 질문은 **무엇을 하느냐**입니다. 어디에 접속하고, 무엇을 떨어뜨리고(drop), 어디에 숨을까? 누군가 두 번째 사본을 더블클릭하기 **전에**, 되도록이면 내가 직접 실행하지도 않고 답을 알고 싶습니다.

프로그램은 자기가 갈 "주소"를 몸에 지니고 다녀야 합니다. 악성코드가 어떤 URL로 비컨을 보내거나, Run 키에 자신을 등록하거나, `%APPDATA%`에 파일을 떨어뜨릴 거라면, 그 URL, 키 경로, 파일 이름이 **파일 안 어딘가에** 저장돼 있어야 합니다(아니면 실행할 때 조각들을 이어 붙여 만드는데, 그 조각이라도 들어 있어야 하죠). `strings`는 파일 속 읽을 수 있는 글자 덩어리를 몇 초 만에 모두 뽑아냅니다. 봉인된 편지 봉투를 밝은 전등에 비춰 보는 것과 비슷합니다. 편지 전체를 읽을 수는 없지만 주소, 전화번호, 단어 몇 개는 비쳐 보입니다. 기술적으로는, 파일의 바이트를 한 번에 한 가지 인코딩으로 풀어 보고, 의미가 있을 만큼 긴 덩어리만 출력하는 겁니다.

그러면 아주 빨리 이런 걸 얻습니다.

- 차단하거나 헌팅할 **지표**(도메인, IP, URL, 파일 경로, 레지스트리 키, 뮤텍스 이름, 사용자 에이전트).
- 불러오는 라이브러리와 API 이름이 암시하는 **능력**(`WinHttpOpen`, `CreateRemoteThread`, `CryptEncrypt`).
- **계열(family) 단서**: 이상하고 유일한 단어, 디버그 경로(`C:\Users\dev\...\Release\loader.pdb`), 버전 문자열.
- **뭔가 숨겨져 있다는 경고**: 문자열이 거의 없거나, 패커의 섹션 이름이 보임.

## 문자열이란 { #what-are-strings }

### 바이트, 인코딩, 그리고 "찍힌다"는 것 { #printable }

파일은 바이트의 줄이고, 바이트 하나는 `0x00`부터 `0xFF`까지의 숫자입니다. 바이트 자체는 글자가 아닙니다. **인코딩**은 "이 숫자는 이 글자다"라고 약속한 표입니다. ASCII로 예를 들면:

| 글자 | `t` | `e` | `s` | `t` | `S` | `O` | `C` |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 바이트(16진수) | `74` | `65` | `73` | `74` | `53` | `4F` | `43` |

ASCII는 값 128개(`0x00`–`0x7F`)만 정의하고, 그중에서도 `0x20`(공백)부터 `0x7E`(`~`)까지만 **찍히는** 글자입니다. `0x00`–`0x1F`와 `0x7F`는 제어 코드(널, 탭, 줄바꿈, 벨, ESC…)이고, `0x80`–`0xFF`는 아예 ASCII가 아닙니다. 그러니까 무작위 바이너리 데이터에서 바이트 하나가 찍히는 글자로 보일 확률은 대략 37%(256개 중 95개)입니다. 이 숫자가 `strings` 잡음의 정체를 전부 설명해 줍니다. 무작위 바이트도 서너 개쯤은 우연히 연달아 찍히는 값이 되기 쉽거든요.

**문자열**은 그 바이트 줄 속의 **찍히는 글자가 끊김 없이 이어진 덩어리**입니다. 찍히지 않는 바이트를 처음 만나면 끝납니다. 이 11바이트를 보세요.

```
00 01 02 03 74 65 73 74 04 05 06
```

- `00 01 02 03` — 제어 코드. 찍히지 않습니다.
- `74 65 73 74` — `t`, `e`, `s`, `t`. 찍히는 글자 네 개가 연달아 있습니다.
- `04 05 06` — 찍히지 않으니 덩어리가 여기서 끝납니다.

여기서 문자열은 `test` 하나뿐입니다. 만약 바로 앞에 찍히는 바이트가 하나 더 있었다면(예: `41`, `A`) 문자열은 `Atest`가 됐을 겁니다. `strings`는 "단어"가 어디서 시작하는지 모릅니다. 찍히는 게 어디서 시작하고 끝나는지만 봅니다. 아래 실제 출력에서 이 현상을 그대로 보게 됩니다.

### 텍스트 파일과 바이너리 파일 { #plaintext-binary }

파일을 흔히 "텍스트 파일"과 "바이너리 파일"로 나눕니다. 이 말은 위험한지가 아니라 **찍히느냐**에 관한 겁니다.

- **텍스트 파일**은 어떤 인코딩 기준으로 찍히는 글자(그리고 줄바꿈과 탭)만 있습니다. 스크립트(`.ps1`, `.vbs`, `.js`, `.bat`, `.sh`), `.txt`, `.csv`, `.html`, `.svg`, `.xml`, 대부분의 로그. 여기에 `strings`를 돌리면 파일이 줄 단위로 그대로 나옵니다. 얻는 게 없죠. 그냥 읽으면 됩니다(안전하게, 텍스트 뷰어로 — 다음 페이지들 참고).
- **바이너리 파일**에는 표준 인코딩 어느 것으로도 글자가 아닌 바이트가 있습니다. 기계어, 압축된 데이터, 이미지 픽셀, 구조화된 헤더. 실행 파일, DLL, ZIP/DOCX/XLSX, JPEG/PNG, PCAP. 여기서는 읽을 수 있는 부분이 찍히지 않는 바이트의 바다에 떠 있는 섬이고, `strings`가 그 섬을 찾아 줍니다.

앞 페이지에서 말했듯 "텍스트"가 "무해"는 아닙니다. PowerShell 스크립트는 텍스트 파일이지만 무엇이든 할 수 있습니다.

### `strings` 명령 { #strings-command }

Linux에서 `strings`는 GNU binutils에 들어 있습니다. 기본 사용법:

```
$ strings suspicious_file
```

파일을 읽다가 찍히는 글자가 **4개**(기본값) 이상 이어진 덩어리를 찾을 때마다 그 덩어리를 한 줄에 하나씩 출력합니다. 늘 쓰게 될 옵션:

| 옵션 | 하는 일 | 언제 쓰나 |
| --- | --- | --- |
| `-n N`(또는 `-N`) | 최소 길이. 기본 4 | 큰 바이너리에서 잡음을 줄일 때 `-n 8`이나 `-n 10`, 짧은 걸 찾을 때 `-n 4` |
| `-t x` / `-t d` / `-t o` | 각 문자열의 **오프셋**을 16진수 / 10진수 / 8진수로 출력 | 헥스 덤프에서 그 위치로 가 보거나 주변을 잘라 낼 때 |
| `-e s` | 7비트 한 바이트 글자(ASCII). **기본값** | 첫 번째 검사 |
| `-e S` | 8비트 한 바이트 글자(`0x80`–`0xFF`도 찍히는 걸로 침) | Latin-1/Windows-1252 글, UTF-8 바이트 그대로 |
| `-e l` | 16비트 **리틀 엔디언** | **Windows UTF-16 글.** Windows 파일에는 꼭 이 검사도 함 |
| `-e b` | 16비트 빅 엔디언 | Java, 일부 네트워크 형식, x86이 아닌 일부 파일 |
| `-e L` / `-e B` | 32비트 리틀 / 빅 엔디언 | 드묾(UTF-32) |
| `-a` | 파일 전체를 훑음 | 요즘 binutils에서는 이미 기본값. 아래 주의 참고 |
| `-f` | 문자열마다 앞에 파일 이름을 붙임 | 여러 파일에 돌리고 `grep`할 때 |

<strong>[보충]</strong> Windows에서는 Sysinternals **Strings**(`strings64.exe`)가 같은 일을 하는데, 기본으로 ASCII와 유니코드(UTF-16LE) 문자열을 **한 번에 둘 다** 찾습니다. `-a`는 ASCII만, `-u`는 유니코드만, `-n`은 최소 길이(기본 3), `-nobanner`는 저작권 머리글을 숨깁니다. CyberChef의 "Strings" 기능이나 [2026년 관점](#trends)에 나오는 도구를 쓰는 분석가도 많습니다.

## 실제로 해 보기 { #example }

시험용 실행 파일 `invoice_tool`에 최소 길이 10으로 `strings`를 돌렸습니다.

```
$ strings -n 10 invoice_tool
!This program cannot be run in DOS mode.
MSVBVM60.DLL
ELORCHIDFALLOW
Software\Microsoft\Windows\CurrentVersion\Run
Mozilla/4.0 (compatible; MSIE 8.0)
```

명령어를 보면:

- `strings` — 도구.
- `-n 10` — 찍히는 글자가 **10개 이상** 이어진 덩어리만 출력. 진짜 실행 파일에 기본값 4로 돌리면 우연한 쓰레기가 수천 줄 나옵니다. 10으로 두면 대부분 진짜 글만 남습니다.
- `invoice_tool` — 대상 파일. 확장자는 필요 없습니다. `strings`는 이름에 관심이 없습니다.

한 줄씩 보면:

- `!This program cannot be run in DOS mode.` — **모든** Windows PE 파일 앞부분에 있는 DOS 스텁 문장입니다(앞 페이지에서 오프셋 `0x4e`의 바이트로 봤죠). 맨 앞 `!`는 문장의 일부가 아닙니다. 아주 작은 DOS 기계어 스텁의 마지막 바이트 `0x21`(`cd 21` = "DOS 인터럽트 21h 호출")인데, 우연히 찍히는 값이고 `T` 바로 앞에 있어서 붙었습니다. 이 파일이 실행 파일인지 몰랐다면 이 한 줄로 알 수 있습니다. 실행 파일이 PCAP, 메모리 덤프, 문서 속에 숨어 있을 때도 이 문장이 보입니다.
- `MSVBVM60.DLL` — DLL 이름. 검색해 보면 **Microsoft Visual Basic 6 가상 머신** 런타임이라는 걸 알 수 있습니다. 그러니 이 프로그램은 VB6로 만들어졌을 가능성이 아주 크고, 실행될 때 이 DLL을 불러올 겁니다. 이게 왜 중요할까요? VB6는 아주 오래된 언어라 요즘 정상 소프트웨어에서는 드물지만, 흔한 악성코드와 드로퍼(dropper)에서는 아직 보입니다. 리버스 엔지니어에게는 어떤 도구를 꺼내야 할지도 알려 줍니다.
- `ELORCHIDFALLOW` — 잘 보세요. 진짜 단어는 아마 `ORCHIDFALLOW`이고, `EL`은 바로 앞에 우연히 있던 찍히는 바이트 두 개(`0x45`, `0x4c`)입니다. 위에서 말한 "`strings`는 단어가 어디서 시작하는지 모른다"가 바로 이겁니다. 그런데 뜻 없는 단어에 왜 신경을 쓸까요? **유일하고 뜻 없는 문자열**은 헌팅에 금 같은 재료이기 때문입니다. 캠페인 표시일 수도, 뮤텍스 이름일 수도, XOR 키일 수도, 개발자의 농담일 수도 있는데, 같은 계열의 다른 샘플에도 나올 가능성이 큽니다. YARA 규칙 후보로 딱입니다.
- `Software\Microsoft\Windows\CurrentVersion\Run` — 레지스트리 경로. `HKCU\...\Run`이나 `HKLM\...\Run` 아래 등록된 프로그램은 로그온할 때마다 실행됩니다. 정체 모를 "인보이스 도구"에 이 경로가 박혀 있다는 건 Run 키로 <strong>지속성(persistence)</strong>을 확보하려 한다는 강한 신호입니다. MITRE ATT&CK **T1547.001 Boot or Logon Autostart Execution: Registry Run Keys / Startup Folder**. 이제 엔드포인트에서 무엇을 찾을지 알았습니다(레지스트리 이벤트 `Sysmon 13`, 레지스트리 감사를 켰다면 `4657`. [지속성](../../../adversary/persistence.md) 참고).
- `Mozilla/4.0 (compatible; MSIE 8.0)` — Internet Explorer 8인 척하는, 코드에 박힌 HTTP **User-Agent**. 2026년에 이런 걸 보내는 진짜 브라우저는 없습니다. 아주 좋은 네트워크 지표입니다. 프록시 로그와 Zeek `http.log`에서 이 값을 그대로 찾아보세요([사용자 에이전트](../http-analysis/user-agents-cookies.md)).

**없는 것**도 눈여겨보세요. URL도, 도메인도, 떨어뜨릴 파일 이름도 없습니다. 지속성을 만들고 HTTP로 통신하는 프로그램이라면 *어딘가에* 접속해야 하는데 말이죠. 주소가 숨겨져 있거나, ASCII 모드로는 볼 수 없는 방식으로 저장돼 있다는 뜻입니다. 어느 쪽인지 헥스 덤프가 알려 줍니다.

### 헥스 덤프로 보면 { #example-hex }

파일 앞부분:

```
$ hexdump -C -n 96 invoice_tool
00000000  4d 5a 90 00 03 00 00 00  04 00 00 00 ff ff 00 00  |MZ..............|
00000010  b8 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00  |................|
00000020  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00  |................|
00000030  00 00 00 00 00 00 00 00  00 00 00 00 80 00 00 00  |................|
00000040  0e 1f ba 0e 00 b4 09 cd  21 b8 01 4c cd 21 54 68  |........!..L.!Th|
00000050  69 73 20 70 72 6f 67 72  61 6d 20 63 61 6e 6e 6f  |is program canno|
```

- `00000000` 줄: `MZ`는 찍히는 글자지만 **2**글자뿐이고 뒤에 `90`(안 찍힘)이 옵니다. `-n 10`에서는 빠집니다. 기본값 `-n 4`에서도 빠집니다.
- `0x10`–`0x30` 줄: 거의 전부 `00`. 찍히는 게 하나도 없으니 `strings`가 출력할 것도 없습니다. 그래서 위 출력이 곧바로 DOS 문장으로 넘어간 겁니다.
- `00000040` 줄: `0e 1f ba 0e …`는 DOS 기계어입니다. 몇 바이트(`!`, `L`, `!`)가 우연히 찍히지만 덩어리마다 10보다 짧다가, `21 54 68 69 73…`에서 긴 덩어리 `!This program cannot be run in DOS mode.`가 시작됩니다. 출력 첫 줄 그대로입니다.

이번엔 더 안쪽, 오프셋 `0x300`을 봅니다.

```
$ hexdump -C -s 0x300 -n 64 invoice_tool
00000300  02 00 45 00 02 45 00 4c  45 02 8b 01 01 00 24 00  |..E..E.LE.....$.|
00000310  68 00 74 00 74 00 70 00  3a 00 2f 00 2f 00 6d 00  |h.t.t.p.:././.m.|
00000320  65 00 64 00 69 00 61 00  2d 00 63 00 64 00 6e 00  |e.d.i.a.-.c.d.n.|
00000330  2e 00 65 00 78 00 61 00  6d 00 70 00 6c 00 65 00  |..e.x.a.m.p.l.e.|
```

- `-s 0x300` — 오프셋 `0x300`으로 건너뜀. `-n 64` — 64바이트만 보여 줌.
- ASCII 칸에 `h.t.t.p.:././.m.e.d.i.a.-.c.d.n.`이 보입니다. 글은 **거기 있습니다**. 다만 글자마다 뒤에 `00` 바이트가 붙어 있습니다. `68 00` = `h`, `74 00` = `t`, 이런 식입니다.
- 이게 **UTF-16 리틀 엔디언**입니다. 영문자 하나가 두 바이트를 쓰는데, 뜻이 있는 바이트가 먼저, 높은 자리 바이트 `00`이 나중에 옵니다(앞 페이지 [유니코드와 인코딩](file-identification.md#unicode) 참고).
- ASCII 모드의 `strings`에게는 `h`(찍힘), `00`(안 찍힘, 덩어리 끝), `t`, `00`… 즉 한 글자짜리 덩어리가 줄줄이 이어진 것으로 보이고, 어느 것도 최소 길이를 넘지 못합니다. URL이 첫 검사에서 안 보이는 건 누가 숨겨서가 아니라 **인코딩 방식 자체 때문**입니다.

## 다른 인코딩과 바이트 순서 { #encodings }

### 글자당 두 바이트, 순서는 두 가지 { #byte-order }

글자 하나가 두 바이트 이상이면, 어느 바이트를 먼저 쓸지 정해야 합니다. 이걸 <strong>바이트 순서(byte order)</strong> 또는 <strong>엔디언(endianness)</strong>이라고 합니다.

- <strong>리틀 엔디언(little-endian, LE)</strong>: **낮은** 자리 바이트가 먼저. `h` = `U+0068`이 `68 00`으로 저장됩니다. x86/x64 CPU와 Windows가 이걸 씁니다.
- <strong>빅 엔디언(big-endian, BE)</strong>: **높은** 자리 바이트가 먼저. `h`가 `00 68`로 저장됩니다. Java 클래스 파일, 많은 네트워크 프로토콜("네트워크 바이트 순서"), x86이 아닌 일부 옛 시스템이 씁니다.

날짜 쓰는 법을 떠올려 보세요. `20/11/2026`과 `2026/11/20`. 같은 날짜, 같은 조각인데 순서만 다르고, 한쪽 규칙으로 다른 쪽을 읽으면 엉터리가 됩니다. 기술적으로, `strings`가 어느 바이트 쌍이 글자인지 알아보려면 **폭**(단위당 8, 16, 32비트)과 **순서**를 둘 다 알아야 합니다.

그게 `-e`의 역할입니다. GNU `strings` 설명서 내용을 정리하면:

| `-e` 값 | 단위 | 순서 | 흔한 내용 |
| --- | --- | --- | --- |
| `s` | 7비트, 1바이트 | — | ASCII(기본값) |
| `S` | 8비트, 1바이트 | — | Latin-1, Windows-1252, UTF-8 바이트 그대로 |
| `b` | 16비트 | 빅 엔디언 | UTF-16BE |
| `l` | 16비트 | 리틀 엔디언 | **UTF-16LE — Windows의 "와이드(wide)" 문자열** |
| `B` | 32비트 | 빅 엔디언 | UTF-32BE |
| `L` | 32비트 | 리틀 엔디언 | UTF-32LE |

### 두 번째 검사 { #second-pass }

같은 파일을 16비트 리틀 엔디언으로, 16진수 오프셋과 함께:

```
$ strings -n 10 -e l -t x invoice_tool
    30e $http://media-cdn.example/img/led/tr.php
    370 %APPDATA%\Microsoft\svchostw.exe
```

- `-e l` — 16비트 리틀 엔디언으로 풀기. `68 00`을 글자 `h` 하나로 봅니다.
- `-t x` — 왼쪽 칸에 각 문자열이 시작하는 **오프셋을 16진수로** 출력.
- `30e` — 이 문자열은 `0x30e`에서 시작합니다. 헥스 덤프를 보면 `0x30e`에는 `24 00`, 즉 `$`가 있습니다. 여기서도 우연히 찍히는 단위 하나(`$`)가 앞에 붙었고, URL 자체는 `68 00`이 있던 `0x310`에서 시작합니다.
- `http://media-cdn.example/img/led/tr.php` — <strong>명령·제어(C2, command and control)</strong> 주소. "CDN"이라는 이름에 "이미지" 경로 아래 `.php` 스크립트 — 비컨 접속 지점을 감추는 전형적인 위장입니다. 가장 중요한 네트워크 IOC입니다. 도메인을 차단하고, 프록시·DNS·Zeek 로그에서 `media-cdn.example`과, 어느 호스트든 `/img/led/tr.php` 경로를 찾습니다(경로는 다른 도메인에서 재사용될 수 있습니다). ATT&CK: **T1071.001 Application Layer Protocol: Web Protocols**.
- `370 %APPDATA%\Microsoft\svchostw.exe` — `0x370`에 있는 파일 경로. `%APPDATA%`는 사용자 로밍 프로필 폴더라 관리자 권한 없이도 쓸 수 있습니다. `svchostw.exe`는 진짜 `svchost.exe`를 흉내 낸 **닮은꼴 이름**인데, 진짜는 오직 `C:\Windows\System32`에만 있습니다. 파일을 떨어뜨릴 **위치**이자 위장일 가능성이 큽니다(**T1036.005 Masquerading: Match Legitimate Name or Location**). 그 경로의 파일 생성 이벤트, 그리고 System32 밖에서 실행되는 `svchost*.exe`를 헌팅합니다.

두 번 돌렸더니 그림이 완성됐습니다. AppData에 `svchostw.exe`로 자신을 떨어뜨리고, Run 키를 등록하고, 가짜 IE8 사용자 에이전트로 `media-cdn.example`과 HTTP 통신을 하는 VB6 프로그램. 아무것도 실행하지 않았습니다.

<strong>[보충]</strong> 바로 쓸 수 있는 습관:

```
$ strings -a -n 8 -t x sample > sample.ascii.txt
$ strings -a -n 8 -t x -e l sample > sample.utf16le.txt
$ cat sample.ascii.txt sample.utf16le.txt | grep -iE 'https?://|\\run|\.exe|\.dll|\.ps1|user-agent|mozilla|[0-9]{1,3}(\.[0-9]{1,3}){3}'
```

- 1–2번 줄은 두 검사 결과를 오프셋과 함께 텍스트 파일로 저장합니다. 사건 기록에 첨부할 수 있습니다.
- 3번 줄은 둘을 합쳐 흔한 IOC 모양만 걸러 냅니다. URL, Run 키, 실행 파일·스크립트 이름, 사용자 에이전트, 점 네 개짜리 IP. `-i`는 대소문자 무시, `-E`는 확장 정규식, `|`는 "또는"입니다.
- 이건 첫 번째 거름망일 뿐입니다. 거르지 않은 전체 출력도 꼭 보세요. `ORCHIDFALLOW` 같은 유일한 단어는 어떤 패턴에도 안 걸립니다.

이미 아는 UTF-16LE 문자열 하나를 바로 찾을 수도 있습니다.

```
$ LC_ALL=C grep -obUaP 'h\x00t\x00t\x00p' invoice_tool
784:h t t p
```

- `784`는 10진수 오프셋입니다(= `0x310`, URL이 시작하는 곳). 출력의 "띄어쓰기"는 터미널이 `00` 바이트를 그렇게 보여 주는 겁니다.

### 영어가 아닌 글, `-e S`와 `--unicode` { #non-english }

ASCII 모드(`-e s`)는 `0x20`–`0x7E`만 찍히는 걸로 치기 때문에, 한국어나 키릴 문자, 악센트가 들어간 UTF-8 글은 ASCII가 아닌 바이트마다 토막이 납니다. 해결법은 두 가지입니다.

- `-e S`는 `0x80`–`0xFF`도 찍히는 걸로 칩니다. UTF-8 바이트가 그대로 나오고, 터미널이 UTF-8이면 제대로 보입니다. 대신 잡음도 늘어납니다. 이제 무작위 바이트 넷 중 셋은 찍히는 값이 되니까요.
- <strong>[보충]</strong> 최근 GNU binutils(2.38부터, 2022년)에 `-U`/`--unicode=` 옵션이 생겼습니다. `locale`(올바른 UTF-8 글자를 글자로 보여 줌), `escape`(`\u` 형태로 바꿔 보여 줌), `highlight`(바꾼 걸 색으로 강조) 같은 방식이 있습니다. `--unicode=escape`는 숨은 속임수를 찾을 때 좋습니다. 예를 들어 박혀 있는 파일 이름 속 오른쪽에서 왼쪽 강제 문자 `U+202E`를 터미널이 몰래 적용해 버리지 않고 그대로 드러내 줍니다.

## 문자열이 어떻게 도움이 되나 { #how-strings-help }

### 실행하지 않고 얻는 IOC { #iocs }

악성코드는 파일과 레지스트리 키를 바꾸고 서버에 접속해야 합니다. 그 모든 것의 이름은 어딘가에서 와야 하고, 아주 흔하게는 파일 안에 그대로 컴파일된 글에서 옵니다. 그래서 샘플의 문자열은 그 샘플이 **할 수도 있는** 일의 빠른 목록입니다. 악성코드가 다른 PC에서 그 값을 써먹기 **전에** 차단하고, 경보를 걸고, 헌팅할 수 있습니다. 상대가 비밀을 털어놓게 만들어 한발 앞서는 셈이죠.

찾을 것, 대략 쓸모 있는 순서로:

| 종류 | 문자열 예 | 어떻게 쓰나 |
| --- | --- | --- |
| URL, 도메인, IP | `http://media-cdn.example/img/led/tr.php`, `198.51.100.23` | 차단. 전체 환경의 프록시/DNS/Zeek/방화벽 로그 검색 |
| 파일 경로와 이름 | `%APPDATA%\Microsoft\svchostw.exe`, `\Temp\upd.ps1` | 그 경로의 파일 생성(Sysmon 11), 프로세스 생성(4688/Sysmon 1) 헌팅 |
| 레지스트리 키 | `...\CurrentVersion\Run`, `...\Image File Execution Options` | 레지스트리 이벤트(Sysmon 13), 자동 실행 항목 헌팅 |
| 사용자 에이전트, HTTP 헤더 | `Mozilla/4.0 (compatible; MSIE 8.0)` | 프록시, `http.log` 검색 |
| 명령 | `cmd.exe /c `, `powershell -enc`, `schtasks /create`, `vssadmin delete shadows` | 행위에 대응(T1059, T1053.005, T1490). 프로세스 명령줄 헌팅 |
| 불러오는 DLL과 API | `WININET.dll`, `InternetOpenUrlA`, `VirtualAllocEx`, `WriteProcessMemory` | 능력 힌트(다운로드, 인젝션). 리버스 엔지니어에게 전달 |
| 유일한 단어, 뮤텍스, PDB 경로 | `ORCHIDFALLOW`, `Global\x7Q2mutex`, `C:\dev\loader\Release\loader.pdb` | 계열·캠페인 묶기. YARA 규칙 |

하나하나를 **단서**로 다루세요. 정상 프로그램에도 URL(업데이트 서버), 레지스트리 경로, API 이름이 들어 있습니다. 판단은 맥락이 합니다. 그 밖에 무엇이 들어 있나, 파일이 어디서 왔나, 엔드포인트가 실제로 무엇을 했나.

### 정적 분석과 동적 분석 { #static-dynamic }

- **정적 분석** = 파일을 **실행하지 않고** 살펴보기. `file`, 헥스 덤프, `strings`, 해시, 헤더 해석, 디스어셈블. 안전하고(그 파일이 노리는 프로그램으로 열지만 않으면), 빠르고, 공격자 인프라에 흔적을 남기지 않습니다.
- **동적 분석** = 통제된 환경(샌드박스나 격리 VM)에서 파일을 **실행**하고 하는 짓을 지켜보기. 프로세스, 파일, 레지스트리, 네트워크 트래픽. 진짜 행위를 보여 주고 일부 숨기기 기법을 무력화하지만, 느리고, 회피당할 수 있으며(샘플이 샌드박스를 알아채고 얌전히 있음), 샘플이 살아 있는 C2 서버에 접속하면 공격자에게 들킬 수 있습니다.

문자열은 정적 분류의 한가운데에 있고, 동적 분석에도 도움이 됩니다. C2 URL을 미리 알면 샌드박스의 네트워크 캡처에서 무엇을 찾아야 할지 알게 되니까요.

### 샌드박스가 내가 못 찾는 문자열을 보여 주는 이유 { #sandbox-strings }

공개·상용 샌드박스(Hybrid Analysis, ANY.RUN, Joe Sandbox, VirusTotal 행위 보고서, EDR 업체의 실행 분석 서비스)는 보통 보고서에 긴 **문자열** 목록을 보여 줍니다. 읽을 때 알아 둘 두 가지:

1. **인코딩을 섞어서 보여 줍니다.** 샌드박스는 대개 ASCII, UTF-16LE, 때로는 다른 인코딩까지 뽑아서 합쳐 보여 주고, 어느 문자열이 어느 인코딩에서 나왔는지 말해 주지 않는 경우가 많습니다. 그래서 내 첫 `strings` 검사보다 목록이 길고, `-e l` 두 번째 검사를 하면 대개 차이가 메워집니다.
2. **메모리에서 긁어 옵니다.** 많은 샌드박스가 **실행 중인 프로세스의 메모리**도 덤프해서 거기서 문자열을 뽑습니다. 패킹되거나 암호화된 악성코드는 메모리에서 스스로 풀리기 때문에, 디스크 어디에도 없는 문자열이 거기서 나타납니다. 출력은 `strings`처럼 보여도 이건 동적 분석입니다. 샌드박스 보고서에 있는 URL을 내 두 번의 검사로 못 찾았다면 거의 틀림없이 이 이유입니다.

설명용(가상) 샌드박스 문자열 일부:

```
Extracted Strings (static + memory, all encodings)
  MSVBVM60.DLL
  ORCHIDFALLOW
  http://media-cdn.example/img/led/tr.php
  %APPDATA%\Microsoft\svchostw.exe
  POST /img/led/tr.php HTTP/1.1          [memory]
  id=%s&os=%s&av=%s                      [memory]
```

- 처음 네 줄은 우리가 디스크에서 두 번 검사해 찾은 것과 같습니다.
- `[memory]` 두 줄은 실행할 때만 존재합니다. 비컨 요청 줄, 그리고 <strong>형식 문자열(format string)</strong>(`%s` 자리 표시자). 이 형식 문자열은 비컨이 피해자 ID, OS 버전, 설치된 백신을 보낸다는 걸 알려 줍니다. 네트워크 탐지 규칙을 쓸 때 아주 값진 정보지만, 디스크 위의 파일에서는 얻을 수 없었습니다.

<strong>[주의]</strong> 샘플을 **공개** 샌드박스에 올리면 다른 사람에게, 어쩌면 자기 해시를 지켜보는 공격자에게도 보이게 됩니다. 표적 공격 사건이라면 해시 조회, 비공개 샌드박스, EDR 업체의 비공개 실행 분석을 우선하세요([샌드박스와 OPSEC](../http-analysis/screenshots-sandboxes.md)).

### 패킹, 암호화, 압축 { #packing }

`strings`는 **저장된 상태 그대로** 글자인 바이트만 봅니다. 저장된 바이트를 바꿔 버리는 게 세 가지 있습니다.

- <strong>패킹(packing)</strong>(ATT&CK **T1027.002 Software Packing**). 진짜 프로그램을 압축하거나 암호화하고, 실행할 때 메모리에서 원래대로 되돌리는 작은 풀기용 스텁(stub)으로 감쌉니다. 디스크에서는 대부분 스텁만 보입니다. 전형적인 징후: 뜻 있는 문자열이 거의 없음, 엔트로피가 높음(무작위처럼 보이는 바이트), `LoadLibraryA`, `GetProcAddress`, `VirtualAlloc`/`VirtualProtect` 같은 몇 안 되는 임포트, 때로는 패커 자체의 섹션 이름. 오픈 소스 패커 UPX가 가장 쉬운 예입니다.

    ```
    $ strings -n 4 packed_sample | head -6
    !This program cannot be run in DOS mode.
    UPX0
    UPX1
    UPX!
    KERNEL32.DLL
    LoadLibraryA
    ```

    - `UPX0`, `UPX1`은 UPX의 섹션 이름이고 `UPX!`는 표시입니다. UPX 자체는 정상 도구이고(`upx -d`로 풀 수 있음), 하지만 패킹된 "인보이스 도구"는 강한 신호입니다.
    - `KERNEL32.DLL` + `LoadLibraryA`, 그 밖엔 거의 없음: 스텁은 라이브러리를 불러오고 함수를 찾기만 하면 되니까요. 진짜 임포트는 풀린 뒤에 나타납니다.

- **난독화되거나 암호화된 문자열**(**T1027**, 실행 중 풀기는 **T1140 Deobfuscate/Decode Files or Information**). 파일 전체를 패킹하는 대신, 중요한 문자열만 XOR하거나 암호화하거나, 스택 위에서 한 글자씩 조립합니다("스택 문자열", stack strings). `strings`에는 쓸 만한 게 안 보이고, FLOSS 같은 도구가 해독 루틴을 에뮬레이션해서 되살릴 수 있습니다([2026년 관점](#trends) 참고).

- **압축.** ZIP, gzip, 7z, DOCX/XLSX(ZIP이니까요), 압축된 PDF 스트림, PNG 픽셀 데이터. 압축은 내용을 새로운 바이트 패턴으로 다시 쓰기 때문에 안의 읽을 수 있던 글이 읽을 수 없게 됩니다. 예를 들어:

    ```
    $ gzip -c invoice_tool > t.gz
    $ strings -n 10 t.gz
    invoice_tool
    ```

    - 앞에서 찾은 문자열이 다 사라졌습니다. 남은 건 `invoice_tool` 하나 — gzip이 헤더에 **압축하지 않고** 저장하는 **원래 파일 이름**입니다. (작은 덤: 압축 파일 헤더가 원래 이름과 경로를 흘릴 수 있습니다.)
    - 해결법은 **먼저 풀고, 그다음 `strings`**입니다. `zcat t.gz | strings -n 10`, `unzip -p invoice.docx word/document.xml | strings`, 또는 분석 VM의 폴더에 풀기. PDF 스트림을 풀어 주는 도구는 이 섹션 뒤쪽에서 다룹니다.

<strong>[정정]</strong> "볼 만한 문자열이 없으니 깨끗하다"는 틀렸습니다. 실행 파일에 문자열이 적다는 건 오히려 누군가 숨기려고 애썼다는 뜻인 경우가 많습니다.

### 실행 파일 말고도 { #beyond-executables }

압축만 안 돼 있으면 문자열은 무엇에나 통합니다.

- **PCAP.** 암호화되지 않은 프로토콜은 글을 실어 나릅니다. 캡처를 빠르게 훑어보면:

    ```
    $ strings -n 8 capture.pcap | grep -E '^(Host|User-Agent|Cookie):' | sort | uniq -c | sort -rn | head
         41 Host: media-cdn.example
         41 User-Agent: Mozilla/4.0 (compatible; MSIE 8.0)
         12 Host: intranet.corp.example
          3 Cookie: sid=7f3a9c0e21
    ```

    - `strings -n 8`이 패킷에서 글 줄을 뽑고, `grep -E '^(Host|User-Agent|Cookie):'`가 그 HTTP 헤더 줄만 남깁니다.
    - `sort | uniq -c | sort -rn`은 같은 줄의 개수를 세어 가장 많은 것부터 보여 줍니다(HTTP 섹션의 빈도 분석과 같은 생각).
    - 가짜 IE8 사용자 에이전트로 `media-cdn.example`에 똑같은 요청 41번: 비컨을 몇 초 만에 찾았습니다. 물론 **평문** 트래픽에서만 통합니다. TLS 내용은 암호화돼 있지만, 핸드셰이크의 SNI와 인증서는 여전히 읽을 수 있습니다.

- **문서와 PDF**: 작성자 이름, 만든 프로그램(`Microsoft Word`, `LibreOffice`), 박힌 URL, 압축 안 된 PDF 개체 속 `/JavaScript`나 `/OpenAction` 같은 키워드.
- **이미지**: 카메라 모델, 편집 프로그램(`Adobe Photoshop`), 시각, 때로는 GPS 같은 EXIF 메타데이터 — 그리고 이미지에 있으면 안 되는 글, 예를 들어 `<script>`나 이미지가 끝난 뒤의 `PK`(앞 페이지의 폴리글랏 단서).
- **메모리 덤프**: 명령줄, URL, 복호화된 설정. 메모리 포렌식 도구가 많은 증거를 바로 이렇게 찾습니다.

평범한 파일들에 `strings`를 이것저것 돌려 보는 것도 좋은 공부입니다. 형식마다 "정상"이 안에서 어떻게 생겼는지 알게 되고, 그러면 비정상이 더 빨리 눈에 띕니다.

## 정리 — 파일 내용과 알아보기 { #recap }

이 페이지로 이 섹션의 "이 파일 뭐지?" 묶음이 끝납니다. 가져갈 생각들:

- **파일은 그냥 바이트의 줄이다.** 이름과 확장자는 바이트에게 아무 의미가 없습니다. 사람이나 공격자가 붙인 꼬리표일 뿐입니다.
- 어떤 때는 모든 바이트가 읽을 수 있는 글자입니다(**텍스트** 파일: 스크립트, 글, HTML, SVG). 어떤 때는 아닙니다(**바이너리** 파일: 실행 파일, 압축 파일, 이미지, Office 파일).
- **확장자 없는 파일**을 만나게 됩니다(PCAP에서 잘라 낸 것, 메모리에서 뽑은 것, 악성코드가 무작위 이름으로 떨어뜨린 것). 정상적인 일이고, 내용으로 알아봅니다.
- 헥스 덤프의 **매직 바이트**가 바이너리 형식을 알려 주고, 파일을 잘라 낸 뒤에는 Linux **`file`** 명령이 이걸 자동으로 해 줍니다([파일 알아보기](file-identification.md)).
- **문자열**은 바이너리 파일이 무엇이고 무엇을 하는지 빠른 단서를 줍니다.
- 글은 **여러 인코딩**으로 옵니다. ASCII, 그리고 유니코드의 UTF-8, UTF-16, UTF-32, 바이트 순서도 두 가지. 그러니 한 가지만으로 찾지 않습니다.

파일을 바이트 수준에서 이해하면 두 가지가 좋아집니다. 형식이 숨겨지거나 잘못 붙은 파일을 알아볼 수 있고, 엉뚱한 프로그램으로 열어서 **스스로 감염되는** 일을 피할 수 있습니다. 다음 페이지들은 여기서 이어집니다. 의심 파일을 안전하게 다루는 법, 그리고 공격자가 어떤 파일 형식을 어떻게 무기로 만드는지.

## 2026년 관점 { #trends }

!!! success "[2026 현재] 지금도 그대로 유효"
    문자열의 정의, 텍스트/바이너리 구분, `strings` 명령과 `-n`, `-t`, `-e` 옵션, 그리고 핵심 교훈 — **언제나 두 가지 이상의 인코딩으로 찾고, Windows 파일은 특히 UTF-16LE로** — 은 그대로입니다. GNU `strings`(요즘 배포판의 binutils 2.4x)와 Sysinternals Strings는 여전히 표준 첫 도구이고, 분석가가 제일 먼저 뽑는 IOC 종류(URL, 도메인, IP, 경로, 레지스트리 키, 사용자 에이전트, 유일한 표시)도 같습니다. 정적/동적 분석 구분, 그리고 샌드박스가 메모리에서 긁은 문자열을 더해 준다는 사실이 "그 문자열이 왜 나한테는 안 보이지?"라는 질문 대부분을 여전히 설명해 줍니다.

!!! info "[변경됨] 바뀐 점"
    - **난독화를 풀어 주는 문자열 도구가 이제 일상입니다.** FLOSS(FLARE Obfuscated String Solver, Google Mandiant FLARE 팀)는 정적 문자열을 뽑을 뿐 아니라 코드를 에뮬레이션해서 평범한 `strings`가 못 보는 **스택 문자열, "타이트(tight)" 문자열, 해독된 문자열**을 되살립니다. 3.x 버전부터는 **Go와 Rust** 바이너리도 이해합니다. 이 언어들의 문자열은 널로 끝나지 않아서 그냥 돌리면 거대한 한 덩어리로 붙어 나오는데, 요즘 악성코드 상당수가 Go와 Rust로 만들어지니 중요한 변화입니다.
    - **잡음에 순위 매기기.** StringSifter(머신러닝으로 문자열을 악성코드 분석에 얼마나 중요한지 순위를 매김) 같은 도구와 요즘 샌드박스의 문자열 보기가 쓰레기를 아래로 내려 줍니다.
    - **AI 요약.** 샌드박스와 위협 인텔리전스 플랫폼이 이제 코드와 문자열을 LLM으로 요약해 줍니다(VirusTotal의 Code Insight가 한 예). 빠르긴 하지만 틀릴 수 있으니, 실제 문자열과 행위로 확인합니다.
    - **문자열에서 탐지로.** 유일한 문자열은 여전히 YARA 규칙의 고전적인 재료입니다. YARA를 Rust로 다시 쓴 YARA-X(2025년 1.0)가 이제 새 규칙에 권장되는 엔진이고, 문법은 대부분 호환됩니다.
    - **GNU `strings`는 기본으로 파일 전체를 훑습니다**(binutils 2.26부터. 2014년 개체 파일 해석 경로의 취약점 이후 바뀜). 최근 버전에는 UTF-8 표시와 이스케이프를 위한 `--unicode`가 생겼습니다.
    - 이 페이지에서 쓴 **ATT&CK 이름**: T1027.002 Software Packing, T1027 Obfuscated Files or Information, T1140 Deobfuscate/Decode Files or Information, T1547.001 Registry Run Keys, T1036.005 Match Legitimate Name or Location, T1071.001 Web Protocols.

!!! warning "[주의] 옛 방식대로 하면 틀리거나 위험한 점"
    - **ASCII 검사로 끝내지 마세요.** Windows 글은 대개 UTF-16LE이고 ASCII 모드로는 절대 안 보입니다. 최소 두 번(`-e s`와 `-e l`), 아니면 둘 다 해 주는 도구를 씁니다.
    - **문자열이 적다고 "깨끗하다"고 결론 내리지 마세요.** 패킹이나 문자열 난독화의 전형적인 징후입니다. 엔트로피, 임포트, 패커 표시를 확인하고 FLOSS, 언패킹, 메모리 분석으로 넘어갑니다.
    - **압축 파일과 압축된 문서에 `strings`를 돌리고 그 결과를 믿지 마세요.** 먼저 풉니다.
    - **아주 오래된 시스템에서는 `strings -a`를 직접 붙이세요.** 옛 binutils는 기본으로 알아본 개체 파일의 데이터 섹션만 훑었고, 그 해석 과정 자체가 취약점의 원인이 되기도 했습니다. 분석 도구는 최신으로 유지하고 격리된 VM에서 돌립니다.
    - **문자열 하나를 결론으로 삼지 마세요.** 정상 프로그램에도 URL, Run 키, 무서워 보이는 API 이름이 있습니다. 출처, 서명, 해시 평판, 실제 엔드포인트 행위와 함께 판단합니다.
    - **공개 샌드박스의 OPSEC를 생각하세요.** 표적 공격 샘플을 올리면 공격자가 들킨 걸 알 수 있습니다. 해시 조회와 비공개 분석을 우선합니다.
    - **파일을 그 파일의 프로그램으로 열어서 "글을 보려고" 하지 마세요**(더블클릭, Word나 브라우저로 열기). 분석 장비에서 `strings`, 헥스 뷰어, 평범한 텍스트 뷰어를 씁니다.

## 확인 문제 { #quiz }

### 문제 1

Windows 실행 파일에 `strings -n 10 dropper.bin`을 돌렸더니 DOS 스텁 문장과 DLL 이름 두 개만 나왔습니다. 동료가 말합니다. "문자열이 거의 없으니 별것 안 하겠네." 그런데 `strings -n 10 -e l dropper.bin`을 돌리니 `http://upd-check.example/a.php`와 `%TEMP%\wuauclt32.exe`가 나왔습니다. 첫 검사가 왜 이걸 놓쳤는지, 각 문자열이 무엇을 암시하는지, 다음에 무엇을 할지 설명하세요.

??? success "정답과 해설"
    **첫 검사가 놓친 이유:** 기본 모드(`-e s`)는 글자 하나를 한 바이트로 풉니다. 이 문자열들은 **UTF-16 리틀 엔디언**으로 저장돼 있어서 글자마다 뒤에 `00` 바이트가 붙습니다(`http`는 `68 00 74 00 74 00 70 00`). ASCII 모드에서는 `00`마다 덩어리가 끝나서 한 글자짜리 덩어리만 남고, 최소 길이에 못 미칩니다. `-e l`은 16비트 리틀 엔디언 단위로 읽어 제대로 풀어 줍니다. 동료의 결론은 두 번 틀렸습니다. 문자열은 처음부터 거기 있었고, 설령 문자열이 적었더라도 안심할 일이 아니라 의심할 일입니다.

    **암시하는 것:** `http://upd-check.example/a.php`는 C2나 다운로드 URL일 가능성이 큽니다("업데이트 확인"이라는 이름의 PHP 스크립트 — T1071.001). `%TEMP%\wuauclt32.exe`는 떨어뜨릴 경로일 가능성이 크고, `wuauclt32.exe`는 System32에 있는 진짜 Windows 업데이트 클라이언트 `wuauclt.exe`를 흉내 낸 이름입니다. 위장, T1036.005.

    **다음:** 프록시/DNS/Zeek 로그에서 `upd-check.example`과 경로 `/a.php`를 차단·헌팅하고, 어느 Temp 폴더에서든 `wuauclt32.exe`의 파일 생성·프로세스 생성 이벤트를 헌팅하고, 샘플 해시를 구해 평판을 확인하고, 필요하면 비공개 샌드박스에서 실행해 행위를 확인합니다.

### 문제 2

`strings -n 6 report_q3.exe` 결과는 `!This program cannot be run in DOS mode.`, `UPX0`, `UPX1`, `UPX!`, `KERNEL32.DLL`, `LoadLibraryA`, `GetProcAddress`, `VirtualProtect` — 그리고 그 밖에는 거의 없습니다. 같은 해시의 샌드박스 보고서에는 도메인 하나와 `POST` 요청 형식 문자열이 있습니다. (a) `strings` 출력은 무엇을 말해 주나요? (b) 샌드박스는 왜 `strings`가 못 찾는 문자열을 보여 줄 수 있나요? (c) ATT&CK 기법은 무엇인가요?

??? success "정답과 해설"
    **(a)** **UPX로 패킹된** Windows 실행 파일입니다. `UPX0`/`UPX1`은 섹션 이름, `UPX!`는 UPX 표시입니다. 아주 짧은 임포트 목록(`LoadLibraryA`, `GetProcAddress`, `VirtualProtect`)은 풀기용 스텁이 메모리에서 진짜 프로그램을 다시 세우는 데 필요한 것들입니다. 진짜 문자열은 압축돼 있어 디스크에서는 안 보입니다. 패킹된 "분기 보고서" 실행 파일이라는 것 자체가 의심스럽습니다.

    **(b)** 샌드박스는 파일을 **실행**했습니다(동적 분석). 스텁이 진짜 코드를 메모리에 풀었고, 샌드박스가 프로세스 메모리를 덤프해 거기서 문자열을 뽑았기 때문에 도메인과 요청 형식이 나타난 겁니다. 우리 `strings`는 디스크에 있는 패킹된 바이트만 읽었습니다(정적 분석). 분석 VM에서 사본에 `upx -d`를 시도해 정적으로 풀고 `strings`를 다시 돌려 볼 수도 있습니다.

    **(c)** **T1027.002 Obfuscated Files or Information: Software Packing.**

### 문제 3

(a) 출력 줄 `ELORCHIDFALLOW`에서 진짜 문자열이 `ORCHIDFALLOW`일 수 있는 이유는 무엇이고, 뜻 없는 유일한 단어를 왜 기록해 둘 가치가 있나요? (b) `.docx` 파일에 `strings`를 돌리면 왜 쓸 만한 게 거의 안 나오고, 어떻게 해결하나요? (c) 실행 파일이 아닌 곳에 `strings`를 쓰는 예를 두 가지 드세요.

??? success "정답과 해설"
    **(a)** `strings`는 찍히는 게 어디서 시작하고 끝나는지만 알지, 단어가 어디서 시작하는지는 모릅니다. 진짜 글 바로 앞에 우연히 있던 찍히는 바이트(여기서는 `0x45` `E`와 `0x4c` `L`)가 앞에 붙어 버립니다. 문자열의 오프셋(`-t x`)을 헥스 덤프에서 확인하면 알 수 있습니다. 뜻 없는 유일한 단어는 정상 소프트웨어에 나올 가능성이 낮아서, 같은 계열이나 캠페인의 샘플을 이어 주고 좋은 **YARA** 규칙이나 헌팅 검색어가 되기 때문에 값집니다.

    **(b)** `.docx`는 **ZIP** 압축 파일이고, 안의 XML 부분들이 deflate로 압축돼 글이 읽을 수 없는 바이트로 바뀌어 있습니다. 압축 안 된 조각(ZIP 헤더와 `word/document.xml` 같은 부분 이름)만 읽힙니다. 먼저 풉니다. `unzip -l`로 목록을 보고, `unzip -p file.docx word/document.xml`로 꺼내거나 분석 VM에 풀고, 그다음 `strings`를 돌리거나 XML을 읽습니다.

    **(c)** 다음 중 둘: **PCAP**에서 평문 HTTP `Host`, `User-Agent`, `Cookie` 줄과 URL 뽑기(개수를 세면 비컨이 보임). **PDF**에서 박힌 URL, 만든 프로그램, 압축 안 된 개체 속 `/JavaScript` 같은 키워드 찾기. **이미지**에서 EXIF 메타데이터나 있으면 안 되는 글(`<script>`, 끝에 붙은 `PK`) 찾기. **메모리 덤프**에서 명령줄, URL, 복호화된 설정 찾기.
