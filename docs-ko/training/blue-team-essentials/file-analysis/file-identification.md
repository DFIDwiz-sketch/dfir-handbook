# 파일 알아보기 — 바이트, file 명령, 매직 바이트, 중첩 파일, 폴리글랏, 유니코드와 인코딩 { #file-identification }

!!! abstract "이 페이지에서 다루는 것"
    파일이 진짜로 무엇인지(프로그램이 해석하기로 약속한 바이트의 줄), 그리고 수상한 다운로드나 첨부 파일을 만났을 때 첫 질문 — **이거 진짜 무슨 파일이지?** — 에 답하는 법을 다룹니다. 파일 이름, 확장자, 서버가 말한 `Content-Type`은 믿지 않습니다. 헥스 덤프를 칸별로 읽고, 확장자 없는 샘플 여섯 개에 Linux `file` 명령을 돌려 출력 줄마다 해석하고, 외워 둘 만한 <strong>매직 바이트(magic bytes, 파일 시그니처)</strong>와 ZIP과 요즘 Office 파일이 왜 같은 시그니처를 쓰는지 배웁니다. 이어서 날것의 바이트 흐름 속에서 **다른 파일 안에 숨은 파일**을 찾아 잘라 내고, 파일 하나가 왜 **동시에 두 가지 정상 형식**일 수 있는지(폴리글랏)와 공격자가 이제 그걸 실제로 쓴다는 걸 봅니다. 마지막은 **유니코드와 인코딩**(코드 포인트, UTF-8, UTF-16, UTF-32, BOM) — 다음 페이지의 `strings` 출력을 읽기 전에 꼭 필요한 바탕입니다. 끝에 확인 문제와 해설이 있습니다.

!!! note "표기"
    **[보충]** = 꼭 알아야 할 실무 보충, **[정정]** = 흔히 잘못 알려진 내용 정정, **[변경됨]**/**[주의]** = 최근 바뀐 점과 옛 방식대로 하면 위험한 점. 호스트 이름, 도메인, 계정, IP, 파일 이름은 모두 설명용 가상 값(`.example`, 문서용·사설 IP)입니다. 샘플 파일은 이 페이지를 위해 만든 무해한 시험용 파일입니다.

## 한눈에 보는 핵심 8가지 { #key-points }

1. 파일은 **그냥 바이트가 줄지어 있는 것**이다. "PDF", "EXE", "DOCX"는 파일이 들고 다니는 성질이 아니라, 프로그램이 그 바이트를 **어떻게 해석하기로 하느냐**다.
2. **이름, 확장자, HTTP `Content-Type`은 주장일 뿐**이고, 셋 다 공격자가 정할 수 있다. 증거는 바이트다.
3. Linux에서 가장 빠른 첫 확인은 **`file`**이다. 이름이 아니라 내용을 읽어 알려진 형식 목록과 비교한다. Windows에는 기본 내장된 같은 도구가 없지만, 헥스 보기로 같은 원리를 쓸 수 있다.
4. 대부분의 형식은 **매직 바이트**로 시작한다. Windows 실행 파일은 `MZ`, ZIP은 `PK\x03\x04`, PDF는 `%PDF-`, Linux 실행 파일은 `\x7fELF`, PNG는 `\x89PNG`, RTF는 `{\rtf1`, gzip은 `1F 8B`.
5. **DOCX, XLSX, PPTX는 ZIP 파일이다.** XML 파일들을 묶은 ZIP 압축 파일 그 자체라서 매직 바이트가 같다. 옛 `.doc`/`.xls`는 다른 그릇(OLE, `D0 CF 11 E0`)을 쓴다.
6. `file`은 파일의 **맨 앞**만 본다. **다른 파일 안에 박힌 파일**이나 네트워크 바이트 흐름 속 파일은 시그니처를 **아무 위치에서나** 찾는 도구(binwalk, foremost, scalpel, 또는 간단한 `grep`)와 분석가의 눈이 필요하다.
7. 파일 하나가 **동시에 두 가지 정상 형식**일 수 있다(<strong>폴리글랏(polyglot)</strong>). 멀쩡한 이미지이면서 ZIP이기도 한 파일, PDF이면서 HTML 애플리케이션으로도 실행되는 파일. 파일이 "무엇인지"는 **어느 프로그램이 여느냐**에 달렸다.
8. 텍스트에도 함정이 있다. 같은 글자가 UTF-8, UTF-16, UTF-32에서 **서로 다른 바이트**가 된다. 인코딩을 잘못 고르면 깨진 글자가 나오거나, 찾던 문자열을 놓친다.

## SOC에서 왜 중요한가 { #why }

흔한 경보 하나를 떠올려 봅시다. 프록시 로그에 어떤 워크스테이션이 `http://cdn-update.example/x`를 받아 갔고, 응답은 312 KB에 `Content-Type: image/png`였습니다. 조금 뒤 같은 PC가 비컨(beacon)을 보내기 시작했습니다. 패킷 캡처에서 응답 본문을 뽑아냅니다(Wireshark의 **File → Export Objects → HTTP**, 또는 Zeek 파일 추출). 이제 손에 `x`라는 파일이 있습니다. 확장자도, 힌트도 없습니다.

빠르고 안전하게 답해야 할 질문은 두 가지입니다.

1. **진짜 무슨 파일인가?** 말한 대로 이미지인가? Windows 프로그램인가? 스크립트인가? 안에 파일이 더 들어 있는 압축 파일인가?
2. **위험한가?** 이건 1번 답에 크게 달려 있습니다. 진짜 PNG가 위협인 경우는 거의 없지만, PNG인 척하는 Windows DLL은 거의 언제나 위협입니다.

방법은 대략 비용이 싼 순서로 이렇습니다.

- **`file`** — 내용을 보고 자동으로 알아냅니다. 몇 초.
- **헥스 덤프** — 앞쪽 바이트를 직접 보고 **매직 바이트**를 찾습니다. 몇 초에서 몇 분.
- **`strings`**와 **안에 든 내용** 찾기 — 단서, URL, 박혀 있는 파일. 몇 분. (다음 페이지에서 다룹니다.)
- **샌드박스 / 동적 분석** — 통제된 환경에서 실행해 보며 지켜봅니다. 몇 분 이상 걸리고, 작전 보안(OPSEC) 문제도 따라옵니다([스크린샷, 샌드박스, 그리고 수동 분석으로 넘어갈 때](../http-analysis/screenshots-sandboxes.md) 참고).

비유를 들면, "초콜릿"이라고 적힌 택배가 왔습니다. 라벨이 확장자입니다. 사무실에서 바로 뜯어 보지 않고 먼저 **엑스레이**를 찍죠. 헥스 덤프와 `file` 명령이 그 엑스레이입니다. "실행"하지 않고 안을 봅니다. 기술적으로는, 거의 모든 파일 형식은 그 프로그램이 읽을 수 있도록 <strong>명세(specification)</strong>를 따라야 하고, 명세는 거의 언제나 정해진, 알아보기 쉬운 패턴으로 시작하기 때문에 이 엑스레이가 통합니다.

<strong>[주의]</strong> 이 작업은 전부 **분석용 장비**(격리된 Linux VM이나 전용 분석 PC)에서 하세요. 평소 업무 PC에서 하거나, 더블클릭으로 열어 보면 절대 안 됩니다. 파일을 알아본다는 건 바이트를 **읽는** 것이지, 그 파일이 노리는 프로그램으로 **여는** 게 아닙니다. 안전하게 다루는 법은 이 섹션 뒤쪽에 따로 페이지가 있습니다.

## 파일은 바이트의 줄이다 { #bytes }

모든 파일 — 메모, 사진, 프로그램 — 은 <strong>바이트(byte)</strong>의 줄로 저장됩니다. 바이트 하나는 8비트, 즉 0~255의 숫자이고, 보통 `00`부터 `ff`까지 두 글자 <strong>16진수(hexadecimal)</strong>로 씁니다. 어떤 파일은 PDF이고 어떤 파일은 프로그램인 이유는 오직 **그 숫자들이 어떻게 놓여 있느냐**, 그리고 어느 프로그램에게 해석을 맡기느냐뿐입니다.

날것의 바이트를 보려면 <strong>헥스 덤프(hex dump)</strong> 도구를 씁니다. Linux에서는 `hexdump -C`, `xxd`, `od`가 대표적입니다. 작은 PDF의 앞부분입니다.

```
$ hexdump -C sample_e | head -3
00000000  25 50 44 46 2d 31 2e 37  0a 25 e2 e3 cf d3 0a 31  |%PDF-1.7.%.....1|
00000010  20 30 20 6f 62 6a 0a 3c  3c 20 2f 54 79 70 65 20  | 0 obj.<< /Type |
00000020  2f 43 61 74 61 6c 6f 67  20 2f 50 61 67 65 73 20  |/Catalog /Pages |
```

명령어를 보면:

- `hexdump -C` — "표준(canonical)" 보기. 위치, 16바이트의 16진수, 같은 바이트를 글자로 보여 줍니다.
- `| head -3` — 처음 세 줄(48바이트)만 봅니다.

한 줄을 칸별로 읽으면:

- `00000000` — <strong>오프셋(offset)</strong>. 이 줄이 파일 맨 앞에서 얼마나 떨어진 곳에서 시작하는지를 16진수로 씁니다. 2번 줄은 `0x10` = 16번째 바이트, 3번 줄은 `0x20` = 32번째 바이트에서 시작합니다. 분석가들은 오프셋으로 파일 속 위치를 가리킵니다("ZIP이 0x15be6에서 시작해").
- `25 50 44 46 2d 31 2e 37  0a 25 …` — 그 줄의 **16바이트**를 16진수로. 읽기 편하게 8개씩 두 묶음으로 나눴습니다.
- `|%PDF-1.7.%.....1|` — 같은 바이트를 **ASCII 글자**로 보여 줍니다. 찍을 수 있는 글자가 없는 바이트(줄바꿈 `0a`나 `e2` 같은)는 `.`으로 나옵니다.

그러니까 `25 50 44 46 2d`는 `%`, `P`, `D`, `F`, `-`입니다. 파일이 스스로 "나는 PDF 1.7이야"라고 밝히는 거죠. 두 번째 줄의 이상한 바이트 `e2 e3 cf d3`는 일부러 넣은 겁니다. PDF를 만드는 프로그램은 위쪽에 127보다 큰 바이트를 몇 개 넣어서, 전송 도구들이 이 파일을 텍스트가 아니라 **바이너리**로 다루게 합니다. 명세가 바이트를 정한다는 작은 예입니다.

글에서 자주 보게 될 `xxd`로 보면 바이트를 두 개씩 묶어 보여 줍니다.

```
$ xxd -l 16 sample_c
00000000: 8950 4e47 0d0a 1a0a 0000 000d 4948 4452  .PNG........IHDR
```

- `-l 16` — 16바이트까지만.
- `8950 4e47 0d0a 1a0a` — 8바이트짜리 PNG 시그니처(아래에서 자세히)를 2바이트씩 네 묶음으로.
- `0000 000d 4948 4452` — PNG의 첫 "청크(chunk)"의 길이(`0x0d` = 13)와 이름(`IHDR`, 이미지 헤더). 시그니처 뒤의 모든 것도 PNG 명세가 정합니다.

<strong>[보충]</strong> Windows에는 `hexdump`가 없지만 PowerShell에 `Format-Hex`가 있습니다.

```powershell
Format-Hex -Path .\x -Count 16
```

```
   Label: C:\triage\case-2611\x

          Offset Bytes                                           Ascii
                 00 01 02 03 04 05 06 07 08 09 0A 0B 0C 0D 0E 0F
          ------ ----------------------------------------------- -----
0000000000000000 4D 5A 90 00 03 00 00 00 04 00 00 00 FF FF 00 00 MZ�� ���  ÿÿ
```

- `-Path .\x` — 읽을 파일. `-Count 16`은 16바이트만 보여 줍니다(PowerShell 7. Windows PowerShell 5.1에는 `-Count`가 없으니 `Select-Object -First 1`로 자릅니다).
- `Offset`, `Bytes`, `Ascii` — `hexdump -C`와 같은 세 칸입니다.
- 처음 두 바이트가 `4D 5A` = `MZ`. 이 "이미지"는 **Windows 실행 파일**입니다.

## `file` 명령 { #file-command }

손으로 16진수를 읽는 건 느리니까, Linux에서 제일 먼저 해 볼 건 `file`입니다. 형식 시그니처 데이터베이스(`libmagic` 라이브러리의 **magic** 데이터베이스)를 갖고 있어서, 파일마다 **내용을 보고** 가장 잘 맞는 형식을 알려 줍니다. 확장자는 무시합니다.

확장자 없는 샘플 여섯 개입니다.

```
$ file *
sample_a:     PE32+ executable (GUI) x86-64, for MS Windows
sample_b:     ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, BuildID[sha1]=3c9e…, for GNU/Linux 3.2.0, stripped
sample_c:     PNG image data, 640 x 480, 8-bit/color RGBA, non-interlaced
sample_d:     SVG Scalable Vector Graphics image
sample_e:     PDF document, version 1.7, 0 page(s)
sample_f:     PE32 executable (DLL) (GUI) Intel 80386, for MS Windows
```

명령어: `file *` — 지금 폴더의 모든 파일에 `file`을 돌립니다(`*`는 셸이 파일 이름들로 바꿔 줍니다).

한 줄씩 보면:

- `sample_a` — **PE32+** = Windows의 "Portable Executable" 형식, 64비트판(`+`). `(GUI)`는 콘솔 프로그램이 아니라 창이 있는 프로그램으로 만들어졌다는 뜻. `x86-64` = 64비트 Intel/AMD CPU용. Windows 프로그램입니다.
- `sample_b` — **ELF** = Linux/Unix 실행 파일 형식. `64-bit LSB` = 64비트, 리틀 엔디언(낮은 자리 바이트가 먼저). `pie executable` = 위치 독립 실행 파일, 요즘 기본값. `dynamically linked` + `interpreter /lib64/ld-linux-x86-64.so.2` = 시스템 라이브러리가 필요하고 그 로더가 불러옵니다. `BuildID` = 컴파일러가 만든 ID. `stripped` = 디버깅용 심볼 이름을 지웠다는 뜻(정식 배포판에서 흔하고, 악성코드에서도 흔합니다).
- `sample_c` — 진짜 **PNG**. `file`이 헤더까지 읽어서 640×480 픽셀, RGBA 색상이라고 알려 줍니다.
- `sample_d` — **SVG** 이미지. 이건 눈여겨보세요. SVG는 **XML 텍스트**이고 JavaScript를 담을 수 있습니다. [변경됨](#trends) 참고.
- `sample_e` — **PDF**, 버전 1.7. `0 page(s)`는 아주 작거나 이상한 파일이라는 뜻입니다. 진짜 문서라면 페이지가 있죠.
- `sample_f` — **PE32**(32비트), `(DLL)` = 혼자 실행되는 프로그램이 아니라 라이브러리. DLL은 다른 프로세스가 불러서 씁니다(예: `rundll32.exe`, 또는 속아서 불러오는 정상 프로그램).

몇 초 만에 Windows 바이너리 둘, Linux 바이너리 하나, 이미지 둘, PDF 하나라는 걸 알았습니다. 경보의 `x`가 `sample_f`처럼 나왔다면, 그 "PNG"는 **DLL**이고 사건이 갑자기 심각해진 겁니다.

### 텍스트 파일과 스크립트 { #file-text }

평범한 텍스트에 대해서는 `file`이 별말을 안 합니다.

```
$ file notes update_sh invoice_0412 x.gz
notes:        ASCII text
update_sh:    Bourne-Again shell script, ASCII text executable
invoice_0412: Microsoft Word 2007+
x.gz:         gzip compressed data, last modified: Fri Nov 20 21:49:48 2026, max compression, original size modulo 2^32 5
```

- `notes` — `ASCII text`: 찍을 수 있는 글자와 줄바꿈만 있습니다. 그 글이 무슨 *뜻*인지는 `file`이 알려 주지 못합니다.
- `update_sh` — 첫 줄이 `#!/bin/bash`(셔뱅, shebang)라서 **bash 스크립트**로 알아봤습니다. 여기서 `executable`은 "셔뱅이 있다"는 뜻이지, 실행 권한이 켜져 있다는 뜻이 아닙니다. 셔뱅이 없는 스크립트(PowerShell, VBScript, JavaScript, 배치 파일 대부분)는 그냥 `ASCII text`나 `UTF-8 text`로 나오는 경우가 많습니다. 그러니 **"텍스트"가 "무해"는 아닙니다.**
- `invoice_0412` — `Microsoft Word 2007+`: `file`이 ZIP을 보고, 안의 `[Content_Types].xml`까지 들여다본 다음 DOCX라고 알아봤습니다.
- `x.gz` — gzip. gzip 헤더의 정보(시각, 압축 수준, 원래 크기)도 같이 보여 줍니다.

### 쓸 만한 옵션 { #file-options }

| 옵션 | 하는 일 | 언제 쓰나 |
| --- | --- | --- |
| `file -i x`(또는 `--mime`) | MIME 형식을 출력. 예: `application/pdf; charset=binary` | 서버가 보낸 `Content-Type`이나 Zeek의 `mime_type`과 바로 비교할 때 |
| `file -k x` | <strong>계속 찾기(keep going)</strong>: 첫 번째만이 아니라 맞는 시그니처를 전부 | 폴리글랏이 의심되거나 이상한 파일 |
| `file -z x` | gzip 같은 압축 파일 **안**을 들여다봄 | 풀지 않고 `.gz` 내용 살짝 보기 |
| `file -b x` | 간단히: 파일 이름을 앞에 붙이지 않음 | 스크립트, 반복문 |
| `file --extension x` | 알아낸 형식에 보통 붙는 확장자를 제안 | 카빙한 파일 이름을 다른 도구용으로 바꿀 때 |

```
$ file -i sample_e invoice_0412
sample_e:     application/pdf; charset=binary
invoice_0412: application/vnd.openxmlformats-officedocument.wordprocessingml.document; charset=binary
```

프록시 로그는 `Content-Type: image/png`라는데 `file -i`는 `application/x-dosexec`라고 한다면 <strong>콘텐츠 형식 불일치(content-type mismatch)</strong>입니다. 그것만으로도 강한 신호입니다([HTTP 응답의 Content-Type](../http/responses.md#content-type) 참고).

### `file`은 어떻게 판단하나 — 그리고 어떻게 속나 { #file-limits }

`file`은 세 종류 검사를 차례로 합니다. **파일 시스템 검사**(비었나? 폴더인가? 링크인가?), **매직 검사**(정해진 위치의 바이트를 시그니처 데이터베이스와 비교), **언어 검사**(텍스트처럼 보이면 문자 집합과 어쩌면 언어까지 추측). 처음 성공한 검사가 답이 됩니다.

이 구조 때문에 분석가가 알아 둘 점이 있습니다.

- 대체로 **앞쪽 바이트**를 믿습니다. 텍스트 파일 앞에 `MZ`를 붙이면 DOS 실행 파일이라고 할 수 있고, ZIP 앞에 PNG 헤더를 붙이면 PNG라고 합니다. 시그니처가 맞는다는 건 바이트가 그 형식처럼 **시작한다**는 증거이지, 파일 전체가 정상이라는 증거가 아닙니다.
- 기본으로 답을 **하나**만 냅니다. 폴리글랏은 먼저 맞은 형식으로 보입니다(`-k`를 쓰세요).
- 안쪽 **깊이**는 보지 않습니다. 89,062번째 바이트에 ZIP이 묻힌 OLE `.doc`도 `file`에게는 그냥 "Composite Document File"입니다.
- 결국 적대적인 입력을 파싱하는 소프트웨어입니다. `libmagic` 자체도 그동안 취약점이 있었습니다. 격리된 분석 VM에서, 최신 패키지로 돌려야 하는 이유가 하나 더 있는 셈입니다.

<strong>[보충]</strong> 그 밖에 만나게 될 식별 도구: **TrID**(Windows/Linux, 가능한 형식을 확률(%)로 순위를 매김), **Detect It Easy(DIE)**(실행 파일의 컴파일러와 패커까지 알아봄), 그리고 **Zeek 파일 분석**. Zeek는 네트워크로 지나가는 모든 파일에 자체 시그니처를 적용해 [files.log](../../../network/zeek/files-log.md)에 `mime_type`을 남깁니다. 그래서 파일을 하나도 건드리지 않고 네트워크 전체에서 "이미지"로 배달된 실행 파일을 찾아낼 수 있습니다.

## 매직 바이트 — 파일 시그니처 { #magic-bytes }

`file`은 <strong>매직 바이트</strong>, 다른 말로 <strong>파일 시그니처(file signature)</strong>를 알아보는 방식으로 일합니다. 형식의 명세가 요구하는 고정된 바이트 줄이고, 보통 파일 맨 앞(오프셋 0)에 있습니다. 읽는 프로그램은 나머지를 해석하기 전에 이걸 보고 "그래, 내 파일이 맞네"를 확인합니다.

외워 둘 만한 것들:

| 파일 형식 | 시작 바이트(16진수) | ASCII로 | 참고 |
| --- | --- | --- | --- |
| Windows 실행 파일(EXE, DLL, SYS, SCR, CPL…) | `4D 5A` | `MZ` | DOS 개발자 Mark Zbikowski의 머리글자. 뒤에 `PE\0\0` 헤더도 있음 |
| ZIP — 그리고 DOCX, XLSX, PPTX, JAR, APK 등 | `50 4B 03 04` | `PK..` | PKZIP을 만든 Phil Katz의 머리글자 |
| gzip(`.gz`, `.tgz`) | `1F 8B` | (찍히지 않음) | |
| PDF | `25 50 44 46 2D` | `%PDF-` | 뒤에 버전이 옴, 예: `1.7` |
| RTF | `7B 5C 72 74 66 31` | `{\rtf1` | Rich Text Format. 이 섹션 뒤에서 다룸 |
| PNG | `89 50 4E 47 0D 0A 1A 0A` | `.PNG....` | |
| **[보충]** ELF(Linux 바이너리) | `7F 45 4C 46` | `.ELF` | |
| **[보충]** OLE / Compound File(옛 `.doc`, `.xls`, `.ppt`, `.msi`, `.msg`) | `D0 CF 11 E0 A1 B1 1A E1` | (찍히지 않음) | 16진수 말장난으로 "DOCFILE"처럼 읽힘 |
| **[보충]** JPEG | `FF D8 FF` | | |
| **[보충]** GIF | `47 49 46 38 37 61` / `…39 61` | `GIF87a` / `GIF89a` | |
| **[보충]** 7-Zip | `37 7A BC AF 27 1C` | `7z....` | |
| **[보충]** RAR | `52 61 72 21 1A 07` | `Rar!..` | |
| **[보충]** Windows 바로 가기(LNK) | `4C 00 00 00 01 14 02 00` | `L...` | 흔한 피싱 페이로드 |
| **[보충]** Microsoft Cabinet(CAB) | `4D 53 43 46` | `MSCF` | |
| **[보충]** ISO 9660 디스크 이미지 | 오프셋 `0x8001`에 `43 44 30 30 31` | `CD001` | 맨 앞이 아님 — "앞쪽 바이트"가 규칙의 전부는 아니라는 좋은 예 |

전부 외울 필요는 없습니다. 위의 여섯 개에 ELF와 OLE만 알아도 SOC 일상의 대부분이 해결되고, 이걸 **바이트 흐름 속에서** 알아보는 능력은 계속 쓸모가 있습니다.

두 가지를 덤프로 보겠습니다.

**Windows 실행 파일:**

```
$ hexdump -C sample_a | head -9
00000000  4d 5a 90 00 03 00 00 00  04 00 00 00 ff ff 00 00  |MZ..............|
00000010  b8 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00  |................|
00000020  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00  |................|
00000030  00 00 00 00 00 00 00 00  00 00 00 00 80 00 00 00  |................|
00000040  0e 1f ba 0e 00 b4 09 cd  21 b8 01 4c cd 21 54 68  |........!..L.!Th|
00000050  69 73 20 70 72 6f 67 72  61 6d 20 63 61 6e 6e 6f  |is program canno|
00000060  74 20 62 65 20 72 75 6e  20 69 6e 20 44 4f 53 20  |t be run in DOS |
00000070  6d 6f 64 65 2e 0d 0d 0a  24 00 00 00 00 00 00 00  |mode....$.......|
00000080  50 45 00 00 64 86 01 00  b0 a2 31 67 00 00 00 00  |PE..d.....1g....|
```

- 오프셋 `0x00`: `4d 5a` = **`MZ`**, DOS 헤더 시그니처. 모든 Windows 실행 파일은 하위 호환을 위해 아직도 아주 작은 DOS 프로그램으로 시작합니다.
- 오프셋 `0x3c`: `80 00 00 00` = 숫자 `0x80`(리틀 엔디언이라 바이트를 거꾸로 읽어서 `00 00 00 80`). 이 칸(`e_lfanew`)은 **진짜 PE 헤더가 어디서 시작하는지** 알려 줍니다. 여기서는 오프셋 `0x80`.
- 오프셋 `0x40`–`0x7f`: <strong>DOS 스텁(DOS stub)</strong> — 기계어와 그 유명한 문장 `This program cannot be run in DOS mode.`. 헥스 덤프든, 패킷 캡처든, `strings` 출력이든 이 문장이 보이면, `MZ`가 잘려 나갔거나 다른 파일 속에 박혀 있더라도 **바로 거기에 Windows 실행 파일이 있습니다.**
- 오프셋 `0x80`: `50 45 00 00` = **`PE\0\0`**, PE 시그니처. 이어서 `64 86` = `0x8664` = 기계 종류 x86-64(32비트 파일은 `4c 01` = `0x14c`, Intel 386). 그다음 `01 00` = 섹션 1개, 그다음 `b0 a2 31 67` = <strong>컴파일 시각(timestamp)</strong>(`0x6731a2b0`, 1970년부터 센 초 = 2024년 11월). 시각은 조작할 수 있지만 쓸 만한 단서입니다.

**DOCX는 ZIP이다:**

```
$ hexdump -C invoice_0412 | head -3
00000000  50 4b 03 04 14 00 00 00  08 00 38 ae 74 5d c6 12  |PK........8.t]..|
00000010  7a 07 af 00 00 00 f1 00  00 00 13 00 00 00 5b 43  |z.............[C|
00000020  6f 6e 74 65 6e 74 5f 54  79 70 65 73 5d 2e 78 6d  |ontent_Types].xm|
```

- `50 4b 03 04` = **`PK\x03\x04`**, ZIP의 <strong>로컬 파일 헤더(local file header)</strong>. 압축된 파일 하나가 여기서 시작합니다.
- `14 00` = 풀 때 필요한 버전(`0x14` = 20 → "2.0"), `08 00` = 압축 방식 8 = **deflate**.
- 오프셋 `0x1a`의 두 바이트 `13 00` = `0x13` = 19 = 그 파일 이름의 길이이고, 바로 이름이 따라옵니다: `[Content_Types].xml`. 이 이름이 <strong>Office Open XML</strong> 문서의 표시입니다.

ZIP과 Office가 왜 매직 바이트를 같이 쓸까요? Office 2007부터 `.docx`, `.xlsx`, `.pptx`는 XML 파일, 이미지, 설정을 담은 **ZIP 압축 파일 그 자체**이기 때문입니다. 직접 확인할 수 있습니다.

```
$ cp invoice_0412 invoice_0412.zip
$ unzip -l invoice_0412.zip
Archive:  invoice_0412.zip
  Length      Date    Time    Name
---------  ---------- -----   ----
      241  2026-11-20 21:49   [Content_Types].xml
       16  2026-11-20 21:49   _rels/.rels
       13  2026-11-20 21:49   word/document.xml
---------                     -------
      270                     3 files
```

- `unzip -l` — 풀지 않고 안에 든 파일 **목록**만 봅니다.
- `[Content_Types].xml` — 각 부분이 무엇인지. `_rels/.rels` — 부분끼리 어떻게 이어지는지. `word/document.xml` — 실제 본문(Excel이면 `xl/`, PowerPoint면 `ppt/`).
- 진짜 악성 문서라면 이런 부분을 찾습니다. `word/vbaProject.bin`(매크로. 그럼 보통 `.docm`), URL을 가리키는 `word/_rels/document.xml.rels`의 외부 연결(원격 템플릿 주입), `word/embeddings/` 아래 박힌 개체.

<strong>[보충]</strong> 옛 바이너리 형식(`.doc`, `.xls`, `.ppt`, Office 97–2003)은 ZIP이 아니라 <strong>OLE 복합 파일(Compound File)</strong> 그릇을 쓰고, 매직은 `D0 CF 11 E0 A1 B1 1A E1`입니다. Outlook `.msg`와 `.msi` 설치 파일도 이걸 씁니다. oletools의 `oledump.py`, `olevba` 같은 도구가 읽는데, 그건 이 섹션 뒤쪽 Office 문서 페이지에서 다룹니다.

## 중첩 파일 — 중간에 있는 시그니처 { #nested-files }

`file`이 알아서 해 주는데 왜 외워야 할까요? `file`은 파일이 **이미 잘려 나와 있고** 시그니처가 맨 앞에 있을 때만 통하기 때문입니다. 매일 그게 깨지는 상황이 두 가지 있습니다.

- **날것의 바이트 흐름.** 패킷 캡처, 메모리 덤프, 디스크에서 나온 정체 모를 덩어리 — 관심 있는 파일이 중간 어딘가에서 시작합니다.
- **다른 파일 안에 박힌 파일.** 많은 형식이 다른 파일을 실어 나를 수 있습니다. 개체가 박힌 Word 문서, 첨부가 있는 PDF, 압축 속 압축, 이미지 뒤쪽 남는 바이트에 쑤셔 넣은 실행 파일. 바깥 파일이 대충 보기에는 무해해 보이니 피싱에서 늘 씁니다. MITRE ATT&CK에서는 **Embedded Payloads(T1027.009)**, 형식 위장은 <strong>Masquerade File Type(T1036.008)</strong>으로 다룹니다.

피싱 메일로 온 옛 형식 Word 문서(`quote_q4.doc`)의 한 조각입니다. 두 번째 파일이 보이나요?

```
$ hexdump -C -s 0x15bd0 -n 80 quote_q4.doc
00015bd0  ac 1e ac c6 65 10 ce 6f  cb f8 cf 6c 60 99 39 ac  |....e..o...l`.9.|
00015be0  45 99 03 65 2d ca 50 4b  03 04 14 00 00 00 08 00  |E..e-.PK........|
00015bf0  40 ae 74 5d d9 53 f9 65  0c 00 00 00 2f 00 00 00  |@.t].S.e..../...|
00015c00  0e 00 00 00 71 58 76 54  72 62 6d 50 4c 61 2e 78  |....qXvTrbmPLa.x|
00015c10  6d 6c b3 a9 b0 73 24 12  d8 e8 57 d8 01 00 50 4b  |ml...s$...W...PK|
```

옵션: `-s 0x15bd0` = 그 위치로 건너뛰기, `-n 80` = 80바이트만 보기.

- `00015be0` 줄: 7번째와 8번째 바이트가 `50 4b` = **`PK`**이고 뒤에 `03 04`가 옵니다. ZIP 로컬 파일 헤더 시그니처입니다. **ZIP이 오프셋 `0x15be0 + 6` = `0x15be6`(10진수 89,062)에서 시작합니다.** ASCII 칸에서 `PK`는 쉽게 눈에 띄고, 그 뒤의 찍히지 않는 `03 04`가 확정해 줍니다.
- 같은 줄: `14 00`(버전 2.0)과 `08 00`(deflate) — 앞에서 DOCX에서 본 헤더 칸과 똑같습니다. 우연히 나온 `PK`가 아니라는 뜻입니다.
- `00015c00` 줄: `0e 00`이 이름 길이(14)였고, 이름이 이어집니다. **`qXvTrbmPLa.xml`** — 박힌 압축 파일 속, 무작위로 보이는 파일 이름.
- `00015c10` 줄: 압축된 데이터 바로 뒤에 또 `50 4b` — ZIP의 다음 구조(중앙 디렉터리, `PK\x01\x02`)의 시작입니다.

이 ZIP이 악성 부분인지는 아직 모릅니다. 하지만 이걸 찾아내고, 무작위 이름까지 확인한 것 — 이게 바로 악성코드 분석가에게 넘길(또는 직접 더 분석할) 재료입니다.

**아무 위치에서나 시그니처 찾기 — 간단한 방법:**

```
$ LC_ALL=C grep -obUaP "PK\x03\x04" quote_q4.doc
89062:PK
```

- `LC_ALL=C` — 바이트를 UTF-8 글자가 아니라 바이트 그대로 다룹니다(안 그러면 `grep`이 바이너리를 잘못 읽을 수 있음).
- `-o` 맞은 부분만 출력, `-b` 그 **바이트 오프셋** 출력, `-U` 바이너리 모드, `-a` 바이너리를 텍스트처럼 다루기, `-P` Perl식 정규식이라 `\x03\x04`가 정확히 그 바이트를 뜻함.
- 출력 `89062:PK` — 시그니처가 **89,062**번째 바이트 = `0x15be6`에 있습니다. 눈으로 찾은 답과 같습니다.

**잘라 내기(카빙, carving):**

```
$ dd if=quote_q4.doc of=carved.zip bs=1 skip=89062 status=none
$ file carved.zip
carved.zip: Zip archive data, at least v2.0 to extract, compression method=deflate
$ unzip -l carved.zip
Archive:  carved.zip
  Length      Date    Time    Name
---------  ---------- -----   ----
       47  2026-11-20 21:50   qXvTrbmPLa.xml
```

- `dd if=… of=…` — 입력 파일에서 출력 파일로 복사. `bs=1 skip=89062` — 1바이트 단위로, 앞의 89,062바이트는 건너뜀. `status=none` — 진행 상황 출력 안 함.
- `PK`부터 끝까지 전부 복사되니 뒤에 남는 바이트도 따라오지만, ZIP 도구는 압축 파일의 끝 기록을 찾아서 읽기 때문에 괜찮습니다.
- 이제 시그니처가 오프셋 0에 있으니 `file`이 알아봅니다.

**자동으로 해 주는 도구.** **binwalk**(펌웨어 분석에서 많이 씀), **foremost**와 **scalpel**(포렌식 카빙 도구)은 파일 **전체**에서 알려진 시그니처를 찾고, 찾은 걸 뽑아낼 수 있습니다. binwalk 결과는 대략 이렇게 생겼습니다(줄임).

```
$ binwalk quote_q4.doc
DECIMAL       HEXADECIMAL     DESCRIPTION
--------------------------------------------------------------------------------
89062         0x15BE6         Zip archive data, at least v2.0 to extract, compressed size: 12, uncompressed size: 47, name: qXvTrbmPLa.xml
89178         0x15C5A         End of Zip archive, footer length: 22
```

- `DECIMAL` / `HEXADECIMAL` — 찾은 곳의 오프셋.
- `DESCRIPTION` — 어떤 시그니처가 맞았는지와 그 헤더에서 읽어 낸 칸(크기, 안의 파일 이름). "End of Zip archive" 줄이 압축 파일이 끝나는 곳이라, 카빙 도구는 얼마만큼 잘라야 할지 압니다.
- `binwalk -e`(extract)를 쓰면 잘라 내서 폴더에 풀어 줍니다.

<strong>[주의]</strong> 시그니처 스캐너는 <strong>오탐(false positive)</strong>을 냅니다. 큰 바이너리에서는 2바이트짜리 `MZ`나 `PK`가 우연히 늘 나옵니다. 그래서 위에서 시그니처 **뒤의** 바이트(버전, 압축 방식, 말이 되는 이름 길이)를 확인한 겁니다. 시그니처 하나 맞은 건 단서이지 결론이 아닙니다. 네트워크 캡처에서도 Wireshark/Zeek 추출로 같은 생각을 적용합니다. [유출된 데이터 카빙하기](../../network-forensics/part-1/lab-carving-exfiltrated-data.md) 참고.

## 폴리글랏 — 파일 하나, 정상 형식 둘 { #polyglots }

파일을 "PDF"로 만드는 건 뭘까요? 이름도 확장자도 아닙니다. 바이트가 **PDF 매직을 갖고**, **PDF 명세를 따르고**, **PDF 리더에서 열리면**, 실질적으로 그 파일은 PDF **입니다**. 그런데 그 파일이 동시에 다른 것일 수도 있을까요? 있습니다. 여러 형식에서 동시에 정상인 파일을 <strong>폴리글랏(polyglot)</strong>이라고 부릅니다.

이게 가능한 건 형식마다 **보는 곳**이 다르기 때문입니다.

- PDF 리더는 `%PDF-`를 꼭 0번 바이트가 아니라 대략 **처음 1KB 안**에서 찾고, 개체는 **끝** 근처의 표를 읽어서 찾습니다.
- ZIP 리더는 파일 **끝**(중앙 디렉터리 끝 기록)에서 시작해 거꾸로 읽습니다.
- HTML·HTA 엔진은 태그가 아닌 건 건너뛰고, 찾은 `<script>`는 무엇이든 실행합니다.
- 이미지 뷰어는 **앞**에서부터 읽고, 이미지가 끝난 뒤의 바이트는 무시합니다.

그래서 파일이 정상 JPEG로 시작하고(뷰어 만족), 정상 ZIP으로 끝날 수 있으며(압축 프로그램 만족), 두 프로그램이 각자 "자기" 파일을 엽니다. 잘 알려진 시연으로, 소셜 미디어에 올라온 그림 한 장을 저장해서 이름을 바꾸면 셰익스피어 전집이 든 분할 압축 파일로 풀리는 사례가 있었습니다.

비유하면, 보는 방식에 따라 꽃병으로도, 마주 본 두 얼굴로도 보이는 그림입니다. 잉크는 그대로이고, 읽는 쪽만 바뀝니다. 기술적으로는, 폴리글랏의 "형식"은 **어느 파서가 여느냐**에 달려 있습니다. 그래서 앞쪽 바이트만 확인하는 게이트웨이("이미지네")와, 사용자 PC에서 다른 프로그램으로 여는 쪽("압축 파일이네", "스크립트네")의 판단이 엇갈릴 수 있고, 공격자는 바로 그 틈을 씁니다.

예전엔 신기한 장난이었지만, 이제는 실제 침해에서 보입니다. 알아 둘 두 가지 예:

- 2023년 JPCERT/CC가 "**MalDoc in PDF**"를 소개했습니다. 스캐너에게는 PDF로 보이지만(`%PDF-` 헤더, PDF 개체), 안에 매크로가 든 MHT/Word 문서가 들어 있어서, 파일 이름을 `.doc`로 바꾸면 **Word가 문서로 열고** 매크로를 실행합니다.
- 2025년 초 Proofpoint는 UAE 항공·운송 조직을 노린 표적 공격을 보고했는데, 새 백도어의 단계별 페이로드를 숨기는 데 **폴리글랏 파일**(예: PDF이면서 HTA인 파일, 뒤에 ZIP을 붙인 PDF)을 썼습니다.

알아보는 방법:

- `file -k`(전부 찾기)나 `trid`가 **강하게 맞는 형식을 둘 이상** 보여 줌.
- 시그니처 스캔(`binwalk`, `grep -obUaP`)에서 **엉뚱한 곳에 다른 형식의 헤더나 꼬리**가 나옴 — "PDF"의 끝에 `PK\x05\x06` 끝 기록, "이미지" 안에 `<script`나 `<HTA:APPLICATION`.
- **내용과 안 맞는 크기** — 2 MB짜리 "파비콘".
- 형식의 **논리적 끝 뒤에 남은 데이터** — PNG의 `IEND` 청크 뒤, JPEG의 `FF D9` 끝 표시 뒤, PDF의 마지막 `%%EOF` 뒤.

## 유니코드와 인코딩 { #unicode }

파일 속 읽을 수 있는 글자를 찾기 전에(다음 페이지, `strings`), 글자가 어떻게 바이트가 되는지 알아야 합니다. 같은 단어가 **완전히 다른 바이트 줄 세 가지**가 될 수 있기 때문입니다.

**ASCII**는 옛 미국 표준입니다. 128개 글자(영문자, 숫자, 문장 부호, 제어 코드)를 한 바이트씩, `A` = `0x41`. 영어에는 괜찮지만 한국어, 일본어, 아랍어, 키릴 문자, 이모지는 안 됩니다. 여러 방식이 경쟁하다가 결국 <strong>유니코드(Unicode)</strong>가 이겼습니다. **모든 글자에 고유한 번호**를 붙인 하나의 큰 목록이고, 그 번호를 <strong>코드 포인트(code point)</strong>라고 부르며 `U+` 뒤에 16진수로 씁니다. `A`는 `U+0041`, 한자 学("배울 학")은 `U+5B66`, 😀는 `U+1F600`입니다.

번호 공간은 `U+0000`부터 `U+10FFFF`까지 — 가능한 코드 포인트가 **1,114,112개**입니다. 전부 쓰이는 건 아니고, 유니코드 17.0(2025년 9월)이 정의한 글자는 약 16만 개입니다.

코드 포인트는 그냥 숫자입니다. 그 숫자를 파일에 어떻게 적을지는 <strong>인코딩(encoding)</strong>이 정합니다. 모든 글자에 3바이트를 쓰면 전체 범위를 덮지만 컴퓨터가 다루기 어색한 크기이고, 4바이트씩 쓰면 쉽지만 대부분의 글이 앞자리가 0투성이인 평범한 글자라 공간이 낭비됩니다. 그래서 인코딩이 여러 개 있습니다.

| 인코딩 | 글자당 바이트 | `A`(U+0041) | 学(U+5B66) | 😀(U+1F600) |
| --- | --- | --- | --- | --- |
| ASCII | 1(128글자만) | `41` | 표현 불가 | 표현 불가 |
| UTF-8 | 1–4, 가변 | `41` | `E5 AD A6` | `F0 9F 98 80` |
| UTF-16(빅 엔디언으로 표시) | 2 또는 4, 가변 | `00 41` | `5B 66` | `D8 3D DE 00`(서로게이트 쌍) |
| UTF-32(빅 엔디언으로 표시) | 항상 4 | `00 00 00 41` | `00 00 5B 66` | `00 01 F6 00` |

문자열 **`学SOC1`**을 각각으로:

```
UTF-8   : e5ada6 53 4f 43 31
UTF-16  : 5b66 0053 004f 0043 0031
UTF-32  : 00005b66 00000053 0000004f 00000043 00000031
```

(읽기 편하게 글자 사이에 띄어쓰기를 넣었습니다.) 읽어 보면:

- **UTF-8** — 영문자는 **ASCII와 똑같고**(`53 4f 43 31` = `SOC1`) 채우는 바이트가 없습니다. 学는 **세** 바이트. 이게 UTF-8의 핵심 요령입니다. ASCII 글은 그대로 정상 UTF-8이고, 다른 글자만 필요할 때 바이트를 더 씁니다. 웹과 Linux가 UTF-8 천하인 이유입니다.
- **UTF-16** — 여기서는 모든 글자가 **두** 바이트이고, 영문자에는 `00` 바이트가 붙습니다. `U+FFFF`보다 큰 글자(이모지 같은)는 **네** 바이트, 이른바 "서로게이트 쌍(surrogate pair)"이 필요해서 UTF-16도 가변 길이입니다. Windows가 내부적으로 UTF-16을 쓰기 때문에 `strings`와 PowerShell에서 아주 중요합니다.
- **UTF-32** — 모든 글자가 정확히 **네** 바이트. 처리하기는 가장 쉽고(n번째 글자는 4n번째 바이트), 공간은 가장 낭비합니다.

学가 UTF-8에서 `E5 AD A6`이 되는 과정 — 한 번은 볼 만합니다. UTF-8 바이트를 알아볼 수 있는 이유가 보이거든요.

```
U+5B66 in binary:          0101 1011 0110 0110   (16 bits)
3-byte UTF-8 template:     1110xxxx 10xxxxxx 10xxxxxx
fill the 16 bits in:       1110 0101  10 101101  10 100110
in hex:                    E5         AD         A6
```

- 첫 바이트의 `1110` 머리는 "이 글자는 **3**바이트야"라는 뜻입니다(`110` = 2바이트, `11110` = 4바이트).
- 뒤따르는 바이트는 모두 `10`으로 시작합니다("이어지는 바이트").
- 그래서 정상 UTF-8에서 `0x80`–`0xFF` 바이트는 언제나 이런 모양으로만 나옵니다. 도구들(그리고 `file`)이 UTF-8과 무작위 바이너리를 구별할 수 있는 이유입니다.

**바이트 순서와 BOM.** UTF-16과 UTF-32는 한 단위의 바이트를 큰 쪽 먼저(`00 41`) 쓸 수도, 작은 쪽 먼저(`41 00`) 쓸 수도 있습니다. Windows는 **리틀 엔디언 UTF-16**("UTF-16LE")을 쓰니 `A`는 `41 00`입니다. 파일은 맨 앞의 <strong>바이트 순서 표시(BOM, byte order mark)</strong>로 인코딩을 밝힐 수 있습니다. `FF FE`(UTF-16LE), `FE FF`(UTF-16BE), `EF BB BF`(BOM 있는 UTF-8, Windows 도구가 저장한 파일에서 흔함). BOM이 없으면 프로그램이 짐작해야 합니다.

```
$ file bom8 bom16 u16
bom8:  Unicode text, UTF-8 (with BOM) text
bom16: Unicode text, UTF-16, little-endian text, with no line terminators
u16:   data
```

- `bom8`, `bom16` — `file`이 BOM을 읽고 확신합니다.
- `u16` — 같은 UTF-16LE 글인데 BOM이 **없으니** `file`이 포기하고 `data`라고 합니다. `file`이 "data"라고 한다고 꼭 바이너리는 아닙니다.

SOC 분석가가 신경 써야 하는 이유:

- **인코딩을 잘못 고르면 깨진 글자가 나옵니다.** UTF-8 `e5 ad a6`를 Latin-1로 읽으면 `å­¦`가 되고, UTF-16으로 읽으면 뜻 없는 글자 두 개가 됩니다. 로그나 웹 페이지에 이런 "깨진 글자(mojibake)"가 보이면 데이터가 아니라 인코딩이 틀린 겁니다.
- **검색이 빗나갑니다.** 바이너리나 메모리 덤프에서 `powershell`의 ASCII 바이트를 찾으면 UTF-16LE 버전 `p\0o\0w\0e\0r\0…`은 안 나옵니다. Windows 프로그램은 대부분의 문자열을 바로 그렇게 저장합니다. PowerShell의 `-EncodedCommand`도 **UTF-16LE** 글을 Base64로 만든 것입니다([Base64](../http-analysis/base64.md) 참고).
- **닮은꼴 글자.** 키릴 문자 `а`(`U+0430`)는 라틴 문자 `a`(`U+0061`)와 똑같아 보이지만 다른 코드 포인트, 다른 바이트입니다. 이걸 이용한 도메인 위장은 [블록체인 DNS와 IDN](../dns/blockchain-dns-and-idn.md)에서 다룹니다.
- **눈에 안 보이는 제어 문자.** <strong>오른쪽에서 왼쪽 강제(RLO, right-to-left override)</strong> `U+202E`는 이름의 나머지가 **화면에 보이는 순서**를 뒤집습니다. 실제 이름이 `invoice_<U+202E>fdp.exe`인 파일은 탐색기에서 `invoice_exe.pdf`로 보입니다. 그래도 여전히 `.exe`이고, 매직 바이트는 `MZ`라고 말합니다. ATT&CK: **Masquerading: Right-to-Left Override(T1036.002)**.

## 모아 보기 — 정체 모를 파일 분류 순서 { #routine }

경보로 돌아갑시다. `image/png`로 배달된 `x`.

```
$ file x
x: PE32 executable (DLL) (GUI) Intel 80386, for MS Windows
$ file -i x
x: application/x-dosexec; charset=binary
$ hexdump -C x | head -1
00000000  4d 5a 90 00 03 00 00 00  04 00 00 00 ff ff 00 00  |MZ..............|
$ sha256sum x
5e0c7a…(64 hex characters)  x
```

1. `file` → 32비트 **DLL**. PNG가 아닙니다.
2. `file -i` → `application/x-dosexec`. 서버가 말한 `Content-Type: image/png`와 어긋납니다. 이 불일치만으로도 보고할 만합니다.
3. 헥스 → 오프셋 0의 `MZ`를 내 눈으로 확인합니다.
4. 해시를 구하고(해시는 이 섹션 뒤쪽에 페이지가 있음), OPSEC이 중요하면 **파일을 올리지 말고** 해시로 위협 인텔리전스 도구에서 조회합니다.
5. 다음 단계: `strings`로 단서 찾기(다음 페이지), 실행됐는지 확인(엔드포인트에서 Sysmon 7 이미지 로드, `rundll32.exe`/`regsvr32.exe` 프로세스 생성 — [프로세스 생성](../important-events/process-creation.md) 참고), Zeek `files.log`에서 같은 `mime_type` 불일치를 네트워크 전체로 찾기.

SOC 기록 한 줄로: *"`cdn-update.example`의 응답은 `image/png`라고 선언했으나 내용은 PE32 DLL(MZ, PE 헤더, i386). SHA-256 5e0c7a…. T1036.008 파일 형식 위장."*

## 2026년 관점 { #trends }

!!! success "[2026 현재] 지금도 그대로 유효"
    파일은 여전히 바이트의 줄이고, 확장자와 `Content-Type`은 여전히 공격자가 정하는 주장이며, 알아보는 순서 — `file`, 헥스 보기, 매직 바이트, 중첩 내용 시그니처 스캔, 그다음 깊은 분석 — 도 그대로입니다. 매직 바이트 자체는 바뀌지 않고(`MZ`, `PK\x03\x04`, `%PDF-`, `\x7fELF`…), Office Open XML은 여전히 ZIP입니다. 유니코드, UTF-8/16/32, Windows의 UTF-16LE 사용도 설명한 그대로입니다. `file`(요즘 배포판의 libmagic 5.4x)은 여전히 표준 첫 단계입니다.

!!! info "[변경됨] 바뀐 점"
    - **폴리글랏이 신기한 장난에서 실제 공격 기법이 됐습니다.** "MalDoc in PDF"(JPCERT/CC, 2023)는 PDF처럼 보이지만 Word가 매크로 문서로 열어 실행하는 파일을 보여 줬고, 2025년 Proofpoint는 UAE 항공·운송 기업을 노린 표적 첩보 공격이 폴리글랏 파일(PDF/HTA, ZIP을 붙인 PDF)로 이뤄졌다고 보고했습니다. "이 파일은 두 형식에 다 맞는다"는 잡학이 아니라 발견 사항으로 다룹니다.
    - **Microsoft가 인터넷에서 온 매크로를 막기 시작한 뒤(Office, 2022년부터) 배달 파일 구성이 바뀌었습니다.** 공격자는 압축 파일과 디스크 이미지(ZIP, RAR, 7z, ISO, IMG, VHD), LNK 바로 가기, OneNote 파일, HTML 스머글링, 그리고 특히 2024–2025년에는 JavaScript나 HTML 피싱 페이지를 품은 **SVG 첨부 파일**로 옮겨 갔고, 여러 이메일 보안 업체가 급증을 보고했습니다. `file`이 `SVG Scalable Vector Graphics image`라고 하는 "이미지"는 안을 들여다볼 가치가 있습니다. 브라우저가 실행하는 텍스트이기 때문입니다.
    - **도구.** binwalk가 Rust로 다시 작성됐습니다(v3, 2024–2025). 더 빠르고, 옛 안내서에 나오는 Python v2와 출력·옵션이 다릅니다. Windows에서는 Detect It Easy와 TrID가 여전히 흔하고, 많은 EDR과 이메일 게이트웨이가 이제 "진짜 파일 형식" 판별을 기본 기능으로 갖고 있습니다.
    - **ATT&CK 이름.** 파일 형식 위장은 **T1036.008 Masquerade File Type**(2023년 추가), 박힌 페이로드는 **T1027.009**, 오른쪽에서 왼쪽 강제는 **T1036.002**, 이중 확장자는 **T1036.007**입니다.
    - **유니코드는 계속 늘어납니다**(2025년 9월 유니코드 17.0, 약 16만 글자). 그래서 파일 이름, URL, 코드 속 닮은꼴 글자와 보이지 않는 글자 문제는 계속 변해 가는 숙제입니다.

!!! warning "[주의] 옛 방식대로 하면 틀리거나 위험한 점"
    - **`file`의 첫 답을 전부라고 믿지 마세요.** 파일 앞부분만 읽고 하나만 답합니다. 수상하면 `file -k`, 시그니처 스캔, 파일 끝부분 확인까지 합니다.
    - **`%PDF-`가 꼭 0번 바이트에 있어야 한다거나, ISO 매직이 맨 앞에 있다고 가정하지 마세요.** PDF 리더는 대략 처음 1KB 안의 헤더를 받아 주고(공격자가 이걸 씀), ISO의 `CD001`은 `0x8001`에 있습니다.
    - **"텍스트"면 안전하다고 생각하지 마세요.** 셔뱅 없는 스크립트, SVG, HTML, HTA 모두 텍스트로 보입니다. 실행되는 텍스트 파일은 가장 흔한 피싱 페이로드 중 하나입니다.
    - **바이너리에서 ASCII로만 찾지 마세요.** Windows 문자열은 대개 UTF-16LE입니다. 둘 다 찾거나, 둘 다 찾아 주는 도구를 씁니다(다음 페이지).
    - **내 업무 PC에서, 또는 열어 보는 방식으로 파일을 알아보지 마세요.** 격리된 분석 VM을 쓰고, `file`/libmagic을 최신으로 유지합니다. 식별 도구도 적대적인 입력을 파싱하는 프로그램입니다.
    - **큰 바이너리에서 시그니처 스캔이 찾은 2바이트 하나를 믿지 마세요.** 뒤따르는 헤더 칸을 확인합니다.

## 확인 문제 { #quiz }

### 문제 1

프록시 로그에 `GET http://static-img.example/logo.png`가 `200`, `Content-Type: image/png`, 418,816바이트로 응답한 기록이 있습니다. 본문을 뽑아 이렇게 돌렸습니다.

```
$ file logo.png
logo.png: PE32+ executable (DLL) (GUI) x86-64, for MS Windows
$ hexdump -C logo.png | head -1
00000000  4d 5a 90 00 03 00 00 00  04 00 00 00 ff ff 00 00  |MZ..............|
```

이 파일은 무엇이고, 거짓이었던 "주장" 세 가지는 무엇이며, 다음에 무엇을 하겠습니까?

??? success "정답과 해설"
    **정체:** **64비트 Windows DLL**입니다. `file`이 `PE32+ … (DLL) … x86-64`라고 하고, 헥스 덤프가 `4d 5a` = **`MZ`**, Windows 실행 파일 시그니처로 시작합니다. 진짜 PNG라면 `89 50 4E 47 0D 0A 1A 0A`로 시작해야 합니다.

    **거짓 주장:** (1) **파일 이름·확장자** `logo.png`, (2) 서버의 **`Content-Type: image/png`**, (3) 무해한 이미지처럼 보이게 하는 URL 경로(`static-img`, `logo`). 셋 다 서버를 운영하는 쪽이 마음대로 정합니다. 증거는 바이트뿐입니다. **T1036.008 Masquerade File Type**에 해당합니다.

    **다음:** 해시를 구해 평판을 조회하고(OPSEC이 중요하면 파일은 올리지 않음), `strings`로 단서를 찾고, 엔드포인트에서 불러오거나 실행됐는지 확인하고(그 파일을 쓴 `rundll32.exe`/`regsvr32.exe` 프로세스 생성, Sysmon 7 이미지 로드, 디스크 어디에 쓰였는지), 네트워크 전체에서 판별된 MIME 형식이 `application/x-dosexec`인 다른 "이미지"를 찾고(Zeek `files.log`), 도메인을 차단합니다.

### 문제 2

동료가 말합니다. "`file`이 `Composite Document File V2 Document`라고 했으니 그냥 옛날 Word 파일이야. 안에 다른 건 없어." 그런데 `LC_ALL=C grep -obUaP "PK\x03\x04" quote_q4.doc`를 돌리니 `89062:PK`가 나왔습니다. 동료의 결론이 왜 성립하지 않는지, 출력이 무슨 뜻인지, 어떻게 확인할지 설명하세요.

??? success "정답과 해설"
    **왜 성립하지 않나:** `file`은 파일 **앞부분**(여기서는 OLE 시그니처 `D0 CF 11 E0…`)을 보고 **하나**만 답합니다. 나머지 부분은 찾아보지 않으니, 더 안쪽에 **박힌** 파일은 `file`에게 보이지 않습니다.

    **출력의 뜻:** ZIP 로컬 파일 헤더 시그니처 **`PK\x03\x04`**가 **바이트 오프셋 89,062**(`0x15be6`)에 있습니다. 문서 안에 ZIP 압축 파일의 시작처럼 보이는 것이 묻혀 있습니다.

    **확인 방법:** 우연한 `PK`일 수도 있으니 시그니처 뒤의 바이트가 ZIP 헤더로 말이 되는지 봅니다(버전 `14 00`, 압축 방식 `08 00` deflate, 말이 되는 파일 이름 길이와 이어지는 이름 — 여기서는 `qXvTrbmPLa.xml`). 그다음 그 위치부터 잘라 내고(`dd … skip=89062` 또는 `binwalk -e`), 결과에 `file`/`unzip -l`을 돌리고, 분석으로 넘깁니다. ATT&CK로는 <strong>Embedded Payloads(T1027.009)</strong>입니다. 이 ZIP이 악성인지는 아직 분석이 필요합니다.

### 문제 3

(a) DOCX와 ZIP 파일은 왜 같은 바이트로 시작하나요? (b) Windows 프로그램이 문자열 `cmd`를 `63 00 6d 00 64 00`으로 저장했습니다. 어떤 인코딩이고, ASCII로만 `63 6d 64`를 찾으면 왜 놓치나요? (c) 사용자가 탐색기에 `invoice_exe.pdf`로 보이던 파일을 열었는데, EDR은 PE 실행 파일이 실행됐다고 합니다. 어떤 속임수일 수 있나요?

??? success "정답과 해설"
    **(a)** DOCX가 ZIP **이기 때문**입니다. Office 2007부터 Office Open XML 문서(`.docx`, `.xlsx`, `.pptx`)는 XML 부분들(`[Content_Types].xml`, `word/document.xml`, …)을 묶은 ZIP 압축 파일이라서, ZIP 시그니처 `50 4B 03 04`(`PK\x03\x04`)를 갖습니다. `.zip`으로 이름을 바꾸면 `unzip -l`이 안의 부분들을 보여 줍니다. (옛 `.doc`는 대신 OLE 그릇 `D0 CF 11 E0…`을 씁니다.)

    **(b)** **UTF-16 리틀 엔디언**(UTF-16LE)입니다. 영문자 하나가 두 바이트를 쓰고, 그 글자의 ASCII 값 뒤에 `00`이 붙습니다. Windows는 내부 문자열 대부분에 UTF-16LE를 씁니다. ASCII 검색은 연속된 바이트 `63 6d 64`를 찾는데, 파일에서는 사이사이에 `00`이 끼어 있어 맞지 않습니다. 두 인코딩을 다 찾습니다(대부분의 문자열 도구에 16비트 리틀 엔디언 옵션이 있음).

    **(c)** 파일 이름 속 **오른쪽에서 왼쪽 강제(RLO)** 문자 `U+202E`일 가능성이 큽니다. 예를 들어 실제 이름은 `invoice_` + `U+202E` + `fdp.exe`입니다. `U+202E` 뒤는 **보이는 순서**가 뒤집혀서 `invoice_exe.pdf`로 보이지만, 이름은 진짜로 `.exe`로 끝나고 Windows는 프로그램으로 실행합니다. 매직 바이트(`MZ`)와 EDR이 실행 파일이라고 일치합니다. ATT&CK: **T1036.002 Right-to-Left Override**. 탐지: 프로세스 생성·파일 생성 로그의 파일 이름에서 `U+202E`(UTF-8로 `E2 80 AE`)를 찾습니다.
