# 경보 분류와 "위험하다"의 뜻 — 거의 끝나 가는 공격, 공격자 목표까지의 거리 { #defining-dangerous }

!!! abstract "이 페이지에서 다루는 것"
    근무 시간마다 맨 처음 내리는 결정, <strong>"다음에 어떤 경보를 열까?"</strong>를 다룹니다. 먼저 <strong>분류(triage)</strong>가 무엇이고 왜 "오래된 것부터"가 틀린 답인지, 응급실 비유로 시작해서 SOC 상황(분석가는 적고, 경보는 많고, 결과의 무게는 제각각)으로 옮겨 봅니다. 그다음 실무에서 "<strong>위험하다(dangerous)</strong>"가 무슨 뜻인지 정합니다. 우선순위 순서대로 네 가지 정의(거의 끝나 가는 공격, 가치 높은 대상, 고급·표적 공격자, 드물거나 처음 보는 경보)와, 그 넷을 꿰뚫는 하나의 기준(피해, 비용, 되돌리기 어려움)입니다. 이어서 **거의 끝나 가는 공격**을 자세히 봅니다. 공격자의 목표를 왜 미리 정해 둬야 하는지, 그리고 마지막 단계의 뚜렷한 신호가 실제 로그에서 어떻게 생겼는지(유출, 곧 닥칠 파괴, 보호 구역과 잠가 둔 호스트에서의 활동, 높은 권한 계정의 이상한 사용 — Windows 이벤트 **4624**, **4672**, **4688**을 칸 단위로). 그다음 두 가지 공격 모델로 **목표까지 남은 거리**를 어림합니다. 7단계 사이버 킬 체인(어느 단계가 공격자 쪽인지, 호스트에서 보이는지 네트워크에서 보이는지)과, 실제 침해에 더 잘 맞는 반복 고리 모양의 공격 수명 주기입니다. 마지막으로 가상의 경보 8개를 직접 분류해 순위를 매기고 결정 하나하나의 이유를 설명합니다. 끝에 확인 문제와 해설이 있습니다.

!!! note "표기"
    **[보충]** = 꼭 알아야 할 실무 보충, **[정정]** = 흔히 잘못 알려진 내용 정정, **[변경됨]**/**[주의]** = 최근 바뀐 점과 옛 방식대로 하면 위험한 점. 회사(Kestrel Logistics), 호스트 이름, 계정, 도메인, IP는 모두 설명용 가상 값(`.example`, 문서용·사설 IP)입니다.

## 한눈에 보는 핵심 8가지 { #key-points }

1. <strong>분류(triage)</strong>는 분석가보다 경보가 많을 때 다음에 무엇을 볼지 고르는 일이다. 줄 서기가 아니라 **결과의 무게**를 따지는 판단이다. 가장 오래된 경보가 가장 중요한 경우는 드물다.
2. 경보를 고를 때마다 같은 질문을 던진다. **"지금 가진 정보로 봤을 때, 이 중 무엇을 한 시간 동안 내버려 두면 우리가 가장 크게 다칠까?"**
3. "**위험하다**"에는 실무에서 네 가지 뜻이 있고, 이 순서로 본다. (1) 목표 달성에 **거의 다 온** 공격, (2) **가치가 높은 것**(중요한 호스트, 업무 절차, 사용자, 데이터)을 노리는 공격, (3) **고급 또는 표적** 공격자의 흔적, (4) **처음 보거나 아주 드문(가장 적게 울린)** 경보.
4. 넷 모두의 밑바탕에는 기준 하나가 있다. **성공하면 피해를 주거나, 돈이 많이 들거나, 되돌리기 어려운가?** 시간도 피해도 결국 돈이다.
5. "거의 끝났다"를 알아보려면 **공격자가 우리에게서 무엇을 원하는지 미리 정해 둬야** 한다(위협 모델, 위협 인텔리전스). 흔한 목표: 데이터 훔치기, 데이터 파괴·암호화, 특정 시스템 도달, 물리적·운영상 피해.
6. 마지막 단계의 뚜렷한 신호: **데이터 유출**, **곧 닥칠 파괴**(랜섬웨어, 와이퍼), **보호된 네트워크 구역 깊숙한 곳**에서의 활동, **단단히 잠가 둔 호스트**에서의 활동, **높은 권한 계정을 엉뚱한 곳에서 쓰는 것**(낯선 호스트의 4624 + 4672).
7. **목표까지의 거리**를 어림하려면 각 경보를 공격 모델 위에 올려 본다. 흔히 쓰는 기준은 **사이버 킬 체인**(정찰 → 무기화 → 전달 → 익스플로잇 → 설치 → C2 → 목표 행동)이고, 뒤쪽 단계가 "위험 구역"이다.
8. 킬 체인은 **일직선**이지만 실제 침해는 **빙빙 돈다**. 권한 상승, 내부 정찰, 옆으로 이동, 지속성 유지를 목표에 닿을 때까지 되풀이한다. 데스크톱 한 대의 C2도 나쁘지만, 핵심 데이터가 있는 파일 서버의 C2는 끝에 훨씬 더 가깝다.

## SOC에서 왜 중요한가 { #why }

SOC에 남는 분석가는 없습니다. 평범한 아침에도 대기열에는 경보가 수십, 수백 개 쌓여 있고, 대부분은 오탐이거나 영향이 작은 잡음입니다. 그런데 그 더미 어딘가에 나머지를 다 합친 것보다 중요한 경보가 하나 있을 수 있습니다. 맨 위에 있는 것, 즉 가장 오래된 경보부터 집는다는 건 "경보는 중요한 순서대로 도착한다"에 돈을 거는 셈입니다. 그렇지 않습니다. 08:02에 들어온 포트 스캔이 08:20에 들어온 "도메인 관리자가 재무 데이터베이스에 로그온" 경보보다 위에 있고, 스캔에 쓴 한 시간은 침입자가 데이터베이스에서 쓰는 한 시간이 됩니다.

분류는 "경보 더미"를 "다음으로 볼 가장 값진 것"으로 바꿔 주는 일입니다. 네트워크, 호스트, 업무에 대한 분석가의 지식이 빛을 보는 곳도 여기입니다. 지금까지 배운 것(DNS, HTTP, 로그온, 프로세스 생성이 어떻게 생겼는지)이 있어야 경보 제목만 보고도 몇 초 안에 **공격자가 지금 어디쯤 있고 다음에 무엇을 할 수 있는지** 어림할 수 있습니다.

이 페이지가 막아 주는 두 가지 실수:

- **먼저 온 것부터 처리(FIFO, first-in first-out).** 경보에게는 공평하지만 회사에게는 불공평합니다.
- **경보 심각도만 보고 처리.** "Critical"이라는 꼬리표는 어떤 호스트, 어떤 계정, 어떤 다른 경보와 엮일지 모르는 규칙 작성자가 붙인 겁니다. 심각도는 판단 재료 중 하나일 뿐 답이 아닙니다.

## 분류: 응급실처럼 생각하기 { #triage }

응급실을 떠올려 보세요. 손가락을 삔 환자가 가슴 통증 환자보다 두 걸음 먼저 들어왔습니다. 먼저 왔다고 손가락부터 봐야 한다고 생각하는 사람은 없죠. 분류 담당 간호사는 환자를 빠르게 한 번씩 보고, 기다리면 얼마나 나빠질지 어림해서 **급한 정도와 결과의 무게**로 순서를 정합니다. 119 상황실도 신고 전화를 똑같이 다룹니다.

SOC도 재료가 같습니다.

- **자원이 한정돼 있다.** 근무조마다 분석가는 몇 명뿐. 경보 하나를 열면 다른 경보 하나를 못 엽니다.
- **문제가 동시에 여러 개다.** 경보는 끊임없이 들어오고 서로 상관없는 것도 많습니다.
- **결과의 무게가 다르다.** 진짜인데 내버려 둬도 아무 손해가 없는 경보가 있고, 회사에 큰 손해를 주는 경보가 있습니다.

목표도 같습니다. **다음에는 가장 위험한(또는 가장 흥미로운) 경보를 고른다.** 비유에서 기술로 돌아오면, 분류는 빠르고 불완전한 평가입니다. 아직 조사하는 단계가 아닙니다. 경보 제목, 호스트, 사용자, 시각, 보강(enrichment) 필드 한두 개를 읽고 불확실한 상태에서 **순위를 정하는** 결정입니다. 제대로 된 조사(뒤의 섹션들)는 고른 다음에 합니다.

!!! tip "[보충] 분류는 한 번으로 끝나지 않는다"
    사건 하나를 끝낼 때마다, 새 경보가 들어올 때마다 순위를 다시 매기세요. 같은 호스트나 같은 사용자에게 두 번째 경보가 붙으면 중간 경보가 맨 위로 올라갈 수 있습니다. 분류 결정은 시간이 지나면 낡습니다. 08:05에는 맞았던 순위가 08:25에는 틀릴 수 있습니다.

## "위험하다"의 뜻 { #dangerous }

"위험하다"는 당연한 말 같지만, 경보 8개에 순위를 매기려고 하면 막막해집니다. 실무에서 쓰는 네 가지 정의를, 적용하는 순서대로:

1. **거의 끝나 가는 공격.** 공격자가 원하던 일을 막 하려는 것처럼 보입니다. 데이터가 나가고 있거나, 데이터가 곧 파괴되려 하거나, 목표 시스템에 닿았거나. 이보다 위는 없습니다.
2. **가치가 높은 것을 노리거나 건드리는 공격.** 끝나 가는 공격이 없다면, 그다음은 가장 중요한 것을 겨냥하는 공격입니다. **중요한 호스트**(도메인 컨트롤러, ERP 데이터베이스, OT 게이트웨이), **중요한 업무 절차**(결제, 급여, 배차), **중요한 사용자**(도메인 관리자, 임원, 돈을 옮길 수 있는 재무 직원, 설계도에 접근하는 엔지니어), 그리고 **민감한 데이터**. 예를 들어 중요한 서버를 향한 익스플로잇 시도(실패했더라도), 민감한 데이터에 접근할 수 있는 사람의 노트북에서 잡힌 악성코드. 이런 공격은 익스플로잇 단계는 지났지만 아직 목표에는 못 미친 경우가 많습니다. 1번 정의로 가는 "길 위에" 있는 거죠.
3. **고급 또는 표적 공격자.** 표적 공격자는 *우리를* 골랐고, 우리만 가진 무언가를 원합니다. 고객 데이터, 지식 재산, 설계도, 아니면 그냥 모든 걸 지워 버릴 능력. 그 의도 때문에 아무나 노리는 악성코드보다 끈질기고 피해도 큽니다. 문제는 알아보기입니다. "표적 공격자 침입, 지금 대응하세요"라는 제목의 경보는 없습니다. 알아보는 단서는 다음 페이지에서 다룹니다.
4. **처음 보거나, 아주 드물거나, 가장 적게 울린 경보.** 다른 게 눈에 띄지 않을 때는 규칙별로 울린 횟수를 세어 정렬하고 **맨 아래**를 보세요. 이번 달에 딱 한 번 울린 규칙은 하루에 4,000번 울리는 규칙보다 새로운 일 — 진짜 공격을 포함해서 — 을 말하고 있을 가능성이 훨씬 큽니다.

이 넷을 하나로 묶는 결론:

> **위험하다 = 성공하면 피해를 주거나, 돈이 많이 들거나, 바로잡기 어려운 모든 것.**

왜 "비용"이 모든 걸 덮을까요? 업무 중단, 복구 작업, 법적 통지, 잃은 계약, 직원들의 시간이 다 돈이 되기 때문입니다. 배차 시스템이 랜섬웨어로 멈추는 것, 고객 기록이 새는 것, 도메인을 일주일 동안 다시 세우는 것은 결국 표 위의 큰 숫자입니다. 키오스크의 애드웨어 팝업은 아주 작은 숫자고요.

!!! info "[정정] \"위험하다\"와 \"심각도가 높다\"는 같지 않다"
    취약하지 않은 서버(다른 OS, 패치 완료, 공격 차단)를 향한 "High" 시그니처 경보는 무해할 수 있습니다. 반대로 도메인 컨트롤러의 "Low" 경보 — 예를 들어 평소와 다른 로그온 — 가 대기열에서 가장 위험한 것일 수 있습니다. 심각도는 *규칙*을 설명하고, 위험은 *이 자산, 이 맥락에서 일어난 이 사건*을 설명합니다.

## 거의 끝나 가는 공격 { #nearing-completion }

### 목표를 미리 알아야 한다 { #goals-in-advance }

"거의 끝났다"는 **무언가가** 거의 끝났다는 뜻입니다. 목표가 무엇인지 알아야 목표까지의 거리를 잴 수 있습니다. 그래서 이 단계는 경보가 오기 *전에* 해 둔 일에 달려 있습니다. <strong>위협 모델(threat model)</strong>(우리에게 누군가 탐낼 만한 게 뭐가 있고, 누가 탐낼까?)과, 그걸 채워 주는 <strong>위협 인텔리전스(threat intelligence)</strong>(우리 같은 조직을 실제로 누가, 어떻게 공격하나?)입니다.

가상 회사 Kestrel Logistics의 위협 모델은 이렇게 생겼을 수 있습니다.

| 예상 목표 | 누가 원하나 | "끝"은 어떻게 보일까 |
| --- | --- | --- |
| 고객·화물 데이터 훔치기 | 협박 조직, 경쟁사 | 파일 서버나 화물 데이터베이스에서 대량 업로드 |
| IT 시스템 암호화·삭제 | 랜섬웨어 협력자(affiliate) | 대량 파일 변경, 섀도 복사본 삭제, 백업 공격 |
| 창고 자동화 방해 | 핵티비스트, 위기 상황의 국가 배후 조직 | OT 네트워크로의 이상한 접근, HMI/PLC 호스트의 변경 |
| 결제 사기 | 비즈니스 이메일 침해(BEC) 조직 | 메일함 규칙, 거래처 계좌 정보 변경 |

이 표를 머리에 넣어 두면 경보가 더 이상 추상적이지 않습니다. "화물 데이터베이스 서버에서 7-Zip 실행"은 곧바로 표의 첫 줄과 연결됩니다.

### 뚜렷한 신호들 { #clear-signs }

어떤 활동은 공격자의 목표에 너무 가까워서 언제나 새치기를 해야 합니다.

- **데이터 유출.** 데이터가 이미 나가고 있거나, 나가려고 포장되고 있습니다(어떻게 찾는지는 다음 페이지).
- **곧 닥칠 데이터 파괴.** 랜섬웨어나 와이퍼(wiper)의 행동. 백업 삭제, 섀도 복사본 제거, 대량 암호화 시작. 여기서는 분 단위가 중요합니다.
- **보호된 네트워크 깊숙한 곳의 자산에 접근.** 네트워크를 결제 구역, OT 구역, 관리 네트워크로 나눠 놨다면, 그 구역 *안*에서 공격자 활동이 보인다는 건 이미 벽을 여러 개 넘었다는 뜻입니다.
- **단단히 잠가 둔 호스트에 접근.** 로그온할 수 있는 계정이 아주 적은 시스템(도메인 컨트롤러, 특권 접근 워크스테이션, 백업 서버). 허용 명단이 짧으니 명단 밖의 접근은 무엇이든 눈에 띄게 돼 있습니다. 그러니 예상 못 한 접근은 그 자체로 중요합니다.
- **높은 권한 계정을 써서는 안 되는 곳에서 사용.** 도메인 관리자, 엔터프라이즈 관리자, 백업 운영자, 클라우드 전역 관리자가 평범한 워크스테이션에, 새벽 3시에, 한 번도 안 쓰던 호스트에서 로그온.

마지막 신호는 실제 이벤트로 볼 만합니다. 어떤 계정이 Windows 컴퓨터에 로그온하면 그 컴퓨터가 보안 로그에 **4624**("계정이 성공적으로 로그온했습니다")를 남깁니다. 새 세션이 민감한 권한까지 받으면 — 관리자라면 그렇습니다 — 바로 뒤에 같은 Logon ID로 **4672**("새 로그온에 특수 권한이 할당되었습니다")를 남깁니다.

```
Event ID 4624  Computer: KL-FIN-DB01.corp.kestrel.example   2026-11-24 03:12:41
  Subject:            SecurityID S-1-0-0  LogonId 0x0
  Logon Type:         10
  New Logon:          AccountName svc_backup  AccountDomain KESTREL  LogonId 0x5A3F21C
  Network Information: WorkstationName KL-WS-0412  SourceNetworkAddress 10.20.4.112
  Authentication:     LogonProcess User32  AuthenticationPackage Negotiate

Event ID 4672  Computer: KL-FIN-DB01.corp.kestrel.example   2026-11-24 03:12:41
  Subject:            AccountName svc_backup  LogonId 0x5A3F21C
  Privileges:         SeBackupPrivilege SeRestorePrivilege SeDebugPrivilege
                      SeTakeOwnershipPrivilege SeImpersonatePrivilege ...
```

칸별로 보면:

- `KL-FIN-DB01`의 `Event ID 4624` — 재무 데이터베이스 서버가 **자기 자신에게 성공한 로그온**을 기록했습니다. 4624는 언제나 로그온을 *받는* 컴퓨터에 남습니다.
- `Logon Type: 10` — **RemoteInteractive**, 즉 원격 데스크톱(RDP)입니다. 누군가 데이터베이스 서버의 바탕 화면 전체를 쓰고 있습니다([로그온 유형](../important-events/logins.md#logon-types)).
- `AccountName svc_backup` — 백업용 **서비스 계정**. 서비스 계정은 보통 서비스(로그온 유형 5)나 예약 작업(유형 4)으로 돌아갑니다. 서비스 계정이 *대화형 RDP 세션*을 연다는 것부터 이상하고, 새벽 3시 12분이면 더 그렇습니다.
- `WorkstationName KL-WS-0412`, `SourceNetworkAddress 10.20.4.112` — RDP 세션이 **평범한 사용자 PC에서** 왔습니다. 백업 관리라면 백업 서버나 관리자 전용 PC에서 와야지, 물류 사무실 책상 위 PC에서 오면 안 됩니다.
- `LogonId 0x5A3F21C` — 이 세션의 번호. 이 세션이 나중에 하는 모든 일(프로세스, 파일 접근)에 이 번호가 붙으니, 세션이 한 일을 따라갈 수 있습니다.
- **같은 LogonId**의 `Event ID 4672` — Windows가 이 세션에 민감한 권한을 줬습니다. `SeBackupPrivilege`/`SeRestorePrivilege`는 권한 설정과 상관없이 *어떤* 파일이든 읽고 쓰게 해 주고, `SeDebugPrivilege`는 다른 프로세스의 메모리를 열게 해 주며(자격 증명 탈취), `SeTakeOwnershipPrivilege`는 어떤 개체든 소유권을 가져오게 해 줍니다. 한마디로 이 세션을 가진 사람은 데이터베이스 서버 전체를 읽을 수 있습니다.

공격자가 왜 이걸 좋아할까요? 권한이 큰 서비스 계정은 힘이 세고, 잘 감시되지 않고, 비밀번호가 오래됐고, MFA에서 빠져 있는 경우가 많아서 아주 인기 있는 표적입니다. ATT&CK로 말하면 **T1078.002 Valid Accounts: Domain Accounts**를 써서 **T1021.001 Remote Services: Remote Desktop Protocol**을 한 겁니다. 사용자 PC에서 핵심 서버로, 이게 바로 "끝이 가깝다"는 그림입니다. 권한과 위치를 둘 다 가졌으니까요.

같은 세션이 이어서 압축 도구를 실행하면, (프로세스 생성 감사가 켜져 있을 때) 호스트가 **4688**("새 프로세스가 만들어졌습니다")을 남깁니다.

```
Event ID 4688  Computer: KL-FIN-DB01   2026-11-24 03:19:07
  Creator Subject:  AccountName svc_backup  LogonId 0x5A3F21C
  New Process Name: C:\ProgramData\7z\7z.exe
  Creator Process:  C:\Windows\System32\cmd.exe
  Process Command Line: 7z.exe a -pK3str3l! -v200m C:\ProgramData\x\s.7z D:\Exports\Shipments\
```

- `LogonId 0x5A3F21C` — 위 4624와 **같은 RDP 세션**입니다. 세션 하나, 위험한 행동 둘.
- `New Process Name C:\ProgramData\7z\7z.exe` — `Program Files`가 아니라 `ProgramData`에서 실행된 7-Zip. 설치한 게 아니라 복사해 온 겁니다.
- `a` = 압축 파일에 추가, `-p...` = **비밀번호로 잠금**(DLP나 프록시가 안을 못 보게), `-v200m` = **200MB 조각으로 나눔**(올리기 쉽고 크기 제한에 덜 걸림), `D:\Exports\Shipments\` = 포장 중인 데이터.
- ATT&CK **T1560.001 Archive Collected Data: Archive via Utility**. 유출(**TA0010**) 바로 앞에 나오는 전형적인 단계입니다.

이 이벤트 셋을 맞춰 보면 더 이상 짐작할 필요가 없습니다. 목표 한 걸음 앞에 있는 공격입니다.

## 공격자 목표까지의 거리 어림하기 { #distance-to-goal }

대부분의 경보는 이렇게 분명하지 않습니다. 들여야 할 습관은 이겁니다. 경보마다 **"이건 공격의 어느 단계처럼 보이나?"**, 그래서 <strong>"공격자가 원하는 걸 얻기까지 몇 걸음 남았나?"</strong>를 묻는 것. 모델 두 개가 도와줍니다.

### 모델 1: 사이버 킬 체인 { #kill-chain }

<strong>사이버 킬 체인(Cyber Kill Chain)</strong>은 2011년 Lockheed Martin 연구자들(Hutchins, Cloppert, Amin)이 표적 침해의 단계를 설명하려고 발표한 모델입니다. 7단계입니다.

| # | 단계 | 공격자가 하는 일 | 어디서 보이나 | 쪽 |
| --- | --- | --- | --- | --- |
| 1 | **정찰(Reconnaissance)** | 대상 조사: 직원 이름, 노출된 서비스, 메일 주소 형식 | 웹 서버 로그, 방화벽·IDS의 스캔(공개 자료로 하면 안 보이는 경우가 많음) | 대부분 공격자 쪽 |
| 2 | **무기화(Weaponization)** | 공격 도구 만들기: 악성 문서, 익스플로잇 + 임플란트 | 거의 안 보임 | 공격자 쪽 |
| 3 | **전달(Delivery)** | 보내기: 이메일, 웹 다운로드, USB, 노출된 서비스 | 메일 게이트웨이, 프록시, IDS | 네트워크 |
| 4 | **익스플로잇(Exploitation)** | 코드가 돈다: 익스플로잇 작동 또는 사용자가 파일 열기 | EDR, 프로세스 생성(4688/Sysmon 1), 충돌 로그 | 호스트 |
| 5 | **설치(Installation)** | 지속성: 서비스, Run 키, 예약 작업, 웹셸 | EDR, 7045/4698, Sysmon 13 | 호스트 |
| 6 | **명령·제어(C2)** | 임플란트가 공격자와 통신 | DNS, 프록시, Zeek `conn`/`ssl`/`http`, 방화벽 | 네트워크 |
| 7 | **목표 행동(Actions on Objectives)** | 훔치기, 암호화, 파괴, 더 깊이 이동 | DLP, 파일 접근, 대량 전송, 대량 변경 | 호스트 + 네트워크 |

표에서 눈여겨볼 점:

- **어떤 단계는 주로 공격자 쪽에서 일어난다.** 정찰(상당 부분)과 무기화는 공격자 자신의 시스템이나 공개 자료 위에서 이뤄집니다. 우리가 가진 데이터도, 손쓸 기회도 아주 적습니다.
- **어떤 단계는 호스트, 어떤 단계는 네트워크에서 보인다.** 익스플로잇과 설치는 호스트 *위에서* 일어나니 호스트 로그(EDR, 프로세스 생성, 서비스 설치)가 가장 좋은 증거입니다. 전달과 C2는 *데이터의 이동*이라 네트워크 로그(메일, 프록시, DNS, Zeek)가 가장 잘 찾습니다. 이걸 알면 경보마다 **어떤 데이터를 먼저 꺼낼지** 정할 수 있습니다.
- **"위험 구역"은 오른쪽 끝이다.** 3단계 경보(차단된 피싱 메일)는 목표에서 멉니다. 6–7단계 경보(밖과 통신하는 임플란트, 움직이는 데이터)는 가깝습니다.

### 약점: 실제 침해는 빙빙 돈다 { #kill-chain-weakness }

킬 체인은 직선이지만 침해는 직선이 아닙니다. 공격자가 원하는 시스템에 곧바로 내려앉는 일은 드뭅니다. 안내 데스크 직원의 노트북에 먼저 떨어지고, 그다음 권한이 필요하고, 그다음 맞는 서버를 찾아야 하고, 그리로 옮겨 가야 하고, 이걸 여러 번 되풀이하는 경우가 많습니다. 그래서 **데스크톱**의 C2는 "6단계"지만, 공격자는 아직 목표에서 몇 걸음 떨어져 있을 수 있습니다. 정말로 "거의 다 됐다"가 되려면 *더 중요한 호스트를 대화형으로 조종*할 수 있어야 합니다. 킬 체인을 글자 그대로 읽으면 모든 C2 경보가 똑같이 급해 보이는 함정에 빠집니다.

### 모델 2: 공격 수명 주기 { #attack-lifecycle }

널리 쓰이는 두 번째 모델(침해 대응 보고서에서 "표적 공격 수명 주기"로 많이 알려짐)은 침해의 가운데 부분을 **고리**로 그립니다.

```
Initial recon → Initial compromise → Establish foothold →
    ┌─> Escalate privileges → Internal recon → Move laterally → Maintain presence ─┐
    └──────────────────────────────────────────────────────────────────────────────┘
                                                        → Complete mission
```

- <strong>최초 침해(Initial compromise)</strong>가 무기화·전달·익스플로잇·설치를 대신합니다. 더 넓은 말입니다. 모든 침해가 무언가를 "설치"하는 건 아니고, 공격자는 컴퓨터 한 대가 자기 명령을 실행하게 만들 방법만 있으면 되는 경우가 많습니다.
- <strong>거점 확보(Establish foothold)</strong> = 다시 들어올 확실한 방법(백도어, 훔친 VPN 계정). 나머지 환경으로 가는 기지입니다.
- **고리** — 권한 상승(Escalate privileges), 내부 정찰(Internal recon), 옆으로 이동(Move laterally), 존재 유지(Maintain presence) — 가 호스트를 옮길 때마다 되풀이됩니다. 킬 체인이 감춰 버리는 부분이 바로 이겁니다.
- <strong>임무 완수(Complete mission)</strong>는 고리를 충분히 돌아서 목표에 손이 닿은 뒤에야 옵니다.

되풀이를 보여 주기 때문에, 이 모델이 신입 분석가가 실제 경보를 대응시키기에 더 쉽습니다. 분류에 쓸 때의 단점은 "7단계 중 6단계니까 거의 끝"이라고 말할 수 없다는 것입니다. 침해 하나에 "고리" 단계가 여러 번 있으니까요. 지금 보고 있는 게 **몇 바퀴째**인지 해석해야 합니다. 핵심 시스템 *쪽으로* 가는 옆 이동인가, 사용자 노트북 두 대 사이의 이동인가?

### 거리에 숫자 붙이기 { #distance-scoring }

**[보충]** 많은 SOC가 이걸 대략적인 점수로 드러내 놓고 씁니다. 간단한 예:

```
priority ≈ stage_weight × asset_weight × confidence
```

- `stage_weight` — 예: 정찰 1, 전달 2, 익스플로잇 3, 설치 4, C2 5, 옆 이동·권한 6, 수집·유출·피해 8.
- `asset_weight` — 자산 목록에서: 평범한 PC 1, 서버 2, 핵심 자산이나 특권 계정 4.
- `confidence` — 경보가 진짜일 가능성: 시끄러운 규칙 0.2, 정확한 규칙이나 두 번째 경보로 확인된 것 0.9.

숫자는 지어낸 것이고 정확한 값은 중요하지 않습니다. 중요한 건 가장 시끄러운 요소 하나에 반응하지 않고, **공격자가 어디 있나**, **무엇을 건드리나**, **얼마나 확실한가**를 일부러 함께 따진다는 점입니다.

## 실제로 해 보기: 경보 8개 대기열 { #worked-example }

Kestrel Logistics, 08:31입니다. 회의에서 돌아오니 대기열이 이렇습니다(도착 순서).

| # | 시각 | 출처 | 경보 | 호스트 / 사용자 |
| --- | --- | --- | --- | --- |
| A1 | 08:02 | IDS | 203.0.113.50에서 `SCAN inbound TCP port sweep` | DMZ 대역 |
| A2 | 08:05 | 메일 게이트웨이 | 피싱 URL `hxxps://kestrel-payroll.example/login` — **차단**, 40명에게 발송 | 메일함 40개 |
| A3 | 08:11 | 백신 | `Adware.BundleInstaller` **격리** | KL-WS-0388(키오스크) / `kiosk` |
| A4 | 08:14 | EDR | `cdn-sync.example`(198.51.100.77)로 60초마다 HTTPS 비컨, `%APPDATA%`의 `OneDriveSync.exe` 프로세스 | KL-WS-0412 / `j.moreno` |
| A5 | 08:20 | SIEM 규칙 | 특권 서비스 계정 대화형 로그온: `svc_backup` 4624 유형 10 + 4672 | KL-WS-0412에서 KL-FIN-DB01로 |
| A6 | 08:22 | IDS | 192.0.2.14에서 KL-WEB02로 `WEB-APP remote code execution attempt` | KL-WEB02(공개 웹) |
| A7 | 08:25 | EDR | 비밀번호·분할 옵션을 붙인 `7z.exe` | KL-FIN-DB01 / `svc_backup` |
| A8 | 08:30 | EDR | `Unsigned kernel driver loaded` — 90일 동안 **딱 한 번** 울린 규칙 | KL-OT-HMI03(창고 OT 구역) |

**1단계 — 순위를 매기기 전에 연결부터 찾는다.** A4, A5, A7은 같은 대상을 공유합니다. A4는 KL-WS-0412에서, A5는 KL-WS-0412*에서* KL-FIN-DB01로 가는 RDP 로그온, A7은 같은 `svc_backup` 계정으로 KL-FIN-DB01에서. 같은 침해 하나를 세 번 본 것일 가능성이 아주 큽니다. 워크스테이션의 임플란트(C2) → 특권으로 옆 이동 → 데이터 포장. 사건 하나로 다룹니다.

**2단계 — 순위.**

| 순위 | 경보 | "위험"의 어떤 정의 | 단계 / 거리 | 이유 |
| --- | --- | --- | --- | --- |
| **1** | **A5 + A7 (+ A4)** | 거의 끝남 + 가치 높은 자산 + 특권 계정 | 옆 이동 끝, **수집·준비**(T1560.001) — 유출(TA0010) 한 걸음 전 | 특권 + 핵심 서버 + 비밀번호 걸어 포장 중인 데이터. 지금 엽니다. KL-WS-0412 즉시 격리와 `svc_backup` 비활성화를 검토합니다(필요한 승인을 받아서). |
| **2** | **A8** | 가장 드문 경보 + 보호 구역 | 모름 — OT 구역의 설치 단계일 수 있음(드라이버 = 커널 접근) | 90일에 한 번, 변하는 게 거의 없어야 하는 분리된 구역 안. 유지 보수 업체일 수도, 루트킷이나 파괴용 원시 디스크 드라이버일 수도 있습니다. 첫 번째 분석가가 1위를 보는 동안 두 번째 분석가가 곧바로 봐야 합니다. |
| 3 | A6 | 가치 높은 것을 노림(공개 웹 앱) | 익스플로잇 **시도** | **성공했는지** 확인: HTTP 응답 코드와 크기, KL-WEB02가 노린 소프트웨어를 쓰는지, 웹 서버 프로세스에서 새 프로세스가 생겼는지. 성공했다면 1–2위로 올라갑니다. |
| 4 | A2 | — | 전달, **차단됨** | 차단됐지만 40명을 노렸고 급여 사이트 닮은꼴 도메인입니다. 빠른 후속 확인: 게이트웨이 뒤에 없는 기기에서 누가 눌렀나? 같은 미끼가 다른 경로로도 오고 있나? |
| 5 | A3 | — | 설치, **치료됨** | 키오스크의 애드웨어, 격리 완료. 영향 작음. 메모와 함께 닫거나 비슷한 경보와 묶어 처리합니다. |
| 6 | A1 | — | 외부 정찰 | DMZ를 향한 인터넷 배경 잡음. 사건이 아니라 맥락으로 씁니다(203.0.113.50이 나중에 A6에 나타났나?). |

**3단계 — FIFO였다면.** 도착 순서대로 처리했다면 처음 30분을 A1, A2, A3 — 스캔, 차단된 메일, 격리된 애드웨어 — 에 썼을 겁니다. 그사이 `svc_backup`은 재무 데이터베이스에서 화물 데이터를 200MB 조각으로 다 포장했겠죠.

**4단계 — 이유를 적어 둔다.** 경보마다 한 줄짜리 분류 메모("A6: 시도만 있음, KL-WEB02의 HTTP 500 응답과 프로세스 트리 확인 중")를 남기면 순위를 나중에 검토할 수 있고 다음 근무조에도 도움이 됩니다.

!!! tip "[보충] 대상별로 묶은 다음 순위를 매긴다"
    대부분의 SIEM과 XDR 도구는 호스트, 사용자, IP별로 경보를 묶어 "인시던트"로 만들어 줍니다. 쓰세요. 다만 손으로도 확인하세요. 공격자가 계정을 바꾸거나(`j.moreno` → `svc_backup`), 연결 고리가 같은 호스트 이름이 아니라 로그온 이벤트 속 출발지 주소일 때 도구는 연결을 놓칩니다.

## 2026년 관점 { #trends }

!!! success "[2026 현재] 지금도 그대로 유효"
    핵심 생각은 그대로입니다. **도착 순서가 아니라 결과의 무게로** 분류하고, 각 경보가 침해의 어디쯤 있는지, 미리 정해 둔 목표에 공격자가 얼마나 가까운지 어림합니다. "위험하다"의 네 가지 뜻과 "피해, 비용, 되돌리기 어려움" 기준은 지금도 경험 많은 분석가들이 순위를 매기는 방식입니다. 사이버 킬 체인은 여전히 단계를 말할 때 모두가 쓰는 공통 언어이고, 고리 모양의 수명 주기는 여전히 침해가 실제로 진행되는 모습을 더 잘 보여 줍니다. Windows **4624/4672/4688**은 여전히 특권 계정이 엉뚱한 곳에서 쓰인 걸 드러내는 이벤트입니다.

!!! info "[변경됨] 바뀐 점"
    - **침해는 빨라지고 분류할 시간은 줄었다.** Mandiant의 M-Trends 2026(2025년 조사 대상)은 전 세계 체류 시간(dwell time) 중앙값을 **14일**(그 전해 11일)로 보고했습니다. 동시에, 최초 접근 브로커가 후속 조직(흔히 랜섬웨어)에게 접근권을 넘기는 시간이 2022년 8시간 이상에서 **중앙값 22초**로 줄었다고 합니다. 첫 감염 때 두 번째 조직의 도구를 미리 깔아 두기 때문입니다. 그러니 "낮은" 최초 접근 경보가 몇 분 뒤 "거의 끝"이 될 수 있습니다.
    - **암호화 없는 협박.** 요즘 랜섬웨어 조직 상당수는 데이터를 훔쳐 암호화 없이 협박하거나(또는 암호화는 두 번째 단계로 미루거나), 최근 보고서에 따르면 복구를 막으려고 **백업, 아이덴티티 서비스, 하이퍼바이저**를 일부러 노립니다. 그래서 "거의 끝"의 신호에는 대량 암호화뿐 아니라 백업 콘솔과 가상화 관리 화면 접근도 들어갑니다.
    - **이제는 아이덴티티와 클라우드가 "특권 계정"이다.** 클라우드 테넌트의 전역 관리자, SaaS 관리자 역할, OAuth 앱 동의, 토큰 탈취가 오늘날의 "워크스테이션에 로그온한 도메인 관리자"입니다. 마지막 단계의 신호는 Windows 이벤트만큼이나 아이덴티티 공급자와 클라우드 감사 로그에 남습니다.
    - **ATT&CK이 바뀌었다.** v19(2026년 4월)부터 옛 Defense Evasion 전술이 <strong>Stealth(TA0005)</strong>와 <strong>Defense Impairment(TA0112)</strong>로 나뉘어, Enterprise ATT&CK의 전술은 15개가 됐습니다. v20(2026년 10월)에는 AI 관련 기법이 추가됐습니다. 이 페이지에서 쓴 ID(T1078.002, T1021.001, T1560.001, TA0010)는 그대로입니다.
    - **자산·위험 점수가 도구에 들어왔다.** 요즘 XDR/SIEM 플랫폼은 중요 자산 표시와 대상별 위험 점수를 흔히 제공하고, 업체들은 경보를 미리 분류하고 첫 요약을 쓰고 판정을 제안하는 **AI 분류 에이전트**를 내놓고 있습니다. 양을 줄이는 데는 도움이 되지만, 도구는 자기가 아는 것으로 순위를 매깁니다. 우리 조직에서 "위험하다"가 무엇인지는 여전히 우리의 위협 모델과 자산 지식이 정합니다.

!!! warning "[주의] 옛 방식대로 하면 틀리거나 위험한 점"
    - **대기열을 FIFO나 업체 심각도만으로 처리하지 마세요.** 단계, 자산, 확신도를 함께 보고, 경보가 들어올 때마다 순위를 다시 매깁니다.
    - **킬 체인 6단계 경보를 모두 똑같이 다루지 마세요.** 지금 몇 바퀴째인지, 그 호스트가 목표에 얼마나 가까운지 물으세요.
    - **차단·격리된 경보를 끝난 일로 여기지 마세요.** 40명에게 간 차단된 메일이나 격리된 파일 하나가, 다른 곳에서는 성공한 전달의 보이는 부분일 수 있습니다.
    - **AI 분류 판정을 증거 없이 받아들이지 마세요.** 근거로 삼은 이벤트를 확인합니다. 모델은 드물고 가치 높은 경보를, 바로 드물다는 이유로 잘못 순위 매길 수 있습니다.
    - **위협 모델을 건너뛰지 마세요.** 적어 둔 공격자 목표가 없으면 "거의 끝"은 짐작일 뿐이고, 백업 서버나 하이퍼바이저 콘솔, OT 구역이 아무의 감시 목록에도 없을 수 있습니다.

## 확인 문제 { #quiz }

### 문제 1

대기열에 이런 경보가 있습니다. (a) IDS 경보, 영업 노트북에서 나가는 C2 시그니처, 07:40. (b) 업체 "Critical" 경보, 공개 웹사이트를 향한 SQL 인젝션 시도, 07:45. (c) SIEM 경보, Domain Admins 계정이 헬프데스크 PC에서 백업 서버로 로그온 유형 3 로그온, 07:50, 바로 뒤 4672. "위험하다"의 정의와 목표까지의 거리로 순위를 매기고 설명하세요.

??? success "정답과 해설"
    **1위: (c).** Domain Admins 계정(특권)이 **백업 서버**(가치 높음 — 랜섬웨어에서 살아나려면 백업이 필요하고, 공격자는 복구를 막으려 백업을 노림)에, 헬프데스크 PC(관리자 전용 PC가 아님)에서 접근했습니다. 4624 유형 3은 네트워크 로그온(SMB, 원격 관리 도구)이고, 4672는 그 세션이 특수 권한을 받았다는 확인입니다. 복구에 결정적인 자산을 향한, 권한을 가진 옆 이동입니다. 끝에 가깝습니다.

    **2위: (a).** 노트북의 C2는 킬 체인 6단계지만, 평범한 노트북 한 대라면 공격자는 아마 고리의 초반에 있습니다. 그래도 진짜 침해일 가능성이 큽니다. (c)의 헬프데스크 PC가 같은 목적지와 통신했는지도 확인하세요.

    **3위: (b).** "Critical"은 규칙의 심각도이지 이 사건의 위험도가 아닙니다. 익스플로잇 **시도**입니다. 성공했는지(응답 코드와 크기, 데이터베이스 오류, 웹 서버에서 생긴 새 프로세스) 확인하고, 성공했다면 순위를 다시 매깁니다.

### 문제 2

"거의 끝나 가는 공격"을 판단하는 데 왜 위협 모델이 필요한지 설명하고, 랜섬웨어를 가장 두려워하는 조직에서 "끝이 가깝다"는 신호 두 가지를 드세요.

??? success "정답과 해설"
    "거의 끝"은 **공격자의 목표**에 가깝다는 뜻이고, 목표까지의 거리는 목표를 알아야 잴 수 있습니다. 우리 같은 조직을 누가 공격하는지에 대한 위협 인텔리전스로 채운 위협 모델이, 공격자가 우리에게서 무엇을 원하는지, 그래서 마지막 단계가 어떻게 보일지 알려 줍니다.

    랜섬웨어 중심 위협 모델의 예: 섀도 복사본 삭제(`vssadmin delete shadows`, `wmic shadowcopy delete`, T1490 Inhibit System Recovery), 백업 서버·콘솔 접근이나 변경, 특권 계정이 짧은 시간에 많은 서버에 로그온, 대량 파일 이름 변경·쓰기, 암호화 전에 데이터를 압축해 올리기(이중 협박), 하이퍼바이저 관리 접근.

### 문제 3

동료가 말합니다. "킬 체인에서 C2는 7단계 중 6단계니까, C2 경보는 다 공격자가 거의 끝났다는 뜻이야." 무엇이 틀렸고, 어떤 모델이 그 이유를 더 잘 보여 주나요?

??? success "정답과 해설"
    킬 체인은 **일직선**이라 침해가 **빙빙 돈다**는 사실을 감춥니다. 데스크톱 한 대에 C2를 가진 공격자는 보통 목표에 닿기 전에 권한 상승, 네트워크 탐색, 옆 이동, 지속성 유지를 — 여러 번 — 더 해야 합니다. 목표를 가졌거나 목표에 닿을 수 있는 시스템을 대화형으로 조종할 때가 정말 "거의 끝"입니다.

    **공격 수명 주기** 모델이 이걸 드러내 놓고 보여 줍니다. 최초 침해와 거점 확보, 그다음 권한 상승 → 내부 정찰 → 옆 이동 → 존재 유지의 반복 고리, 그 뒤에야 임무 완수. 대신 단계 번호를 읽는 게 아니라 지금 몇 바퀴째인지 해석해야 합니다.
