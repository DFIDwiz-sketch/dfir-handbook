# 사이버 킬 체인, 캠페인, 심층 방어, NIST CSF, 사고 대응 주기 — 공격과 방어를 모델로 보기 { #kill-chain-did-nist-ir }

!!! abstract "이 페이지에서 다루는 것"
    SOC에서 대화하다 보면 결국 다 쓰게 되는 모델 다섯 개입니다. 둘은 공격자 쪽, 셋은 방어자 쪽입니다. **사이버 킬 체인(Cyber Kill Chain)**: 표적 침입을 일곱 단계로 그린 Lockheed Martin의 모델. 왜 만들어졌는지("인텔리전스 기반 방어"), 대응 방안 매트릭스로 어떻게 방어 범위 지도가 되는지, 그리고 이 모델이 가르치는 습관 — 조사를 어느 지점에서 시작하든 그 앞에 무슨 일이 있었고 그 뒤에 무슨 일이 일어났을지를 다시 맞춰 보는 것. **캠페인 분석(campaign analysis)**: 여러 사건의 지표와 행동을 함께 추적해서, 공격자가 *바꾸지 않은* 것으로 사건들을 묶는 방법. 사건 세 개를 나란히 놓고 직접 해 봅니다. <strong>심층 방어(defense in depth)</strong>를 예방 → 탐지 → 대응으로 보고, 왜 "대응 없는 탐지"는 거의 쓸모가 없는지 경보 계산으로 보여 줍니다. <strong>NIST 사이버보안 프레임워크(CSF)</strong>의 원래 다섯 기능과 <strong>거버넌스(Govern)</strong>가 추가된 CSF 2.0. **사고 대응 주기**(PICERL: 준비, 식별, 봉쇄, 제거, 복구, 교훈)를 가상 침입 하나로 단계마다 따라가며 Windows 이벤트 **4688**, **4724**, Sysmon **13**을 풀이하고, 교훈 정리 양식을 채워 봅니다. 2026년 관점(NIST SP 800-61 Rev. 3, CSF 2.0, 더 빨라진 넘겨주기, 단계를 건너뛰는 아이덴티티 공격)과 확인 문제로 마칩니다.

!!! note "표기"
    **[보충]** = 꼭 알아야 할 실무 보충, **[정정]** = 흔히 잘못 알려진 내용 정정, **[변경됨]**/**[주의]** = 최근 바뀐 점과 옛 방식대로 하면 위험한 점. 회사(Kestrel Logistics), 호스트 이름, 계정, 도메인, IP, 파일 이름, 로그 줄은 모두 설명용 가상 값(`.example`, 문서용·사설 IP)입니다. 프레임워크와 그 저자에 대한 설명은 제 말로 풀어 썼습니다.

## 한눈에 보는 핵심 8가지 { #key-points }

1. **킬 체인은 표적 침입을 일곱 단계로 나눈다** — 정찰, 무기화, 전달, 익스플로잇, 설치, 명령·제어, 목표 달성. 공격자가 이기려면 모든 단계가 성공해야 한다. 고리 하나만 끊어도, 되도록 일찍 끊으면 침입은 실패한다.
2. **진짜 목적은 인텔리전스 기반 방어다.** 지표를 단계에 붙이고, 통제를 단계에 붙이고, 비어 있는 곳을 찾는다. 그림이 아니라 계획과 분석의 도구다.
3. **완전성 점검표이기도 하다.** C2 비컨(6단계)을 찾았다면, 제대로 된 조사는 1–5단계를 설명하고 7단계가 무엇이었을지 추정한다. 그리고 찾은 단계만이 아니라 모든 단계의 지표를 막는다.
4. **캠페인 분석**은 여러 사건을 킬 체인 위에 나란히 놓는다. 공격자는 값싼 지표(해시, IP)는 갈아 끼우지만 *전부*를 바꾸는 일은 드물다. 그대로인 것이 사건들을 잇고, 공격자가 어떻게 일하고 무엇을 원하는지 드러낸다.
5. **심층 방어 = 예방, 탐지, 대응.** 예방이 잡음을 걷어 내고, 탐지가 빠져나간 것을 잡고, 대응이 있어야 탐지가 의미를 갖는다. 대응할 수 있는 것보다 경보가 많으면 스스로를 무너뜨린다.
6. **NIST CSF**는 보안 조직에 필요한 능력의 목록이다. CSF 1.x는 기능이 다섯 개(식별, 보호, 탐지, 대응, 복구)였고, **CSF 2.0(2024년 2월)이 거버넌스를 추가**하고 모든 조직으로 범위를 넓혔다. 기능 이름은 "예방"이 아니라 *보호(Protect)*다.
7. <strong>사고 대응 주기(PICERL)</strong>는 킬 체인의 방어자 쪽 절반이다. 준비, 식별, 봉쇄, 제거, 복구, 교훈. 어떤 공격에도 통하고, 신입 분석가의 "다음엔 뭘 하지?"에 답해 준다.
8. **교훈 단계가 고리를 닫아** 준비로 돌아가게 한다. 건너뛰면 같은 사고가 또 난다. 기억이 생생할 때 빨리 한다.

## SOC에서 왜 중요한가 { #why }

이어달리기를 떠올려 보세요. 공격자 팀에는 주자가 일곱 명 있고, 바통이 일곱 명 손을 다 거쳐야 결승선에 닿습니다. 아무나 한 명만 넘어뜨려도 경기는 집니다. 킬 체인이 그 주자 명단입니다. 방어 모델들은 트랙의 우리 쪽입니다. 어디에 심판을 세웠는지(심층 방어), 우리 조직이 필요한 일에 사람을 다 배치하긴 했는지(NIST CSF), 그리고 주자 하나를 발견했을 때 우리 팀이 어떤 순서로 움직이는지(사고 대응 주기).

기술적인 현실로 돌아오면, 바쁜 근무 중에 이 모델들은 세 가지 질문에 답해 줍니다. 모델이 없으면 감으로 대충 답하게 되는 질문들입니다. *얼마나 심각한가?* — 이 경보는 킬 체인의 어디까지 왔나([경보 분류](../alert-triage/defining-dangerous.md)에서 바로 이걸 썼습니다). *조사가 끝났나?* — 내가 찾은 단계의 앞과 뒤를 다 설명했나? *다음엔 뭘 하지?* — 나는 대응 주기의 어디에 있고, 다음 단계는 무엇을 요구하나? 이 세 질문에 한 문장으로 답하지 못하는 팀은 사건을 너무 일찍 닫거나, 범위를 알기 전에 봉쇄하거나, 배운 것을 탐지로 되돌리지 못합니다.

## 사이버 킬 체인 { #kill-chain }

### 어디서 왔고 무엇에 쓰나 { #kill-chain-purpose }

2011년 Lockheed Martin의 분석가 세 명, Eric Hutchins, Michael Cloppert, Rohan Amin이 <strong>인텔리전스 기반 네트워크 방어(intelligence-driven computer network defense)</strong>에 관한 논문을 냈습니다. 그들이 풀려던 문제는 당시 "지능형 지속 위협(APT)"이라 부르던, 오래 버티고 자원이 많은 침입자들이었습니다. 이들은 새 악성코드를 들고 계속 돌아왔고, 그래서 악성코드가 나올 때마다 하나씩 막는 건 지는 싸움이었습니다. 그들의 답은 군사 용어 "킬 체인" — 표적을 찾아 타격하기까지 거쳐야 하는 단계들 — 을 빌려 와 뒤집는 것이었습니다. *침입자가* 거쳐야 하는 단계를 적고, 각 단계를 막을 기회를 찾자.

논문이 하려던 일은 네 가지였고, 지금도 이 모델을 이해하는 가장 좋은 길입니다.

- **위협 인텔리전스를 만드는 방법을 알려 준다** — 모은 지표마다 단계를 붙이면, 인텔리전스가 "언제 찾았나"가 아니라 "공격자가 무엇을 하던 중이었나"로 정리됩니다.
- **방어 투자의 우선순위를 알려 준다** — 가진 통제가 전부 전달 단계에 몰려 있고 C2 단계엔 하나도 없다면, 다음 예산이 어디로 가야 하는지 보입니다.
- **위협 그룹을 잇고 추적한다** — 킬 체인 위에 놓인 지표는 사건끼리 비교할 수 있습니다(아래 캠페인 분석).
- **분석의 완전성을 안내한다** — 킬 체인은 제대로 된 조사가 무엇을 설명해야 하는지 적은 점검표입니다.

처음부터 들어 있던 한계도 하나 있습니다. 이 모델은 사람이 직접 단계를 밟아 가는 **표적형 침입**을 위해 쓰였습니다. 흔한 대량 악성코드나 내부자 위협에는 덜 딱 맞습니다(2026년 관점에서 더 봅니다).

### 일곱 단계와 SOC에서 보이는 증거 { #kill-chain-stages }

| # | 단계 | 공격자가 하는 일 | 보일 수 있는 것 | ATT&CK 기법 예 |
| --- | --- | --- | --- | --- |
| 1 | **정찰(Reconnaissance)** | 표적 조사: 직원, 이메일 형식, 노출된 서비스 | 경계에 대한 스캔, 직원 소개 페이지 집중 방문, 정보를 캐내려는 피싱 메일 | T1595 Active Scanning, T1593 Search Open Websites/Domains, T1598 Phishing for Information |
| 2 | **무기화(Weaponization)** | 탑재물 만들기: 익스플로잇이나 매크로에 백도어를 붙임 | 거의 없음 — 공격자 쪽에서 일어나니까. 인텔리전스(악성코드 제작 흔적, 문서 메타데이터)로만 보임 | T1587.001 Develop Capabilities: Malware, T1588 Obtain Capabilities |
| 3 | **전달(Delivery)** | 무기 보내기: 이메일, 링크, USB, 노출된 서비스 | 이메일 게이트웨이 로그, 프록시 다운로드, 익스플로잇을 실은 웹 서버 요청 | T1566.001/.002 Phishing, T1190 Exploit Public-Facing Application |
| 4 | **익스플로잇(Exploitation)** | 코드 실행시키기: 취약점 공격, 또는 사용자의 클릭 | EDR 프로세스 트리(Office가 스크립트 실행기를 띄움), IDS 익스플로잇 시그니처, 충돌 로그 | T1203 Exploitation for Client Execution, T1204.002 User Execution: Malicious File |
| 5 | **설치(Installation)** | 눌러앉기: 백도어, 지속성 | 새 Run 키, 서비스, 예약 작업, 사용자가 쓸 수 있는 경로의 파일 | T1547.001 Registry Run Keys, T1053.005 Scheduled Task, T1543.003 Windows Service |
| 6 | **명령·제어(C2)** | 임플란트와 통신하며 손으로 조종 | 주기적인 비컨, 드문 도메인, 이상한 TLS 지문, DNS 터널링 | T1071.001 Web Protocols, T1071.004 DNS, T1573 Encrypted Channel |
| 7 | **목표 달성(Actions on Objectives)** | 온 목적 이루기: 훔치기, 암호화, 파괴, 염탐, 더 깊이 이동 | 압축 파일 생성, 대용량 업로드, 대량 파일 변경, 새 관리자 계정, 측면 이동 | T1560.001 Archive via Utility, T1567.002 Exfiltration to Cloud Storage, T1486 Data Encrypted for Impact |

이 표에서 놓치기 쉬운 게 두 가지 있습니다. 첫째, **단계가 이를수록 끊는 비용이 싸다.** 피싱 메일(3단계)을 막는 비용은 격리 한 번이지만, 7단계에서 막는 비용은 사고 하나입니다. 둘째, **2단계는 SOC 눈에 거의 안 보인다.** 무기화는 인텔리전스를 통해서만 "보입니다". 논문이 킬 체인을 인텔리전스 업무와 짝지은 이유가 바로 이겁니다.

### 킬 체인을 방어 범위 지도로: 대응 방안 매트릭스 { #coa-matrix }

**[보충]** 원래 논문은 흔히 복사되는 그림보다 한 걸음 더 나갔습니다. 일곱 단계에 여섯 가지 방어 행동 — **탐지(Detect), 거부(Deny), 방해(Disrupt), 약화(Degrade), 기만(Deceive), 파괴(Destroy)** — 을 교차시켜 <strong>대응 방안 매트릭스(courses-of-action matrix)</strong>를 만들었습니다. Kestrel Logistics용으로 줄인 버전입니다. 단계마다 어떤 통제가 무엇을 하는지 보여 줍니다.

| 단계 | 탐지 | 거부 | 방해 | 약화 | 기만 |
| --- | --- | --- | --- | --- | --- |
| 정찰 | 웹 분석, 경계 스캔 경보 | 공개 페이지에서 직원 이메일 내리기 | — | — | 카나리 주소를 단 가짜 직원 프로필 |
| 전달 | 이메일 게이트웨이, 프록시, IDS | ISO/LNK/HTA 첨부 차단 | 게이트웨이 링크 재작성과 클릭 시점 검사 | 첨부 크기 제한 | — |
| 익스플로잇 | EDR 행위 규칙, IDS | 패치, 인터넷 매크로 차단 | EDR이 자식 프로세스 종료 | — | — |
| 설치 | EDR, Sysmon 레지스트리·작업 이벤트 | 사용자 쓰기 가능 경로에 애플리케이션 통제 | — | — | 시작 폴더의 카나리 파일 |
| C2 | DNS·프록시 분석, TLS 지문 | 외부 송신 필터링, DNS 싱크홀 | IPS가 알려진 C2 차단 | 미분류 사이트 대역폭 제한 | 누가 연락하는지 기록하는 싱크홀 |
| 목표 달성 | DLP, 파일 감사 이벤트, UEBA | 최소 권한, 관리 경로에 MFA | SOAR로 계정 비활성화 | 다운로드 속도 제한 | 허니 문서, 허니 계정 |

(여섯째 행동 *파괴*는 공격자 인프라를 직접 치는 것이라 회사 SOC가 아니라 수사기관이나 군의 일입니다. 논문에는 있지만 쓸 일은 없습니다.)

이 매트릭스는 빈칸 보고서처럼 읽습니다. **탐지** 칸이 비었다면 그 단계에서는 공격자가 일해도 내가 영영 모릅니다. **탐지**만 채워진 줄이라면 사람이 제때 대응하는 것에 전적으로 기대고 있다는 뜻입니다. 건강한 환경은 대부분의 단계에서 대부분의 칸에 뭔가가 있습니다. 킬 체인 말로 표현한 심층 방어가 바로 이겁니다.

### 분석의 완전성: 찾은 지점의 앞과 뒤 { #completeness }

이 모델이 주는 가장 쓸모 있는 일상 습관: **어디서 조사를 시작하든, 사슬 전체를 다시 맞춘다.**

이 경보로 사건이 열렸다고 합시다.

```
[NDR] Periodic beaconing to low-reputation domain        severity: high
  src=10.20.6.31 (KL-WS-0631)  dst=203.0.113.77:443  sni=update-cdn.example
  interval=300s±4%  sessions_24h=287  bytes_out_avg=812  bytes_in_avg=356
```

- `src=10.20.6.31 (KL-WS-0631)` — 평범한 재무팀 업무용 PC.
- `dst=203.0.113.77:443`, `sni=update-cdn.example` — 소프트웨어 업데이트 서비스처럼 보이지만 평판이 낮은 도메인으로 가는 HTTPS.
- `interval=300s±4%` — 5분마다 거의 흔들림 없이 연결. 사람은 이렇게 웹을 안 봅니다. 프로그램이 이렇게 합니다.
- `sessions_24h=287` — 거의 하루 내내 돌았습니다(24시간에 5분 칸은 288개).
- `bytes_out_avg=812`, `bytes_in_avg=356` — 작은 안부 확인에 작은 대답. "나한테 시킬 거 있어?" "없어."

이게 6단계입니다. 얕은 분석가는 도메인을 막고, PC를 다시 깔고, 사건을 닫습니다. 완전한 분석가는 사슬을 뒤로, 앞으로 묻습니다.

| 단계 | 질문 | 볼 곳 | Kestrel이 찾은 것 |
| --- | --- | --- | --- |
| 5 설치 | 재부팅 뒤에 어떻게 살아남나? | EDR, Sysmon 13, 예약 작업 | `%APPDATA%\UpdSvc\updsvc.exe`를 띄우는 Run 키 |

| 3 전달 | 파일이 어떻게 들어왔나? | 이메일 게이트웨이, 프록시 | `Invoice_7731.docm`이 붙은 "수정된 운송 청구서" 메일, 09:58 |

이제 봉쇄가 모든 단계를 덮습니다. 여섯 명 모두에게서 메일 격리(3), 매크로 행동 차단(4), 전체 장비에서 Run 키와 파일 경로 헌팅(5), C2 도메인*과* IP 차단(6), 다음 수를 대비해 재무 공유 폴더와 계정 감시(7). 6단계만 막았다면 아직 안 열린 메일 다섯 통이 메일함에 그대로 남았을 겁니다.

## 캠페인 분석 { #campaigns }

### 개념 { #campaigns-idea }

논문의 두 번째 큰 생각은 **캠페인**입니다. 한 행위자가 시간을 두고 우리에게 한 활동의 총합입니다. 사건마다 지표와 행동을 *단계별로* 기록하고, 사건끼리 비교해서 만듭니다. 바탕에 깔린 논리는 비용입니다. IP를 바꾸거나 악성코드를 다시 컴파일해서 새 해시를 얻는 건 싸니까 공격자는 늘 그렇게 합니다. 미끼 메일 스타일, 도구, 인프라 등록 습관, 일하는 시간, 표적을 한꺼번에 다 바꾸는 건 비싸니까 거의 안 합니다. **그들이 못 바꾼 것이 사건들을 이어 줍니다.**

이어지고 나면 사건들이 알려 줍니다. 이 행위자가 어떻게 일하는지(TTP — 전술, 기법, 절차)와 무엇에 관심 있는지. 그러면 어제의 지표가 아니라 *행위자*를 겨냥한 방어를 고를 수 있습니다. 바깥 인텔리전스와 합치면 귀속(attribution)을 뒷받침할 때도 있지만, 그건 보너스지 목표가 아닙니다.

### 예제: Kestrel의 사건 세 개 { #campaign-example }

두 달 동안 Kestrel SOC가 피싱 사건 세 개를 처리했습니다. 단계별로 펼치면:

| 단계 | 사건 A(9월) | 사건 B(10월) | 사건 C(11월) |
| --- | --- | --- | --- |
| 전달: 보낸 사람 | `billing@freight-docs.example` | `accounts@cargo-invoices.example` | `ap@shipping-billing.example` |
| 전달: 미끼 | "연체된 운송 청구서" | "수정된 운송 청구서" | "운송 청구서 이의 제기" |
| 전달: 표적 | 재무팀 4명 | 재무팀 6명 | 재무팀 5명 + 구매팀 2명 |
| 익스플로잇: 파일 | `Inv_2201.docm`(해시 A) | `Invoice_7731.docm`(해시 B) | `Statement_0412.zip` → `.lnk`(해시 C) |
| 익스플로잇: 문서 작성자 메타데이터 | `j.smith` | `j.smith` | —(LNK) |
| 설치 | Run 키, `%APPDATA%\UpdSvc\updsvc.exe` | Run 키, `%APPDATA%\UpdSvc\updsvc.exe` | Run 키, `%APPDATA%\UpdSvc\updsvc.exe` |
| C2: 도메인/IP | `cdn-sync.example` / 198.51.100.23 | `update-cdn.example` / 203.0.113.77 | `telemetry-cdn.example` / 192.0.2.140 |
| C2: URI와 주기 | `/api/v2/ping`, 300초 | `/api/v2/ping`, 300초 | `/api/v2/ping`, 300초 |
| C2: 도메인 등록 | 3일 전 등록, 같은 등록 대행사 | 2일 전 등록, 같은 등록 대행사 | 4일 전 등록, 같은 등록 대행사 |
| 활동 시간대 | 09:00–17:00 UTC+3 | 09:00–17:00 UTC+3 | 09:00–17:00 UTC+3 |

세로로(사건별로) 읽으면 "피싱 메일" 말고는 겹치는 게 없어 보입니다. **가로로(줄별로)** 읽으면 그림이 바뀝니다.

- **매번 바뀐 것:** 보낸 도메인, 파일 해시, C2 도메인과 IP. 싼 것들입니다. 차단 목록에 이것만 있었다면 매달 0에서 다시 시작했을 겁니다.
- **한 번도 안 바뀐 것:** 운송 청구서 주제, 재무팀 표적, 설치 경로와 Run 키, C2 URI 모양과 300초 주기, 도메인 등록 습관, 일하는 시간대.
- **한 번, 의미 있게 바뀐 것:** 11월에 전달 파일이 매크로 문서에서 LNK가 든 ZIP으로 바뀌었습니다. 아마 사건 B 뒤에 Kestrel이 매크로를 막기 시작했기 때문일 겁니다. 공격자가 우리 방어에 맞춰 바꾼 겁니다. 그 자체로 중요한 발견입니다.

기록에 남길 결론: *사건 A, B, C는 동일한 설치 경로, C2 URI 모양과 비컨 주기, 일관된 표적과 미끼 주제, 일관된 인프라 등록 습관을 근거로 하나의 캠페인(내부 추적명 KL-CAMP-01)으로 평가함. 신뢰도: 중간–높음.* 그리고 대응 방안은 이제 오래가는 부분을 겨냥합니다. 새로 등록된 도메인으로 300초 주기 `/api/v2/ping`을 보내는 행동 탐지, `%APPDATA%\UpdSvc\` 헌팅과 애플리케이션 통제 규칙, 재무·구매팀 대상 운송 청구서 미끼 주의 교육, 재무팀 메일함에 들어오는 ZIP 속 LNK 경보. 이 중 어느 것도 다음 달 해시에 기대지 않습니다.

이 섹션 뒤쪽의 고통의 피라미드가 그림 하나로 보여 주는 것도 같은 통찰입니다. 바닥의 지표는 공격자가 바꾸기 쉽고, 꼭대기의 행동은 그렇지 않습니다.

## 심층 방어: 예방, 탐지, 대응 { #defence-in-depth }

### 하나의 방어를 이루는 세 부분 { #pdr }

성은 바깥 성벽 하나만 믿지 않습니다. 해자가 있고, 성벽이 있고, 성벽 위에 경비병이 있고, 안에 내성이 있고, 들어온 적과 싸울 병사들이 있습니다. <strong>심층 방어(defense in depth)</strong>는 그 생각을 네트워크에 옮긴 것이고, 가장 간단히 말하면 <strong>예방(Prevent) → 탐지(Detect) → 대응(Respond)</strong>입니다. 흔히 두 문장으로 요약합니다. "예방이 이상적이지만 탐지는 필수다", "대응 없는 탐지는 가치가 거의 없다".

- **예방** — 막을 수 있는 건 다, 킬 체인에서 최대한 일찍, 자동으로 막습니다. 방화벽, 이메일 필터, 패치, 애플리케이션 통제, EDR 차단, MFA. 예방한 공격 하나는 아무도 분석할 필요가 없는 공격 하나입니다. 예방은 잡음도 걷어 내서 탐지가 눈에 띄게 해 줍니다.
- **탐지** — 완벽한 예방은 없습니다. 침해는 일어난다고 가정합니다. 어떤 공격자 행동은 너무 애매해서 업무를 망치지 않고는 그냥 막을 수 없습니다(관리자도 공격자도 쓰는 관리 도구 같은 것). 그런 건 *차단*이 아니라 *경보*가 됩니다. 탐지는 예방이 어쩔 수 없이 놓칠 것을 받치는 안전망입니다.
- **대응** — 탐지된 것에 빠르고 단호하게 움직입니다. 모든 탐지의 가치가 실제로 생기는 곳이 여기입니다.

이 모델에 앞에는 **식별(Identify)**(보고 지킬 수 있는 환경 만들기), 뒤에는 **복구(Recover)**(예측 가능하게 정상으로 돌아오기)를 붙인 버전도 자주 봅니다. 그 확장판은 아래 NIST CSF와 아주 비슷합니다.

### "대응 없는 탐지" — 계산해 보기 { #detection-without-response }

두 번째 문장은 고개 끄덕이기는 쉽고 어기기도 쉽습니다. 작은 SOC로 계산해 봅시다.

```
Alerts per day reaching analysts ............ 1,200
Analysts on shift (24 h, 3 shifts × 2) ...... 6 analyst-shifts/day
Effective triage time per analyst-shift ..... ~6 h = 360 min
Total triage minutes per day ................ 6 × 360 = 2,160 min
Minutes available per alert ................. 2,160 / 1,200 ≈ 1.8 min
```

- 분석가에게 오는 경보가 하루 1,200개, 3교대 2명씩이니 하루 6명분 근무, 한 근무에서 실제로 분류에 쓰는 시간이 약 6시간(360분). 합치면 하루 2,160분.
- **경보 하나에 1.8분**으로는 프로세스 트리를 열고, 사용자를 확인하고, 원래 메일을 볼 수 없습니다. 실제로는 분석가들이 한꺼번에 닫기 시작하고, 진짜 비컨 하나가 주변 오탐 400개와 함께 닫힙니다.
- 울리기만 하고 제때 조사하지 못하는 탐지는 가치가 거의 0입니다. 게다가 진짜 경보에 쓸 수 있었던 분석가의 주의력을 깎아 먹습니다.

해결책은 절대 "맞을 때까지 사람을 뽑자"가 아닙니다. 세 부분의 균형을 다시 맞추는 겁니다. 잡음이 많지만 확실한 건 **예방**으로 옮기고(경보 말고 차단), 가치 낮은 **탐지**는 조정하거나 없애고, **대응**의 첫 단계(정보 보강, 알려진 정상 패턴 자동 닫기, 클릭 한 번 봉쇄)를 자동화합니다. 하루 200개 경보를 전부 제대로 조사하는 SOC가 1,200개를 훑어보는 SOC보다 훨씬 강합니다.

## NIST 사이버보안 프레임워크 { #nist-csf }

### 무엇인가 { #nist-csf-what }

미국 국립표준기술연구소(NIST)가 2014년에 처음 낸 <strong>사이버보안 프레임워크(Cybersecurity Framework, CSF)</strong>는 사야 할 통제 목록이 아닙니다. 보안 조직이 이뤄야 할 <strong>결과(outcome)</strong>를 높은 수준에서 설명하는 방법이고, <strong>기능(function)</strong>별로 묶여 있습니다. SOC 분석가에게 쓸모 있는 이유는 내 일이 다른 사람들 일 사이 어디에 있는지 보여 주고, SOC 바깥의 일(자산 목록, 백업, 거버넌스)이 SOC가 얼마나 잘 일할 수 있는지를 정한다는 걸 설명해 주기 때문입니다.

원래 다섯 기능을 SOC 말로 하면:

| 기능 | 뜻 | SOC에게 의미하는 것 |
| --- | --- | --- |
| **식별(Identify)** | 무엇을 가졌고 무엇이 중요한지 알기: 자산, 데이터, 위험, 의존 관계 | `KL-FS02`에 급여 자료가 있다는 걸 아는 자산 목록과 중요도 목록, 감시가 *가능하게* 지어진 네트워크 |
| **보호(Protect)** | 사고의 가능성과 영향을 줄이는 보호 조치: 접근 통제, 교육, 하드닝, 데이터 보안 | 사고와 잡음이 줄어듦 — 예방 계층 |
| **탐지(Detect)** | 이벤트와 이상을 빨리 찾기 | 모니터링, 경보, 헌팅 |
| **대응(Respond)** | 탐지된 사고에 움직여 영향을 가두기 | 분류, 조사, 봉쇄, 소통 |
| **복구(Recover)** | *시험해 본* 계획으로 능력과 서비스 되살리기 | 실제로 복원 시험을 해 본 백업, 백업이 소용없을 시나리오에 대한 계획 |

**[정정]** 많은 그림(과 일부 교육 자료)이 두 번째 기능을 "예방(Prevent)"이라고 적습니다. 프레임워크의 단어는 <strong>보호(Protect)</strong>입니다. 뜻은 비슷하지만, 프레임워크를 인용하는 자리에서는 그 용어를 쓰세요.

**식별**은 SOC 분석가가 매일 몸으로 느끼는 부분이라 강조할 만합니다. 네트워크가 감시받도록 지어지지 않았다면 — 중앙 로그도 없고, 서버에 EDR도 없고, 네트워크는 평평하고, 모르는 자산이 있다면 — 분석가가 아무리 뛰어나도 첫날부터 탐지와 예방이 어렵습니다. 그리고 **복구**에는 모든 팀이 답할 수 있어야 하는 질문이 숨어 있습니다. *마지막으로 시험 삼아 백업에서 복원해 본 게 언제이고, 우리 백업이 못 막는 시나리오는 무엇인가?* (백업부터 지우는 랜섬웨어 행위자가 대표적인 예입니다.)

CSF는 *갖춰야 할 능력*을 설명하지, 사고가 벌어지는 순서를 설명하지는 않습니다. 순서는 사고 대응 주기가 맡습니다.

### CSF 2.0과 거버넌스 기능 { #csf-2 }

**[변경됨]** NIST는 **2024년 2월 26일 CSF 2.0**을 냈습니다. 2014년 이후 첫 큰 개정입니다. 가장 중요한 변화는 둘입니다.

- <strong>여섯째 기능, 거버넌스(Govern)</strong>가 나머지 다섯의 한가운데에 놓였습니다. 조직이 보안 전략을 어떻게 세우고 운영하는지를 다룹니다. 위험 관리 전략, 역할과 책임, 정책, 감독, 그리고 **사이버보안 공급망 위험 관리**. 사이버보안은 재무·평판 위험과 나란히 경영진이 책임지는 전사적 위험이라는 메시지입니다.
- **범위 확대.** 원래 프레임워크는 핵심 기반 시설을 겨냥했지만, 2.0은 규모와 업종에 상관없이 모든 조직을 위한 것이라고 분명히 밝힙니다.

분석가 입장에서 거버넌스는 "보안 도구"는 아니지만 내 하루를 결정하는 것들로 나타납니다. 누가 서버를 격리할 수 있는지, 어떤 플레이북이 승인됐는지, 규제 기관 신고는 누가 결재하는지, 위탁 업체가 계약상 무엇을 해 줘야 하는지.

## 사고 대응 주기(PICERL) { #ir-cycle }

### 킬 체인의 방어자 쪽 절반 { #ir-cycle-idea }

CSF가 능력을 나열한다면, **사고 대응 주기**는 **단계를 순서대로** 나열합니다. 킬 체인의 방어자 쪽 절반이라고 생각하면 됩니다. 공격자를 내보내려면 *내가* 거쳐야 하는 단계들입니다. 킬 체인과 달리 공격 종류를 가리지 않습니다. 대량 악성코드든, 표적 침입이든, 내부자든, 잃어버린 노트북이든 단계는 같습니다. 그래서 신입 분석가에게 특히 쓸모 있습니다. 사고가 터졌는데 뭘 해야 할지 모르겠다면, **주기에서 내가 어디 있는지 찾고 다음 단계를 하면 됩니다.**

여섯 단계는 흔히 **PICERL**로 외웁니다. 준비(**P**repare), 식별(**I**dentify), 봉쇄(**C**ontain), 제거(**E**radicate), 복구(**R**ecover), 교훈(**L**essons learned). NIST가 오래 써 온 사고 처리 지침(SP 800-61)에서 나왔고, 그 지침의 네 단계 버전은 조금 다르게 묶었습니다(준비, 탐지와 분석, 봉쇄·제거·복구, 사후 활동). 내용은 같고, PICERL은 각 부분에 따로 이름을 붙였을 뿐입니다.

### 침입 하나로 단계 따라가기 { #ir-walkthrough }

캠페인 예제의 사건 B(KL-WS-0631, 300초 비컨)를 씁니다.

**1. 준비 — 아무 일도 일어나기 전.** 로깅, EDR, 네트워크 센서를 깔아 두고, 탐지를 써 두고, 플레이북과 권한을 정해 두고, 연락처와 대역 외(out-of-band) 소통 수단을 마련해 둡니다. Kestrel에서 NDR 센서가 비컨을 보고 EDR이 프로세스 트리를 남겨 둔 건 준비 덕분입니다. 사고가 잘 풀리느냐는 대부분 여기서 정해집니다.

**2. 식별 — 첫 신호부터 행동하기로 결정할 때까지.** 탐지와 분석입니다. 진짜인지 확인하고, 범위를 파악하고, 공격자가 뭘 하는지 이해합니다. 첫 능동 대응 직전까지가 다 여기 들어갑니다. 호스트의 증거:

```
Event ID 4688  Computer: KL-WS-0631  2026-10-14T10:02:11Z
  New Process Name:     C:\Windows\System32\cmd.exe
  Creator Process Name: C:\Program Files\Microsoft Office\root\Office16\WINWORD.EXE
  Process Command Line: cmd.exe /c copy %TEMP%\~tmp41.dat %APPDATA%\UpdSvc\updsvc.exe && %APPDATA%\UpdSvc\updsvc.exe
  Subject Account Name: r.patel
```

- **이벤트 4688**은 Windows의 "새 프로세스가 만들어졌다" 이벤트로, 프로세스가 시작된 컴퓨터의 Security 로그에 남습니다. 단, *프로세스 생성 감사(Audit Process Creation)*가 켜져 있어야 하고, 명령줄은 "명령줄 포함" 정책을 따로 켜야 기록됩니다([프로세스 생성](../important-events/process-creation.md) 참고). 공격자에게 중요한 이유는 호스트에서 하는 거의 모든 일이 결국 프로세스이기 때문이고, 이 이벤트가 실행을 가장 또렷하게 남기는 기록인 경우가 많습니다.
- `Creator Process Name ... WINWORD.EXE` → `cmd.exe` — Word가 명령 셸을 띄우는 건 정상인 경우가 거의 없습니다. 4단계입니다(매크로 문서를 사용자가 실행 **T1204.002**, 매크로가 **T1059.003 Windows Command Shell**을 띄움).
- `copy %TEMP%\~tmp41.dat %APPDATA%\UpdSvc\updsvc.exe` — 떨궈 놓은 탑재물을 업데이트 프로그램처럼 보이는 이름으로 바꿔 사용자가 쓸 수 있는 폴더에 둡니다.

```
Sysmon Event ID 13  Computer: KL-WS-0631  2026-10-14T10:02:14Z
  EventType:    SetValue
  Image:        C:\Users\r.patel\AppData\Roaming\UpdSvc\updsvc.exe
  TargetObject: HKU\S-1-5-21-...-1844\Software\Microsoft\Windows\CurrentVersion\Run\UpdateService
  Details:      C:\Users\r.patel\AppData\Roaming\UpdSvc\updsvc.exe
```

- **Sysmon 이벤트 13**("레지스트리 값 설정")은 Microsoft의 무료 도구 Sysmon이 감시 대상 레지스트리 값이 바뀔 때 남깁니다. 기본 Security 로그에는 없습니다. 많은 SOC가 Sysmon을 깔거나 레지스트리 원격 측정을 EDR에 맡기는 이유 중 하나입니다.
- `TargetObject ...\CurrentVersion\Run\UpdateService` — 사용자 **Run** 키 아래의 값입니다. 사용자가 로그인할 때마다 Windows가 여기 적힌 걸 실행합니다. 5단계, **T1547.001 Registry Run Keys / Startup Folder**입니다. 관리자 권한이 필요 없어서 가장 오래되고 지금도 가장 흔한 지속성 방법 중 하나입니다.

안전하게 행동할 만큼 알게 되면 식별이 끝납니다. 호스트 하나, 사용자 하나, C2 도메인과 IP 하나, 지속성 방식, 메일 받은 사람 여섯 명, 아직 측면 이동이나 업로드 흔적 없음.

**3. 봉쇄 — 피부터 멈춘다.** 공격자를 흔들고 상황이 더 나빠지지 않게 하는 첫 능동 조치입니다. 보통은 단기 조치이고, 그동안 장기 해결책을 계획합니다. Kestrel에서는: KL-WS-0631을 EDR로 네트워크 격리, DNS와 프록시에서 `update-cdn.example`과 203.0.113.77 차단, 여섯 명 메일함에서 메일 격리, `r.patel` 비밀번호 재설정과 세션 끊기. 비밀번호 재설정은 도메인 컨트롤러에 흔적을 남깁니다.

```
Event ID 4724  Computer: KL-DC01  2026-10-15T09:31:40Z
  An attempt was made to reset an account's password.
  Subject:        Account Name: svc-soar
  Target Account: Account Name: r.patel
```

- **이벤트 4724**는 "계정 비밀번호 재설정을 시도했다"입니다. 권한 있는 누군가가 *다른* 계정의 비밀번호를 재설정한 것이고(사용자가 자기 비밀번호를 바꾸는 4723과 다름), 도메인 컨트롤러에 남습니다. 여기서 주체는 SOAR 서비스 계정이니 봉쇄 중이라면 예상된 일입니다. 공격자도 같은 이벤트에 관심이 있지만 정반대 이유입니다. 피해자나 관리자의 비밀번호를 재설정하는 건 계정을 빼앗는 방법이라서(**T1098 Account Manipulation**), 예상치 못한 주체가 남긴 4724는 경보를 걸 만합니다.

대량 감염과 표적 침입의 봉쇄는 아주 다르게 보일 수 있습니다. 능력 있는 표적형 행위자라면 눈에 보이는 봉쇄 *전에* 범위를 더 파악해야 할 수도 있습니다. 그러지 않으면 공격자가 그냥 다른 발판으로 옮겨 갑니다([앞 페이지](encapsulation-ooda.md#ooda-example)의 OODA 예제가 정확히 그걸 보여 줬습니다). 대응 방법 고르기는 뒤에 따로 섹션이 있습니다.

**4. 제거 — 내보내고 못 들어오게 한다.** 공격자의 접근을 완전히 없애는 장기 조치입니다. Run 키와 실행 파일을 있는 곳 어디서나 지우거나(전체 장비 헌팅 결과 KL-WS-0631 말고는 없었음) 호스트를 다시 깔고, 도메인만이 아니라 C2 URI 모양을 차단하고, 들어온 구멍을 막습니다(인터넷에서 온 매크로를 정책으로 차단). 어디까지 할지는 놓친 게 있을 위험을 얼마나 감수할지에 달렸습니다. <strong>골라서 지우기(surgical removal)</strong>는 빠르고 업무 방해가 적고, <strong>통째로 다시 깔기(full rebuild)</strong>는 공격자가 뭘 바꿨는지 확신할 수 없을 때 더 안전합니다.

**5. 복구 — 정상으로 돌아간다.** 제거 과정에서 멈춘 것을 되살립니다. 사용자는 새로 깐 노트북과 백업에서 되살린 자료를 받고, 호스트는 격리에서 풀리고, 놓친 게 있으면 잡을 수 있게 그 사용자와 호스트의 감시를 몇 주 동안 높입니다. 큰 사고라면 내려 둔 서버들을 정해진 순서대로 다시 올리는 곳이 여기입니다.

**6. 교훈 — 준비로 되돌린다.** 다들 원래 일로 돌아가고 싶어서 가장 자주 건너뛰는 단계이고, 가장 중요한 단계 중 하나입니다. 이게 없으면 다음 공격자에게 아무것도 어려워지지 않으니까요. 사람들이 작은 세부를 기억할 때, 빨리 하세요. 최소 양식을 채운 예:

```
Incident: KL-IR-2026-031 (KL-CAMP-01, Incident B)      Review date: 2026-10-17
What went well:
  - NDR beacon detection fired within 24 h; EDR process tree kept full history.
  - SOAR reset and session revoke took 2 minutes.
What didn't go well:
  - Beacon ran ~24 h before triage; alert sat in a medium-priority queue.
  - 5 of 6 phishing emails were still in mailboxes when found.
What we can do better:
  - Raise severity for periodic beacons to newly registered domains.
  - Auto-search and purge same-sender emails when one is confirmed malicious.
What we will do differently next time (owner, due):
  - Block internet-origin macros by policy (IT ops, 2026-10-31).
  - New detection: /api/v2/ping at fixed 300 s interval (detection eng., 2026-10-24).
  - Hunt %APPDATA%\UpdSvc\ fleet-wide weekly until campaign ends (SOC, ongoing).
```

- `What went well` — 잘된 점: 비컨 탐지가 24시간 안에 울렸고 EDR이 프로세스 기록을 다 남겼음, SOAR로 재설정과 세션 끊기가 2분.
- `What didn't go well` — 안 된 점: 분류 전까지 비컨이 약 24시간 돌았고(경보가 중간 우선순위 대기열에 묻힘), 발견 당시 피싱 메일 6통 중 5통이 아직 메일함에 있었음.
- `What we can do better` — 더 잘할 수 있는 점: 새로 등록된 도메인으로 가는 주기적 비컨의 심각도 올리기, 한 통이 악성으로 확인되면 같은 발신자 메일 자동 검색·삭제.
- `What we will do differently next time (owner, due)` — 다음엔 다르게 할 일, **담당자와 기한**과 함께. 이 넷이 최소이고, 마지막 항목에 담당자와 날짜가 없으면 그냥 희망 목록입니다.
- 첫 조치 항목을 보세요. 매크로 차단. 한 달 뒤 사건 C는 대신 LNK가 든 ZIP으로 왔습니다. 교훈은 효과가 있었고 — 공격자는 적응했습니다. 주기가 계속 돌아야 하는 이유가 바로 이겁니다.

## 다섯 모델은 어떻게 맞물리나 { #fit }

| 모델 | 관점 | 핵심 질문 | 언제 꺼내나 |
| --- | --- | --- | --- |
| 사이버 킬 체인 | 공격자, 침입 하나 | 어디까지 왔고, 앞뒤엔 무엇이 있나? | 분류, 범위 파악, 완전성 점검, 방어 범위 계획 |
| 캠페인 분석 | 공격자, 침입 여러 개 | 같은 행위자인가, 그들이 안 바꾸는 건 뭔가? | 비슷한 사건이 두 번째 나왔을 때, 인텔리전스 업무 |
| 심층 방어 | 방어자, 계층 | 어느 계층이 막았어야 했고, 균형은 맞나? | 사고 후 검토, 경보 과다 문제 |
| NIST CSF | 방어자, 조직 전체 | 필요한 능력을 다 갖췄나? | 보안 계획, 경영진에게 빈틈 설명 |
| 사고 대응 주기(PICERL) | 방어자, 사고 하나 | 나는 어디 있고, 다음은 뭔가? | 모든 사고 중에 |

킬 체인과 PICERL은 같은 사건의 두 반쪽입니다. 공격자가 자기 사슬을 따라 앞으로 가는 동안 나는 내 주기를 돌고, 그 둘의 경주가 앞 페이지의 OODA 속도입니다.

## 2026년 관점 { #trends }

!!! success "[2026 현재] 지금도 그대로 유효"
    다섯 모델 모두 지금도 매일 쓰입니다. 킬 체인은 여전히 "이 공격이 어디까지 왔나?"의 공용어이고, 앞뒤를 맞추는 완전성 습관은 그 어느 때보다 중요합니다. 캠페인 분석 — 행위자가 안 바꾸는 것을 추적하기 — 은 요즘 행위 중심 탐지의 바탕입니다. 예방/탐지/대응과 "대응 없는 탐지" 경고는 오늘날의 경보 피로 문제를 정확히 설명합니다. PICERL은 여전히 대응자들이 자기 일을 설명하는 가장 흔한 방식입니다.

!!! info "[변경됨] 바뀐 점"
    - <strong>NIST CSF 2.0(2024년 2월 26일)</strong>이 여섯째이자 중심 기능인 **거버넌스**(전략, 역할, 정책, 감독, 공급망 위험)를 추가했고, 범위를 핵심 기반 시설에서 모든 조직으로 넓혔습니다.
    - <strong>NIST SP 800-61 Rev. 3(2025년 4월)</strong>이 Rev. 2를 대체했습니다. 이제 **CSF 2.0 커뮤니티 프로필**로 쓰여 있어서, 사고 대응을 예전처럼 따로 떨어진 네 단계 생애 주기가 아니라 전체 위험 관리의 일부로서 CSF의 여섯 기능을 통해 설명합니다. 크게 보면 거버넌스, 식별, 보호가 준비와 개선(교훈 포함)을, 탐지, 대응, 복구가 사고 자체를 맡습니다. 분석가의 작업 모델로 PICERL은 여전히 훌륭하지만, 보고서에서 NIST를 인용한다면 Rev. 3를 인용하세요.
    - **사슬이 더 빨리 돈다.** Mandiant의 M-Trends 2026은 전 세계 체류 시간(dwell time) 중앙값을 **14일**(전년 11일에서 증가)로 집계했고, 최초 침투에서 두 번째 범죄 집단에게 접근권을 넘기기까지의 중앙값이 2022년 8시간 넘던 것에서 **22초**로 줄었다고 보고했습니다. 최초 감염 경로 1위는 6년 연속 익스플로잇(32%)이었고, 2위는 음성 피싱이었습니다. 이제 단계들이 서로 다른 행위자 사이에서 거의 즉시 넘어갈 수 있습니다.
    - **아이덴티티·클라우드 공격은 일곱 단계를 다 밟지 않는다.** 훔친 세션 토큰이나 악용한 OAuth 동의는 악성코드 "설치"도, 전통적인 C2도 없이 전달에서 바로 목표 달성으로 갈 수 있습니다. 그래서 네트워크 안 이동 단계를 추가한 <strong>통합 킬 체인(Unified Kill Chain)</strong>이나 ATT&CK의 전술 목록을 원래 킬 체인과 함께 쓰는 경우가 많습니다.

!!! warning "[주의] 옛 방식대로 하면 틀리거나 위험한 점"
    - **킬 체인을 엄격히 일직선이거나 악성코드 전용으로 보지 마세요.** 실제 침입은 되돌아가고(측면 이동할 때마다 정찰과 C2가 반복됨), 단계를 건너뛰고, 여러 집단이 차례로 진행하기도 합니다. 증거를 일곱 칸에 억지로 넣지 말고, 질문을 던지는 데 쓰세요.
    - **찾은 단계만 막지 마세요.** 모든 단계의 지표를 막고 헌팅하고, 다른 수신자와 호스트를 찾으세요. 아니면 다음 주에 또 보게 됩니다.
    - **차단 목록을 갈아 끼우는 지표로만 만들지 마세요.** 예제의 모든 사건에서 해시, IP, 새 도메인이 바뀌었습니다. 오래가는 건 행동에 대한 탐지입니다.
    - **범위를 알기 전에 밀어 버리지 마세요.** 어떻게 뚫렸고 무엇을 건드렸는지 알기 전에 다시 깔면 증거가 사라지고 다른 발판이 남을 수 있습니다. 제거는 식별 *다음*이지, 식별 *대신*이 아닙니다.
    - **교훈 단계를 건너뛰지 말고, 담당자와 날짜 없이 두지도 마세요.** 그게 없으면 주기는 그냥 직선이 되고, 같은 공격이 두 번 통합니다.

## 확인 문제 { #quiz }

### 문제 1

어떤 업무용 PC의 `rundll32.exe`가 드문 도메인으로 주기적인 HTTPS 연결을 한다는 EDR 경보를 받았습니다. 이건 킬 체인의 어느 단계인가요? 나머지 단계마다 던질 질문을 적고, 사건을 닫기 전에 각 단계에서 무엇을 막거나 헌팅할지 말해 보세요.

??? success "정답과 해설"
    실행 중인 임플란트가 드문 도메인으로 주기적으로 연결하는 건 **6단계, 명령·제어**입니다. 완전한 조사는 뒤로, 앞으로 갑니다.

    - **설치(5):** 어떻게 눌러앉았나? Run 키, 예약 작업, 서비스, 시작 폴더 확인(Sysmon 13, EDR, 수집한다면 4698/7045). 같은 방식과 파일 경로를 전체 장비에서 헌팅하고 지웁니다.
    - **익스플로잇(4):** 무엇이 처음 실행했나? EDR 프로세스 트리와 4688 — 어느 부모가 어떤 DLL로 `rundll32.exe`를 띄웠나? 그 행동(예: Office가 스크립트 실행기를 띄움)을 막습니다.
    - **전달(3):** 이메일, 다운로드, USB, 노출된 서비스 중 어떻게 들어왔나? 다른 사본(다른 수신자, 다른 다운로드)을 모두 찾아 없앱니다.
    - **정찰/무기화(1–2):** 표적형인가? 또 누가 받았고, 역할로 골랐나, 탑재물이 이전 사건과 일치하나?
    - **목표 달성(7):** 공격자가 무엇을 했거나 하려 했나 — 정찰, 자격 증명 접근, 측면 이동, 압축과 업로드? 사용자 계정과 그 사용자가 닿을 수 있는 데이터를 감시합니다.
    - **C2(6) 자체:** 도메인*과* IP를 막고, 이름만이 아니라 비컨 패턴(URI, 주기, TLS 지문)에 대한 탐지를 씁니다.

    모든 단계가 설명되었거나 "모름"으로 기록되었고, 단계마다 지표를 막거나 헌팅했을 때에만 사건이 완전합니다.

### 문제 2

동료가 말합니다. "사건 A, B, C는 관련이 있을 수 없어. 해시, IP, 도메인이 다 다르잖아." 캠페인 표를 써서 이 추론이 왜 틀렸는지, 어떤 증거가 사건들을 잇는지, 하나의 캠페인으로 볼 때 방어가 어떻게 바뀌는지 설명하세요.

??? success "정답과 해설"
    해시, IP, 도메인은 공격자가 바꾸기 **가장 싼** 것이라, 다르다는 건 거의 아무것도 말해 주지 않습니다. 캠페인 분석은 사건들 사이에서 **그대로인** 것을 봅니다. 똑같은 설치 경로와 Run 키(`%APPDATA%\UpdSvc\updsvc.exe`), 같은 C2 URI(`/api/v2/ping`)와 300초 주기, 같은 운송 청구서 미끼 주제, 같은 재무팀(나중엔 구매팀까지) 표적, 같은 도메인 등록 습관(사용 2–4일 전 등록, 같은 등록 대행사), 같은 일하는 시간대. 이것들을 합치면 어떤 지표 하나보다 훨씬 바꾸기 비싸므로, 중간–높은 신뢰도로 사건들을 잇습니다.

    방어의 변화: 오래가는 행동에 대한 탐지(새로 등록된 도메인으로 가는 고정 주기 C2 URI, 설치 경로), 그 경로의 주간 헌팅, 재무·구매팀 대상 맞춤 교육, 그리고 행위자의 적응 예측 — 매크로를 막자 이미 매크로 문서에서 ZIP+LNK로 바꿨으니, 그 팀들에 들어오는 압축 파일 속 LNK에 경보를 겁니다.

### 문제 3

랜섬웨어 전조 사고의 다음 조치들을 PICERL 순서로 놓고 각각의 단계 이름을 말하세요. (a) 어젯밤 백업으로 파일 서버 복원, (b) Cobalt Strike 비슷한 비컨이 있는 호스트 두 대를 EDR로 격리, (c) 검토: 백업 경보가 왜 아무도 호출하지 않았나?, (d) 비컨이 진짜인지 확인하고 C2와 통신하는 모든 호스트 찾기, (e) 두 호스트를 다시 깔고 공격자가 만든 관리자 계정 삭제, (f) EDR이 없던 파일 서버에 EDR 배포. 가장 자주 건너뛰는 단계는 무엇이고, 왜 중요한가요?

??? success "정답과 해설"
    - **(f) 준비** — 감시되지 않던 서버에 EDR을 까는 건 준비입니다(교훈의 *결과*로 할 수도 있는데, 그게 바로 고리가 닫히는 것).
    - **(d) 식별** — 경보를 확인하고 C2 접촉 범위를 파악.
    - **(b) 봉쇄** — 두 호스트를 격리해 피를 멈춤.
    - **(e) 제거** — 호스트를 다시 깔고 불량 관리자 계정을 지워 공격자를 내보냄.
    - **(a) 복구** — 파일 서버를 복원해 정상 운영으로.
    - **(c) 교훈** — 백업 경보가 왜 아무도 호출하지 않았는지 검토.

    순서: f → d → b → e → a → c(그리고 c가 다시 f 같은 준비 항목으로 이어짐). 가장 자주 건너뛰는 건 **교훈**입니다. 급한 불이 꺼지면 다들 원래 일로 돌아가고 싶어 하니까요. 중요한 이유는 다음 사고를 덜 일어나게, 덜 아프게 만드는 유일한 단계이기 때문입니다. 이게 없으면 같은 빈틈(여기서는 아무도 안 보는 백업 경보)이 또 쓰입니다.
