# 보안 사고 모델, 캡슐화, OODA 루프 — 겹을 벗기고 공격자보다 빨리 도는 법 { #encapsulation-ooda }

!!! abstract "이 페이지에서 다루는 것"
    앞 섹션은 처방 하나로 끝났습니다. 정확한 정신 모형을 많이 모아 두라는 것. 이 섹션이 바로 그 모음입니다. 먼저 **표준 보안 모델 지도** — 일반, 공격, 방어, 위협 인텔리전스 — 와 각각이 어디에 쓰이는지 봅니다. 그다음 일반 모델 두 개. **캡슐화(encapsulation)**: 공격은 겹 속에 삽니다. 네트워크 트래픽에도(링크, IP, 전송, 세션, 애플리케이션), 파일에도(이메일 안의 ZIP 안의 문서 안의 실행 파일) 겹이 있고, 맨 위 겹에서 멀쩡해 보이는 것이 아래로 내려가면 악성일 수 있습니다. 피싱 다운로드 하나를 Zeek `conn`, `ssl`, `http`, `files` 로그로 따라가며 어느 겹에서 비로소 정체가 드러나는지 보고, 중첩된 첨부 파일을 명령어 하나씩(`unzip`, `file`, `oleobj`) 단계마다 출력과 함께 벗겨 봅니다. **OODA 루프**(관찰 Observe, 방향 잡기 Orient, 결정 Decide, 행동 Act): 불확실성 속에서 행동하고 일대일 경쟁에서 이기기 위한 John Boyd의 모델, 각 단계가 SOC에서 무슨 뜻인지, 왜 <strong>방향 잡기(Orient)</strong>가 모든 걸 결정하는지, 공격자의 루프 "안으로 들어간다"는 게 무슨 뜻인지. 예제 침입 하나로 방어자와 공격자의 루프를 분 단위로 나란히 놓고 보며, **4624** 로그온 유형 10과 방어자의 느린 결정이 공격자에게 다시 방향을 잡을 시간을 준 순간을 봅니다. 2026년 관점(Encrypted Client Hello, QUIC, 29분 브레이크아웃, 루프 양쪽의 AI)과 확인 문제로 마칩니다.

!!! note "표기"
    **[보충]** = 꼭 알아야 할 실무 보충, **[정정]** = 흔히 잘못 알려진 내용 정정, **[변경됨]**/**[주의]** = 최근 바뀐 점과 옛 방식대로 하면 위험한 점. 회사(Kestrel Logistics), 호스트 이름, 계정, 도메인, IP, 파일 이름, 로그 줄은 모두 설명용 가상 값(`.example`, 문서용·사설 IP)입니다. 프레임워크와 그 저자에 대한 설명은 제 말로 풀어 썼습니다.

## 한눈에 보는 핵심 8가지 { #key-points }

1. **공격의 세부는 계속 바뀌지만, 좋은 큰 그림 모델은 안 바뀐다.** 공격, 방어, 인텔리전스 모델은 새 정보를 걸어 둘 튼튼한 틀이 된다. 기억 페이지에서 말한, 배움과 분석을 빠르게 하는 바로 그것이다.
2. **네 가족:** *일반*(캡슐화, OODA), *공격*(킬 체인, 캠페인, 공격 트리, 그래프 사고, ATT&CK), *방어*(심층 방어, NIST CSF, 사고 대응 주기, 고통의 피라미드, 위협 모델링), *위협 인텔리전스*(인텔리전스 수준, 인텔리전스 주기, F3EAD, 다이아몬드 모델). 각각 다른 질문에 답한다.
3. **캡슐화:** 데이터는 겹겹이 싸여 있다. 악성은 네트워크 2계층부터 7계층 어디에나 있을 수 있고, 요즘 공격 상당수는 **7계층에서만 보인다** — IP, 포트, 도메인은 전부 정상으로 보인다.
4. **모든 계층이 보여야 한다.** HTTPS라면 TLS 검사나 엔드포인트 원격 측정이 필요하다는 뜻인 경우가 많다. 그게 없으면 평판 좋은 클라우드 서비스에서 받은 악성 다운로드는 그냥 "믿을 만한 사이트로 가는 HTTPS"다.
5. **파일에도 겹이 있다:** 이메일 → ZIP → Office 문서 → 안에 심은 실행 파일. 바깥 겹만 검사하면 전부 놓칠 수 있다. 바닥에 닿을 때까지 하나씩 벗긴다.
6. **OODA = 관찰, 방향 잡기, 결정, 행동** — 불확실성 속에서 행동하고 경쟁에서 이기기 위한 John Boyd의 모델. 완벽한 정보는 절대 오지 않는다. 더 빨리 돌고 더 빨리 그림을 고치는 쪽이 이긴다.
7. **방향 잡기가 루프의 심장이다.** 새 관찰이 내 정신 모형과 맥락을 만나 현실의 그림이 되는 곳이다. 모형이 틀렸거나 낡았으면 아무리 빨라도 그 뒤가 전부 무너진다.
8. **속도(tempo)가 이긴다.** 공격자가 한 바퀴 도는 동안 내가 여러 바퀴 도는 것 — 상대의 "루프 안에 들어가는 것" — 이 SOC 탐지·대응 속도의 목표다. 미리 정한 플레이북은 결정을 줄이고, 좋은 모형은 방향 잡기를 줄인다.

## SOC에서 왜 중요한가 { #why }

목수는 연장을 하나만 갖고 있지 않습니다. 연장통을 갖고 있고, 더 중요하게는 어떤 일에 어떤 연장이 맞는지 압니다. 정신 모형이 분석가의 연장통입니다. 경보가 떨어지면 맞는 모형이 다음 질문을 알려 줍니다. 캡슐화는 "이 안에 뭐가 들었지?", 킬 체인은 "이 공격이 어디까지 왔지?", 고통의 피라미드는 "어떤 지표를 막아야 진짜 아프게 할까?", OODA는 "얼마나 빨리 움직여야 하고, 내가 움직이면 공격자는 뭘 할까?"를 묻게 합니다.

기술적인 현실로 돌아오면, 경보 분석의 나쁜 판단은 거의 다 둘 중 하나에서 나옵니다. 엉뚱한 계층을 봤거나(IP가 깨끗하니 세션도 깨끗하다), 속도가 틀렸거나(측면 이동을 막기엔 너무 느렸거나, 너무 빨라서 범위를 알기도 전에 공격자가 눈치채고 전술을 바꿨거나). 이 페이지의 두 모델이 겨냥하는 게 정확히 이 두 실패입니다.

## 모델 지도 { #model-map }

이 섹션이 다루는 표준 모델을 쓰임새별로 묶으면 이렇습니다.

| 가족 | 모델 | 답하는 질문 |
| --- | --- | --- |
| 일반 | **캡슐화**(네트워크·파일 계층) | 이 트래픽이나 파일 안에 진짜 뭐가 들었나? |
| 일반 | **OODA 루프** | 불확실성 속에서 어떻게, 상대보다 빨리 행동하나? |
| 공격 | **사이버 킬 체인**(Cyber Kill Chain) | 이 공격은 어느 단계에 있고, 목표까지 얼마나 남았나? |
| 공격 | **캠페인, 지표, 행동** | 이건 사건 하나인가, 같은 행위자의 더 큰 패턴의 일부인가? |
| 공격 | **공격 트리 / 그래프 사고** | 공격자가 이 목표에 닿을 수 있는 길은 어떤 것들인가? |
| 공격 | **MITRE ATT&CK** | 이건 정확히 어떤 기법이고, 보통 앞뒤에 뭐가 오나? |
| 방어 | **심층 방어**(defense in depth) | 어떤 방어 겹이 이걸 막았어야 했고, 어느 겹이 실패했나? |
| 방어 | **NIST 사이버보안 프레임워크** | 보안 프로그램의 모든 기능을 다 챙기고 있나? |
| 방어 | **사고 대응 주기** | 지금 대응의 어느 단계에 있고, 다음은 뭔가? |
| 방어 | **고통의 피라미드**(Pyramid of Pain)와 탐지 성숙도 | 어떤 지표가 탐지하고 막을 가치가 있나? |
| 방어 | **위협 모델링** | 이 시스템에서 무엇이 잘못될 수 있고, 어떻게 대비하나? |
| 위협 인텔 | **인텔리전스 수준**(전략, 작전, 전술) | 이 정보는 누구에게, 어떤 형태로 필요한가? |
| 위협 인텔 | **인텔리전스 주기**와 **F3EAD** | 데이터를 어떻게 인텔리전스로, 인텔리전스를 어떻게 행동으로 바꾸나? |
| 위협 인텔 | **다이아몬드 모델**(Diamond Model) | 누가, 무엇으로, 누구를, 어떤 인프라로 공격했나? |

이 중 "정답"은 없습니다. 각 모델은 상황의 어떤 면은 밝히고 어떤 면은 가립니다. 그래서 여러 개가 필요합니다. 이 페이지는 일반 모델 두 개를 다루고, 다음 페이지들이 나머지를 차례로 다룹니다.

## 캡슐화: 공격은 겹 속에 산다 { #encapsulation }

### 개념 { #encapsulation-idea }

러시아 인형 마트료시카를 떠올려 보세요. 바깥 인형은 밝게 칠해져 있습니다. 안에 뭐가 있는지는 열어 봐야만, 그리고 그다음 것, 또 그다음 것을 열어 봐야만 압니다. 네트워크 트래픽과 파일도 똑같이 만들어져 있습니다. 각 겹이 안쪽 겹을 감싸고, 각 겹의 "칠"은 완전히 정상으로 보일 수 있습니다.

네트워크에서 **캡슐화**는 말 그대로의 동작 원리입니다. 애플리케이션 데이터(예: HTTP 요청)가 TLS 레코드에 싸이고, 그게 TCP 세그먼트에, 다시 IP 패킷에, 다시 이더넷 프레임에 싸입니다. 각 계층은 자기 헤더를 붙이고, 안에 뭘 싣고 있는지는 모릅니다. 분석가에게 주는 결론은 단순합니다. **계층마다 숨기거나 드러내는 게 다르고**, 한 계층만 보고 내린 판단은 그 계층에 대해서만 말해 줍니다.

### 모든 계층의 악성 { #evil-per-layer }

| 계층 | 거기서 보이는 것 | 이 계층에서 보이는 악성 활동 예 |
| --- | --- | --- |
| 2 — 링크 | MAC 주소, ARP, VLAN | 트래픽 중간에 끼어들기 위한 ARP 스푸핑(**T1557.002 Adversary-in-the-Middle: ARP Cache Poisoning**), 네트워크에 몰래 붙은 장치 |
| 3 — 네트워크 | 출발지/목적지 IP | 알려진 악성 IP로의 연결, 내부 호스트가 한 번도 안 가 본 주소와 통신 |
| 4 — 전송 | 포트, TCP 플래그, 연결 시간, 바이트 | 포트 스캔, 이상한 포트의 C2(**T1571 Non-Standard Port**), 받는 것보다 보내는 게 많은 오래 가는 연결 |
| 5/6 — 세션/표현(TLS) | 인증서, SNI, TLS 지문 | "은행" 도메인에 자체 서명 또는 막 발급된 인증서, 알려진 악성코드 계열과 같은 TLS 클라이언트 지문([HTTPS 인증서](../http-analysis/https-certificates.md), [TLS 지문](../http-analysis/tls-fingerprints-tls13.md)) |
| 7 — 애플리케이션 | HTTP 메서드, URI, 헤더, 파일 내용, DNS 질의, SMB 명령 | 믿을 만한 사이트에서 받은 실행 파일이 든 ZIP, POST 본문 속 스크립트, DNS 질의에 숨긴 데이터 |

마지막 줄을 보세요. 점점 더 많은 요즘 공격에서 **7계층이 공격이 보이는 유일한 계층**입니다. 공격자가 아래 계층들에는 일부러 정상 인프라를 쓰기 때문입니다.

### 예제: 믿을 만한 클라우드 서비스에서 받은 악성 다운로드 { #encapsulation-example }

Kestrel의 한 사용자가 이메일을 받습니다. "청구서가 준비되었습니다 — 여기서 확인하세요." 링크는 크고 평판 좋은 클라우드 파일 공유 서비스(여기선 `files.cloudshare.example`)의 파일로 갑니다. 사용자가 클릭합니다. 로그의 계층마다 무엇을 알려 주는지 봅시다.

**3/4계층 — Zeek `conn.log`:**

```
#fields ts  uid  id.orig_h  id.orig_p  id.resp_h  id.resp_p  proto  service  duration  orig_bytes  resp_bytes  conn_state
1795521601.2  Cq81  10.20.4.57  52844  198.51.100.40  443  tcp  ssl  2.91  1288  412877  SF
```

- `id.orig_h=10.20.4.57` — 사용자 PC, KL-WS-0457.
- `id.resp_h=198.51.100.40`, `id.resp_p=443` — 클라우드 업체의 거대한 공용 대역에 속한 주소. 443은 평범한 HTTPS. 수천 개의 정상 고객이 같이 쓰니 평판 피드는 이 주소를 **깨끗하다**고 봅니다.
- `resp_bytes=412877` — 약 400 KB가 돌아왔습니다. 파일 다운로드지만 어떤 파일인지는 알 수 없습니다.
- 이 계층의 판정: **정상**.

**5/6계층 — Zeek `ssl.log`:**

```
#fields ts  uid  id.orig_h  id.resp_h  version  server_name  subject  issuer  validation_status
1795521601.2  Cq81  10.20.4.57  198.51.100.40  TLSv13  files.cloudshare.example  -  -  -
```

- `version=TLSv13` — TLS 1.3이라 서버 인증서가 핸드셰이크 안에서 암호화되어 Zeek가 `subject`와 `issuer`를 못 읽습니다(`-`로 표시).
- `server_name=files.cloudshare.example` — SNI(클라이언트가 요청한 이름)가 잘 알려진 믿을 만한 서비스입니다. 도메인 평판: **깨끗함**.
- 이 계층의 판정: **정상**.

**7계층 — Kestrel 프록시가 TLS 검사를 하기 때문에야**(복호화하고, 검사하고, 다시 암호화) 프록시 안쪽의 Zeek가 HTTP를 봅니다.

```
#fields ts  uid  id.orig_h  method  host  uri  status_code  resp_mime_types  user_agent
1795521601.4  Cq81  10.20.4.57  GET  files.cloudshare.example  /s/9fK2/Invoice_4471.zip?dl=1  200  application/zip  Mozilla/5.0 (Windows NT 10.0; Win64; x64) ...
```

```
#fields ts  fuid  uid  source  mime_type  filename  total_bytes  extracted
1795521601.6  FhA2  Cq81  HTTP  application/zip  Invoice_4471.zip  412610  extract-FhA2.zip
```

- `uri=/s/9fK2/Invoice_4471.zip?dl=1` — "바로 다운로드"를 강제한 공유 링크.
- `resp_mime_types=application/zip` — Zeek가 이름이 아니라 매직 바이트로 내용이 ZIP임을 알아냈습니다.
- `files.log`의 `extracted=extract-FhA2.zip` — Zeek가 분석용 사본을 저장했습니다. **이제야** 볼 게 생겼고, 열어 보면(다음 절) 안에 실행 파일이 있습니다.

공격은 3, 4, 5계층에선 안 보였고 7계층에서만 나타났습니다. 정상 서비스에 탑재물을 올려 둔(**T1608.001 Stage Capabilities: Upload Malware**) **T1566.002 Phishing: Spearphishing Link**이고, **T1204.002 User Execution: Malicious File**로 이어지는 모양입니다. TLS 검사가 없다면 남은 수단은 엔드포인트 원격 측정(브라우저가 `Invoice_4471.zip`을 디스크에 쓰고 무엇이 풀려 실행되는지 EDR이 봄)과 이메일 게이트웨이의 링크 분석입니다.

### 파일에도 겹이 있다 { #file-layers }

같은 미끼인데 이번엔 링크가 아니라 파일이 이메일에 첨부됐다고 합시다. 이메일 게이트웨이는 ZIP을 봅니다. 백신이 ZIP을 검사하고 딱히 나쁜 걸 못 찾습니다. 여기서 멈출까요? 아닙니다. 벗기세요. ([중첩 파일](../file-analysis/file-identification.md#nested-files)에 이론이 있고, 여기선 실제 순서를 봅니다.)

**겹 1 — 이메일.** MIME 구조의 일부:

```
Content-Type: application/zip; name="Invoice_4471.zip"
Content-Disposition: attachment; filename="Invoice_4471.zip"
Content-Transfer-Encoding: base64
```

- `Content-Type: application/zip` — 첨부 파일 종류에 대한 보낸 사람의 주장.
- `Content-Transfer-Encoding: base64` — 파일이 이메일 안에서 Base64로 인코딩되어 있습니다. 게이트웨이는 검사 전에 이걸 풉니다.

**겹 2 — ZIP.** 격리된 분석용 VM에서:

```
$ unzip -l Invoice_4471.zip
Archive:  Invoice_4471.zip
  Length      Date    Time    Name
---------  ---------- -----   ----
   409984  2026-11-23 22:14   Invoice_4471.docx
---------                     -------
   409984                     1 file
```

- `unzip -l`은 풀지 않고 내용만 *목록으로* 보여 줍니다.
- 파일 하나, `Invoice_4471.docx`, 약 400 KB. 한 장짜리 청구서치고는 아주 큽니다. 벌써 수상합니다.

**겹 3 — Word 문서.** `.docx`는 그 자체가 XML 파일들을 담은 ZIP이라 같은 방법으로 목록을 볼 수 있습니다.

```
$ unzip -o -q Invoice_4471.zip -d stage1
$ unzip -l stage1/Invoice_4471.docx | grep -v xml
Archive:  stage1/Invoice_4471.docx
  Length      Date    Time    Name
   398848  1980-01-01 00:00   word/embeddings/oleObject1.bin
     4286  1980-01-01 00:00   word/media/image1.emf
```

- `unzip -o -q … -d stage1` — `stage1` 폴더에 조용히 풉니다.
- `grep -v xml` — 정상적인 XML 부분은 가려서 특이한 것만 눈에 띄게 합니다.
- `word/embeddings/oleObject1.bin` — **심어 놓은 OLE 개체**, 거의 390 KB로 문서 대부분을 차지합니다. 정상 청구서는 뭔가를 심어 둘 이유가 없습니다.
- `word/media/image1.emf` — 사용자가 문서에서 보는 아이콘(흔히 누르라고 만든 가짜 "PDF"나 "클릭해서 보기" 그림).

**겹 4 — OLE 개체.**

```
$ unzip -o -q stage1/Invoice_4471.docx -d stage2
$ file stage2/word/embeddings/oleObject1.bin
stage2/word/embeddings/oleObject1.bin: Composite Document File V2 Document, Cannot read section info
$ oleobj stage2/word/embeddings/oleObject1.bin
...
Parsing OLE Package
Filename = "Invoice_details.exe"
...
saving to file oleObject1.bin_Invoice_details.exe
```

- `file` — OLE "복합 파일" 컨테이너 형식(옛 Office 바이너리 형식)은 알아보지만 안에 뭐가 있는지는 말해 주지 못합니다.
- `oleobj`(무료 `oletools` 모음의 도구) — Office가 아무 파일이나 심을 때 쓰는 OLE **Package** 개체를 해석해 꺼냅니다. 심어 둔 파일 이름은 `Invoice_details.exe`입니다. (출력 일부 생략.)

**겹 5 — 바닥.**

```
$ file oleObject1.bin_Invoice_details.exe
oleObject1.bin_Invoice_details.exe: PE32 executable (GUI) Intel 80386, for MS Windows
$ sha256sum oleObject1.bin_Invoice_details.exe
<64-hex-digit hash>  oleObject1.bin_Invoice_details.exe
```

- `PE32 executable (GUI)` — Windows 프로그램입니다. 사용자는 문서 속 아이콘을 보고 두 번 클릭하고, Office는 심어 둔 프로그램을 실행할지 묻습니다.
- `sha256sum` — EDR과 위협 인텔 플랫폼에서 찾아보고 차단할 해시([해시](../file-analysis/hashing-signatures.md)).

다섯 겹: 이메일 → ZIP → DOCX → OLE 패키지 → EXE. 각 겹은 자기 겹만 보는 검사에는 무해해 보입니다. 이 사슬은 **T1566.001 Phishing: Spearphishing Attachment** → **T1204.002 User Execution: Malicious File**이고, 겹쳐 싼 것 자체가 **T1027 Obfuscated Files or Information** 역할을 합니다.

### 교훈: 바닥까지 내려가라 { #to-the-bottom }

파일이나 네트워크 거래가 겉으로 무해해 보인다고 정말 무해한 건 아닙니다. 악성이 아니라고 확신하려면 데이터를 **하나씩 계속 분해해야** 하는 경우가 많습니다. **[보충]** 실무 체크리스트:

- **네트워크 이벤트라면:** 내가 실제로 가진 계층은 무엇인가? 3–4계층(NetFlow, 방화벽)만 있으면 3–4계층만 깨끗하다고 말할 수 있습니다. 티켓에 그렇게 적으세요("7계층 가시성 없음, 악성 내용 배제 불가").
- **클라우드·CDN 목적지라면:** IP와 도메인 평판은 거의 의미가 없습니다. 어디로 갔는지가 아니라 무엇이 오갔는지를 물으세요.
- **파일이라면:** 압축 파일, 디스크 이미지(ISO/IMG/VHD), Office 컨테이너, 심어 둔 개체, HTML 속 스크립트를 컨테이너가 *아닌* 것이 나올 때까지 계속 푸세요. 자동화하세요. 샌드박스나 `binwalk`, 재귀 추출 도구가 해 주지만, 정말 모든 겹을 내려갔는지 확인하세요.
- **비밀번호 걸린 압축 파일이라면:** 비밀번호는 보통 이메일 본문에 있습니다. 공격자가 게이트웨이가 겹 하나를 못 열게 일부러 막은 겁니다.
- **겹을 사건 노트에 적으세요.** 예: `email → ZIP → DOCX → OLE → EXE (sha256 …)`. 다음 분석가가 무엇을 확인했는지 알 수 있게.

## OODA 루프 { #ooda }

### 어디서 왔나 { #ooda-origins }

**John Boyd**(1927–1997)는 미 공군 전투기 조종사이자 교관이었고, 불리한 위치에서 시작해도 40초 안에 모의 공중전을 이기는 걸로 유명했습니다. 그 경험에서 1960년대에 공중전 이론을 만들었고, 나중에는 1970년대 후반과 1980년대에 걸친 긴 브리핑으로 더 넓은 분쟁 이론을 내놓았습니다. **OODA 루프** — **관찰(Observe), 방향 잡기(Orient), 결정(Decide), 행동(Act)** — 는 그중 가장 잘 알려진 부분입니다.

Boyd의 통찰은 기술적으로 뒤지는 비행기와 불완전한 정보를 가진 조종사도 상대보다 **결정을 더 빨리 돌리고** 바뀌는 상황에 더 빨리 적응하면 이길 수 있다는 것이었습니다. 두 조종사 모두 머릿속에서 계속 이 루프를 돌리고 있고, 상대가 아직 상황을 파악하는 동안 보고, 이해하고, 고르고, 행동하는 — 루프를 더 빨리 끝내는 — 쪽이 우위를 잡습니다.

이 모델의 핵심 목표는 두 가지이고, 둘 다 SOC 일과 잘 맞습니다.

1. **불확실성을 다루는 일반적인 방법** — 현실이 바뀌는 대로 그림을 계속 고치는 학습 시스템.
2. **일대일 경쟁에서 이기는 전략** — 사고 대응이 바로 그렇습니다. 내가 하는 일에 맞춰 바뀌는 똑똑한 상대가 있으니까요.

Boyd에 관한 글들에 늘 나오는 주제는 **모호함은 두려워하거나 끝나길 기다릴 대상이 아니라 원래 그런 상태**라는 것입니다. 완전하고 완벽한 정보는 절대 갖지 못합니다. 이기는 쪽은 불확실성을 없애는 쪽이 아니라, 불확실성 *속에서도* 잘 행동하고 계속 고쳐 나가는 쪽입니다.

이 모델이 경고하는 건 앞 섹션에서 본 경향입니다. 사람은 상황이 바뀌어도 정신 모형을 충분히 빨리 고치지 않습니다. 낡은 그림은 나쁜 선택으로, 나쁜 선택은 패배로 이어집니다.

### 네 단계를 SOC 말로 { #ooda-stages }

| 단계 | 일반적인 뜻 | 보안 운영에서 |
| --- | --- | --- |
| **관찰(Observe)** | 주변 환경에 대한 새 정보 받아들이기 | 네트워크·호스트 보안 모니터링 데이터 모으기: 로그, 경보, 패킷, 파일, EDR 원격 측정, 사용자 신고 |
| **방향 잡기(Orient)** | 관찰을 정신 모형과 맥락에 합쳐 현실의 그림 만들기 | 공격자가 하는 일을 네트워크·사용자 맥락, 위협 인텔, 공격 모형과 합쳐 진행 중인 공격과 그 목표의 그림 만들기 |
| **결정(Decide)** | 행동 방침을 고르기 — 가설로서 | 다음 판에서 우위를 잡도록 공격자를 어떻게 흔들지 정하기: 격리, 차단, 더 지켜보기, 더 모으기 |
| **행동(Act)** | 실행하고 결과를 다시 관찰로 돌려보내기 | 호스트 격리, 계정 비활성화, 도메인 차단, 탐지 배포 — 그리고 무슨 일이 일어나는지 지켜보기 |

**방향 잡기가 가장 중요한 단계입니다.** 앞의 두 페이지에서 다룬 모든 것 — 지각, 기억, 마음가짐, 정신 모형 — 을 새 정보가 통과하는 곳입니다. 어떤 모형이 이 상황을 설명하는지 고르는 곳이고, 그 선택의 질은 **좋은 모형을 얼마나 많이 가졌는지**, 그리고 안 맞게 된 모형을 얼마나 기꺼이 버리는지에 달려 있습니다. 방향 잡기가 틀리면 빠른 결정과 행동은 틀린 곳에 더 빨리 데려다줄 뿐입니다. Boyd는 방향 잡기를 다른 모든 단계를 빚는 단계로 그렸습니다. 다음에 무엇을 관찰할지, 무엇을 결정할지 모두에 영향을 줍니다.

**결정**은 최종 답이 아니라 시험해 볼 가설을 고르는 것으로 생각하는 게 좋습니다. **행동**이 그 시험이고, 그 결과 — 비컨이 멈췄나? 다른 곳에서 새로 시작됐나? — 가 다음 관찰이 됩니다.

### 작전 속도: 공격자의 루프 안으로 들어가기 { #ops-tempo }

OODA의 핵심 성질은 **상대에 대한 상대적인 속도**입니다. 공격자가 한 바퀴 도는 동안 여러 바퀴를 돌 수 있다면 — 흔히 상대의 루프 "안에" 있다고 말합니다 — 이길 가능성이 아주 높습니다. 상대가 행동할 때마다 나는 이미 그걸 보고, 이해하고, 대응했고, 상대의 상황 그림은 써먹기도 전에 낡아 버립니다.

이게 SOC의 <strong>작전 속도(ops tempo)</strong>와 바로 이어집니다. 얼마나 빨리 막고, 탐지하고, 대응하는지, 그리고 매 바퀴에서 얼마나 빨리 배우는지. 구체적으로:

- **빠른 관찰:** 좋은 수집과 경보, 짧은 수집 지연, 몇 시간이 아니라 몇 분 안에 사람(이나 자동화)에게 닿는 경보.
- **빠른 방향 잡기:** 좋은 모형을 가진 분석가와 바로 꺼내 쓸 맥락 — 자산 중요도, 사용자 역할, 평소 행동, 위협 인텔.
- **빠른 결정:** **미리** 내려 둔 결정 — 플레이북과 사전 승인된 조치("C2가 확인된 업무용 PC는 분석가가 승인 없이 격리할 수 있다"). 새벽 3시에 관리자를 기다리는 건 느린 결정입니다.
- **빠른 행동:** 클릭 한 번이나 SOAR 자동 단계로 끝나는 EDR 격리, 계정 비활성화, 차단.

반대도 있습니다. 공격자도 나를 상대로 자기 루프를 돌립니다. 그들의 관찰은 비컨이 아직 응답하는지, 계정이 아직 되는지 지켜보는 것이고, 그들의 방향 잡기는 들켰는지 판단하는 것입니다.

### 예제: 침입 하나, 루프 둘 { #ooda-example }

공격자가 Kestrel 사용자 한 명을 피싱해서 업무용 PC KL-WS-0219에 비컨을 심었습니다. 다음 90분을 두 루프로 봅니다.

**방어자 루프 1(느린 버전).**

```
[EDR] Beaconing behaviour: periodic HTTPS to rare domain   severity: medium
  host=KL-WS-0219  process=C:\Users\a.cho\AppData\Local\Temp\onenote_sync.exe
  dest=cdn-telemetry.example (203.0.113.51)  interval≈60s  first_seen=09:12Z
```

- **관찰(09:14):** 경보 도착. 사용자 `Temp` 폴더의 프로세스가 약 60초마다 드문 도메인에 연결합니다(**T1071.001**, 가짜 "OneNote" 이름은 **T1036.005**).
- **방향 잡기(09:14–09:50):** 경보가 대기열에서 25분을 기다리고, 분석가가 11분 동안 업데이트 에이전트인지 고민합니다.
- **결정(09:50–10:20):** 분석가는 호스트를 격리하고 싶지만 규정상 관리자 승인이 필요하고, 관리자는 회의 중입니다.
- **행동(10:20):** KL-WS-0219 격리.

**같은 시간에 돌아가는 공격자 루프.**

- **09:20 관찰/방향 잡기:** 비컨으로 공격자가 셸을 얻습니다. 도메인을 훑어보고 `a.cho`가 파일 서버에 RDP할 수 있는 그룹에 속해 있다는 걸 알아냅니다.
- **09:41 결정/행동:** `a.cho`의 자격 증명으로 KL-WS-0219에서 KL-FS02로 RDP합니다. KL-FS02의 Security 로그:

```
Event ID 4624  Computer: KL-FS02  2026-11-24T09:41:07Z
  Account Name: a.cho   Logon Type: 10
  Source Network Address: 10.20.2.19   Logon Process: User32
```

- **4624**에 **Logon Type 10**(*RemoteInteractive*) — RDP(원격 데스크톱) 로그온입니다. 로그온당한 컴퓨터에 남습니다. 공격자에게 중요한 이유는 이미 가진 자격 증명으로 대상의 데스크톱을 통째로 쓸 수 있기 때문입니다(**T1021.001 Remote Services: Remote Desktop Protocol**). 재무팀 사용자가 자기 PC에서 파일 서버로 RDP 세션을 여는 건 드문 일이고, 관리자가 아닌 계정이 서버에 남긴 유형 10 로그온은 좋은 헌팅 단서입니다([로그온 이벤트](../important-events/logins.md)).
- **09:55 행동:** KL-FS02에 다른 도메인으로 4시간마다 연락하는 더 조용한 두 번째 임플란트를 심습니다.
- **10:21 관찰:** KL-WS-0219의 비컨이 응답하지 않습니다. **방향 잡기:** "PC를 들켰다." **결정/행동:** KL-FS02의 임플란트로 갈아타고 조용히 숨습니다.

방어자가 루프를 **한** 바퀴 도는 동안 공격자는 **세** 바퀴를 돌았습니다. PC를 격리했을 때 공격자는 이미 옮겨 간 뒤였고, 격리 자체가 들켰다는 신호를 줬습니다.

**방어자 루프, 빠른 버전.** 같은 경보, 속도가 더 좋은 SOC:

- **관찰(09:14):** 바이너리가 `Temp`에 있고, 서명이 없고, 드물다는 이유로 비컨 경보가 자동으로 높게 매겨집니다.
- **방향 잡기(09:14–09:20):** 분석가가 [기억 페이지](../analyst-cognition/memory-experience.md#case-notes)의 사건 노트 습관대로 대상 목록과 타임라인을 쓰고, EDR에서 프로세스 트리를 확인합니다(09:10에 열린 이메일 첨부 뒤 `ONENOTE.EXE`가 띄움). C2 확인.
- **결정(09:20):** 플레이북: "업무용 PC에서 C2 확인 → 분석가가 즉시 격리 가능, 그다음 범위 파악." 기다림 없음.
- **행동(09:21):** KL-WS-0219 격리, `a.cho` 세션 끊고 비밀번호 재설정.
- **다시 관찰(09:22–09:40):** 전체 장비에서 `cdn-telemetry.example`과 바이너리 해시를 찾고, 지난 24시간 `a.cho`의 로그온을 확인합니다. KL-WS-0219 말고는 없습니다.

09:41에 공격자의 RDP 시도는 실패합니다. 자격 증명은 이미 바뀌었고 출발지 호스트는 격리됐으니까요. 방어자가 **공격자의 루프 안에** 있었습니다. 공격자의 그림("쓸 만한 발판과 유효한 자격 증명이 있다")은 써먹기도 전에 낡아 버렸습니다.

!!! tip "빠른 것과 서두르는 것은 다르다"
    속도는 방향 잡기를 포함한 루프 *전체*에 적용됩니다. 범위를 알기 전에 행동하면 — 다른 임플란트가 셋이나 있는데 도메인 하나만 막으면 — 공격자에게 내가 보고 있다는 걸 가르쳐 주고 더 찾기 어렵게 만들 뿐입니다. 언제 행동하고 언제 지켜볼지는 뒤의 침해 대응 섹션에서 다룹니다. OODA의 교훈은 방향 잡기를 건너뛰라는 게 아니라 매 바퀴를 *빠르고 방향이 잘 잡히게* 만들라는 것입니다.

### 일상 SOC 업무에서 OODA가 쓰이는 곳 { #ooda-daily }

- **사고 중에:** 대응 회의에서 지금 단계를 소리 내어 말하세요. "아직 방향 잡는 중 — 범위를 모릅니다"는 섣부른 행동을 막고, "방향은 잡혔고 결정이 필요합니다"는 끝없는 분석을 막습니다.
- **속도 지표에:** 탐지까지 걸린 시간은 관찰, 분류·범위 파악 시간은 방향 잡기, 승인까지 걸린 시간은 결정, 격리까지 걸린 시간은 행동입니다. 각각을 재면 내 루프의 어디가 느린지 보입니다.
- **플레이북에:** 미리 내릴 수 있는 결정 하나하나가 한밤중의 결정 시간을 줄입니다.
- **공격자를 생각할 때:** 속임수, 리빙 오프 더 랜드(living-off-the-land), 정상 트래픽에 섞이기는 모두 *나의* 관찰과 방향 잡기를 노립니다. 캡슐화는 그걸 위한 그들의 가장 좋은 도구 중 하나입니다.

## 2026년 관점 { #trends }

!!! success "[2026 현재] 지금도 그대로 유효"
    캡슐화와 OODA는 여전히 그대로 중요합니다. 공격자는 지금도 평판 좋은 클라우드 서비스에 탑재물을 올리고 컨테이너 안에 겹겹이 싸며, 그걸 드러내는 건 여전히 7계층이나 엔드포인트 가시성입니다. OODA는 군사, 경영, 사고 대응에서 계속 널리 쓰이고, "상대의 루프 안으로 들어간다"는 SOC 탐지·대응 속도를 설명하는 흔한 방식입니다.

!!! info "[변경됨] 바뀐 점"
    - **선 위에서 보이는 게 줄었다.** TLS 1.3은 서버 인증서를 암호화하고, QUIC(HTTP/3)은 웹 트래픽을 UDP 443으로 나르며, 2026년 3월 **RFC 9849**로 발행되고 주요 브라우저와 일부 CDN이 이미 지원하는 <strong>Encrypted Client Hello(ECH)</strong>는 SNI까지 숨길 수 있습니다. 5–7계층을 보려면 점점 더 TLS 검사나 **엔드포인트 원격 측정**이 필요하고, 많은 SOC에서 EDR이 "7계층 진실"의 주 출처가 됐습니다.
    - **매크로 차단 뒤 컨테이너가 바뀌었다.** 2022년 Office가 인터넷 매크로를 기본으로 막기 시작한 뒤, 겹겹이 싸기는 ISO/IMG/VHD 이미지, LNK 파일, OneNote, HTML 스머글링(**T1027.006**)으로 옮겨 갔고, Mark-of-the-Web을 피하려는(**T1553.005**) 경우가 많습니다. 모든 겹을 벗기는 습관이 덜이 아니라 더 중요해졌습니다.
    - **공격자의 루프가 빨라졌다.** 2026년 한 업계 위협 보고서는 사이버 범죄 집단의 평균 브레이크아웃 시간(첫 침투에서 측면 이동까지)을 **29분**, 가장 빠른 경우를 **27초**로 집계했고, AI를 쓰는 공격자의 공격이 크게 늘었다고 보고했습니다. 회의가 끝나길 기다리는 결정 단계로는 더 이상 버틸 수 없습니다.
    - **AI가 양쪽 루프에 들어오고 있다.** 방어자는 AI 분류와 SOAR로 관찰과 방향 잡기를 줄이고, 공격자는 AI로 정찰, 피싱, 도구 제작을 빠르게 합니다. ATT&CK v20(2026년 10월)은 AI 관련 악용 기법을 추가했고, ATT&CK v19(2026년 4월)는 옛 Defense Evasion 전술을 Stealth와 Defense Impairment로 나눴습니다.

!!! warning "[주의] 옛 방식대로 하면 틀리거나 위험한 점"
    - **클라우드나 CDN 뒤의 목적지에서 "IP와 도메인이 깨끗하다"는 판정이 아닙니다.** 실제로 검사한 계층만 깨끗하다고 하고, 못 본 계층은 못 봤다고 적으세요.
    - **TLS 검사 하나에만 기대지 마세요.** 인증서 고정(pinning), QUIC, ECH, 개인정보 예외(은행, 의료), 법적 제한이 빈틈을 남깁니다. 엔드포인트 가시성도 계획하고, 내가 일하는 곳에서 검사가 합법이고 승인됐는지 확인하세요.
    - **방향 잡기 없이 행동을 자동화하지 마세요.** 약한 신호 하나로 자동 차단하면 업무 서비스가 깨지거나 범위를 알기 전에 공격자에게 들킬 수 있습니다. 모형이 믿을 만한 부분만 자동화하세요.
    - **첨부 파일을 한 겹만 검사하고 믿지 마세요.** 바깥 압축 파일이 깨끗하다는 건 그 압축 파일만 깨끗하다는 뜻입니다. 샌드박스나 게이트웨이가 비밀번호 걸린 것까지 포함해 모든 겹을 정말 내려갔는지 확인하세요.

## 확인 문제 { #quiz }

### 문제 1

클라우드 다운로드 예제에서 3/4계층, 5/6계층, 7계층이 분석가에게 각각 무엇을 알려 줬는지 적고, 왜 7계층만 공격을 드러냈는지 설명하세요. TLS 검사가 없었다면 SOC는 무엇을 쓸 수 있었을까요?

??? success "정답과 해설"
    - **3/4계층(`conn.log`):** 큰 클라우드 업체 공용 대역 주소로 가는 443 포트 HTTPS 연결, 약 400 KB 다운로드. IP 평판 깨끗 — 전부 정상.
    - **5/6계층(`ssl.log`):** TLS 1.3(인증서 안 보임), SNI는 잘 알려진 믿을 만한 서비스 `files.cloudshare.example`. 도메인 평판 깨끗 — 정상.
    - **7계층(TLS 검사를 거친 `http.log`, `files.log`):** `Invoice_4471.zip` 바로 다운로드, MIME 형식 `application/zip`, 분석용으로 추출됨 — 안에 실행 파일이 있었음.

    공격자가 아래 계층 전부에 일부러 **정상 인프라**를 썼기 때문에 7계층만 공격을 드러냈습니다. 악성인 건 *내용*이었습니다. TLS 검사가 없다면: **엔드포인트 원격 측정**(EDR이 파일이 쓰이고, 풀리고, 실행되는 걸 봄), **이메일 게이트웨이의 링크 분석**이나 URL 실행 검사, 그리고 클라우드 서비스 자체의 악용 신고.

### 문제 2

OODA 각 단계가 SOC에서 무슨 뜻인지, 왜 방향 잡기가 가장 중요하다고 하는지 설명하세요. 예제의 느린 방어자 루프에서 시간을 가장 많이 잡아먹은 단계는 무엇이었고, 빠른 버전은 그걸 어떻게 고쳤나요?

??? success "정답과 해설"
    **관찰** — 모니터링 데이터 모으기(로그, 경보, 패킷, 파일, EDR). **방향 잡기** — 관찰을 정신 모형과 맥락(자산, 사용자, 위협 인텔, 공격 모형)과 합쳐 공격과 그 목표의 그림 만들기. **결정** — 행동 방침을 가설로 고르기(격리, 차단, 관찰, 수집). **행동** — 실행하고 결과를 관찰로 돌려보내기.

    **방향 잡기**가 가장 중요한 이유는 모형과 맥락이 데이터를 이해로 바꾸는 곳이고, 다음에 무엇을 관찰하고 결정할지까지 빚기 때문입니다. 모형이 틀렸거나 낡았으면 빠른 결정과 행동은 쓸모없거나 해롭습니다.

    느린 루프에서는 대기열 25분과 갈팡질팡한 방향 잡기 11분(약 36분), 그리고 **결정** 단계 — 관리자 승인을 기다린 30분 — 이 가장 큰 지연이었습니다. 빠른 버전은 자동 점수 매기기와 구조화된 사건 노트 습관으로 방향 잡기를 줄였고, C2가 확인된 업무용 PC는 바로 격리할 수 있게 한 **사전 승인 플레이북**으로 결정 지연을 없앴습니다. 그래서 방어자가 공격자의 루프 안에 들어갔습니다.

### 문제 3

이메일 게이트웨이가 `Statement.zip`에 대해 "첨부 파일 검사: 깨끗함"이라고 보고했습니다. 동료가 경보를 닫으려고 합니다. 캡슐화 사고를 어떻게 적용할지, 명령이나 확인 단계를 셋 이상 들고, 파일이 악성이라면 각 단계에서 무엇이 보일지 설명하세요.

??? success "정답과 해설"
    "깨끗함"은 바깥 겹이 게이트웨이의 검사를 통과했다는 뜻일 뿐입니다. 격리된 분석 환경에서 벗기세요.

    1. `unzip -l Statement.zip` — 내용 목록 보기. 수상한 것: Office 문서, 디스크 이미지(ISO/IMG), LNK, 스크립트(`.js`, `.vbs`, `.hta`), HTML 파일, 또 다른 압축 파일. 비밀번호 걸린 압축 파일(비밀번호는 이메일 본문에)은 그것만으로도 위험 신호입니다.
    2. 풀어서 각 항목에 `file` 실행 — 매직 바이트로 진짜 형식 확인. 수상한 것: 사실은 PE 실행 파일인 "PDF", 이상한 부분이 든 ZIP인 "DOCX".
    3. Office 파일이면 문서를 `unzip -l`로 보고 `word/embeddings/`나 `vbaProject.bin`을 찾고, `oleobj`/`olevba`(oletools)로 심어 둔 개체나 매크로를 꺼냅니다. 수상한 것: `.exe`나 스크립트가 든 OLE Package.
    4. 마지막에 나온, 컨테이너가 아닌 파일들의 해시(`sha256sum`)를 구해 EDR과 위협 인텔에서 찾고, 누가 열었는지 확인합니다.

    사건에 사슬을 적고(`email → ZIP → … → 마지막 파일 + 해시`), 바닥 겹까지 내려간 뒤에만 닫으세요.
